# How does the Curator MCP server work?

## Overview

How does the Curator MCP server work? InterWorks' Curator 2026.11-02 ships an MCP server that lets an AI client such as Claude Code or Claude Desktop work directly on a Curator analytics portal — the layer that fronts Tableau, Power BI, ThoughtSpot, and Sigma content — through one endpoint, POST /curator/mcp, authenticated with a personal token that can do nothing its owner cannot do. Counted from Curator's own MCP documentation (updated November 13, 2026, read November 15, 2026), the server exposes 48 named tools: 27 read and administrative tools that a new token allows by default, and 21 content tools that change portal content and are never checked by default — the owner must opt each one in. The content surface is the consequential part: 4 page tools (create, edit content, update settings — which can publish several pages at once — and delete), 4 navigation tools, 2 theme tools, 4 file tools, 1 snapshot-restore tool, 2 REST API key tools, and 4 API relay tools. Curator's guardrails are real and unusually well documented: content tools are off by default, every call checks the owner's backend permissions at run time and is written to the Usage Log, pages and themes are snapshotted before an MCP change (the newest 25 snapshots per page or theme, kept up to 90 days), most content tools accept dry_run: true, new pages start hidden, and managed portals refuse changes outright. What Curator does not ship is a decision: 0 per-action decision scores, 0 confidence thresholds, and 0 scored approval steps are named anywhere in its documentation. The sharpest example is in Curator's own text: the create_api_key tool mints a REST API key that, in the documentation's words, has full REST API access and does not expire — and the only control in front of that mint is the same token checkbox that enables a theme edit. Content tools off by default, opted in one by one per token, is the strongest default posture in this series — most vendors ship the writes on and call a settings page governance. The snapshot system is real undo, not a promise: 25 snapshots per page and theme, 90 days, with a restore that snapshots again before it runs and refuses when the page has moved on since. And the documentation is honest about its own sharp edges — it tells you the created page carries no group restrictions, that menu and file changes have no snapshot, that a deleted file cannot be restored, and that an MCP-created API key never expires. But read what a permission system decides and what it never touches. A token checkbox answers a standing question — may this client ever call this tool — asked once, at setup, for every future call alike. It never asks the per-act question: should THIS publish, to THIS portal, carrying THIS content, happen now — and what is the scored evidence? The standing answer also ages silently: a token set to Never expire, holding a checked create_api_key box, is a standing invitation whose risk grows with every month the portal changes around it. Curator's own safety rules concede the gap in one place — a created page has no group restrictions, so the documentation instructs a human to check them in the backend before publishing. That check is a decision. Curator leaves it unscored, unrecorded as evidence, and dependent on a person remembering. A permission is a gate left open or closed. A decision is a score, a threshold, and a sealed receipt. Curator ships the gate.
