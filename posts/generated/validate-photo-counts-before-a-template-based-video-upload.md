# Validate photo counts before a template-based video upload

## Overview

A photo-upload form can become invalid when the user changes templates, even though every selected file is still a valid image. A two-portrait scene and a one-photo dance clip need different input counts. For a visible example, AI Pop Video presents photo requirements alongside its video templates. The Hotel Lobby example requests two individual portraits; other examples request one photo. Requirements should come from the selected template rather than a count hard-coded into the upload component. Disclosure: I am affiliated with AI Pop Video. AI assistance was used to prepare this post and its teaching example. The executable cases below were run locally. This code is independent of the product's implementation and does not call its service. Define what a passing result means Here, canContinue means the selected files match the local preflight rules, so the UI can let the user review the request. It does not authorize an upload, confirm available credits, or start generation. The example policy uses JPEG/PNG, a 10 MiB limit per file, and an exact photo count. These are illustrative policy values , not claims about any particular service's supported formats or upload limits. In an integration, obtain the policy from an authorized, versioned source and match it to the backend's rules. Keep these checks separate: Missing or malformed template requirements: block continuation and explain what is unavailable. Incorrect file count: tell the user the count for the currently selected template. Unknown or unsupported MIME metadata: ask for a supported file rather than silently treating it as an image. Empty or oversized file: identify the affected selection. The byte-limit boundary is intentional: a file at the limit passes; one byte above it fails. Empty metadata also fails explicitly. It does not become a one-photo template through a default value. Revalidate when the template changes Run the validator on both file selection and template changes. If your UI loads template requirements asynchronously, keep continuation disabled while the new requirements are unavailable. Associate the response with the selected template ID and version so an older response cannot replace the current requirements. Show the returned messages near the file input. Keep an explicit next step for reviewing the selected template and any current credit cost. Do not trigger a paid generation request just because local validation passed. Keep server validation authoritative A browser file's reported type is a preflight hint, not proof of its contents. The server still needs to enforce its size and count limits, inspect and decode the received files, verify ownership and authorization, and validate the template and charging rules. The browser's accept attribute helps selection; it does not replace those checks. The example also says nothing about portrait suitability, consent, image dimensions, pose, or the generated video's quality. Add those checks where your actual workflow requires them, with clear messages and appropriate review steps. References: MDN's file input documentation and Using files from web applications .
