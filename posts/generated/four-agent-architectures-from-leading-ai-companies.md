# Four Agent Architectures from Leading AI Companies

## Overview

🙋 I’m Luhui Dev , a developer who has been breaking down Agent engineering and exploring how AI can be applied in education. I focus on Agent Harness, LLM application engineering, AI for Math, and the productization of education SaaS. An Agent is a model-driven program that can use tools to complete a task. A customer service Agent , for example, can understand a refund request and call an order lookup API to check the purchase. Orchestration determines what happens first, which steps can run together, when a person needs to approve an action, and where each result goes. Agents, application code, and human approval can all participate. The diagram compares one typical use of each public framework from Microsoft, OpenAI, Google, and Anthropic. Consider the same refund request in each case. Microsoft Agent Framework expresses explicit branches. The program verifies the order, requests approval, and waits for a person to decide whether it should proceed or send the case for manual handling. OpenAI Agents SDK offers two ways for Agents to work together. The support Agent can hand off the conversation to a refund specialist or ask that specialist to check eligibility and then reply itself. Google ADK lets code run steps in parallel. One branch checks the purchase date while another asks an Agent whether the complaint qualifies for a policy exception. The workflow combines both results. Claude Agent SDK lets the model choose its next action from tool results. It can look up the order, discover a previous contact, and read the old support ticket to gather enough information. Three questions help compare these approaches: Who decides what happens next, what does the runtime save, and what work repeats after a failure? Microsoft Agent Framework: Give approvals an explicit path Microsoft Agent Framework brings together AutoGen's multi-agent collaboration and Semantic Kernel's application integration foundations. [1] An Executor in a workflow can run code or an Agent. It handles incoming messages and sends its outputs downstream, which gives you a way to trace how a case moved through the workflow. After verifying an order, the verification executor sends a “case verified” message. The approval executor uses a RequestPort to issue an external request. If the reviewer answers the next day, the workflow can load a checkpoint and follow the appropriate branch for approval or rejection. With checkpointing enabled, the runtime saves workflow state and messages queued for the next round. You can test both paths with simulated approval messages. An approval should lead to execution, and a rejection should send the case for manual handling. An auditor can look up the decision without reconstructing the Agent's train of thought from a chat transcript. OpenAI Agents SDK: Two execution paths for one refund request Suppose a customer says, “I'd like a refund for the membership I bought yesterday.” The application passes the message and the support Agent to the SDK's Runner . The Runner calls the Agent's model, follows the tool calls or handoffs it requests, and continues the run. Developers configure which tools the support Agent can use and which Agents it can hand off to. Path one: Hand off to the refund Agent [2] Customer requests a refund → support Agent identifies the intent → Runner switches to the refund Agent → refund Agent looks up the order and replies The switch happens within the same run. The refund Agent becomes active and uses its own instructions and tools. If the order number is missing, it can ask the customer for it directly. Path two: Use the refund Agent as a tool to check eligibility Customer requests a refund → support Agent calls the refund Agent → refund Agent returns its eligibility finding → support Agent replies using that finding The tool call starts a subtask. Once the refund Agent reports that the order qualifies, the support Agent can check the refund status or reply directly. A handoff changes which Agent is active. Using an Agent as a tool delegates a piece of work and returns the result to the original Agent. If business rules require approval for large refunds, the application can enforce that rule and use RunState to preserve the paused run while the refund tool call awaits approval. Google ADK: If a condition will do, skip the model meeting Google ADK began with Agent hierarchies and built-in workflows for sequential, parallel, and loop execution. ADK 2.0 adds explicit workflow graphs . [3] Developers can put code and Agents in the same graph, specify which nodes run first and when edges can be followed, and pass structured outputs between nodes with events. The refund window and policy exceptions can be checked at the same time. One branch uses code to calculate the age of the order. The other asks an Agent to read the complaint and find the relevant policy clause. After receiving both results, the workflow applies the amount rule to decide whether the case needs approval. Downstream steps get the deadline check and the applicable policy clause without reading both full conversations again. Claude Agent SDK: Look at the evidence, then decide what to do Claude Agent SDK comes from Claude Code. It brings context management, tool calls, and permission controls into an ongoing tool loop. [4] When investigating a disputed refund, the Agent first reads the complaint and the order. If it finds that customer support promised compensation, it looks up the earlier ticket. If the case involves a policy that subsequently changed, it finds the version in force at the time. For larger investigations, the main Agent can ask several subagents to work in parallel. With the Workflow tool enabled, Claude can also write a task-specific JavaScript script for parallel checks, cross-checking, and synthesis, then pass it to the runtime. The plan can vary with the task, and the runtime schedules the steps expressed in the script. That flexibility suits investigation. When money is actually refunded, business rules should still control eligibility and payment approval. Final thoughts All four frameworks face the same trade-off. The clearer the rule, the more sense it makes to put it in code. The more a task depends on what turns up along the way, the more room the model needs to adapt its plan. Microsoft advances the workflow through messages. OpenAI lets Agents hand off a conversation or delegate a subtask. Google brings graph scheduling and Agents together. Claude can inspect a task and turn its plan into a script.
