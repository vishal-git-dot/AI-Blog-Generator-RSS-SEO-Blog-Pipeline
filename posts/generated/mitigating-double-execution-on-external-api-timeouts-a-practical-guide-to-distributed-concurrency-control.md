Mitigating Double Execution on External API Timeouts: A Practical Guide to Distributed Concurrency Control The Problem: Duplicate Execution in the Wake of Timeouts During the backend development of payment processing systems, timeout failures caused by network latency when communicating with external Payment Service Providers (PSPs) are a notorious source of data inconsistencies. Analyzing transaction logs reveals a recurring post-timeout race condition: A client initiates a payment request to the API server. The API server dispatches an outbound HTTP request to the external PSP. The external PSP successfully executes the transaction on their ledger. However, due to a transient network severance or packet drop during response transmission, the API server triggers a gateway timeout (such as 504 Gateway Timeout or socket read timeout). The client application (or an upstream resilient retry mechanism like an exponential backoff worker) interprets this as an unhandled failure and promptly dispatches an identical retry request with the exact same parameters. While the first request is still in-flight or already completed in the background, the server receives the retry and spawns a secondary thread/process to process the payment once again. To prevent duplicate charges, it is not enough to simply reject identical transactions after the fact. The architecture demands an atomic, in-flight state detection mechanism that immediately intercepts and throttles concurrent or duplicated incoming requests . Production Insights & Operational Best Practices 1. TTL (Time-To-Live) Calibration Setting an optimal lease duration for your distributed locks requires balancing two opposing risks: TTL is too short : If an upstream PSP experiences an extended processing delay and the lock expires while the thread is still awaiting a response, a concurrent retry will acquire a new lock, leading directly to duplicate charges. TTL is too long : If the processing application node crashes ungracefully before releasing the mutex, subsequent valid client retries remain locked out in a deadlocked state until the TTL elapses. In practice, the TTL should be calculated as: $$\text{Lock TTL} = \text{External HTTP Client Timeout} + \text{Clock Drift Margin} + \text{Grace Period}$$ For payment integrations where downstream PSP read timeouts are configured to 15 seconds, a distributed lock TTL between 20 to 30 seconds is generally standard. 2. Dual-Layer Defense: Redis Mutex + RDBMS Unique Constraints Redis serves as an in-memory, low-latency filter to absorb fast-frequency retry storms before they saturate database connection pools. However, distributed in-memory systems face failovers, asynchronous replication lag, and potential data loss during cluster topology shifts. Therefore, absolute consistency demands that the durable storage layer (such as PostgreSQL or MySQL) enforces a strict UNIQUE index constraint on (transaction_id) or (idempotency_key) . If an unexpected Redis split-brain occurs, the database transaction will cleanly reject the concurrent execution via an integrity violation error ( UNIQUE constraint violation ), preserving financial ledger correctness across the entire infrastructure.
