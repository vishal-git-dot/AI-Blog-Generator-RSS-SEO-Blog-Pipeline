# How I Built an 8-Language Shopify Store for LUVA Organic: hreflang, a 1px LCP Fix and AI Crawlers

## Overview

Disclosure: I build and maintain the online store for LUVA Organic , a small hair, scalp and body care brand based in Ajman, United Arab Emirates. This is a write-up of client work. This post was generated with an AI writing tool from the store's theme code and live pages, and every technical detail below was checked against the live store on November 24, 2026. LUVA Organic sells a deliberately small collection: Phyto Elixir (a pre-wash hair oil), a shampoo, two scalp care products, Hair Mist Parfum (a fragrance for hair and skin, whose scent the brand describes as sophisticated, sweet and enveloping), Silk Skin (a body emulsion with the same scent) and a Ritual Pack. The store runs on Shopify with a custom theme, and the brief came down to four requirements: Eight languages, including right-to-left Arabic, plus Japanese, Korean and Russian. A fast first paint on phones. Consent that really gates analytics for visitors in Europe. Pages that search engines and AI assistants can read without guessing. Here's what worked, with the real snippets from the theme. 1. Eight locales, one URL prefix each, hreflang everywhere The store publishes eight locales: English (primary), Spanish, French, Italian, Russian, Japanese, Korean and Arabic. Each one lives in its own subfolder ( /es , /fr , /it , /ru , /ja , /ko , /ar ), and every page carries a full set of hreflang alternates plus x-default . The Hair Mist Parfum page , for example, points to /es/products/luva-hair-mist-parfum , /ja/products/luva-hair-mist-parfum and the other six versions. Arabic needs more than translated strings. The <html> element takes its language and direction from the request: {% - assign is_rtl = false - %} {% - if request . locale . iso_code contains 'ar' - %} {% - assign is_rtl = true - %} {% - endif - %} <html lang = "{{ request.locale.iso_code }}" dir = "{% if is_rtl %}rtl{% else %}ltr{% endif %}" > Language-specific fonts load only where they're needed: an Arabic font snippet for ar , and a separate snippet for ja , ko and ru . Visitors browsing in English never download them. 2. The 1-pixel LCP fix The home page opens with a full-screen photo. For a while, Lighthouse kept naming Shopify's cookie-banner text as the Largest Contentful Paint element. That text painted about a second after the photo, and mobile PageSpeed sat at 79. The cause: Chrome's LCP heuristics skip images that cover the entire viewport, because they look like backgrounds. On phones the hero was exactly one screen high, so the photo never qualified, and the next big thing on screen, the banner text, won. The fix is a single declaration: @media ( max-width : 767px ) { .hero-image { clip-path : inset ( 0 0 1px 0 ) ; } } Clipping the bottom pixel row means the image no longer covers the whole viewport, so it becomes the LCP element at first paint. Nothing is resized or moved, and the missing row sits under a dark shade where nobody notices it. The same rule now applies on tablets and desktops too, where the banner text had also been winning. 3. Preload the right hero for each screen The hero preload uses Shopify's CDN parameters on theme assets ( &width= and &quality= ), with a separate image for phones: <link rel = "preload" as = "image" fetchpriority = "high" media = "(max-width: 767px)" imagesrcset = "{{ hero_m }}&width=480&quality=85 480w, {{ hero_m }}&width=720&quality=85 720w, {{ hero_m }}&quality=85 958w" imagesizes = "100vw" > hero_m comes from asset_url , which already carries a ?v= query string, so the sizing parameters are appended with & . A matching preload with a (min-width: 768px) media query serves the desktop image, up to 2000px wide. 4. Critical CSS per template, the rest non-blocking The home, product and collection templates each inline their own critical CSS, and the full stylesheet loads without blocking the first paint: <style id = "luva-critical" > { % - case template .name - % } { % - when 'index' - % } { % - render 'luva-crit-index' - % } { % - when 'product' - % } { % - render 'luva-crit-product' - % } { % - when 'collection' - % } { % - render 'luva-crit-collection' - % } { % - endcase - % } </style> <link rel = "stylesheet" href = "{{ 'luva.css' | asset_url }}" media = "print" onload = "this.media='all'" > <noscript> {{ 'luva.css' | asset_url | stylesheet_tag }} </noscript> The three critical snippets are generated by a script that replays each template's first screen, and they're regenerated whenever the main stylesheet changes. Arabic pages and the theme editor keep the normal stylesheet load. Pruning unused rules also cut the main stylesheet by about 29%. In tests in October 2026, PageSpeed Insights scored the home page 100 on desktop and 95 to 98 on mobile on clean runs. Lab scores move from run to run, so read those as a range, not a promise. 5. Consent that actually gates analytics GA4 runs as a Shopify custom pixel instead of a hard-coded tag. The pixel receives the visitor's consent state, and visitors in Europe see a cookie banner first, so analytics only collects what each visitor has allowed. 6. Let AI assistants read the store More and more shoppers ask an assistant before they open a store. Three things help. Name the AI crawlers, but keep the default rules. The theme ships a robots.txt.liquid that keeps Shopify's default rules and adds the AI crawlers to the general group: {% - assign ai_agents = 'GPTBot,OAI-SearchBot,ChatGPT-User,ClaudeBot,Claude-SearchBot,Claude-User,PerplexityBot,Perplexity-User,Google-Extended,Applebot-Extended,Bingbot' | split : ',' - %} {% - for group in robots . default_groups - %} {% - capture block - %} {{ group . user_agent }} {% - if group . user_agent . value == '*' - %} {% - for agent in ai_agents %} User-agent: {{ agent }} {% - endfor - %} {% - endif - %} {% - for rule in group . rules %} {{ rule }} {% - endfor - %} {% - if group . sitemap != blank %} {{ group . sitemap }} {% - endif - %} {% - endcapture - %} {{ block }} {{ '' }} {% endfor %} Why not one group per bot? In robots.txt, a group that names a crawler replaces the * rules for that crawler. A lone User-agent: GPTBot plus Allow: / group would quietly reopen the cart, checkout and account paths for it. Listing the bots as extra user-agents in the general group gives them exactly the same rules as everyone else. Capturing each group first also keeps blank lines out of the middle of a group, which older parsers read as the end of it. Structured data on every page type. The home page outputs Organization , WebSite (with a SearchAction ) and FAQPage . Product pages output Product with Offer and Brand , plus a BreadcrumbList . Machine-readable instructions and categories. Shopify serves an agents.md file for the store (the same text is at /llms.txt ), and every product carries a category from Shopify's standard product taxonomy, which is what shopping agents and catalogs read. What I'd do again, and what I'd change Check which element is your LCP, not just the score. A decent score can hide the wrong LCP element. Name AI crawlers explicitly, but inside the default group, never in a group of their own. Settle the language list early. Adding a locale later is easy; changing URLs after launch means redirects. You can see the result at luvaorganic.com , or switch languages, for example to Spanish or Japanese .
