# EAGLE-4 does not run on a Mac. I measured MTP instead: +92% on one model, -19% on another

## Overview

A release announcement for EAGLE-4, a speculative decoding method, reported up to 3.4x faster generation for Qwen3.8-27B on four NVIDIA B300 GPUs. I run local models on a Mac Studio, and I wanted to know one thing: does it make my models faster? The short answer: EAGLE-4 as released does not run on a Mac. But my runtime already has a related technique, MTP (multi-token prediction), and I can measure that. The result depends strongly on the model: On a dense 27B model, MTP made code generation 92% faster (thinking off, one request). On a 35B mixture-of-experts (MoE) model, MTP made prose generation 19% slower (thinking off, one request). With MTP on, the output text changed at temperature 0 in 7 of 8 test cases. I did not measure quality yet. This post covers speed only. All numbers below come from my own runs, except the EAGLE-4 numbers, which come from the EAGLE-4 README. What EAGLE-4 is, and why I did not test it Speculative decoding works like this. A small, fast drafter proposes several next tokens. The large model checks all of them in one forward pass and keeps the tokens that match its own choice. If most drafts are correct, you get several tokens for the cost of about one large-model pass. EAGLE-4 is a trained drafter for this job. Facts from the official repository ( github.com/eagle-hq/eagle-4 , package eagle-harness ): The drafter is EAGLE-Corp/Qwen3.8-27B-EAGLE4 : 3B parameters, BF16. It runs inside SGLang, vLLM and TokenSpeed (experimental). The quick start requires Linux, four NVIDIA GPUs with a CUDA 13 driver and about 70 GB of disk. A separate guide covers AMD Instinct MI355X. The README does not mention Metal, MLX, llama.cpp or Apple Silicon. The license is source-available, not OSI-approved. Read LICENSE and NOTICE in the repository for the terms. The README reports these speedups for Qwen3.8-27B at temperature 0. MTPLX ( github.com/youssofal/MTPLX ) and dflash-mlx ( github.com/bstnxbt/dflash-mlx ). A post on aiweekly.co ( aiweekly.co ) says MTP makes M1 to M3 chips up to 25% slower. This report is anecdotal, and other reports disagree with it. I found no EAGLE-4 result on a Mac or on MLX anywhere. So I tested the technique that I can run. What I tested Some new models ship with an MTP head: a small extra layer, trained with the model, that predicts tokens further ahead. A runtime can use this head as the drafter. You do not need a separate draft model. My runtime, oMLX, calls this feature "Lightning MTP" and turns it on per model with mtp_enabled . On Ornith with the long prompt, oMLX parked MTP in all 5 runs, and the result was still 11% slower than MTP off. Why the dense and MoE models differ This section is my explanation of the data. The numbers come from oMLX's own MTP log lines. The cause is an inference that I did not prove with a profiler. Each MTP cycle drafts several tokens and verifies them in one pass of the main model. Two numbers decide the result: Tokens per cycle : how many tokens one cycle produces. Cycle cost : how long one cycle takes, in units of one normal decode step with MTP off. The speedup is about tokens per cycle divided by cycle cost. This is accounting, not a model, but it shows which factor matters. Values below come from runs that were not parked. A Qwen cycle costs about 2.1 to 2.2 normal steps. An Ornith cycle costs about 2.6 to 2.7. So Ornith needs about 2.6 tokens per cycle only to break even, and on prose it produces about 2.1. Why is verification more expensive for the MoE model? My explanation: in a dense model, all tokens in the verification pass use the same weights, so one read of the weights from memory serves several tokens. In an MoE model, each token selects 8 of 256 experts, and different tokens select different experts. Verifying four or five tokens therefore reads many more expert weights than one normal step does. Also, a normal Ornith step is short (7.5 ms against 29.8 ms for Qwen), so any fixed cost per cycle is a larger share. In the logs, the main model's pass takes 92% of Ornith's cycle time and 96% of Qwen's. I did not profile the kernels, so treat this as a hypothesis. It can also be a property of the oMLX implementation and not of MoE models in general. MTP changed the output text Speculative decoding with greedy verification is supposed to produce exactly the text the model produces alone. In my runs, it did not: With MTP off, every scenario produced one identical text across all 20 runs. With MTP on, the output matched the MTP-off text in only one scenario: Qwen code with thinking off (20 of 20 runs). In the other seven scenarios, 0 of 20 runs matched. The first difference appeared between character 26 and character 423, depending on the scenario, and the texts continued differently after it. The MTP-on texts also differed from each other between runs. In the samples I read, the differences are changes of wording, not obvious errors. But I did not measure quality, so I cannot say if they matter. One possible cause is small numerical differences between the multi-token verification pass and the normal single-token pass. Such differences can flip a near-tie between two tokens. I did not prove this. For the speed numbers, it means that MTP on and MTP off produced texts of the same length (almost all runs reached the 512-token limit), but not the same texts. Practical takeaways These apply to these models on oMLX 0.7.1rc1 and an M2 Ultra: Turn MTP on for Qwen3.8-27B on code. It gave +92% with thinking off and +39% with thinking on. Leave MTP off for Ornith-1.5-35B-A3B by default. It gave +9% to +12% on code, but −7% to −19% on prose, −11% with a long prompt and −8% with four parallel requests. Measure each model. Dense or MoE mattered more for the result than any headline number for the technique. For agents, prefill matters as much as decode. The dense model needs 75 seconds to read a 16k-token prompt, and MTP makes prefill slightly slower. With MTP off, Ornith reads the same prompt in 12 seconds. Check output quality before you rely on MTP. It changed the text in 7 of 8 scenarios. What I did not measure Quality of any output, with MTP on or off. Ornith's 4x decode speed says nothing about whether its code is as good as Qwen's. Temperatures above 0. Other runtimes (llama.cpp, mlx-lm directly, LM Studio) and other drafters (EAGLE-3, DFlash). Other Apple chips. An M1, M3 or M4 has different bandwidth and compute, and the balance can change. Prompts longer than 16k tokens, and real agent sessions with tool calls. Energy use.
