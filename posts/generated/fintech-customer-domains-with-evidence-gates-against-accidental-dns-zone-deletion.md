# Fintech Customer Domains With Evidence Gates Against Accidental DNS Zone Deletion

## Overview

Customers should be able to point their own domain at a fintech product without a cleanup job becoming permission to erase that domain's DNS zone. The least complex starting point is a record-only cleanup policy, with zone deletion excluded from ordinary automation. TL;DR: Require an explicit runtime allowlist for destructive DNS operations. Default to deleting individual records, log intent before any destructive call, and review mail deliverability evidence before approving a whole-zone deletion. Deleting a zone removes everything under that domain, with no useful undo. Keep that decision in application code behind a stable capability contract. When the provider behind the capability changes, the calling code can keep its contract; the approval policy should remain yours. A shared DNS and email interface also makes it practical to carry the domain returned by a DNS lookup directly into a mail-domain lookup, using one credential rather than a dashboard handoff. For a Python AI application, this is a useful notebook-to-prod boundary. An agent can propose that a customer hostname is obsolete. It shouldn't turn that inference into authority to delete the surrounding zone. Prompt cost belongs in the proposal path; destructive authorization belongs in deterministic code. How can deliverability evidence prevent accidental DNS zone deletion? Separate the product hostname from the domain whose DNS zone would be deleted. In an illustrative fintech tenant, removing portal.customer.example from the product might justify removing a specific record. It does not establish that the customer has stopped using mail under customer.example . These names are sample data, not a customer incident. The data flow is small: read the DNS domain, extract its domain name, use that output to read the corresponding email-domain state, and attach both responses to a review artifact. A reviewer checks the requested scope and deliverability evidence before placing that exact domain on a runtime allowlist. The cleanup worker records its intent before it acts; routine cleanup stays at record scope. Evidence comes first. DMARC reporting gives the review a concrete source of authentication evidence. RFC 7489 describes DMARC's relationship to SPF and DKIM and its reporting mechanisms. A mail-domain configuration response alone does not prove that messages reached an inbox. Nor does a quiet report interval prove that nobody still needs the domain. For this workflow, treat configuration state, authentication reports, and the customer's retirement decision as separate inputs. An absent report should lead to a question about coverage, not automatic approval. Make the destructive boundary survive notebook-to-prod Build an eval-driven release gate around the policy, not around the eloquence of an agent's explanation. Use at least three illustrative cases: record cleanup without zone approval, zone cleanup without approval, and zone cleanup with an exact domain allowlist entry. The first may proceed under the record policy; the second must stop; the third only passes the scope guard and still needs the rest of the retirement checks. Add a fourth case where the proposed target is a parent domain while approval names a subdomain. Exact matching should reject it. That last distinction is easy to miss. A suffix match can expand an approval beyond what a person actually reviewed. Keep domain representation consistent before approval, and bind the authorization to the operation and the reviewed target. Don't let an agent rewrite either after review. Operationally, start each cleanup by resolving the customer's intended hostname and the actual deletion scope. Read fresh DNS and mail-domain state, preserve the evidence needed to explain the decision, and check whether SPF/DKIM configuration still serves an active mail identity.
