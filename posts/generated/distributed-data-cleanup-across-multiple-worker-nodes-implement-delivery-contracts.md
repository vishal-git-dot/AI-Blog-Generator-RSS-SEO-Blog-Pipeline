# Distributed Data Cleanup Across Multiple Worker Nodes: Implement Delivery Contracts

## Overview

Short answer: use a short nightly trigger to enqueue bounded reconciliation work, then let several worker nodes consume it. For a gaming payment ledger, the important contract is delivery: standard queues are at-least-once, so the cleanup operation must be idempotent before workers scale out. I would start with that contract in the evaluation harness, not with a vendor demo. A single cron execution is a bad place to process a large ledger. The scheduler has a 900-second execution limit, while a queue lets the trigger describe the reconciliation window and lets workers do the slow work independently. The queue provider is secondary to the rule that a worker may see the same payment twice. Keep the message small. A date, shard, game identifier, and stable reconciliation key are usually more useful than copying an entire payment record into the queue. The worker can fetch the current row, check its expected version, apply the correction, and acknowledge only after the database transaction succeeds. How should I implement distributed data cleanup across multiple workers? Start with the duplicate. Consider this failure: a worker commits a refund-state correction, then dies before acknowledging its message. The queue delivers that message again. That is normal at-least-once behavior, not a broken queue. For every message, derive a key such as arena-7:pay-1842:2026-10-25 . Store that key with the state change under a unique constraint. A retry then becomes a lookup and a no-op instead of a second side effect. I initially treated FIFO deduplication as enough protection; the more useful distinction is that FIFO deduplication lasts only five minutes, while the business operation may need a durable idempotency record. The duplicate is the test case. In a real consumer, the payment update and the idempotency record belong in the same durable transaction. Acknowledge after that transaction succeeds. On a transient failure, leave the message available for retry or route it to the queue's dead-letter path according to the chosen policy. Acknowledging first reverses the failure mode: the work can disappear even though the process never committed it. This is also where a worker pool needs discipline. Standard queues permit duplicate delivery, and concurrent consumers can touch related records at the same time. Partition messages around a business key, use conditional updates or row-level protection in the database, and make the final state safe to apply twice. FIFO can help with ordering, but it does not remove the need for an idempotent consumer. Where should the scheduler stop? The scheduler should identify work, not perform an unbounded cleanup run. A nightly trigger can enqueue one message per game shard or reconciliation partition. Multiple worker nodes then consume those messages. If the work may exceed 900 seconds, this cron-trigger-plus-worker shape is required by the execution limit rather than being a minor optimization. Keep queue settings inside their actual limits: delay is at most 7 days, message bodies are at most 256 KB, and retention is at most 30 days. Acknowledgment deletes the message, so this is not Kafka-style replay with multiple consumer groups. A push subscription also needs a public HTTPS target; a private-only endpoint will not receive it. These constraints belong in the test matrix. There is no native DAG orchestration or fan-out-and-join primitive in this queue capability. If twelve partitions must finish before one exact settlement step can run, store an explicit aggregation record or choose a workflow engine such as Temporal. Likewise, there is no native debounce or throttle, and one queue is not a topic with many independent consumer groups. Treating those as queue features would make the design look simpler while moving the hard state management into application code. What should the evaluation harness measure? The useful experiment is deliberately uncomfortable. Replay one reconciliation message, terminate a worker after the database commit but before acknowledgment, delay one partition, and send a body above the agreed envelope size. Then run the ordinary nightly case with several consumers. Measure duplicate side effects, recovery behavior, ordering, dead-letter handling, and operator visibility. I would also test a paused schedule. Missed cron triggers are not backfilled after a pause, and trigger timing has second-level jitter. The result should be visible in the reconciliation window rather than inferred from an assumed exact timestamp. Use SQS first when managed AWS operations dominate. Use Celery when the broker and Python worker estate already exist. Use Temporal when the job has durable dependencies and joins. Test a REST queue option when portability and a thin HTTP adapter are more important than adopting a workflow runtime. The decision rule is compact: choose queue-based distributed cleanup for independent, load-heavy work; require idempotent consumers; put long execution behind the scheduler-to-queue boundary; and change abstractions when dependencies become the product.
