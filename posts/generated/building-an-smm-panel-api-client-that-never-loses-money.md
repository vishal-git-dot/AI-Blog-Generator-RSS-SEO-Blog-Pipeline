# Building an SMM panel API client that never loses money

## Overview

Money bugs in API clients are rarely dramatic. Nobody's bank account empties in one line of code. What happens is quieter: a retry after a timeout creates a second order, a float sum drifts by a fraction of a cent, and six weeks later the reconciliation spreadsheet disagrees with the panel dashboard by $0.03 that nobody can trace. I maintain a small Python client for the Perfect Panel v2 API, the shape most SMM panels speak: one POST endpoint, an action= field, seven operations. This post is about the three decisions that keep it from losing money — and the one place where the obvious implementation is wrong. The API shape is a single order desk POST /api/v2 key=...&action=services key=...&action=add&service=12&link=...&quantity=1000 key=...&action=status&order=23501 key=...&action=balance Four calls carry almost all the weight: list services, place an order against a prepaid balance, poll status, read the balance. Everything else ( cancel , refill , batch status) is a variant. The full contract is at talonpanel.com/api-docs . Two properties of that contract matter more than the rest. Errors arrive as HTTP 200. A rejected action returns 200 OK with {"error": "ORDER_REJECTED"} because older reseller panels never learned status codes. So response.raise_for_status() tells you nothing. You have to read the body and branch on error_code , which is the stable part; the human message gets reworded between deployments. Charges arrive as decimal strings. "0.6327" . Not cents, not floats — strings that look like money, which means the moment you do float(charge) you have already lost. Money is an integer, not a float Sum 10,000 charges of 0.1 as floats and you get 999.9999999999997 (or something very close, depending on order). Compare that to 1000.0 and your "balance mismatch" alarm fires at 3 a.m. for no reason. The fix is to parse every amount into an integer number of micro-units — one millionth of a currency unit: from decimal import Decimal , ROUND_HALF_UP MICRO = 1_000_000 def to_micro ( value ) -> int : amount = Decimal ( str ( value ) . strip ( ) ) * MICRO return int ( amount . quantize ( Decimal ( 1 ) , rounding = ROUND_HALF_UP ) ) "0.6327" becomes 632700 . Integers add exactly, compare exactly, and survive a round trip through SQLite, JSON and CSV without a single binary rounding surprise. Rounding half-up rather than truncating matters too: 0.0000005 should be 1 , not 0 , or tiny per-unit prices silently vanish. The client stores money in that integer form and refuses to mix currencies, so Money("1") + Money("1", "RUB") raises instead of adding dollars to rubles. The call that can charge you twice This is the part worth reading twice. Placing an order is not idempotent , and the v2 API has no idempotency key . There is no header, no client reference field, no dedupe window. Two identical add requests are two orders and two charges. Now combine that with retries. The standard pattern — retry on timeout, retry on 502 / 503 / 504 — is correct for reads and dangerous for writes: You send add for 1,000 followers. The panel processes it, charges your balance, then the response is lost to a read timeout. Your client retries. The panel has no way to know it is the same request. You now own two orders and paid twice. The first version of my client had exactly this bug: one retry loop for all seven actions. The tests were green because the fake panel never charged anything. The fix is a per-action retry policy: def _call ( self , action , params = None , * , idempotent = True ) : . . . if not idempotent and request_may_have_been_processed : raise AmbiguousOrderError ( . . . ) # do not send it again Concretely, for add : Outcome Retry? Why DNS failure, connection refused yes The request never left the process. 429 Too Many Requests yes The panel refused it before doing anything. Honour Retry-After . Read timeout, connection reset mid-body no The order may exist and the balance may already be gone. 500 / 502 / 503 / 504 no Same ambiguity — a gateway error says nothing about whether the app committed the order. Ambiguity is raised as an exception with a message that tells you what to do next, not what went wrong. Calls that only read ( services , status , balance ) keep the full retry budget with exponential backoff and jitter, because repeating them costs nothing. Reconcile with the only two facts you have When an add is ambiguous, the API cannot tell you whether the order exists. But the balance can. Read the balance before the call, read it again after the failure, and subtract — in integers: before = panel . balance ( ) . balance try : order = panel . add ( service , link , quantity ) except AmbiguousOrderError : spent = before - panel . balance ( ) . balance if spent == Money ( 0 ) : pass # nothing was charged: safe to retry elif spent == expected : pass # it was placed: find the id, never place it again else : pass # partial or unrelated movement: needs a human That is the whole trick, and it turns a guess into three explicit states. examples/reconcile_add.py in the repo runs this against a SQLite ledger. The second half is the charge id . Every successful add returns order , charge and balance , and the order id is the panel's primary key for that charge. Store it with a UNIQUE constraint: create table if not exists order_charge ( panel_order_id integer primary key , -- the charge id client_ref text not null unique , -- your own idempotency token charge_micro integer not null , placed_at text not null ) ; The unique index is what makes replays harmless at the application layer: if the same logical order is ever submitted twice, the second insert fails loudly instead of becoming a second charge. It does not replace an idempotency key, but it stops the duplicate from reaching your accounting. Retries worth having For the calls that are safe to repeat, the details matter: Retry 429 and 5xx only; a 400 -class rejection is a bug in the request, not a temporary condition. Exponential backoff with jitter ( 0.5s, 1s, 2s, ... plus up to 10%) so a queue of workers does not synchronise into a thundering herd. Retry-After wins over your own schedule when the panel sends it, capped so a hostile header cannot stall a worker forever. Validate input before the first request. A quantity of -5 should cost zero HTTP calls. And log the action name, attempt number and timing — never the API key, which should also be redacted from every exception message and repr() . Panel keys are bearer credentials for your whole balance. Putting it together The client is about 700 lines including tests: typed frozen dataclasses, seven methods, exact micro-unit money, and the retry policy above. It is panel-agnostic — any panel that follows the v2 shape works with it, and Talon is only the default base URL. Source: gitea.com/talonpanel/perfectpanel-client (MIT, httpx only) API contract: talonpanel.com/api-docs 158 tests, 100% line and branch coverage, no network in CI pip install "git+https://gitea.com/talonpanel/perfectpanel-client.git" Disclosure, since it belongs in the post rather than a footer: I work on Talon, an SMM panel that publishes its prices and its methodology. The client is deliberately not tied to it — the interesting problem here is the Perfect Panel v2 contract, which dozens of panels share, and the money bugs it invites in every client that speaks it. If you integrate against a similar order desk, the useful takeaway is not the library: it is that retrying writes without an idempotency key is a purchase, not a retry.
