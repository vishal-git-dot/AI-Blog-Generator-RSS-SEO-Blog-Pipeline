# I Made Hindsight Memory Survive a New Interaction

## Overview

I Made Hindsight Memory Survive a New Interaction The hardest part of a support assistant is not writing a plausible answer to the issue on screen. It is making the next answer better because of what happened last time, without carrying the wrong customer's history into the conversation. I built this system around that boundary. A support interaction is short-lived browser state; customer memory is not. Hindsight sits between those lifetimes: it retrieves relevant history before generation and receives the new issue and response afterward. That sounds like a small integration, but it changed how I thought about identity, retrieval, and what “start a new interaction” should mean. A request should outlive the page The interface is deliberately simple. An operator enters a customer name and an issue, submits them to a Next.js route, sees any recalled memory, and reads the generated response. The client clears its fields when the operator starts over. That reset should not erase the facts the system just learned. The request path is split at a useful boundary. The React page owns transient form state and presentation. The server route owns calls to Hindsight and Groq, so credentials stay server-side and the browser does not need direct access to either service. The API validates the two fields, recalls memory, creates a completion, retains the interaction, then returns the memory and response together. The important part is the order. Recall happens before generation; retention happens after generation. Hindsight is not a transcript attached to the prompt by the browser. It is the persistent store that connects separate requests. That distinction matters because a chat transcript and customer memory have different jobs. A transcript preserves a conversation in sequence. Support memory should help answer a new question: what has this customer already tried, what fixed the last issue, and what preference should the agent remember? Hindsight provides a retrieval interface for that context rather than requiring the client to resend every prior message. The interface makes the customer issue → Hindsight memory → AI response path visible before an interaction is submitted. The boundary is customer identity The first design decision was how to keep one customer's recall from crossing into another customer's response. The implementation uses one configured Hindsight bank and scopes each customer’s memories with a tag. The tag is derived from a normalized customer name, so capitalization and repeated whitespace do not create different partitions. There is an important limitation in the current input contract: the operator supplies a name, not a durable customer identifier. Two different people with the same normalized name map to the same tag. Hashing does not solve that identity problem; it only makes the tag stable and avoids putting the raw name in the tag. If Ravi reports a Wi-Fi issue, receives steps that resolve it, and returns later with another connectivity problem, the earlier issue and resolution can be recalled before the new answer is generated. If Mina submits an issue, Ravi's tagged records are outside Mina's recall scope. Starting a new interaction clears the page; it does not clear either customer's Hindsight memory. I judge memory behavior with three separate questions: Is the retrieved item relevant to the current issue? Does it belong to the right customer? Did the response use it correctly? Those are distinct failure modes. A retrieval score alone cannot prove the other two. What I learned Choose the memory boundary before tuning prompts. A polished answer is still a failure if its context belongs to another customer. I made the customer tag part of both recall and retention before spending effort on response wording. Use durable identity, not convenient identity. A normalized name is enough to explain the flow, but real customer separation needs an immutable ID from the system of record. A hash cannot make ambiguous input unique. Treat migration as part of the memory design. New metadata does not retroactively annotate old records. A conservative fallback can preserve identifiable history without making every old memory eligible for every prompt. Make memory visible. Showing the recalled item beside the generated response helps an operator see whether memory was found and gives the system a review point when retrieval is wrong. The useful property of Hindsight here is continuity with a boundary. The interaction can end, the form can reset, and the next request can still begin with relevant customer context. The engineering work is making sure that continuity is durable, scoped, and visible enough to trust.
