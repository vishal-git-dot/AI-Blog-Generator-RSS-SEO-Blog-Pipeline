# From Monthly Files to Trusted Metrics: Engineering an Incremental Pipeline for 9.5 Million NYC Taxi Records

## Overview

Introduction: I wanted to build something beyond a small extract transform load tutorial. One clean file and one successful notebook run can demonstrate syntax, but they do not force decisions about repeated execution, rejected records, operational evidence, or downstream performance. I wanted those harder decisions to be the project. Official https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page was a good fit because it is public, substantial, and published as monthly files. That delivery pattern creates a realistic incremental-processing problem: a new month should be added without treating every previous month as new work. I used Yellow Taxi data from January through March 2024, covering more than 9.5 million source records. The completed pipeline validates each monthly file, separates accepted and rejected trips, builds hourly pickup-zone metrics, enriches location IDs, and records execution and quality evidence. Here I explain the design choices, source data problems, repeatability tests, and performance measurement behind it without turning one benchmark into a universal claim. The business problem: Imagine a transportation analytics team producing monthly reporting on demand and revenue. Its analysts need dependable trip information for hourly trends and pickup zone comparisons. Previously processed months must remain available when the next file arrives. Invalid records should be retained for investigation, not disappear during cleaning. The team also needs evidence that a run completed correctly, beyond a message saying a script finished. A full refresh design would download and process every historical file whenever a new month appeared. That may suit an early experiment, but it repeats work whose inputs have not changed. As history grows, so do the waste and operational risk more data is read, more outputs are rewritten, and more steps can fail. The requirement was therefore not merely load taxi data. It was to process one month independently, preserve validated history, expose questionable records, and reconcile every layer. Numeric pickup identifiers also had to become location information that a business user could understand. Those needs shaped the architecture more than the choice of programming language. Architecture and technology choices: I organized the pipeline into distinct paths so raw evidence, accepted data, rejected data, and business metrics would not be mixed together. Bronze preserves each original monthly source file. Silver contains standardized, deduplicated trips that pass hard rules. Quarantine retains rejected records with reasons. Gold stores hourly pickup-zone business metrics. Dimension maps taxi-zone IDs to readable location attributes. Audit database records execution and quality evidence. Python handles pipeline logic and the command line interface because it works well for orchestration, file operations, validation flow, and packaging repeatable commands. SQL expresses transformations, aggregations, and reconciliation checks clearly. DuckDB runs those SQL operations directly over Parquet and provides a lightweight audit database. Parquet supplies compressed, columnar storage that fits analytical reads and monthly partitions. The layers are intentionally complementary. Bronze is the reproducible source boundary. Silver is the accepted trip level contract. Quarantine makes rejection inspectable. Gold provides a defined business grain. The dimension translates location keys into borough, zone, and service zone descriptions. The audit database connects an output to the run that created it. This separation also lets each stage be tested and explained without obscuring the responsibilities of the others. Docker makes the execution environment reproducible, while GitHub Actions verifies code and containers automatically. I deliberately kept the implemented stack modest. This version runs locally and in containers; it is not an AWS deployment and does not use Airflow, dbt, Spark, or Snowflake. The objective was not to collect platform names. It was to complete a testable path whose behavior and results I could support with evidence. Incremental and resilient ingestion: A concise manifest identifies all the available monthly partitions. Each entry supplies the taxi type, year, month, and source location, so selecting a partition does not require editing transformation code. Storage follows Hive style keys such as taxi type = yellow/year=2024/month=02, aligning the physical layout with the unit of processing. A downloaded file remains untrusted until validation succeeds. Downloads use retries for temporary failures. If an attempt fails partway through, the partial file is removed rather than mistaken for a complete source. The pipeline validates the Parquet file before accepting it into Bronze, and a SHA-256 fingerprint provides file-level traceability. If a valid Bronze source already exists, the pipeline verifies and reuses it instead of downloading the same file again. Downstream outputs can still be rebuilt, atomically replaced, and checked deterministically, so reuse never means blindly trusting stale work. I tested this behavior by executing February twice. The first run downloaded the source and recorded that it was not reused. The second reused the validated Bronze file, produced the same 3,006,695 Silver rows and 831 Quarantine rows, and created a separate audit record. Idempotent ingestion therefore meant avoiding an unnecessary download without bypassing validation or losing traceability. Handling imperfect source data: The source data made one lesson unavoidable quality cannot be reduced to drop the nulls. I found trips with zero or negative duration, trips lasting more than 24 hours, pickup timestamps outside the month being processed, and exact duplicates. I also found missing passenger counts, zero distance trips, and negative total amounts. These conditions do not all mean the same thing, so the pipeline should not treat them identically. I divided the rules into two groups. Hard rule failures break the accepted trip contract. A trip cannot have a non-positive duration, a duration beyond 24 hours, or a pickup timestamp that contradicts its source month. Exact duplicates would overstate activity. Rows meeting those conditions go to Quarantine. Soft quality issues are suspicious, but the record may still support some analysis. A trip with a missing passenger count can contribute to hourly pickup demand. A zero distance trip may be a legitimate edge case. A negative total can still matter to demand analysis even if a revenue analyst excludes it. These rows remain in Silver with explicit flags, preserving their usefulness while making uncertainty visible. The monthly results show why the rejected path should be durable. January produced 2,963,720 accepted rows and 904 quarantined rows. February produced 3,006,695 accepted and 831 quarantined. March produced 3,581,457 accepted and 1,171 quarantined. Quarantine records carry applicable reasons for example, invalid duration, out-of-month pickup, or duplication instead of disappearing behind an aggregate count. Retaining rejected records makes rule changes reviewable. If a boundary later proves too strict, the team can inspect affected rows and reprocess from preserved evidence. Silent deletion creates a clean looking table by removing the information needed to explain how it became clean. For me, Quarantine was not a waste bin; it was the pipeline's record of disagreement with the source. Quality gates and auditability: I wanted invariants that would fail when the pipeline dropped, duplicated, or misrepresented data. Every completed month checks that Bronze rows equal Silver rows plus Quarantine rows. Across the three partitions, the arithmetic is exact: 9,551,872 Silver + 2,906 Quarantine = 9,554,778 Bronze. The pipeline also verifies that Silver trip IDs are unique and no Silver row violates a hard rule. At the Gold boundary, summed trip counts must reconcile to Silver. Gold's analytical key service date, pickup hour, and pickup location must be unique, and every Gold trip count must be positive. Separately from the automated pipeline quality gates, I executed a validation that joined Gold location IDs to the validated taxi zone dimension. All 9,551,872 accepted trips matched; none were unmatched. These checks are persisted in DuckDB, not left only in console output, so evidence remains available after the process exits. The pipeline runs table assigns each execution a unique run ID and records status, timestamps, partition, layer row counts, source-reuse status, and any error. The quality results table stores the individual checks and outcomes. A failed stage can therefore leave a failed run record with its error preserved. The checks answer different questions. Reconciliation shows whether data was accounted for. Uniqueness detects duplication. Hard rule validation protects the Silver contract. The separately executed dimension validation demonstrates reference coverage. Together, the audit tables answer not only "What data do we have?" but also "Which run produced it, what was reused, and which automated checks passed?" That turns a successful execution into durable evidence. Building the Gold layer: Silver preserves accepted trip detail, but analysts should not repeatedly scan millions of trips to answer the same hourly demand questions. I defined Gold as one row per service date, pickup hour, and pickup location. That grain supports daily, hourly, and location analysis and is easy to test for uniqueness. Each record includes trip count known passenger count total distance; fare, tip, and net total amounts; average duration, distance, and total amount; and counts of the three soft quality flags. These measures support demand, revenue, trip characteristic, and quality analysis without reconstructing the same aggregation repeatedly. Gold contains 240,850 rows representing all 9,551,872 accepted trips. A 265 row taxi zone dimension maps pickup keys to borough, zone, and service zone descriptions. Gold used 262 pickup locations. In the separately executed validation, no represented trip lacked a matching zone. The dimension turns an opaque number into a place analysts can discuss. Preaggregation does not guarantee that every possible query will be faster. Trip level investigation still belongs in Silver, and performance depends on the workload. Gold is useful because it gives repeated business questions a smaller, purpose built surface with a stated grain. It reduces work for the questions it was designed to answer without pretending to replace detailed data. Benchmark methodology and results: I compared a Silver query over accepted trip level records with a Gold query over reaggregated metrics. Both represented the same accepted trips and returned equivalent business results. That equivalence check came first: a faster query that answers a different business question is not an optimization. I excluded one warm-up, then timed 15 complete executions for each path. Complete matters because the results were consumed rather than timing only planning. I used the median to reduce sensitivity to an unusually fast or slow run. This makes the comparison less dependent on one noisy measurement. The input-row reduction was calculated from 9,551,872 Silver rows and 240,850 Gold rows, while both queries continued to represent all accepted trips. For this workload, Gold reduced input rows by 97.48% and the median time from 0.042986 seconds to 0.008073 seconds, a measured 5.32 speedup. The result supports a specific conclusion: preaggregation helped this hourly pickup-zone query on this machine and dataset. It does not establish that Gold is always 5.32 times faster. Hardware, operating system, storage, caching, and query shape can change timing. By publishing the warm-up policy, run count, grain, row counts, and median, I made the claim narrow enough to evaluate and repeat. That is stronger than broadly calling a pipeline optimized without clearly defining the comparison. Testing, containers, and CI: The project uses Ruff for linting and Pytest for automated checks, with 27 tests passing in release v0.1.0. Ruff catches style and static-quality issues before they become review noise. The tests cover transformations, quality rules, reconciliation, and repeatable pipeline behavior. A multi stage Dockerfile separates verification from normal execution. The dedicated test image includes development dependencies for linting and tests. The smaller runtime image excludes test-only packages and runs the command-line interface as non-root user ID 10001, reducing unnecessary runtime surface. I verified the container locally on Linux ARM64. GitHub Actions provided a separate Linux AMD64 check. Its two jobs divide responsibilities: Python quality checks run Ruff and Pytest container verification builds the test stage, executes containerized checks, builds the runtime stage, verifies the command line interface, and confirms non-root execution. That matters to anyone evaluating or maintaining the project. A repository that works only in its author's environment transfers hidden assumptions to the next person. The container documents the runtime boundary, while continuous integration reruns important checks on pushes and pull requests. Cross-architecture verification does not prove compatibility everywhere, but it is stronger evidence than one laptop run. Reproducibility makes the design easier to review, change, and trust. Lessons learned: The transformations were not the hardest part. The difficult work was deciding what the pipeline should mean when the source was imperfect or the same partition ran twice. Data quality required business decisions. Dropping every row with a null would have been easy, but a missing passenger count does not invalidate a pickup event. Accepting an out of month timestamp however, would weaken the monthly partition's meaning. Hard rules and soft flags connected each condition to the analyses it could affect. It is not simply the command can run again. A repeat run should verify the source, avoid an unnecessary download, rebuild deterministic outputs safely, and create new audit evidence. February showed me that reuse and observability must coexist. Reconciliation provided confidence that visual inspection could not. The Bronze to Silver plus Quarantine equality detects missing records; the Silver to Gold equality detects aggregation loss. The benchmark reinforced a related lesson: a modest, measured claim is stronger than a broad unsupported one. If I redesigned the project, I would define data contracts, rejection taxonomy, and audit schema even earlier. I would also plan explicitly for schema evolution before adding many partitions. Those decisions are easier while the pipeline is small than after downstream users depend on its behavior. Limitations and next steps: This is a batch pipeline covering three months. It runs locally and in containers. Cloud deployment and workflow scheduling have not been implemented, and the project does not use dbt or Airflow. The current version therefore does not provide managed storage, automatic monthly execution, distributed access, or production monitoring. Future work could add object storage and a cloud query engine so partitioned datasets are accessible beyond one machine. Scheduled orchestration could run new months and manage operational retries, while infrastructure as code could reproduce the environment. I would also add schema evolution handling before extending the history, then process additional monthly partitions. Monitoring and alerting should cover failed runs, missing source files, quality gate failures, and unexpected row-count changes. These are plans, not completed features. Any future dbt, Airflow, or cloud component should solve a demonstrated need, then arrive with tests, documented failure behavior, and audit evidence before it is presented as part of the system. Conclusion: The challenge was not moving one monthly file. It was adding data without wasting work, keeping invalid records explainable, and proving that each layer preserved meaning. Manifest-driven partitions, validated reuse, hard rejects plus soft flags, reconciliation gates, and DuckDB audits provided that evidence. The verified result covers 9,554,778 source rows: 9,551,872 accepted, 2,906 quarantined, and every accepted trip represented in Gold. For one equivalent workload, Gold reduced input rows by 97.48% and measured 5.32x faster at the median.
