# Building an Ansible Automated Compliance Enforcement Framework for AWS Linux Servers

## Overview

Building an Ansible Automated Compliance Enforcement Framework for AWS Linux Servers Introduction Managing the security configuration of Linux servers is an important responsibility in cloud and infrastructure engineering. When you manage multiple servers, checking their configurations manually can become repetitive, time-consuming and difficult to standardize. You might need to inspect SSH authentication settings, verify firewall rules, review privileged accounts, check sensitive file permissions, inspect running services, monitor pending security updates, validate logging and review network security parameters. Doing these checks manually across multiple servers introduces inconsistencies and makes it difficult to maintain reliable compliance evidence. I wanted to approach this problem differently. Instead of repeatedly connecting to individual servers and running commands manually, I decided to build an Ansible Automated Compliance Enforcement framework that could inspect Linux security configurations across multiple AWS EC2 instances, identify compliance gaps, and support controlled remediation. This project was an opportunity to apply practical skills in Ansible, AWS, Linux administration, infrastructure automation and security hardening. In this article, I will walk through the architecture, implementation approach, security checks, troubleshooting process, actual audit findings and lessons I learned while building the project. The Eight Linux Compliance Categories The framework was organized around eight security categories. Each category focuses on a different aspect of Linux server security. 7.1 SSH Security SSH is one of the most important remote administration services on a Linux server. An insecure SSH configuration can expose systems to unnecessary authentication risks. The audit examined effective SSH configuration, including: Root login restrictions. Password authentication. Public-key authentication. Maximum authentication attempts. During the initial inspection, the following values were observed: MaxAuthTries 6 PermitRootLogin without-password PubkeyAuthentication yes PasswordAuthentication no The intended stricter baseline was: PermitRootLogin no PasswordAuthentication no MaxAuthTries 4 For remediation, I prepared an Ansible-managed configuration file: /etc/ssh/sshd_config.d/00-ansible-compliance.conf An important part of safe SSH remediation is validating the configuration before reloading the daemon. The validation command is: sshd -t If validation succeeds, the configuration syntax is accepted by the SSH daemon. This helps prevent an invalid configuration from breaking remote administrative access. The project also used configuration backups and controlled service handling. The subsequent audit verified the intended effective SSH settings on both managed servers. Engineering lesson: Security hardening should not compromise the ability to administer the infrastructure. Separating Compliance Auditing from Remediation One of the most important architectural decisions was keeping the audit and remediation responsibilities separate. I organized the project around two roles: roles/ ├── compliance_checks/ │ └── compliance_remediation/ Audit mode Audit mode inspects the server configuration and identifies compliance findings. It should not intentionally modify the managed systems. Remediation mode Remediation mode allows the automation to apply selected security configuration changes. The intended workflow is: Gather facts | v Validate execution mode | v Run compliance audit | v Check for remediation mode | v Apply approved remediation | v Run compliance audit again | v Review final findings The project supports two execution modes: audit and: remediate The default execution mode was configured as audit. This is useful because an ordinary audit should not unexpectedly modify infrastructure. Why this design matters Imagine running a compliance check against ten production servers. You want to know which systems are misconfigured before making changes. Separating the two responsibilities allows you to inspect first, review findings and then decide whether remediation is appropriate. It also makes troubleshooting easier because you can distinguish between problems discovered during inspection and changes introduced during remediation. A configuration change that looks harmless can interrupt administrative access or break an application. For SSH remediation, the implementation included a configuration validation step: sshd -t For firewall remediation, SSH access was allowed before enabling UFW. For network remediation, persistent configuration was considered rather than relying only on temporary runtime changes. These are important engineering principles: Back up configurations before modifying sensitive files. Validate configuration syntax before applying service changes. Use handlers where appropriate. Avoid unnecessary service restarts. Apply changes conditionally. Re-run the audit after remediation. Consider rollback and recovery procedures. A particularly important Ansible concept here is idempotency. Idempotency means that if I execute the same automation again, Ansible should recognize that the desired configuration is already present and avoid unnecessary changes. This is important for repeatable infrastructure management. I also learned that changed=0 does not necessarily mean every security requirement has passed. A server can remain unchanged while the audit identifies outstanding compliance gaps. 10. Troubleshooting and Engineering Lessons Building this project involved more than writing task files. Several issues required investigation. Challenge 1: Incorrect SSH private-key path Problem: Ansible could not connect to the managed servers because the configured private-key path was incorrect. Investigation: I compared the inventory configuration with the actual key location and tested SSH connectivity. Resolution: I corrected the key path and restricted its file permissions. Lesson: Always verify the actual SSH key path and test manual SSH before troubleshooting Ansible itself. Challenge 2: Firewall installed but inactive Problem: The initial audit showed that UFW was installed but inactive. Investigation: I checked firewall status and verified the OpenSSH application profile. Resolution: I implemented remediation that allowed SSH before enabling the firewall. Lesson: Remote firewall changes must be designed around administrator access and recovery. Challenge 3: Effective SSH configuration Problem: The effective SSH configuration did not initially match the intended security baseline. Investigation: I inspected effective SSH settings rather than assuming that the main configuration file represented the active configuration. Resolution: I prepared an Ansible-managed SSH configuration and validated the effective values after remediation. Lesson: Configuration files and effective runtime configuration are not always the same. Challenge 4: Network interface discovery Problem: Global network settings alone were not sufficient for a complete network security assessment. Investigation: I gathered Ansible facts to identify available network interfaces. Resolution: I incorporated interface-aware inspection and persistent sysctl checks. Lesson: Security auditing needs to consider the actual configuration of the system, including individual interfaces. Challenge 5: Outstanding package updates Problem: The audit identified pending security updates. Investigation: I inspected package update information and distinguished security updates from other updates. Resolution: The framework reported outstanding patches rather than automatically installing everything. Lesson: Compliance automation should support operational decisions, not blindly make potentially disruptive changes. 11. Key Lessons Learned This project reinforced several important engineering principles. 1. Automation starts with understanding the infrastructure. Before writing automation, I needed to understand SSH connectivity, Linux configuration, firewall behaviour and network interfaces. 2. Ansible roles improve maintainability. Separating audit and remediation made the project easier to understand and extend. 3. Security remediation must be controlled. A security improvement should not accidentally lock administrators out of their own servers. 4. Effective configuration matters. Inspecting the effective SSH configuration was more useful than simply reading a configuration file. 5. Runtime and persistent settings are different. This became especially important during network security auditing. 6. A successful playbook is not the same as a compliant server. The actual security findings matter more than the execution recap alone. 7. Verification is part of automation. Applying a configuration change is only one part of the process. Re-running the audit establishes whether the intended result was achieved. 15.
