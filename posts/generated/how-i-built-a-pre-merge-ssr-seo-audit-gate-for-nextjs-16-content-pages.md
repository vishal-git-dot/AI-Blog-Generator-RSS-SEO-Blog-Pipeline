# How I Built a Pre-Merge SSR SEO Audit Gate for Next.js 16 Content Pages

## Overview

When you ship programmatic or template-driven content pages in Next.js, next build and ESLint will happily pass while your pages quietly fail in Google Search Console as "Crawled - currently not indexed." I ran into this firsthand while building and scaling structured reference pages for Tarot Fortune Cards on Next.js 16 (App Router) + React 19 + next-intl . The UI looked great in Chrome, Lighthouse was green, and every route compiled cleanly—yet inspecting the raw HTML that crawlers actually receive exposed four subtle bugs that were silently hurting indexation. Instead of doing manual spot-checks after deployment, I turned those failure modes into an automated two-stage pre-merge SEO gate (static repo check + live Vercel preview SSR HTML check). Here is what it catches and the exact patterns you can drop into your own Next.js workflow. Why Checking in Chrome DevTools Lies Modern Next.js apps mix Server Components, Client Components, dynamic imports, and next/image . When you inspect a page in Chrome DevTools, you are looking at the post-hydration DOM . Search crawlers do render JavaScript eventually, but initial crawl discovery, canonical evaluation, and structured data extraction still heavily favor clean first-response SSR HTML . If your primary content, comparison tables, or FAQ answers only appear after client hydration—or if your template accidentally repeats 30% of the same sentences across sibling routes—indexation slows down dramatically. The 4 Silent Bugs Our Pre-Merge Gate Catches 1. Cross-Page Boilerplate Overlap (Template Cannibalization) Even when every page is hand-written or carefully edited, shared intros, transition paragraphs, disclaimers, and CTA blocks add up fast. Across a cluster of sibling reference pages, it is surprisingly easy to end up with 25–40% identical sentences , which looks like thin templated content to search engines. Above-the-Fold Media Accidentally Lazy-Loaded or Oversized Template pages often share a single hero or visual component. One careless loading="lazy" attribute (or leaving an unoptimized 300 KB+ PNG in /public ) will silently push mobile LCP past 3 seconds across every route using that template. Our pre-merge rule for primary visual assets: Convert every primary visual to WebP and enforce a hard <= 60 KB file-size cap in the static repo check. Accidental Regression on Existing Top-Ranking Pages This is the one most developers forget until traffic drops. When you refactor a shared layout or metadata helper to support new content pages, it is dangerously easy to alter the <title> , meta description, or <h1> of your existing top-performing URLs . Our static audit keeps a short list of protected slugs (our top organic landing pages) and diffs their resolved title , description , and h1 against origin/main before every PR merge. If a refactor touches any protected page's TDH unexpectedly, the check fails immediately with FAIL > 0 and blocks the merge. The Two-Stage Checklist Summary Stage Target What It Blocks 1.
