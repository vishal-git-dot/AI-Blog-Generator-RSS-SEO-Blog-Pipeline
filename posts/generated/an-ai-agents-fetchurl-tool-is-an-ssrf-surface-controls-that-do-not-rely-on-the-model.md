# An AI Agent's fetch(url) Tool Is an SSRF Surface: Controls That Do Not Rely on the Model

## Overview

A tool that takes a URL and returns the page is one of the most common additions to an AI agent. It is also a server-side request whose destination is chosen by a model, and the model reads content that someone else wrote: web pages, support tickets, documents, e-mail. When that content says "fetch this address next", the request leaves from the server's network position, not from the author's. The question for a review is not "can the model be made to behave". It is "what can this tool reach if it is asked to reach anything". Where the risk is classified The OWASP Top 10 for LLM Applications (2025) describes this as LLM06:2025 Excessive Agency, with three root causes: excessive functionality (the system exposes tools it does not need), excessive permissions (the tool can touch more than its task requires) and excessive autonomy (high-impact actions happen without independent approval). Among its prevention measures: avoid open-ended tools in favour of narrow, purpose-built ones, grant downstream access only at the level needed, and enforce authorization in the downstream system rather than relying on the model's judgment ("complete mediation"). The same page notes that logging, monitoring and rate limiting do not prevent excessive agency; they only limit the damage. The controls below are of the preventing kind. Two cases, two sets of controls The OWASP SSRF Prevention Cheat Sheet separates two situations, and the right control set depends on which one applies. Case 1: the tool only needs a few known destinations. The cheat sheet's guidance is to match the host against an allow-list and build the request in code, instead of passing the model's string to an HTTP client. Most "look up this order", "read this ticket" or "call this internal API" tools belong here, and for them the best design is not a URL parameter at all but an identifier that the server turns into a request. Case 2: the tool must be able to fetch arbitrary public pages. The cheat sheet states that allow-lists cannot be used here because the list of destinations is not known in advance. Control then moves to the network and to what is checked at connection time. It also warns that deny-lists are bypass-prone and a last resort, and that regular expressions over complex formats are hard to maintain and error-prone. Five controls for Case 2 Check the address the socket will use, not the string that was submitted. The cheat sheet notes that domain allow-listing alone does not prevent DNS rebinding, and that checking DNS answers separately does not either. The check has to happen on the resolved address at connection time. Do not follow redirects automatically. The cheat sheet recommends disabling redirect-following in the web client. If redirects are needed, each hop is a new request that goes through every check again. Block non-routable ranges at the network layer too. Application checks can have gaps (one is described below). Egress rules for the process that runs the tool are the second layer. Make the cloud metadata service hard to reach. On AWS, IMDSv2 uses session tokens obtained with a PUT request; a PUT carrying an X-Forwarded-For header is rejected, and the response hop limit defaults to 1. The instance can be configured to accept only IMDSv2, which makes IMDSv1 calls fail. The OWASP cheat sheet's advice is to migrate to IMDSv2 and disable IMDSv1. AWS describes the design goal in the title of its security blog post: "Add defense in depth against open firewalls, reverse proxies, and SSRF vulnerabilities with enhancements to the EC2 Instance Metadata Service". Give the tool the smallest possible identity. Run it as a separate process with no cloud role, no internal network route and no credentials in its environment, so that a successful request has nothing valuable to return. In the first test run, a request to an address given as a literal IP reached a local test server, while the same request by hostname was rejected: the custom lookup is never called when the host is already an address. After the fix, every notation that the URL parser normalises to an IP ( 127.1 , 0x7f000001 , 2130706433 , [::1] ) is rejected by the same line. The practical lesson: a guard has to be tested with the inputs it is meant to stop, not only with the input it was designed around. Two limits are worth stating. A response size cap and a timeout are included because an open fetch tool is also a way to make the server spend resources. And the example does not make the open-fetch case safe on its own; the other four controls, and the model not being the only thing standing between a page and an internal service, still apply. What was tested The code above was run against a local HTTP server and a stubbed client before publication: the address ranges: loopback, private, link-local, carrier-grade NAT and unique-local ranges were blocked, and two public addresses were not a hostname that resolves to loopback ( localhost ) was rejected at connection time IP literals in several notations were rejected a non-HTTPS URL and a host outside the allow-list were rejected a 3xx response was refused (tested with a stubbed client, so the redirect rule is checked in isolation) Not tested: a real DNS-rebinding setup, an IPv6-only network, and behaviour behind a corporate proxy. Those need to be checked in the environment where the tool runs.
