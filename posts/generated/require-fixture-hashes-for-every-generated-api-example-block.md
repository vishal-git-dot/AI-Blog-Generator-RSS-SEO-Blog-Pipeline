# Require Fixture Hashes for Every Generated API Example Block

## Overview

Generated API documentation should compile example blocks from a frozen fixture corpus rather than from conversational output. A language model may reformat those fixtures, add language fences, and apply a reviewed secret denylist during compile. A human reviewer must still own every claim that an example is currently callable, correctly scoped, or sufficient to ship. Unsigned curl recipes and invented HTTP status codes remain merge blockers even when nearby field tables already look complete. Why invented examples fail objective review Readers treat fenced JSON and curl recipes as executable contracts, not as decorative illustration around a schema table. When a model invents a 422 body or a fabricated error code, downstream SDKs and runbooks copy that fiction into production traffic. Chat transcripts also leak bearer tokens, tenant identifiers, and internal hostnames that never belonged on a public reference page. A compile gate that hashes fixtures and rejects unknown status codes removes that defect class before human review starts. What the model may draft versus what a human must own Treat the model as a compiler with a closed input set, not as an author of sample HTTP traffic. If a heading labeled Example or Sample Request has no matching fixture hash, the page is not ready for merge. If a sentence says the sample creates a live object, a named human must sign that sentence in the review record. Those three rules keep example blocks aligned with checked-in tests without asking the model to invent conversations. Model-permitted operations The compiler may pretty-print JSON fixtures, wrap them in fenced blocks, and choose a language tag that matches the fixture kind. It may replace keys listed in a reviewed denylist with the token REDACTED and refuse to emit any Authorization header value. It may copy status codes that already appear in the frozen allowlist derived from the committed OpenAPI document. It must not add query parameters, nested fields, or error members that are absent from the matching fixture file. Human-owned sentences A human owns any statement that the example is currently accepted by production or staging. A human owns scope names, permission narratives, and claims that a token kind is sufficient for the call. A human owns side-effect language such as creates a charge, deletes a customer, or retries without idempotency keys. A human owns every curl recipe that includes a real hostname rather than a placeholder like api.example.test . A six-step compile-and-sign workflow The sequence below is a documentation compile pipeline, not a writing workshop, and each step leaves an auditable file. Skip a step and the later validator cannot distinguish a reviewed payload from a chat improvisation. Keep the OpenAPI file, the fixture corpus, and the denylist on the same branch as the generated pages. Label the scripts as a worked example until your repository actually executes them in continuous integration. Step 1 — Snapshot fixtures as canonical JSON Store one JSON document per example under docs/fixtures/ , with names that match the operation id and outcome. Canonicalize each file so key order and whitespace cannot create a hash mismatch during later validation. Write SHA-256 digests to docs/fixtures/SHA256SUMS and treat that file as merge-critical input, not as generated noise. It also does not replace contract tests, consumer-driven pact files, or staging smoke checks against real auth. Teams without a frozen OpenAPI document or without checked-in fixtures should not generate public curl recipes this way. Marketing pages, design-partner previews, and unreleased endpoint tours need a human author, not a fixture compiler. The free model and free server path is an availability option for the compile job, not a claim about model quality. This article does not assign model names, quotas, hardware, duration, or benchmark numbers to that availability option. If your compliance process forbids vendor-hosted compile jobs, run the same scripts on your existing documentation runners. Duplicate fixture bodies will share a digest, which is acceptable only when two operations truly return one payload. Example blocks earn trust when they are compiled from hashed fixtures and stripped of credential-shaped values. Models can format those fixtures, but they cannot own routability, authorization narratives, or side-effect promises. Put the hash gate in the compile job before the next reference drop, and keep signatures on the remaining callable claims.
