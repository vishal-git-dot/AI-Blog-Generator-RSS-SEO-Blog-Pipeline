# 5 Django Mistakes Beginners Make Again and Again (and How to Fix Them)

## Overview

Hi DEV! 👋 I'm Mehedi Alam, a Python & Django developer and trainer from Bangladesh. I teach Python, Django, and MySQL to batches of 24+ trainees, and I help them build job-ready portfolio projects. When you teach the same framework many times, you start noticing the same stumbling blocks. This post covers five of the most common Django mistakes beginners make, why they matter, and a simple fix for each. TL;DR Skipping virtual environments Committing secrets and leaving DEBUG = True "Fixing" migration errors by deleting everything Hitting the database inside loops (the N+1 problem) Reading request.POST directly instead of using Forms 1. Skipping the virtual environment What it looks like: Running pip install django globally. It works at first, but a second project that needs a different Django version breaks the first one. Sharing the project with a teammate becomes guesswork, too. The fix: Create an isolated environment for every project and record your dependencies. python -m venv venv # macOS / Linux source venv/bin/activate # Windows venv\Scripts\activate pip install django pip freeze > requirements.txt Now anyone can recreate your setup with pip install -r requirements.txt . Add venv/ to your .gitignore so the environment itself never ends up on GitHub. 2. Committing secrets and leaving DEBUG = True What it looks like: The default settings.py is pushed to a public GitHub repo with the SECRET_KEY inside and debug mode on. Debug pages can expose settings and code details, and a leaked secret key is a real security problem. The fix: Read sensitive values from environment variables. # settings.py import os SECRET_KEY = os . environ [ "DJANGO_SECRET_KEY" ] DEBUG = os . environ . get ( "DJANGO_DEBUG" , "False" ) == "True" ALLOWED_HOSTS = [ host for host in os . environ . get ( "DJANGO_ALLOWED_HOSTS" , "" ) . split ( "," ) if host ] Also: Keep local values in a .env file and add .env and db.sqlite3 to .gitignore . If a secret key was ever pushed, treat it as compromised and generate a new one. Before deploying, run python manage.py check --deploy to catch common security settings you forgot. 3. "Fixing" migration errors by deleting everything What it looks like: A migration error appears, so the beginner deletes db.sqlite3 and the migrations/ folders and starts over. On a throwaway local database this is tolerable. As a habit, it is dangerous, because on a real project with real data it destroys history and breaks teammates' databases. The fix: Learn the basic workflow and read the error message. python manage.py makemigrations python manage.py migrate python manage.py showmigrations Change models.py , then run makemigrations , then migrate . Always in that order. Commit migration files to Git. They are part of your project's history. Use showmigrations to see what has actually been applied before changing anything. 4. Hitting the database inside loops (the N+1 problem) What it looks like: Imagine a Book model with a foreign key to Author : # ❌ 1 query for the books + 1 query per book for its author books = Book . objects . all ( ) for book in books : print ( book . title , book . author . name ) With 100 books, that is 101 queries. It feels fine with five rows in development and becomes slow in production. The fix: Fetch related objects up front. # ✅ 1 query using a JOIN books = Book . objects . select_related ( "author" ) for book in books : print ( book . title , book . author . name ) Use select_related for foreign keys and one-to-one fields, and prefetch_related for many-to-many and reverse relations. To see how many queries a page really runs, install Django Debug Toolbar in development. 5. Reading request.POST directly instead of using Forms What it looks like: # ❌ No validation, and a missing field raises KeyError def contact ( request ) : if request . method == "POST" : Message . objects . create ( name = request . POST [ "name" ] , email = request . POST [ "email" ] , body = request . POST [ "body" ] , ) return redirect ( "thanks" ) return render ( request , "contact.html" ) Nothing checks that the email is valid, that the field lengths are right, or even that the fields exist. The fix: Let Django's forms do the validation and cleaning. # forms.py from django import forms from . models import Message class MessageForm ( forms . ModelForm ) : class Meta : model = Message fields = [ "name" , "email" , "body" ] # views.py from django . shortcuts import render , redirect from . forms import MessageForm def contact ( request ) : if request . method == "POST" : form = MessageForm ( request . POST ) if form . is_valid ( ) : form . save ( ) return redirect ( "thanks" ) else : form = MessageForm ( ) return render ( request , "contact.html" , { "form" : form } ) You get validation, error messages, and cleaner code for free. And remember to include the csrf_token template tag inside every POST form in your templates, or Django will reject the submission. Bonus tip: plan your user model early If there is any chance you will need extra user fields (phone number, role, and so on), set up a custom user model at the start of the project. Changing it after the first migrations is much harder. Quick checklist for your next Django project [ ] Virtual environment created and requirements.txt saved [ ] Secrets in environment variables, .env ignored by Git [ ] DEBUG off outside development [ ] Migration files committed [ ] No database queries hidden inside loops [ ] User input handled through Django forms Wrap-up None of these mistakes mean someone is a bad developer.
