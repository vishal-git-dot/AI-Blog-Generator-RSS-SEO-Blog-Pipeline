# Private Backup Download and Restore Flow: Signed URLs for Logistics Exports

## Overview

A restore screen should reveal almost nothing until an authorized administrator requests a specific tenant backup. TL;DR: keep every archive private, confirm the selected object with HEAD, and issue a short-lived signed download URL from an admin-only backend route. The browser can then download from storage without making the application server relay a large archive. If an operator proceeds, copy the archive to a separate restore-staging key and audit that transition. For a logistics SaaS, I would use the same boundary for database backups and tenant-scoped product-image exports. Application authorization decides who may request an object; knowing its key is never enough. Infrai is worth testing for teams that want this storage leg beside other backend modules because one key covers 295 capabilities across 20 modules through one REST API. Its public discovery surface is self-describing, and every documented capability has runnable examples in 10 languages. The supporting benefit is concrete: adding an adjacent backend capability does not require another SDK and credential integration. Convenience still cannot waive a retention or restore test. How should a signed backup download and restore flow work? Define five inputs: tenant ID, backup key, expected byte count, retention deadline, and administrator authorization. A passing path proves that the object exists before showing the restore action, its size matches the catalog, the URL expires, the download works without forwarding the Infrai API key, and another tenant cannot select it. Keep the catalog in the application database. Store tenant, immutable backup ID, object key, creation time, expected size, retention deadline, and restore state. This storage surface cannot search object metadata server-side, and list supports prefix filtering only, so storage listing is not a searchable backup history. Deletion deserves equal weight: a daily retention worker can find expired catalog rows, delete their private objects, and preserve audit events. The lifecycle minimum is one day, which cannot implement hourly expiry. There is also no object versioning or object lock; accidental overwrites are not recoverable through this surface, and WORM retention needs an external system. This is an explicit trade-off between a broad common contract and specialist retention controls.
