# One Query, Six Ranked Lists, One Answer: Tuning Rank Fusion for Multilingual Search

## Overview

How one constant in Reciprocal Rank Fusion lets a confident top match stand out — and why the right value depends on how correlated your retrievers are. When you type a query into SpotRecall, my private on-device browser recall extension, it does not run one search. It runs six. The query is first searched as typed. Then Chrome's on-device Translator turns it into the other two languages SpotRecall covers — English, Japanese, and Chinese — because, as I wrote earlier in this series, translating the query beats shipping a model four times larger. Each of those three variants is searched twice: once by BM25 keyword search and once by a small multilingual embedding model ( multilingual-e5-small , int8, running locally). Three variants times two retrievers gives six ranked lists. The user sees one result page. Version 1.3.1 is about the step in between: how those six lists become one ordering, and how to make the page you are actually looking for land at the top. Measured on 54 real queries against a 1088-page personal history, the full set of changes in this release brings mean reciprocal rank (MRR) to 0.828 . This post covers the fusion stage at the center of it. The fusion step SpotRecall merges its lists with weighted Reciprocal Rank Fusion (RRF), the standard technique for hybrid search. Every document receives, from every list it appears in, a contribution based only on its rank: score(doc) = Σ over lists weight(list) / (k + rank(doc in list)) RRF is popular for good reasons. It needs no score calibration between retrievers — a BM25 score and a cosine similarity live on unrelated scales, but ranks are always comparable. It is a few lines of code. And it rewards agreement: a page that several retrievers like rises. The interesting part is the constant k . What k actually controls k sets how steeply the reward falls with rank. In other words, it decides how much a confident first place is worth compared with a place further down the list. The value you see in tutorials and libraries is k = 60 , from the original RRF paper. Here is what it does to a single list (ranks start at 1): k = 60: rank 1 → 1/61 ≈ 0.0164 rank 20 → 1/80 ≈ 0.0125 (#1 is worth 1.3× #20) k = 3: rank 1 → 1/4 = 0.25 rank 20 → 1/23 ≈ 0.0435 (#1 is worth 5.75× #20) With k = 60 the curve is almost flat: being first is barely better than being twentieth. That shifts the weight of the decision onto how many lists a page appears in. A worked example makes the difference concrete. Take a page that is the clear first result of one list, and another page that sits at rank 10 in three lists (unweighted, for simplicity): scenario k = 60 k = 3 #1 in one list 1/61 ≈ 0.016 1/4 = 0.25 #10 in three lists 3/70 ≈ 0.043 3/13 ≈ 0.23 winner consensus (2.6×) confident #1 Neither answer is universally right. It depends on what agreement between lists means . Why SpotRecall's lists call for a smaller k k = 60 was designed for fusing many independent systems — different engines, different models, different teams. When independent systems agree on a document, that agreement is strong evidence, and a flat curve that rewards it makes sense. SpotRecall's six lists are not independent. A query and its translation describe the same intent; their embeddings sit close together; BM25 over a Japanese translation and BM25 over the Chinese one often retrieve overlapping pages. When correlated lists agree, they are largely repeating one opinion. So for this pipeline, a steeper curve fits better. k = 3 lets a strong first place in one list compete on equal terms with moderate agreement across several, which matches what a user means by "the page I was looking for." Letting the vector list contribute its best matches The second piece concerns the embedding retriever. Nearest-neighbour search always returns the number of results you ask for. It never says "nothing here is really similar." With e5-small, cosine similarities for real pages cluster in a narrow band, roughly 0.75 to 0.9. The top few hits of a vector list are usually meaningful; by rank 18 the score difference from rank 3 can be tiny, and the content often is not related. 1.3.1 therefore keeps only vector hits within a fixed margin of the best one: keep hit if score ≥ topScore − 0.06 (and rank ≤ 20) When the model is confident, several close matches pass. When one page stands out, the list becomes short and decisive. Either way, the vector retriever contributes what it is sure about, and BM25 handles the rest. The user's own words come first Two more weights round out the stage: Translations count at 0.7× the original query. Machine translation is good but lossy; the words the user actually typed remain the strongest evidence of intent. The vector weight is shared across variants. A query and its two translations embed to near-identical vectors. Instead of letting that one opinion count three times, the vector weight is divided by the number of variants. The whole stage is a small pure function, shared by the extension and the offline evaluation so that tuning measures exactly what ships: export const FUSION_PARAMS = { bm25Weight: 1.2, vecWeight: 1.0, rrfK: 3, translationWeight: 0.7, vecMargin: 0.06, vecDepth: 20, contentlessWeight: 0.5, }; Each behaviour is pinned by a test. For example, when the original query and a translation each produce a page at the same rank, the original's page must come first; and a weak vector hit (0.7 next to a 0.9) must not reach the fused list at all. Choosing values that generalize All of these numbers were tuned against 54 labeled queries — Chinese, Japanese, English, and cross-lingual — replayed offline against a real 1088-record backup, with the offline ranking verified to be identical to the live extension. With so few queries, it is easy to find parameters that fit them perfectly and help nobody else. A grid search proposed other values. When I tuned on half of the queries and tested on the other half, those values did not beat the shipped ones, so they did not ship. The values above are the ones that kept their gains on held-out queries. For reference, an early configuration with textbook k = 60 , equal weights, and untrimmed vector lists scored around 0.30 MRR on the first 32 queries. After this release, the full 54-query set sits at 0.828, and the worst-case configuration (simulating bookmark-heavy profiles) at 0.826. Those two figures are not on the same query set, so read them as direction rather than a precise delta. The next posts cover the other contributors and the evaluation loop in detail. The takeaway Rank fusion constants are not magic numbers. They encode an assumption about your retrievers: how independent they are, and how much a confident first place should be worth. If your hybrid search fuses a keyword list, a vector list, and a few query rewrites, those lists are probably correlated. Measure k rather than copying 60 — and give each retriever the chance to contribute only what it is genuinely confident about. The honest caveat: k = 3 is right for this pipeline — few lists, strongly correlated, a personal corpus of about a thousand pages. The general advice is to measure, not to use 3.
