Production means it works every time, for every user, at 3 a.m., under load, after the model provider changes something, with a bill you can predict and a rollback you can trust. The distance between those two states is the subject of MLOps — the discipline of applying DevOps practice (automation, versioning, testing, monitoring, repeatable deployment) to machine learning — and its newer cousin LLMOps , which adapts those practices to applications built on large language models, where "the model" is often someone else's service and the things you ship are prompts, retrieval indexes, tools, and configuration. Two worlds, one discipline: HOSTED-MODEL APPS (LLMOps) You call a managed model (Azure OpenAI and similar). You ship: application code, prompts, retrieval indexes, tool definitions, and configuration. You operate: quotas, gateways, evaluation gates, cost, model-version pinning, provider changes. SELF-HOSTED MODELS (classic MLOps) You run the model: ONNX/ML.NET models in your process, or model servers in containers on CPU/GPU nodes. You ship and operate all of the above PLUS model artifacts, container images, GPU capacity, scaling, and model drift. Most real systems are a mix — a hosted LLM for generation, a self-hosted embedding or vision model, a managed search index — so this guide covers both. The production concerns repeat across both worlds, and they form the sections below: deploy safely, version everything, monitor quality and drift, automate delivery with evaluation gates, package into containers, orchestrate on Kubernetes, cache aggressively and safely, scale to demand, and choose hardware deliberately. It builds directly on earlier guides in this series — AI Observability (what to measure), AI Security (what to lock down), Computer Vision with .NET (serving ONNX models), Microsoft.Extensions.AI (the client abstraction), and RAG (indexes and evaluation) — and focuses on what is specific to running these systems in production. Model Deployment What "deploying a model" means depends on where it runs MANAGED MODEL ENDPOINT A provider hosts the model; you create a "deployment" and call it (Azure OpenAI deployments, Azure AI Foundry model deployments, other hosted APIs). + No GPUs to manage, fastest path, provider handles scaling. - Quotas, per-token cost, provider-driven model lifecycle, data leaves your boundary (unless private networking/terms suffice). IN-PROCESS MODEL The model is loaded inside your app: ONNX Runtime or ML.NET in an ASP.NET Core service (classifiers, detectors, embedding models, small LMs). + Lowest latency, no network hop, simplest topology, scales with the app. - Memory per replica, startup time, CPU/GPU contention with the app, tied to app release cadence. SEPARATE MODEL SERVICE A dedicated inference service over HTTP/gRPC (your own container, NVIDIA Triton, vLLM for LLMs, KServe, Azure ML managed online endpoints, Ollama for development). + Independent scaling, GPU isolation, multiple clients, model updates decoupled from the app. - Another service to operate, network latency, more moving parts. SERVERLESS / SCALE-TO-ZERO Azure Container Apps (including serverless GPU workload profiles) or Functions with a model. + Pay only when used, good for spiky or low traffic. - Cold starts (model load!), GPU availability, limits on size and duration. EDGE / ON-DEVICE Models shipped to devices or local servers (ONNX Runtime, DirectML, NPUs). + Offline, private, no per-call cost. - Update distribution, device variability, no central monitoring unless you build it. Decision shortcuts General LLM, no special data-residency or custom-model needs -> managed endpoint (Azure OpenAI) A small model (classifier, detector, embedder) with tight latency -> in-process ONNX/ML.NET A big or GPU-hungry model shared by several apps -> separate model service on GPU nodes (AKS / Azure ML / Container Apps GPU) Occasional, bursty batch jobs -> scale-to-zero jobs or serverless; batch APIs for hosted models Strict offline/privacy requirements -> self-hosted open-weight model or on-device Deploying managed models as code Treat a model deployment like any other infrastructure: declared in code, reviewed, and pinned. // An Azure OpenAI deployment declared as infrastructure (illustrative — verify the API version, model name, version, SKU names, and capacity units) resource chatDeployment 'Microsoft.CognitiveServices/accounts/deployments@2024-10-01' = { parent: openAiAccount name: 'chat-prod' // the deployment name your app uses (the app never hard-codes the underlying model name) sku: { name: 'Standard' // pay-per-token; provisioned throughput SKUs exist for predictable latency at steady load capacity: 100 // quota units (thousands of tokens per minute) } properties: { model: { format: 'OpenAI', name: 'gpt-4o-mini', version: '2024-07-18' } versionUpgradeOption: 'NoAutoUpgrade' // PIN the model version: upgrades happen when YOU choose, after evaluation raiPolicyName: 'prod-content-policy' // server-side content filter policy } } Why this matters: - PINNED VERSION: a silent upgrade can change behavior (and quality) under you. Release strategies for models BLUE/GREEN Run old and new side by side; switch traffic at once; instant rollback by switching back. Doubles capacity during the switch. CANARY Send a small share (1%, 5%, 25%...) to the new version, watch metrics (quality, latency, errors, cost), and expand or roll back automatically. SHADOW Mirror real traffic to the new version, discard its responses, and compare offline (quality, cost, latency). Zero user risk; best for validating a new model or prompt. A/B TEST Randomly split users between versions and compare outcomes (feedback, task success). Needs enough traffic and a clear success metric. ROLLING Replace replicas gradually (Kubernetes default) — fine for app code, but for models make sure old and new replicas can coexist and produce compatible outputs. ALWAYS Keep the previous version deployable, record which version served each request (trace attribute), and define rollback criteria BEFORE the rollout. 2. Model Versioning Version everything that changes behavior In classic software, the code version identifies behavior. In AI systems, behavior is the product of many artifacts, any of which can change independently — so every one needs a version, and every request should record which versions served it. Model Monitoring The AI Observability guide covers instrumenting logs, metrics, traces, cost, and RAG quality in depth. This section covers what is specific to models in production : detecting that the world has moved out from under them. Why models decay DATA DRIFT The distribution of inputs changes (new customer segment, a new camera, a new product line, seasonal language, a different mix of languages). CONCEPT DRIFT The relationship between inputs and the right answer changes (fraud tactics evolve, "good" customer behavior changes, a policy changes the labels). PREDICTION DRIFT The distribution of outputs shifts (the classifier suddenly predicts one class far more often) — often the earliest visible symptom. UPSTREAM CHANGE A feature pipeline, tokenizer, data source, or the provider's model changes without notice. CORPUS CHANGE (RAG) The documents change or the index is rebuilt; retrieval quality shifts with them. A model that was excellent at launch quietly gets worse. Without monitoring, you learn about it from customers. Layers of model monitoring 1. SYSTEM HEALTH Availability, error classes, latency, throughput, GPU/CPU/memory, queue depth (Section 9 and AI Observability). 2. INPUT / DATA QUALITY Schema and range checks, missing values, new categories, language mix, image size and format distribution, text-length distribution. 3. DATA DRIFT Statistical comparison of live input distributions against a reference (the training or validation data, or a recent healthy window). 4. PREDICTION DRIFT Distribution of predicted classes, scores, and confidence over time; rising share of low-confidence or "unknown" outputs. 5. MODEL PERFORMANCE Actual accuracy/precision/recall/F1 (or task success) — which requires ground truth, often delayed (below). 6. BUSINESS IMPACT The KPI the model exists to move: conversion, fraud caught, handling time, deflection, defect escape rate. Getting ground truth: the hard part Performance metrics need labels, and in production labels arrive late, partially, or never. DELAYED LABELS Outcomes known later (a loan defaults in 12 months, a return occurs in 30 days). Monitor leading indicators (drift, confidence) in the meantime, then backfill performance. HUMAN REVIEW Route a sample (and all low-confidence cases) to reviewers; their decisions are labeled data and a live accuracy estimate. USER FEEDBACK Corrections, overrides, thumbs, escalations — biased and sparse, but valuable signals. CANARY SETS A fixed labeled set re-scored on a schedule detects model/pipeline regressions even without fresh labels. PROXY METRICS Confidence distributions, agreement between the model and a stronger offline model, and consistency checks. Monitoring hosted LLM applications You can't observe weights or training data, so monitor behavior: MODEL VERSION Alert when response.ModelId changes (provider update) — record it on every trace. CANARY GOLDEN SET Run it on a schedule against production configuration; alert on score drops (see AI Observability, Section 8). OUTPUT STATISTICS Length, refusal rate, format-failure rate, finish-reason mix, language, sentiment — sudden shifts mean something changed. INPUT STATISTICS Prompt length, language mix, topic clusters, new intents. QUALITY SAMPLING Sampled LLM-judge scores and user feedback by prompt/model/index version. COST AND LATENCY Tokens per request, cost per outcome, TTFT percentiles. From alert to action: retraining and rollback TRIGGERS Drift above threshold · performance below SLO · new data volume · schedule (for example quarterly) · a significant upstream or business change. RESPONSE Investigate (is it real drift or a pipeline bug?) -> retrain or fine-tune on fresh data, or update prompts/index -> evaluate against the golden set AND recent real data -> shadow/canary -> promote with approval -> monitor. Rollback to the previous version if the new one underperforms. AUTOMATION Automate the pipeline (data -> train -> evaluate -> register), but keep a HUMAN approval gate before promotion to production for anything consequential. GUARDRAIL Beware feedback loops: if model predictions influence the data you later train on (recommendations shape clicks), monitor for self-reinforcing bias. 4. CI/CD for AI Applications What's different about CI/CD for AI A conventional pipeline asks "does the code compile and do the tests pass?" An AI pipeline must also ask "is the behavior still good?" — and that answer is statistical, depends on external models, and costs money to compute. So an AI pipeline adds evaluation gates alongside unit tests, treats prompts, models, and indexes as deployable artifacts, and often separates code deployment from model/prompt promotion. CODE CHANGE build · unit tests (fake chat client) · static analysis · dependency + secret scanning · container build + scan · deploy · smoke test PROMPT CHANGE lint · EVALUATION against the golden set · security (injection) suite · cost/latency check · review · promote · canary MODEL CHANGE registry registration · EVALUATION on held-out + recent data · performance benchmark (latency/throughput on target hardware) · shadow/canary · promote with approval INDEX CHANGE build new index · retrieval evaluation (Recall@k, MRR) · switch alias · monitor · keep the old index for rollback INFRA CHANGE IaC plan/what-if · policy checks · deploy to staging · verify quotas and content-filter policy The test pyramid for AI applications UNIT TESTS (fast, deterministic, free) Business logic, prompt assembly, history trimming, tool wiring and authorization, validators, parsers — against a FAKE IChatClient (see Microsoft.Extensions.AI, Section 10). Run on every commit. INTEGRATION TESTS Real vector store/database in a container (Testcontainers), real HTTP pipeline, still a fake or recorded model. Verifies plumbing. EVALUATION TESTS (slower, statistical, costs money) The golden set run against the REAL model/prompt/index: retrieval metrics, judged faithfulness, citation validity, task success, refusal behavior, cost and latency. Repeat each case several times (non-determinism). Compare to a baseline. Run when prompts, models, retrieval, or tools change — not necessarily on every commit. SECURITY TESTS The adversarial suite: injection, exfiltration, cross-tenant access, tool misuse (see AI Security, Section 14). A release gate. LOAD / PERFORMANCE TESTS Throughput, latency percentiles, saturation, and cost at target traffic — on production-like hardware. SMOKE / SYNTHETIC CHECKS After deploy and continuously in production: a handful of real end-to-end requests. Each saves a different cost — and each has distinct staleness and security risks. The kinds of caching 1. RESPONSE CACHE (EXACT) Same inputs -> stored output. Skips the model entirely. 2. SEMANTIC CACHE "Similar enough" questions share a stored answer, matched by embedding similarity. 3. PROVIDER PROMPT CACHE The provider discounts and speeds up requests that begin with a recently processed prompt prefix. 4. EMBEDDING CACHE Content hash -> vector. Avoids re-embedding unchanged text or repeated queries. 5. KV CACHE (self-hosted LLMs) The attention key/value cache inside the inference server, including prefix caching across requests. 6. MODEL ARTIFACT CACHE Model files cached on nodes/volumes so pods don't re-download them; image layers cached; warm pools of loaded models. 7. IN-PROCESS MODEL CACHE The loaded model session held in memory (singleton), or an LRU of several models when you serve many. 8. PREDICTION CACHE For deterministic classical models: input features -> prediction. Scaling Inference Start with the arithmetic LITTLE'S LAW: concurrency = throughput x latency A service handling 50 requests/second at 0.4 s per request has ~20 requests in flight on average. If one replica can handle 5 concurrent requests before latency degrades, you need ~4 replicas at average load — plus headroom for peaks (commonly 30-50%) and for losing a replica. For LLM calls to a hosted provider, also compute TOKEN throughput: requests/s x (input + output tokens) must fit your tokens-per-minute quota. Always LOAD TEST: measure latency percentiles at increasing load on production-like hardware, find the knee where latency climbs, and set capacity and autoscaling targets below it. Levers for scaling, in rough order of leverage 1. DON'T DO THE WORK Caching (Section 8), deduplication, cheaper routing — the fastest request is the one you skip. 2. MAKE EACH REQUEST CHEAPER Smaller or distilled models, quantization (FP16/INT8), shorter prompts and outputs, graph optimization, efficient runtimes (ONNX Runtime, TensorRT, OpenVINO, DirectML). 3. BATCH Process several requests per model invocation — raises throughput substantially on GPUs (and helps CPUs), at a latency cost (below). 4. SCALE OUT More stateless replicas behind a load balancer, autoscaled on the right signals (Section 7). 5. SCALE UP Bigger or faster hardware (more cores, a GPU, a larger GPU) when one model invocation itself is the bottleneck. 6. SHIFT WORK OFF THE REQUEST PATH Queues and background workers for anything users aren't waiting on. Stateless replicas and load balancing Inference services should be stateless (conversation and cache state live in external stores) so any replica can serve any request and replicas can be added or removed freely. LOAD BALANCING GOTCHA: inference request durations vary enormously (a 50-token answer vs. a 2,000-token answer). Plain round-robin can pile long requests on one replica. Prefer least-connections or queue-aware balancing, and cap per-replica concurrency so overload is rejected quickly instead of queueing indefinitely. GPU vs. CPU Considerations The decision is about utilization and cost per inference, not raw speed A GPU does a lot of parallel arithmetic quickly, but it is expensive whether or not it is busy. A CPU is slower per operation but cheap, flexible, and everywhere. The right choice depends on model size, traffic shape, latency target, and — above all — how well you can keep the hardware utilized . Where GPUs win LARGE MODELS Transformers, large vision models, and LLMs with many millions or billions of parameters. HIGH, STEADY THROUGHPUT Enough traffic to keep the GPU busy, especially with batching. LATENCY-CRITICAL HEAVY MODELS When a CPU simply can't meet the latency target for the model size. BATCH EMBEDDING / BULK INFERENCE Large offline jobs where throughput per dollar dominates. SELF-HOSTED LLM SERVING Practically requires GPUs (or accelerators) for useful speed at scale. Where CPUs win SMALL MODELS Classical ML, gradient-boosted trees, small neural nets, small embedding/classification models (tens to low hundreds of millions of parameters, quantized). LOW OR BURSTY TRAFFIC An idle GPU burns money; CPU instances scale to zero or run cheaply at low utilization. BATCH SIZE OF ONE, LOW LATENCY Small single-item inferences often run just as fast on CPU (no host-to-device transfer overhead). OPERATIONAL SIMPLICITY No driver/CUDA/image-version matrix, easier scheduling and autoscaling, broader availability. QUANTIZED MODELS INT8/INT4 on modern CPUs (AVX2/AVX-512/VNNI instructions) can be surprisingly fast for the right models. ARM CPUs Often the best price/performance for CPU-bound inference where supported. The binding constraint is often memory, not compute MODEL MEMORY (rule of thumb): parameters x bytes per parameter 7-billion-parameter model: FP16 (2 bytes) ≈ 14 GB; INT8 ≈ 7 GB; 4-bit ≈ 3.5-4 GB — PLUS the KV cache and activations KV CACHE grows with context length and concurrent sequences; for LLM serving it frequently limits concurrency more than the weights do. A model that doesn't fit in GPU memory doesn't run (or must be split across GPUs/offloaded to CPU at a heavy speed penalty). Quantization is therefore both a cost lever and a feasibility lever. For LLM decoding, speed is often limited by memory BANDWIDTH rather than raw compute. GPU for large/steady; size for memory; verify GPU is actually used Readiness Production checklist SLOs, rollback, quotas, security, cost, runbooks, kill switches Conclusion Production AI is mostly the disciplined application of ideas you already know — versioned artifacts, automated pipelines, gradual rollouts, health probes, autoscaling, monitoring, and rollback — adapted to systems whose behavior is statistical, whose dependencies change without notice, and whose cost scales with usage. The adaptations are what matter: version everything that affects behavior (weights, tokenizers, prompts, indexes, tools, evaluation sets) and stamp each request with those versions; gate releases on evaluation and security tests , not just unit tests, using repeated runs and baselines to handle non-determinism; monitor drift and quality , not just uptime, with canary evaluations that catch the silent provider and data changes nobody announces; and roll out gradually through shadow, canary, and blue/green strategies with rollback criteria defined in advance. On the infrastructure side, the same few themes recur. Gate traffic on readiness , not on process start. Keep model delivery out of the request path (verified downloads, node-local caches, warm capacity). Scale on the right signals (concurrency, queue depth, GPU metrics) and shed load early instead of queueing until everything is slow. Put a gateway in front of hosted models for authentication, token limits, metrics, caching, and failover, and use keyless identity everywhere. Cache aggressively but safely — keyed on everything that changes the answer, scoped by tenant, invalidated on every version change. And choose hardware by cost per inference at the utilization you will really achieve , sizing for memory as well as compute and verifying that the GPU you pay for is actually the one doing the work. Pair those practices with a readiness checklist, rehearsed rollbacks, kill switches, and runbooks, and an AI feature stops being a demo that works until it doesn't and becomes a service your team can change confidently, operate predictably, and afford.
