How I'd Run Bug Triage on 40 Defect Reports Before a Release Date Say it's my feature, and AI review just handed me 40 defect reports. They're real defects, not noise, and I have a few weeks before the release date. Here's how I'd spend the first afternoon of bug triage. 1. Cluster the Reports by Feature and Root Cause I'd start by merging duplicates and grouping by root cause. Forty reports rarely mean forty problems. Ten of them might be one missing check that shows up in ten code paths. Clustering defect reports is how you pay the fixed per-report overhead (reproduce, test, review, commit) fewer times. One owner, one branch, one round of tests and one commit series per cluster beats 40 separate threads. 2. Score Each Cluster by Blast Radius Blast radius is how far a defect reaches if it ships. I'd rank clusters by what they can damage, not by how many reports they contain or how big the fix looks. Blast Radius Signals for a Database Feature Wrong query results with no error Data loss or corruption on disk Security and permission checks skipped Crashes or hangs in the server Behavior you can't change after release without breaking users Odd combinations of features, such as Peter Eisentraut's example of a domain over a composite type inside a partition inside a view Odd feature combinations are where LLM-assisted review shines. Writing about cases like a domain over a composite type inside a partition inside a view, Peter Eisentraut, a PostgreSQL core team member, said "no one can manually test this or even enumerate these test cases," but LLM-assisted fuzzing "can find problems with this really quickly." Qodo's code quality report shows edge cases are a real pain point in review too. In the August 2026 survey of 500 U.S. developers at organizations already using AI meaningfully in the software development lifecycle, 21.8% named hidden bugs or edge cases as their greatest challenge when reviewing AI-generated code. Edge cases are hard for people, so reports about them deserve a real look. 3. Separate Severity vs Priority Severity is how bad a defect is. Priority is how soon you fix it. Keep them as two separate fields, because a deadline changes priority without changing severity. A severe bug in a feature you can revert might get low priority for this release, because the fix is "revert." A mild bug in an on-disk format gets high priority, because you can't patch it later without pain. Tom Lane, a PostgreSQL core team member, captured the priority question in a remark The Register quoted about SQL Property Graph Queries (SQL/PGQ): "At this point I'd be willing to bet dinner that if we ship it in v19 there will be post-release bug discoveries that are unfixable until v20." Whether you can fix a defect after release is what decides its priority. 4. Split Must-Fix From Follow-Up My bug triage table sorts defect reports into five buckets: must-fix, fix if cheap, follow-up, design call and close. The Postgres 19 examples come from the PostgreSQL 19 Open Items wiki page and Tomas Vondra's analysis. The buckets are my own call, not the project's. If your project has feature flags or preview labels, design-call defects are what they're for. The bug triage decision tree turns the five buckets into four questions in order: can it corrupt or leak data, can we fix it after release, is the fix small, and does it point at the design? The "long tail of relatively harmless issues" Peter Eisentraut described would mostly exit at the third question. 5. Do the Hours Math Before Anyone Starts Fixing Once every cluster of defect reports has a bucket, I'd do the hours math out loud in the triage meeting. My rough numbers per report: The fix: about 20 minutes for a three-line change. The overhead: about two more hours to reproduce it, write a test, get review and commit. The total: at about two hours and 20 minutes per report, 40 defect reports cost about 90 hours. If two people have three weeks of part-time attention, 90 hours is tight but doable for must-fix and fix-if-cheap. If the must-fix list includes a design flaw, the math says revert. Better to say it in week one than in week three. 6. Move Review Earlier So the List Doesn't Land at the End The real fix for a late pile of defect reports is upstream. The revert chart from Tomas Vondra, a PostgreSQL major contributor, shows the Postgres 19 problem was timing: the review happened, it just happened late. One defect costs very different amounts at two points in the cycle: Found before commit: one person, a few minutes. Found in beta: a thread, a reviewer and a release slot. Catching defects before commit is the whole argument for shift-left code review : run review on the diff while the author still has context. Peter Eisentraut, a PostgreSQL core team member, reached a similar conclusion for Postgres, writing that LLM-assisted fuzzing "probably needs to be part of feature development in the future." Liz Fong-Jones, Technical Fellow at Honeycomb, described moving review earlier on The Agentic Review podcast in September. Her team is doing "peer reviews sooner, doing peer reviews more often at the design stage." People review the design. Machines catch the off-by-one. A Short Bug Triage Workflow for AI Review Findings Here's the seven-step bug triage workflow I'd pin in the team channel. It fits in one afternoon for 40 AI review defect reports. Collect. Put every finding in one tracker view with one label, for example ai-review . Cluster. Merge duplicates and group by feature and root cause. Score. Give each cluster a blast radius (Large, Medium, Small) and a yes or no for "fixable after release." Bucket. Sort clusters into must-fix, fix if cheap, follow-up, design call or close. Do the math. Hours needed for must-fix plus fix-if-cheap, against hours left. If it doesn't fit, cut or revert now. Assign. One owner per cluster, one fix series per cluster. Feed it back. For every must-fix, write down which earlier check would have caught it, and add that check before the next freeze.
