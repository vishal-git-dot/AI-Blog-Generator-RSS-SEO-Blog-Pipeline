# Reachability Receipts: Prove an Agent Patch's Green Build Came From Tests That Touched It

## Overview

A green build is a fact about your test suite, not about the patch. If no executed test line intersects the lines the patch changed, the pipeline measured the repository's steady state and reported it as approval. The receipt format below records that intersection explicitly, and it closes the most common abuse of a flaky-test freeze: freezing a test that never touched the patch and then counting the green result as evidence. The Three Fields a Receipt Needs Every merge decision in this workflow reduces to three sets. Changed lines — the exact new-side line ranges of the patch, not a diffstat. Per-test executed lines — which lines each test actually ran. The freeze set — tests currently quarantined as flaky, with an expiry. Everything else is bookkeeping. The verdict comes from intersecting the first two, then asking the third whether that intersection is trustworthy. Step 1: Derive Changed Line Ranges, Not Counts git diff --stat counts insertions and hides where they landed. A patch can add forty lines and still touch none of the functions your properties cover. Use zero context so each hunk is exactly the changed region. git fetch origin main --depth = 1 git diff -U0 --no-color origin/main...HEAD > patch.diff grep -c '^@@' patch.diff The third command tells you how many changed regions you are dealing with. If that number is zero on a non-empty patch, your merge base is wrong and the rest of this workflow is measuring nothing. Step 2: Collect Per-Test Line Hits Line-level execution is the only signal here that cannot be faked by a passing suite. coverage.py records which test covered which line when dynamic contexts are enabled. # .coveragerc [run] dynamic_context = test_function coverage run -m pytest -q coverage json --show-contexts -o coverage-contexts.json python tools/contexts_to_trace.py coverage-contexts.json > trace.jsonl A minimal adapter from that JSON to the JSONL the receipt consumes: # tools/contexts_to_trace.py import json , sys doc = json . load ( open ( sys . argv [ 1 ])) by_test = {} for path , filedata in doc [ ' files ' ]. items (): for ln , contexts in ( filedata . get ( ' contexts ' ) or {}). items (): for ctx in contexts : by_test . setdefault ( ctx , set ()). add (( path , int ( ln ))) for test_id , hits in sorted ( by_test . items ()): print ( json . dumps ({ ' test_id ' : test_id , ' hits ' : sorted ( map ( list , hits )), ' status ' : ' unknown ' })) Two caveats matter. Contexts prove coverage, not outcome, so the status field above is a placeholder that must be merged from your JUnit XML before the receipt is trusted. A flaky test that never touched the patch should stay frozen without blocking anything, because freezing it was a scheduling decision, not a statement about this change. The third row is the opposite: once a known-flaky test intersects the patch, no one can separate the flake from the regression on those lines. Step 5: Self-Test the Gate Before You Trust It A gate that rejects nothing is decoration. Run these three cases against a scratch branch before wiring the script into CI. Reformat-only patch. Whitespace changes across one file, no behaviour change. Expected: changed_lines above zero, evidence count zero, exit non-zero. Single-line behaviour patch. One condition inverted in a function a property covers. Expected: at least one evidence test, exit zero when the property is declared. Freeze scoping. Add the flaky test to freeze.json , run twice — once on a patch that touches its lines, once on a patch that does not. Expected: frozen-blocking appears only in the first run. Freeze entries should carry an expiry so quarantine does not become permanent: { "tests/test_rates.py::test_fx_cache" : { "class" : "flake" , "expires" : "2026-11-01" }} The expiry date is not enforced by the script above. Reject any freeze entry whose expiry has passed in a separate check, otherwise the freeze set becomes an allowlist for failures. Limitations and Who Should Not Use This Execution is not falsifiability. A line hit means the line ran, not that an assertion could have failed. Pair this with mutation testing or a tautology classification step; a reachability receipt alone will happily certify an assertion-free test. Rename and move handling. With -U0 , moved code can appear as a full rewrite, inflating the changed set and producing false evidence verdicts. Cost. Dynamic contexts slow the suite and produce large trace files. On a large monorepo, restrict tracing to the packages the patch touches. Language coverage. This depends on a line-level tracer. Compiled or out-of-process code needs a different mechanism, and none of the script above applies. Do not use it if your repository has one meaningful test file, if your runner cannot emit per-test hits, or if the receipt is destined to become a checkbox nobody reads. Manual review of a handful of tests is cheaper and more honest. Where MonkeyCode Fits One part of this workflow is genuinely tedious: naming the properties for a patch you did not write.
