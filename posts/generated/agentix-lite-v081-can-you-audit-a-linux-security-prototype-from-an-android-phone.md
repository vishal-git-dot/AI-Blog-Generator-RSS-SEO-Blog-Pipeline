Part 1: The 2-minute explanation for everyone What is Agentix Lite trying to do? Imagine a small security guard for a Linux server. It watches incoming activity, looks for suspicious behavior, evaluates the source, and records what happened. Its basic architecture looks like this: A sensor notices something suspicious. It creates a small event describing what happened. The event travels through a local UNIX socket. The main engine evaluates the event and updates reputation. The result is stored in SQLite. In Shadow Mode, the system can recommend an action without actually blocking anyone. That final point matters. Shadow Mode is observation, not enforcement. The system can say: "This IP looks suspicious. It would qualify for a temporary ban." But it does not have to touch the firewall. Think of it as a fire alarm being tested without actually flooding the building with water. What did we test? We did not just inspect Python functions and declare victory. We created temporary databases, local sockets, separate processes, synthetic events, and a local TCP connection. One experiment followed this complete route: TCP connection → honeypot listener → authenticated UNIX datagram → EventReceiver → Agentix Engine → SQLite. The actual TCP connection came from the local IPv6 loopback address "::1". Then we injected a separate synthetic event using "8.8.8.8" to verify the Shadow Mode decision. The results: The real TCP event reached the engine. The loopback address was not turned into a ban candidate. The synthetic external address became "BAN_CANDIDATE". No real firewall operation happened. Both actors remained stored in SQLite. Result: 8/8 checks passed. Why not just say it works? Because there is a difference between a working prototype and a production security system. Our tests ran on Android through Termux. We did not install Agentix on a real Debian or Ubuntu VPS during this audit. We tested many internal mechanisms, but we did not prove how the whole system behaves under real server traffic, real systemd supervision, or long-term operating conditions. That distinction is not a weakness in the report. It is the point of the report. UNIX sockets and authenticated event delivery Agentix separates telemetry into three ingress lanes: Normal events. Honey critical events. Host critical events. The receiver enables Linux peer credential passing: sock.setsockopt( socket.SOL_SOCKET, socket.SO_PASSCRED, 1, ) It extracts the credentials from the received ancillary data and checks the sender UID against the expected identity for the lane. This is more meaningful than trusting an event's JSON field claiming to be from a particular service. We also tested concurrency, queue limits, and per-IP fairness. One honeypot limitation We also tested a failed telemetry delivery. The honeypot listener updates its per-IP cooldown before sending the event. The telemetry client performs one non-blocking send and does not retry. If the receiver is missing, the event is lost, but the cooldown is still consumed. A second connection from the same IP during the cooldown therefore does not generate another event. This was reproduced with a controlled local experiment. Finding: "HONEYPOT-001". It is an event availability limitation, not evidence of a firewall bypass. MCP interfaces and runtime truth We tested the Python MCP server and the Go gateway separately. MCP-STATUS-001: Enforcement status is not authoritative The Go gateway's shadow summary hardcodes: mode = shadow enforcement_enabled = false It does not derive these values from an authoritative daemon runtime snapshot. The Python MCP interface reads its own process configuration, which is not necessarily the same thing as the running daemon's actual state. An AI client could therefore receive an inaccurate description of the system's enforcement state. A read-only interface still needs trustworthy status data. Deployment limitations discovered Architecture mismatch The bundled gateway is: bin/agentix-mcp-linux-amd64 ELF 64-bit LSB x86-64 The Android test environment is: aarch64 The native validator includes both x86-64 and ARM64 builds, but the Go MCP gateway currently has only the AMD64 binary in this checkout. The installer checks whether the binary is executable, not whether its architecture matches the host. This could cause the MCP service to fail on an ARM64 VPS if enabled with that binary. Existing nftables table The installer applies the nftables ruleset only if the Agentix table does not already exist. If an older table exists but lacks one of the expected sets or chains, the preflight can fail rather than automatically reconciling it. That is safer than silently assuming the firewall is correct, but it is an installation and upgrade limitation. Android runtime path The prototype uses: /run/agentix/status.json In our Termux environment "/run" did not exist and the write failed with: errno 30: Read-only file system Writing to a temporary writable directory succeeded. The Linux deployment installs a systemd tmpfiles configuration to create "/run/agentix" and its subdirectories. Therefore, this Android failure is an environment difference, not proof that the Linux deployment has the same problem. Final verdict Agentix Lite v0.8.1 has a substantial amount of locally tested functionality. The audit demonstrated: Event processing and reputation decisions. Authenticated local event transport. SQLite persistence and capacity handling. A real local TCP honeypot-to-engine path. Shadow Mode behavior without real firewall operations. Python and Go MCP interface tests. Watchdog integration logic. A set of reproducible Observer edge cases. But there is a boundary we must respect. This was a prototype tested in Termux on Android. It was not a production VPS audit. We did not perform: A live Debian/Ubuntu systemd deployment. A real production Docker-to-host socket integration. A real nftables enforcement test. A 24-hour Shadow Mode observation. A seven-day observation period. A DDoS-resilience assessment. The next meaningful validation step is a dedicated Debian/Ubuntu AMD64 VPS running Agentix in Shadow Mode, with enforcement disabled. Collect real runtime evidence, explain anomalies, inspect candidate-ban precision, and only then consider further operational claims. No automatic enforcement should be enabled just because the local test suite is green. A green test suite is a useful signal. It is not a production certificate. Experiment first. Headline second.
