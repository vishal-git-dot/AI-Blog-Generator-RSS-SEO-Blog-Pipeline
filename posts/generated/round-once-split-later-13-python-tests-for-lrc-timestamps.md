A timestamp serializer looks like a small formatting task until a rounded value crosses a boundary. An input just below a minute can become exactly a minute at the precision chosen for export. If the code splits the original value into minutes and seconds before rounding, it can produce a seconds field that should have carried into the next minute. The useful design question is therefore not only how many decimal places to print. It is which units the function accepts, when rounding happens, and which invariants should hold after that decision. This example uses integer centiseconds as its output units and a deliberately narrow contract. One public function accepts nonnegative integer milliseconds. A second accepts unsigned ASCII decimal seconds as text and rounds directly to centiseconds. Both use round-half-up, then split the already rounded total into fields. They do not open recordings, infer words, repair cue order or validate an entire lyric document. Keeping that boundary explicit makes the small module easier to test and prevents its tests from being presented as evidence about problems the code does not attempt to solve. State the representation before writing the formatter The chosen output is a bracketed minute, seconds and hundredths representation. Minutes have a minimum width of two digits but are not wrapped at an hour. Seconds and hundredths always stay inside their respective ranges because they are obtained from integer division after rounding. This is an example policy, not a claim that every player accepts an arbitrarily wide minute field. A real export pipeline may need additional limits for its destination. Those limits should be a separate validation decision rather than an accidental side effect of using a clock or date formatting API. The millisecond interface intentionally rejects floats and booleans. In Python, booleans are integer subclasses, so a broad integer instance check can admit values that were probably not intended as durations. The exact type check here is a policy choice for a small teaching interface. A larger application could accept more numeric types, but it should document their conversion and error behavior. Silent truncation is particularly unhelpful when a caller believes it supplied a fractional duration. Rejecting the unsupported type makes that disagreement visible at the boundary instead of hiding it inside a plausible-looking timestamp. Round the total, then split the fields For integer milliseconds, adding five before integer division by ten implements the selected half-up rule for nonnegative values. The result is a total number of centiseconds. Dividing that total by six thousand produces minutes and a remainder; dividing the remainder by one hundred produces seconds and hundredths. A carry across a second or minute is already represented in the rounded total, so the formatting step does not need a collection of special-case repairs. The function is small because the arithmetic order does most of the work. The decimal-text interface should not round through an intermediate millisecond value. Consider the textual duration 59.9949 seconds. Rounding that first to milliseconds yields 59.995 seconds, which rounds again to 60.00 at centisecond precision. Rounding the original decimal directly to centiseconds yields 59.99. Neither intermediate operation is mysterious; the mismatch comes from composing two quantization steps. If the intended output precision is already known, perform that quantization once. If an upstream system has already delivered integer milliseconds, treat that as its explicit input representation rather than pretending the earlier precision is still available.
