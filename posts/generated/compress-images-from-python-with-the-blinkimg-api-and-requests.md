# Compress images from Python with the Blinkimg API and requests

## Overview

To compress an image from Python with the Blinkimg API you make four HTTP calls with requests : ask for an upload slot, PUT the bytes, create a job, then read the result link. The client below is 40 lines with no SDK. In my run it turned a 576.8 KB JPEG into a 93.9 KB AVIF with targetBytes: 100000 . What does the API flow look like? The API has three endpoints you need, under https://api.blinkimg.com/v1 : POST /v1/uploads with filename and contentLength . It answers with an uploadId and a signed url . You PUT the file to that url . POST /v1/jobs with the uploadId and an options object: format , quality or targetBytes , resize , stripMetadata . GET /v1/jobs/{id} until status leaves queued and processing , then GET /v1/jobs/{id}/result for a signed link to the file. Every call carries Authorization: Bearer <key> . You create the key from your account; the API docs list the endpoints and the OpenAPI description. One Session . The requests docs say a session reuses the underlying TCP connection to the same host ( requests: Session objects ). The polling loop makes several calls per file, so that saves a handshake each time. A timeout on every call. By default requests do not time out unless you set one ( requests: Timeouts ). A script that runs overnight should never hang on one socket. An Idempotency-Key on the job. The API accepts this header on POST /v1/jobs . If you add a retry around that call and keep the same key, a repeated POST returns the first job instead of creating (and charging for) a second one. Note: The upload url points at object storage, not at the API. That is why the client PUTs with plain requests.put and not with the session: the session carries your Bearer key, and the key has no business going to the storage host. Send only the bytes there. What does an error look like? Every API error has the same body: {"error": {"code", "message", "requestId"}} . The call() helper turns it into one exception. With a wrong key (the message text came from my local stand-in; the code is the API's): __main__.BlinkimgError: 401 UNAUTHORIZED: bad key The codes you will meet most in a batch script are UNAUTHORIZED , FILE_TOO_LARGE , INSUFFICIENT_CREDITS and RATE_LIMITED . A 429 also carries a Retry-After header; sleep that many seconds and try again. Keyed requests are shaped at 120 writes a minute. What does it cost? The API calls ran against a local stand-in of /v1 that I wrote from the API's published request and response contract ( packages/shared/src/api/uploads.ts and jobs.ts ), with the Blinkimg engine ( processImage , the code the workers run) doing every encode. The byte counts are the engine's; the error body shape and codes come from the API's own schema.
