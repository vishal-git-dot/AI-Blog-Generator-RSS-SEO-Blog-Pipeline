# Hornet: A Local Coding Goal You Can Inspect, Pause, and Resume

## Overview

A useful coding run should leave more than a convincing final message. It should leave changed files, checks you can examine, and enough saved state to understand what happened if the process stops. That is the problem Hornet addresses. It gives a local model a coding goal, organizes the work into small scoped cells, and keeps the goal, attempts, questions, and execution evidence on disk. This walkthrough uses Hornet 0.15.1 , Python 3.13 on Windows , LM Studio , and a new Ubuntu worker VM in VirtualBox . We will repair one Python function, inspect the result, and see how to return to unfinished work. The commands follow the release’s starter walkthrough; the live-model measurements later in this article come from the separately documented 0.15.0 trial. Hornet was created and is led by Daniel F. MacDonald , with engineering contributions credited in the project. It is available under AGPL-3.0-only . Source and current documentation Installable PyPI release: matrixswarm-hornet 0.15.1 Signed starter release What a durable coding goal contains Hornet separates the saved work from the model’s current working context. A coding cell has an explicit task, permitted files, an expected result with a declared type, acceptance checks, and execution limits. The controller records those commitments, runs the work, and checks the result before accepting completion. Larger goals can be divided into ordered cells within configured limits; this first exercise deliberately uses one. The active request contains bounded context and references to retained evidence. Source is read as needed. Earlier exchanges can leave the active request while their full records remain available on disk. This limits what each request carries without treating an old failure as if it never happened. Situation What Hornet retains or does An attempt fails Keeps its conditions, errors, and verification evidence The model needs a decision Saves a question and waits for an explicit answer The controller is interrupted Uses checkpoints and operation receipts to assess whether work can resume A goal completes Keeps its workspace and exports candidate changes for review A finished file needs a follow-up Creates a revision workspace that records its parent The current workers and model roles run sequentially . A plan with multiple cells is not a claim that several models are working concurrently. The detailed behavior is documented in the CLI reference . 1. Choose an unused VM name and loopback port. The helper creates a new worker; it does not adopt an existing VM or overwrite an established worker configuration. During setup it generates fresh SSH keys, pins the worker’s host key, restricts the local private directory, and binds SSH forwarding to loopback. Shared folders, shared clipboard, and drag-and-drop are not enabled. The VM uses NAT and has outbound networking. The guest hornet account has no sudo access. Separate goal directories share its account; they are not separate sandboxes for hostile code. Keep unrelated secrets out of the VM. Give it one precise coding goal The starter’s calculator.py deliberately returns its input: def double ( n ): """ Return twice an integer (the starter intentionally needs a repair). """ return n There is a useful trap here: the existing tests check the integer return type and the zero case. This incorrect function can pass those tests. A green test suite is only as informative as the behavior it exercises. The supplied demo-goal.txt makes the missing behavior explicit: Fix calculator.py so double(n) returns 2*n for an integer n, with an integer return type. Required examples: double(-3) == -6, double(0) == 0, double(7) == 14. Only calculator.py may change. Preserve its public function name and argument. Keep the existing tests unchanged. Use one coding cell and verify the required behavior. That gives the run a small file scope, concrete examples, a return-type requirement, and a constraint against solving the task by rewriting the existing tests. Start the goal with the documented limits: . \.venv\Scripts\hornet.exe --root . \my-first-goal autowork --worker-config worker.json --goal-file demo-goal.txt --model $model --base-url http://127.0.0.1:1234/v1 --protocol lmstudio-json --max-cells 1 --max-turns 30 --max-tools 40 --cell-turns 10 --cell-tools 16 --context-chars 16000 --max-tokens 2048 --timeout 120 --json The command is long because its limits are explicit: Setting Meaning in this exercise --max-cells 1 Keep the plan to one coding cell --max-turns 30 , --max-tools 40 Bound model requests and tool operations across the goal --cell-turns 10 , --cell-tools 16 Bound the individual coding cell --context-chars 16000 Bound active working context in characters --max-tokens 2048 Cap a model response’s output tokens --timeout 120 Set the socket-operation timeout; not an overall completion deadline The context setting is a character budget, not a token count or a change to the model’s loaded context window. Backend framing adds overhead. Use the recorded usage to assess the actual run. Hornet prepares a separate goal workspace in the VM. Planning and verification roles establish checks before coding, and the controller keeps the frozen checks outside the worker’s editable source. It requires new source changes, the suite, and the applicable cell and goal checks before reporting completion. For this autonomous goal, success means completed , with the coding cell ready_for_review . A zero process exit, waiting_for_user , or paused is not equivalent to completed coding work. 6. Inspect the changed source and saved evidence Save the exact run_dir returned by the command: $run = 'PASTE_THE_EXACT_RUN_DIR_FROM_THE_RESULT' . \.venv\Scripts\hornet.exe --root . \my-first-goal goal-files $run . \.venv\Scripts\hornet.exe --root . \my-first-goal questions $run Use that run’s paths rather than guessing the newest directory. goal-files connects file hashes, cell identities, changes, and revision provenance; it rebuilds this view from validated evidence. There are two locations to understand: Inside the VM: each autonomous goal has its own source directory under /home/hornet/workspace/goals/ , with its generated workspace ID. The original worker baseline remains separate. On the controller: the project retains the run directory, normally beneath my-first-goal/coding/recipes/ , containing its goal, checkpoints, cell jobs, results, and evidence. Within the reported run, the useful records include: Record What to inspect goal.json and goal-acceptance.json Original requirements and frozen overall checks recipe-checkpoint.json Saved execution phase, source state, and counters goal-status.json Derived progress and outcome view file-index.json File hashes and the cells responsible for them cells/<cell-id>/return-manifest.json Declared result, changed-file hashes, and references to checks and attempts cells/<cell-id>/jobs/<job-run>/changes.json Exported changed-file content and tracked diff The job’s verification/ and attempts/ directories Verification rounds and retained attempt evidence goal-completion.json Links the completed goal to its source state, receipts, and final evidence Open the calculator.py entry in the job’s changes.json : its content field contains the exported source. Compare it with the starter and read the recorded diff. Confirm that only the allowed file changed and that the function handles the required examples while preserving its interface. For this exercise, a minimal repair is to preserve the function and return 2 * n . Inspect the actual exported implementation rather than assuming it took that form. The resulting behavior should be: Call Required result double(-3) -6 double(0) 0 double(7) 14 Read the assertions as well as their verdicts. Hornet can verify that checks ran and that declared result types matched; a model-authored assertion can still misunderstand the task. Exported work remains a candidate for your review, with integration into your own source as a separate step. 7. Answer a saved question or resume unfinished work If the run returns waiting_for_user , list its questions with the command above. Copy the exact question ID and answer that question: . \.venv\Scripts\hornet.exe --root . \my-first-goal answer $run q-EXACT_ID --text 'Your answer' . \.venv\Scripts\hornet.exe --root . \my-first-goal autoresume $run --json Replace both placeholders with the actual run and a substantive answer. Saving the answer does not start execution. autoresume explicitly continues the autonomous goal. While a required question waits, the controller process can exit. There is no response deadline or repeated model inference consuming resources while you are away. Resuming without an answer keeps the work waiting. The question is allowed to be more patient than a chat window. Use autoresume for an interrupted autonomous goal too. Standalone work jobs use resume instead. A completed goal is not unfinished work to resume; use a revision for a new request. Keep the project, run evidence, worker keys, VM, and source intact. Resume checks identities and saved source state before continuing. For supported worker operations, durable receipts can resolve a lost reply when the operation and its completed result match. A started operation without a completed receipt remains uncertain. Hornet stops for inspection instead of assuming it is safe to repeat. This supports recovery from specific interruptions; it does not promise exactly-once effects in external systems or universal recovery from every power loss. 8. Make a targeted revision and retain the parent After the first goal completes, a small follow-up is: . \.venv\Scripts\hornet.exe --root . \my-first-goal revise $run --file calculator.py --goal 'Add triple(n) returning 3*n for integers. Preserve double(n).' A revision creates another workspace and records the parent. It selects the requested file scope and declared dependencies, then uses new checks and retained regression checks. Inspect the revision’s own result and run directory just as you did for the original. Declared dependencies are not a complete static analysis of every consumer in a codebase. Start with a scope you can review. After the controller exits, you can shut down the demo VM through VirtualBox’s ACPI mechanism: & 'C:\Program Files\Oracle\VirtualBox\VBoxManage.exe' controlvm hornet-first-goal acpipowerbutton Restart the same retained VM before resume or revision: & 'C:\Program Files\Oracle\VirtualBox\VBoxManage.exe' startvm hornet-first-goal --type headless Adjust the executable path and VM name if you chose different ones. Shutting down the worker preserves it; deleting it would remove part of the saved working environment.
