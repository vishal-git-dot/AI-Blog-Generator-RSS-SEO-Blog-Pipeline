# Store generated images in user folders: object lifecycle deletes for Express

## Overview

Short answer: give each generated image an immutable object key, record that key in a database at write time, and use a scheduled retention policy plus a storage lifecycle rule to remove old data. The visible "per-user folder" is a key prefix, not a database index or a deletion receipt. This matters most when an AI feature moves from a notebook into an Express API. A single request can create several candidates; an evaluation run can create many more. If the gallery is built by listing a bucket prefix and retention is judged from a successful job log, the system has no durable account of which image belongs to which run, user, or policy decision. I would treat the experiment as failed until it can answer two questions from independent data: which objects should exist now, and which objects were actually deleted. Fast uploads are not enough. What does a per-user folder mean in object storage? Object storage does not require a real directory for each user. A name such as images/u_8f12/run_20260807/a31c.webp is an object key; the slashes make a useful prefix for people and tools, but the application should not depend on directory semantics. In particular, a prefix is a poor substitute for a gallery query: listing is paginated and ordered by key, while a gallery needs filters, stable pagination, and a record of soft-deleted images. Use opaque internal identifiers in the key. Email addresses and display names change, and putting them in names can spread personal data into logs and operational tooling. A run identifier earns its place too. It lets a model evaluation retain the exact image set used for a comparison without confusing it with a user's normal gallery. A URL can change with a CDN hostname, a signing policy, or a route rewrite. The exact key is the value that the storage API operates on. Small distinction. Expensive consequence. How should Express store AI-generated images in per-user object storage and delete old images? The HTTP handler should validate the authenticated user, construct the key on the server, write the bytes, and persist the exact key and metadata. In a production system, make the database write retryable and reconcile incomplete pairs later: an object without a row is an orphan, and a live row without an object is a missing asset. Neither state should silently become a successful gallery entry. The following Python is deliberately provider-neutral. The retention policy needs two layers Use the database for rules that understand product state. "Keep the newest 30 images for this user," "retain evaluation runs for 14 days," and "hold images attached to an active review" all require ordering and metadata that an object name alone cannot provide. A scheduled worker can select the rows beyond the rule, attempt deletion using their stored object_key , and mark only the confirmed outcomes according to the API's documented response semantics. Then add a lifecycle rule in the storage system as a coarse backstop for the images/ prefix. Lifecycle policies are good at age-based expiry and at aborting incomplete multipart uploads. They are not suitable when the business rule depends on the newest N objects per user, a legal hold, or a review state; keep those decisions in the ledger. The catch is that lifecycle expiry is usually an asynchronous storage operation, so it is not a deletion acknowledgement suitable for a user-facing "erase now" promise. For a deletion requirement that must be demonstrable per object, keep an explicit audit trail and confirm the storage-side outcome. For a low-risk thumbnail cache, an age-based lifecycle policy may be the entire answer. Your retention window should be driven by reproducibility and product expectations, not by an assumed storage bargain. There is a useful ordering to these decisions. First decide what the user is allowed to see and for how long; that is an application policy, so it belongs in a queryable record. Next decide how a background worker identifies candidates without racing a fresh upload: a row state, an eligibility timestamp, and an idempotent attempt record make that decision inspectable. Then decide how long untracked or abandoned bytes may remain before lifecycle expiry clears them. The three layers serve different failure modes, which is why compressing them into one prefix convention is tempting but wrong. A prefix can scope a broad rule. It cannot explain why one image was retained while its neighbor was erased, nor can it reconstruct the image set that produced an evaluation result after the fact. Those answers come from application metadata. Measure the cleanup path before trusting it Start with a small reconciliation job. Select a sample of active users, compare ledger keys with keys observed under each prefix, and publish counts for orphaned objects, missing objects, bytes by retention class, and the age of the oldest eligible object. An evaluation-driven image workflow benefits from one more metric: how long an evaluation artifact remains reproducible after the test result was recorded. The practical design is modest: immutable keys, a ledger, explicit policy, and a backstop.
