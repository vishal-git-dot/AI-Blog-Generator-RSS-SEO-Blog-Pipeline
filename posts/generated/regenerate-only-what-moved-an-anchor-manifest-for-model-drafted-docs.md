# Regenerate Only What Moved: An Anchor Manifest for Model-Drafted Docs

## Overview

Most documentation pipelines that use a model regenerate the whole page, and that is where both the risk and the cost live. A page is a bundle of claims with different owners, different evidence, and very different lifetimes. Regenerating a page to fix one stale paragraph quietly rewrites five paragraphs that were already correct and already approved. The fix is structural: bind every claim to the code that justifies it, then regenerate only the claims whose evidence actually moved. The workflow below is small enough to adopt in an afternoon and specific enough to argue with. It has an anchor manifest, a four-state drift plan, a drafting step where a model is allowed to write, and a review queue where it is not. Every number this workflow reports comes from your own repository, which is the only honest source of such numbers. The failure mode, stated precisely A diff of a regenerated page mixes three kinds of change, and reviewers cannot separate them from the rendered result. Some changes are real drift caused by a code change, some are sampling noise from the model, and some are the model's editorial taste applied to prose that was fine. Under a whole-page pipeline these three arrive in one lump, so the reviewer either approves all of it or abandons the diff. The second problem is cost asymmetry. A page with fourteen claims usually has one or two that are stale, so you spend model calls and human attention on twelve claims with nothing wrong with them. Repeated often enough, that pattern teaches reviewers to rubber-stamp, which is the worst outcome a documentation review process can produce. The manifest approach removes both problems by making regeneration a targeted operation instead of a bulk one. You first prove which claims drifted, then you spend model time only there, and the reviewer sees a short, explainable queue instead of a page-sized diff. Step 1: Anchor one claim per code reference An anchor is an HTML comment on the line immediately above a claim, and it names the code location that would make the claim false if it changed. Keep the granularity tight; one anchor covers exactly one claim, never a section. ## Retry behavior <!-- anchor: src/limiter/backoff.py#compute_backoff --> Retries use exponential backoff with jitter and stop at the configured cap. <!-- /anchor --> <!-- anchor: src/limiter/backoff.py#MAX_ATTEMPTS --> The limiter allows `MAX_ATTEMPTS` attempts per request. <!-- /anchor --> The reference format is path#symbol , where the symbol is a function, a class, or a module-level constant. Step 6: Schedule the planning run, not the drafting run Running the planner on a schedule is cheap and safe, because it only reads code and writes a JSON plan. The drafting loop should stay manual until your approval rate stabilizes, since a scheduled drafting loop mostly produces orphan drafts nobody reads. A free server option is a reasonable home for the planning job, since the work is a short weekly read over a checkout. Stale ratio is stale / (stale + fresh) ; orphan count is the number of anchors that no longer resolve; median staleness age is how long stale claims waited for an owner. Add one process number on top: regeneration precision, the share of model drafts a reviewer accepted without substantive edits. If precision drops while the stale ratio holds steady, your drafting step is the problem, not your anchors. If the orphan count grows every week, your anchors are too fine-grained for the refactor rate of the code they track. Neither signal requires a new tool; both require a decision about claim granularity. Limitations and who should skip this The fingerprint detects change, not meaning, so a comment-only commit or a pure rename-preparation refactor can flip a claim to stale with no semantic drift. Expect false positives and budget a few minutes per week to dismiss them. The symbol extraction here is Python-shaped and will miss decorators with multi-line bodies, dynamically created methods, and most non-Python languages without a rewrite. A fresh fingerprint is not a correctness guarantee, and this is the limitation that matters most. A sentence that was wrong when it was accepted stays wrong forever if the code behind it never changes, which is why the new state needs a real human read rather than a rubber stamp. Skip this workflow if your claims live outside the repository, such as pricing pages, SLAs, or anything legal reviews. Skip it if you have no git-tracked version of record, since the manifest is meaningless without one. Skip it as well if nobody can spare a reviewer for the human queue, because this design trades model time for human attention rather than the reverse. If your docs already live beside your code, the manifest is a one-time afternoon of annotation and a weekly read afterwards. Start with the behavior class only, measure regeneration precision for two weeks, and widen the scope only when reviewers stop rewriting the drafts.
