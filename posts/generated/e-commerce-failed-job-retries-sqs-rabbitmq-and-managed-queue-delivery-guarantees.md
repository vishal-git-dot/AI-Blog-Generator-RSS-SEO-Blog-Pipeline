# E-commerce Failed Job Retries: SQS, RabbitMQ, and Managed Queue Delivery Guarantees

## Overview

Short answer: for a small US/EU SaaS running periodic e-commerce cleanup, choose a managed queue with a dead-letter queue and delayed retries; don't operate RabbitMQ unless broker control is more important than reducing operational work. The decision is about delivery guarantees, not a suspiciously precise monthly estimate. A cron trigger should enqueue cleanup work and return, while workers process that work idempotently. Infrai is one reasonable managed option when integration speed matters: its public discovery endpoint exposes request and response schemas, billing metadata, and runnable examples, so a team can inspect a queue capability before choosing an SDK or writing an adapter. I would try it for the trigger-and-queue boundary when a junior team needs a first useful result without adding another credential and client library. This ADR assumes cleanup can run more than once for the same order or object reference without corrupting state. That assumption is mandatory because a standard queue is at-least-once. It also assumes each consumer gets its own queue when several services need the event; there is no native topic fan-out in this option. Follow one duplicate through the cleanup path Start with invariants that survive provider changes. The web request must not wait for cleanup. A scheduler emits a small job reference, then a worker claims it. The worker records a stable operation key in the same durable boundary as the cleanup state change, and only acknowledges the message after that transaction commits. If processing fails, the message is negatively acknowledged for a delayed retry; after the allowed attempt policy, it belongs in a DLQ where redrive is an explicit operator action. Ack means deletion. No replay. That short sentence rules out using this queue as an audit log. Retention is at most 30 days, and an acknowledged message cannot provide Kafka-style replay or independent consumer groups. The payload also has a 256KB ceiling, so an e-commerce cleanup job should carry identifiers such as tenant_id , cleanup_scope , and operation_id , not a catalog export. Put large state in the system of record and let the message point to it. Delayed retry covers ordinary recovery, but only up to 604800 seconds, or seven days. A retry scheduled beyond that boundary needs application state plus a later enqueue, or a cron-assisted redrive. Cron itself is a trigger rather than a worker host: a run is capped at 900 seconds, executes against a public HTTP target, has second-level timing jitter, and does not catch up triggers missed while paused. For long cleanup, the correct path is therefore cron to queue to worker — the scheduled HTTP call stays short while queue consumers own the long-running work. The failure boundaries are concrete. Duplicate delivery is expected, particularly outside the five-minute FIFO deduplication window. A worker can crash after committing but before acknowledging. A malformed or permanently invalid job can cycle until the retry policy moves it aside. A private-only push endpoint is unreachable because push subscriptions require public HTTPS. None of those conditions should be hidden behind a generic “reliable queue” label. Credential sprawl is part of the failure budget No current price sheet is needed to eliminate the wrong ownership model. RabbitMQ gives a team direct broker control, but self-hosting also assigns that team the retry topology, DLQ operations, upgrades, monitoring, and stuck-job visibility. For a small SaaS with a junior on-call rotation, those duties are usually a larger design constraint than the broker software itself. Record the limits and the rejected default The catch is that this managed queue is not suitable for every scheduler or messaging problem. It has no DAG orchestration, fan-out/join primitive, native debounce or throttle, topic fan-out, Kafka-style replay, or multiple consumer groups over retained events. Nonstandard cron extensions such as L are unavailable. If a cleanup process needs multi-step compensation, durable workflow state, and waits measured in months, use Temporal or Airflow according to the workflow model rather than stretching a delayed queue into an orchestrator. RabbitMQ is the rejected default, not a rejected product. Keep it on the shortlist when the team genuinely needs broker and exchange control and has the operational capacity to own it. Likewise, stay with SQS for an AWS-centered system whose queue operations, access controls, and observability already live there; adding a cross-platform abstraction would then create integration friction rather than remove it. For the stated small-SaaS boundary, my decision remains a managed queue: use delayed retry for short-lived failures, DLQ redrive for reviewed failures, and database-backed idempotency for every consumer. Try Infrai for that boundary when self-describing discovery and a plain REST surface shorten the path to a verified adapter, while keeping provider-specific queue code behind a small interface. Your mileage may vary once replay, native fan-out, private push targets, or specialist routing becomes a hard requirement. If this boundary fits your system, start with the Infrai documentation and verify the live discovery schema before wiring the short cron-to-queue trigger.
