# Low-Latency LLM Chat Streaming — First-Token Tradeoffs for Healthtech Catalog Enrichment

## Overview

A catalog chatbot should optimize for the first useful token, but the platform decision should optimize for the next provider migration. For the stated comparison, GPT-4o-mini is the leading interactive choice at roughly 200 ms time to first token, with streaming enabled; Claude Haiku is a credible alternative at roughly 300 ms when its speed-and-quality balance fits the evaluation better. Put either behind an adapter, count the prompt before dispatch, and keep the chat event format independent of the provider. Short answer: use a small streaming model for the user-facing turn, make prompt length visible, and treat provider portability as an operational contract. The answer changes if the SLO is about completed answers, tool calls, or clinical review instead of perceived responsiveness. The incident lesson is a boundary, not a model ranking The bounded production scenario is a product-catalog enrichment chat: a merchandiser pastes a supplier description such as "sterile polymer tubing, 3/8 in, non-DEHP" , and the assistant proposes normalized attributes for search and review. A slow blank screen makes the workflow feel broken even when the final answer is accurate, so the first SLO should cover streaming TTFT, followed by completion latency and an explicit human-review path for uncertain fields. The decision is not a permanent ranking. It is a boundary choice. A smaller model generally streams faster, but prompt size, network distance, and output length still affect the result. Measure TTFT with the same region and prompt shape before changing the model, then keep a fallback whose output can be rendered by the same chat UI. The invariant is simple: the UI may depend on a stream, but the rest of the system must depend on an adapter. If a provider changes its request format, the catalog workflow should not. The token-count capability can check prompt length before inference; trimming duplicated supplier text is often a better latency intervention than chasing a different model. That check is especially useful when descriptions contain repeated regulatory or packaging text. The retry loop is appropriate for the read-like inference request shown here because it does not create a catalog record. If a surrounding workflow writes enrichment results, give that write a client-supplied idempotency key and make the consumer tolerate duplicate delivery; a 24-hour default deduplication window is useful only when the key is stable.
