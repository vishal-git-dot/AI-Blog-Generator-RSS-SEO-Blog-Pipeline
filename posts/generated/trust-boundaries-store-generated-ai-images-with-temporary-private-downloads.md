# Trust Boundaries: Store Generated AI Images with Temporary Private Downloads

## Overview

Short answer: keep AI-generated images in private object storage, authorize each download in your application, and return a temporary signed URL so the storage provider sends the large file directly to the browser. Keep the user ID, generation job ID, object key, MIME type, and byte size in your database; a signed link is an access mechanism, not a catalog or a retention policy. This is the notebook-to-production boundary I care about. A notebook can return image bytes and call the job done. A developer tool serving 180 MB render bundles needs a control plane that stays small under load, plus evidence about region, deletion, and every processor that can still hold a copy. How should an AI app store generated images and create temporary downloads? Split the request into control and data paths. The Python app authenticates the user, looks up the database record, checks policy, and asks storage for a short-lived download capability. The browser then fetches the object from the returned URL. Application workers never relay the body, so large-file throughput is limited by the object service rather than by the web process that also runs authorization and generation callbacks. The database record matters more than it first appears. Store user_id , job_id , object_key , mime_type , and size_bytes , then add the region and deletion deadline your policy needs. Deletion gets harder when copies exist: if a render must be duplicated across prefixes, object copy avoids downloading and uploading the same bytes through the application server, but every destination key becomes another deletion target.
