# Building a RAG Pipeline from Scratch: Embeddings, Vector Store, and Generation

## Overview

Large language models know a lot, but not your data. They don't know last week's policy update, your product catalog, or your internal docs, and when asked anyway they may confidently make something up. Retrieval-Augmented Generation (RAG) fixes this by finding the relevant facts first and giving them to the model with the question. What RAG is and why it matters RAG combines two steps: retrieve relevant passages from your own data, then generate an answer using those passages as context. It matters because it: Grounds answers in real sources , which reduces hallucinations. Stays current without retraining: update the index, and answers update too. Supports citations , so users can check where an answer came from. Respects access control , because you decide which documents each user can retrieve. The pipeline Document ingestion. Load PDFs, web pages, wiki pages, or database rows. Extract clean text and keep metadata such as title, URL, date, and permissions. Chunking. Split text into passages of roughly 300 to 800 tokens with some overlap (around 10 to 20%). Split on headings and paragraphs where possible rather than at fixed character counts. Embedding. Turn each chunk into a vector with an embedding model, such as text-embedding-3-small . Similar meanings produce nearby vectors. Storing in a vector database. Save each chunk's text, vector, and metadata in a vector store like Azure AI Search, Pinecone, pgvector, or Qdrant. Retrieval. Embed the user's question and find the nearest chunks. Hybrid search (vector plus keyword) usually beats vector search alone. Prompt augmentation. Put the retrieved chunks into the prompt with clear instructions: answer only from the context, and cite sources. Generation. The LLM writes the answer. Evaluation basics Measure retrieval and generation separately. Retrieval: build a small test set of questions with the chunks that should be found. Track recall@k (did the right chunk appear in the top k?) and MRR (how high did it rank?). Generation: Groundedness: is every claim supported by the retrieved context? Answer relevance: does it actually answer the question? Correctness: does it match a reference answer? Tooling: frameworks like Ragas or the Azure AI Foundry evaluators use an LLM as a judge for these metrics. Spot-check their scores by hand. Regression testing: run the test set every time you change chunking, embeddings, or prompts. Common pitfalls Bad chunking. Chunks that are too small lose context, and chunks that are too big dilute relevance. Respect document structure. Vector search only. Exact terms like product codes and names need keyword search too, so use hybrid search plus a reranker. Mismatched embedding models. Queries and documents must use the same model. Re-embed everything when you switch. Stuffing too much context. More chunks isn't always better; irrelevant text confuses the model and costs tokens. No "I don't know" path. Without it, the model fills gaps with guesses. Ignoring permissions. Filter by user access at retrieval time, not after generation. Stale indexes. Schedule re-ingestion and delete chunks for removed documents. No evaluation. Without a test set, every change is a guess. RAG isn't magic. It's a pipeline of ordinary, testable steps: get the text right, chunk it sensibly, retrieve with hybrid search, instruct the model clearly, and measure everything. Start with the small example above, add evaluation early, and improve one stage at a time.
