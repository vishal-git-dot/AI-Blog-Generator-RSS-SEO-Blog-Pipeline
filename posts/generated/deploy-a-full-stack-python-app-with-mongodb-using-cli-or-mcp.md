# Deploy a full-stack Python app with MongoDB using CLI or MCP

## Overview

You have a Python app working on your laptop. Now you need somewhere to run it, a database that keeps its data, and a way to find out what went wrong when a request fails. This guide walks through that next step. You will build a small notes app with a browser interface, a Flask backend, and MongoDB for storage, then deploy it on NEXUS AI. You can deploy from your terminal with the CLI or ask an AI assistant to deploy through MCP. Both paths use the same application and database setup. Choose one deployment path to avoid creating two copies. Step 1: Understand what you are deploying The app has three parts: Part What it does Frontend An HTML page with a form and a list of saved notes Python backend Flask routes that read and write notes through PyMongo MongoDB Stores notes outside the app container The request flow is: Browser | | HTTPS v Flask app on NEXUS AI | | PyMongo connection over the deployment network v MongoDB service Flask serves the HTML and the API from the same origin, so this example needs one web deployment and no separate frontend build. We will use NEXUS AI managed infrastructure with provider: docker . Its MongoDB sidecar service supplies the app's connection settings, including MONGO_URI and MONGO_DATABASE . The MongoDB sidecar option is not supported on the Cloud Run, ECS Fargate, or Azure Container Apps deployment paths. Before starting, have these ready: Python 3.12 and Git. Docker for the local MongoDB example. A GitHub account and an empty repository named python-mongo-notes . A NEXUS AI account with access to managed container deployments and enough quota for the app and database. Node.js 18 or later for the NEXUS AI CLI, or an MCP client such as Cursor or Claude Code. This is a shared public demo: everyone who opens the URL can read and add notes. Use sample content. Add authentication and per-user access controls before storing private information. Step 5: Run the complete app locally Start a local MongoDB container: docker run -d \ --name python-mongo-notes-db \ -p 127.0.0.1:27017:27017 \ -v python-mongo-notes-data:/data/db \ mongo:7 This local development database has no authentication and binds only to your machine's loopback interface. The named volume stores data separately from the container. On later runs, start the existing container with docker start python-mongo-notes-db . Create a local .env file: MONGO_URI=mongodb://127.0.0.1:27017/appdb MONGO_DATABASE=appdb Start Flask: flask --app app run --port 8000 Open http://127.0.0.1:8000 , save a note, and refresh the page. The note should still appear. In another terminal, check the database connection: curl --fail-with-body http://127.0.0.1:8000/health Expected response, with key order allowed to vary: { "database" : "connected" , "status" : "ok" } Checkpoint: the page loads, a note survives a refresh, and /health reports a database connection. Fix local errors before deploying. For this tutorial, use a public repository containing only demo code. A private repository requires repository access configured in NEXUS AI. Step 7: Deploy using the CLI If you prefer an AI assistant, skip to Step 8. You only need one deployment path. Install the CLI and sign in: npm install -g nexusapp-cli@latest nexus auth login nexus auth whoami Deploy the GitHub repository with its MongoDB service: nexus deploy source \ --repo https://github.com/YOUR_USERNAME/python-mongo-notes.git \ --branch main \ --name python-mongo-notes \ --provider docker \ --environment DEVELOPMENT \ --framework python \ --dockerfile Dockerfile \ --services mongodb \ --wait Here is what matters in that command: Flag Purpose --dockerfile Dockerfile Builds the app using your repository's Dockerfile --provider docker Selects NEXUS AI managed container infrastructure --services mongodb Adds the MongoDB sidecar and injects its connection environment --environment DEVELOPMENT Labels this tutorial deployment as development --wait Waits for the deployment to reach a terminal build/run state Do not pass your local .env file to this deployment. Its 127.0.0.1 address points to the app container in the cloud, which is a different machine from your laptop. The platform supplies the database connection instead. Save the deployment ID from the output. Inspect its status and public URL: nexus deploy status python-mongo-notes For command details and version-specific options, see the NEXUS AI CLI reference . Step 8: Deploy using MCP instead MCP, the Model Context Protocol, lets an AI assistant call NEXUS AI deployment tools. You describe the task, and the assistant sends structured tool calls. For Claude Code, connect the server: claude mcp add --transport http nexus-ai https://mcp.nexusai.run/mcp Complete browser sign-in when prompted. For Cursor, add the same URL in its MCP settings. The NEXUS AI MCP setup guide explains the connection flow. Allow the deployment read, create, and log scopes needed for this workflow: deployments:read , deployments:create , and deployments:logs . Then send your assistant this prompt, replacing the repository URL: Deploy https://github.com/YOUR_USERNAME/python-mongo-notes.git from branch main to NEXUS AI. Name it python-mongo-notes, use the docker provider and DEVELOPMENT environment, build with the repository Dockerfile, and attach the mongodb service. Keep health checks enabled. Confirm my account and available providers first. Follow the returned deployment ID until it is running, inspect health, and return its public URL. If deployment fails, inspect the build and runtime logs. Do not print database credentials. The assistant should first call nexusai_whoami and nexusai_providers_list with empty argument objects. The source deployment tool call then uses these arguments: MCP tool: nexusai_deploy_source { "repoUrl" : "https://github.com/YOUR_USERNAME/python-mongo-notes.git" , "repoBranch" : "main" , "name" : "python-mongo-notes" , "provider" : "docker" , "environment" : "DEVELOPMENT" , "framework" : "python" , "dockerfile" : "Dockerfile" , "services" : [ "mongodb" ], "healthCheckEnabled" : true } These JSON blocks are MCP tool arguments for your assistant, not terminal commands. Tool names may have a client-specific prefix. If your connection does not expose the services field, update the connection before proceeding with this recipe. With the returned ID, the assistant checks progress: MCP tool: nexusai_deploy_status { "deploymentId" : "REPLACE_WITH_RETURNED_DEPLOYMENT_ID" } Once running, it checks platform health: MCP tool: nexusai_deploy_health { "deploymentId" : "REPLACE_WITH_RETURNED_DEPLOYMENT_ID" } A queued deployment is not yet a working application. Keep the actual returned ID and follow status through completion. Step 9: Verify the deployed app and MongoDB Whichever deployment path you used, copy the actual public HTTPS URL from the deployment output. Set it in your terminal, replacing the example: APP_URL = 'https://REPLACE_WITH_YOUR_APP_HOSTNAME' curl --fail-with-body " $APP_URL /health" The expected result is status: ok and database: connected . This explicit request tests the application's database check even if platform health checks use another route. Create a note through the deployed API: curl --fail-with-body -X POST " $APP_URL /api/notes" \ -H 'Content-Type: application/json' \ -d '{"text":"My Python app is live with MongoDB."}' curl --fail-with-body " $APP_URL /api/notes" Open the public URL in your browser. The same note should appear. Add another note through the form and refresh. Checkpoint: the HTTPS page works, the API can write and read notes, and the database health check succeeds. You have verified the full request path from browser to Python to MongoDB. Step 10: Read logs and deploy updates If something fails, start with the logs. Afterward, repeat the /health and notes checks. Existing notes should still be present; verifying this also catches accidental attachment to a new or empty database. Before using the app for real users The tutorial gives you a working deployment foundation. Before collecting real data, add authentication, per-user note ownership, and rate limits. Confirm persistent database storage and a backup policy, then test restoring a backup. App container storage and database backups serve different purposes. If you choose MongoDB Atlas later, supply its connection URI through secure deployment settings and configure Atlas network access for your deployment's outbound traffic. Atlas permits connections from entries in its IP access list . For MCP workflows, keep credential-bearing URIs out of chat and tool arguments; configure them through the authenticated dashboard. Start by saving one note, refreshing the page, and seeing it again at your public URL. From there, you can build on an application whose frontend, Python backend, and MongoDB connection have all been checked.
