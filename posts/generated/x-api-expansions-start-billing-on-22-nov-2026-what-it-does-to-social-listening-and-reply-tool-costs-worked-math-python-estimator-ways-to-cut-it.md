# X API Expansions Start Billing on 22 Nov 2026: What It Does to Social Listening and Reply-Tool Costs (Worked Math, Python Estimator, Ways to Cut It)

## Overview

If your code calls the X API with expansions=author_id , your bill is about to change. On the pay-per-use (PPU) plan, the user, post, media, poll and place objects that come back in the includes section of a response have not counted toward usage. From 22 November 2026 they do, at the same rate as a direct lookup. For a keyword monitor that pulls each post's author, that can mean the author objects cost more than the posts themselves. This post covers what X announced, which rates X's own pages show today, three worked cost examples with labeled inputs, a standard-library Python script that estimates the change from responses you've saved, and ways to cut the bill. Rates and rules below come from three X pages opened on 16 Nov 2026: the X Developer Community announcement [Inform] X API PPU - Expansions Update (posted 23 Oct 2026), the docs page X API pay-per-usage pricing and credits , and the docs page Usage and Billing . All prices are in USD and are as of 16 Nov 2026. X says prices are subject to change and that current rates are always in the Developer Console, so check there before you budget. Appie details are from appie.run/pricing and appie.run/twitter-marketing, checked 16 Nov 2026. The estimator script was tested on Python 3.13.5 against fixture JSON files, not live API calls. Disclosure: Appie.run publishes this article. Appie's Twitter Marketing app, covered in one short section near the end, is our product. Nothing else in this post depends on it. What X announced The forum post from the X Developer Platform team says that on PPU, "usage is based on the data objects the API returns," and that "right now, objects that come back through expansions aren't counted towards usage." Then the change: "From November 22nd, objects returned through expansions will be billed at the standard PPU rate for that resource, the same as direct lookups. This covers post, user, media, poll and place expansions." The post lists the rates: Object returned through an expansion: Post; Rate per resource (X forum post, read 16 Nov 2026): $0.005; Also on the docs pricing page today?: Yes, as "Posts: Read" $0.005 per resource Object returned through an expansion: User; Rate per resource (X forum post, read 16 Nov 2026): $0.010; Also on the docs pricing page today?: Yes, as "User: Read" $0.010 per resource Object returned through an expansion: Media; Rate per resource (X forum post, read 16 Nov 2026): $0.005; Also on the docs pricing page today?: No, not listed Object returned through an expansion: Poll; Rate per resource (X forum post, read 16 Nov 2026): $0.005; Also on the docs pricing page today?: No, not listed Object returned through an expansion: Place; Rate per resource (X forum post, read 16 Nov 2026): $0.005; Also on the docs pricing page today?: No, not listed X calls this "not a new pricing model," and that is accurate: the Post and User rates are the same ones you already pay for data . What changes is how many objects count. Some gaps you should know about, because X's pages don't fill them as of 16 Nov 2026: No time of day or time zone. The post says "November 22nd." X's pricing docs say deduplication resets at midnight UTC, so the safe plan is to treat 00:00 UTC on 22 Nov as the start. That is 7:00 PM EST and 4:00 PM PST on Saturday 21 Nov, and 5:30 AM IST on 22 Nov. This is our planning assumption, not X's statement. The docs haven't caught up. The Expansions page doesn't mention billing, the pricing page has no Media, Poll or Place rows, and the changelog had no entry about this change when we checked. Owned Reads. Your own app reading your own mentions ( GET /2/users/{id}/mentions ) is billed at $0.001 per resource as an Owned Read. X doesn't say whether the users expanded on that call get the $0.001 rate or the standard $0.010. The post says "standard PPU rate for that resource," so the examples below use $0.010. The 3 million cap. PPU is capped at 3 million Post reads per monthly billing cycle. X doesn't say whether expanded posts count toward that cap. The billing rules that shape the math These come from the two docs pages and apply to every example below: Reads are charged per resource returned. Ten posts in data are ten Post reads. With the change, three distinct users in includes.users are three User reads on top. Daily deduplication. "All resources are deduplicated within a 24-hour UTC day window," and this "applies to all billable resources (Posts, users, etc.)". The same author on 40 posts in one UTC day is charged once that day and again the next day. X calls deduplication "a soft guarantee" and says edge cases such as outages may not be deduplicated. Failed requests aren't billed. "Only successful responses that return data are billed." Spending limits and auto-recharge are set in the Developer Console. When a spending limit is reached, requests are blocked until the next billing cycle. Worked math: three common workloads Every volume below is an example input , chosen to show how the change scales. Treat the total as an estimate and compare it with the Developer Console after 22 Nov. Ways to cut the bill Roughly in the order we'd do them. Audit every expansions= parameter. Search your codebase for expansions . Expansions are often copied from a docs example (X's own "Full post context" pattern asks for author_id,attachments.media_keys,referenced_tweets.id ) and never trimmed. If your listening dashboard never renders images, attachments.media_keys is pure cost from 22 Nov. In Example 1 that is $1.00 of $14.25. Cache users across days instead of expanding on every call. Deduplication resets every midnight UTC, so a regular author is charged again every day you expand them. Drop the author_id expansion from the search, keep tweet.fields=author_id so each post still carries its author's ID, and call GET /2/users?ids= (up to 100 IDs per request, same $0.010 User rate) only for IDs not already in your cache. Example input: if Example 1's 700 daily author objects are 350 distinct accounts over the month, a 30-day cache cuts that line from $7.00 to $3.50. Filter before you enrich. Score posts on their text first, then fetch context only for the ones a person will look at. If only 50 of Example 1's 250 replies are worth answering, fetching their parent posts with GET /2/tweets?ids= costs $0.25 instead of $1.25. Run the second pass in the same UTC day as the search so any post you fetch again is deduplicated. Tighten the query. -is:retweet , lang: and excluding your own handle (operators listed in X's search operators docs) cut posts and every object those posts pull into includes . A repost is the worst case: you pay for the repost, the original in includes.tweets , and possibly the original's author. Stay inside one UTC day. If you poll several times a day, schedule the runs so they don't straddle 00:00 UTC. In November that is midnight in London, 1 AM in Berlin and 7 PM Eastern the evening before. Use Owned Reads where they apply. For your own account's mentions, the mentions timeline at $0.001 per post is far cheaper than searching for @yourhandle at $0.005, even if the expanded users end up at $0.010. Set a spending limit and watch usage. A spending limit in the Developer Console blocks requests when it's reached, which is better than finding a drained balance. A request parameter that pulls related objects (the post's author, the post it replies to or quotes, attached media, polls and places) into the includes section of the same response, so you don't need a second request. X's Expansions page lists them per object type. When does X start charging for expansions? 22 November 2026, per X's developer forum post of 23 Oct 2026. The post gives a date but no time or time zone. Because X's billing day runs on UTC, plan for 00:00 UTC on 22 Nov. How much does an expanded object cost?
