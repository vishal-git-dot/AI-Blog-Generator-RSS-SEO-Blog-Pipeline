# I Built a Python Tool to Analyze Googlebot Server Logs

## Overview

How to parse access logs, identify crawler requests, detect HTTP errors, and build a simple crawling diagnostics report with Python. When working on technical SEO audits, I often need to answer a question that cannot be solved by looking at a website in a browser: What are search engine crawlers actually requesting from the server? A page may be listed in an XML sitemap but have no internal links. Another page may return HTTP 200 but contain almost no useful content. Some URLs may generate repeated server errors, while others may redirect through several intermediate addresses. A regular website crawl is useful, but it does not show the complete history of requests made by search engine bots. This is where server access logs become valuable. In this tutorial, I'll build a small Python tool that analyzes Apache/Nginx access logs, extracts requests containing the Googlebot User-Agent, groups URLs by HTTP status code, and exports the results to CSV. The goal is not to build a complete log analysis platform. I want a simple, reproducible tool that can help identify suspicious crawling patterns during a technical website audit. 1. What information can we get from access logs? A typical Apache Combined Log Format entry looks like this: 66.249.66.1 - - [22/Nov/2026:08:15:10 +0300] "GET /catalog/ HTTP/1.1" 200 18452 "-" "Mozilla/5.0 (compatible; Googlebot/2.1; +http://www.google.com/bot.html)" It contains several useful fields: Field Description IP address Client IP address Timestamp Date and time of the request HTTP method GET, POST, etc. Request path Requested URL path Protocol HTTP protocol version Status code Server response Response size Number of bytes sent Referer Referring URL User-Agent Client identification string For crawling diagnostics, I am particularly interested in: Which URLs were requested? How frequently were they requested? What HTTP status codes did they return? When was each URL requested last? Are there repeated server errors? Are there suspicious URLs with parameters? Are crawlers spending requests on unnecessary URL variations? These questions help turn raw server logs into actionable technical information. 2. Important: User-Agent is not proof of Googlebot Before writing the parser, there is one security detail worth mentioning. It is easy to filter log entries containing the word Googlebot . However, User-Agent strings can be spoofed. A request like this: Mozilla/5.0 (compatible; Googlebot/2.1) does not prove that the request came from Google. For reliable identification, Google recommends verifying the requesting IP address using reverse DNS followed by forward DNS confirmation, or checking Google's published IP ranges. Official documentation: https://developers.google.com/search/docs/crawling-indexing/googlebot In this first version, I will filter by User-Agent to demonstrate the parsing workflow. I will also show where IP verification should be added. Important: The sample log entries in this tutorial are synthetic test data. They are not presented as verified Googlebot traffic. 3. For larger projects, I would also consider processing rotated log files and combining logs from multiple web servers. 7. What does the report tell us? A simplified example of the resulting report: URL Requests 2xx 3xx 4xx 5xx /catalog/ 1 1 0 0 0 /catalog/?page=2 1 1 0 0 0 /product/product-103/ 2 1 1 0 0 /product/product-104/ 1 0 0 1 0 /product/product-105/ 2 1 0 0 1 Now we can identify several things worth investigating. Product 103: redirect The URL returned HTTP 301 and was requested again with HTTP 200 in our sample. This is not necessarily a problem. However, if redirects form long chains, I would investigate whether the internal links point directly to the final destination. Product 104: 404 The server returned HTTP 404. If the product was permanently removed, this may be the correct response. If the product is still available, the routing or application logic needs investigation. Product 105: 503 followed by 200 This is more interesting. The server temporarily returned HTTP 503, but a later request succeeded. I would check whether the issue is related to application availability, backend performance, rate limiting, or infrastructure instability. A single 503 response does not prove a crawling problem. Repeated patterns and their timing are much more useful. 8. What I would add next This script is intentionally small. It is a starting point, not a complete crawler analytics platform. For a more advanced version, I would add: Reverse DNS and forward DNS verification of Googlebot IP addresses. IPv6 support. Sitemap parsing. Internal URL inventory from a website crawl. Detection of URLs missing from internal links. Redirect-chain analysis. Response-time analysis. Daily crawling trends. HTML and CSV reports. Filtering by Googlebot type. The most useful next step would be combining three datasets: URLs listed in XML Sitemap. URLs discovered through internal links. URLs requested by verified Googlebot. This makes it possible to identify pages that are listed in Sitemap but have no discovered internal links or no recorded crawler requests during the selected period. That does not prove Google has never discovered them. It gives us a list of URLs that deserve further investigation. 9.
