Set three budgets before selecting a model or service: malformed-output budget, latency budget, and spend budget. A cheaper token can lose quickly if it produces more unusable decisions. The useful unit is an accepted score, not a request. Step 1: Define the acceptance contract before the call A candidate decision is accepted only when it is parseable, complete, and consistent with the rubric version attached to the request. Treat those as separate checks. A response can be valid JSON and still omit a required explanation, use an out-of-range score, or cite a requirement that is not present in the supplied evidence. Keep the contract small. For example, the application can require an integer score from 0 through 100, a rubric identifier, and an array of evidence references. How do you verify a change and roll it back? Verification begins with a fixed test corpus and a versioned rubric. Before rollout, assert that every accepted result is parseable, within range, tied to the expected rubric, and backed by evidence. Track invalid-output rate, accepted-result rate, p95 latency, token usage per accepted result, and review rate by rubric version. These are release signals, not decorative dashboards. Canary the new runtime or prompt behind a routing flag. Keep the old path available until the new path meets the same acceptance and latency SLOs over a representative window. Roll back on a contract breach, a sustained SLO violation, a sudden rise in review outcomes, or a budget alarm. Preserve the request and rubric identifiers so a rejected candidate can be reprocessed deterministically after the cause is understood. The rollback target should be a known-good configuration, not an improvised prompt edit.
