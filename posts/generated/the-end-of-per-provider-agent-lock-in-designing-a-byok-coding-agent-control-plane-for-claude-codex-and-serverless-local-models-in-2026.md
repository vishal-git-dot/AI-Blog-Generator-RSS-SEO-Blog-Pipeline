# The End of Per-Provider Agent Lock-In: Designing a BYOK Coding-Agent Control Plane for Claude, Codex, and Serverless Local Models in 2026

## Overview

Originally published on tamiz.pro . The past two years of AI coding agents have been defined by a paradox. The models are commoditizing — Claude, GPT, and open-weight models increasingly converge on the same chat-completion core — but the agents aren't. Claude Code, OpenAI Codex, Cursor, and a dozen open-source clones each ship their own CLI, their own session model, their own prompt templates, their own MCP client, and, most painfully, their own provider contract. The result is lock-in not to a model, but to a vendor's implementation of an agent. That's changing. Why the Agent Layer Is the New Lock-In In 2023, the lock-in problem was simple: you couldn't swap models without rewriting prompts. That's largely solved. Anthropic and OpenAI both expose OpenAI-compatible endpoints, and open-weight models run on the same protocol. A chat.completions call is a chat.completions call. But the agent layer is a different story. An agent isn't a model call — it's a system : a prompt template, a tool schema, a loop that calls the model, parses tool calls, executes them, and feeds results back. Each vendor implements that loop differently, with different conventions for: Session format — how conversation history is stored and rehydrated. Tool-calling protocol — the JSON schema for tool definitions and the parsing of tool_calls . Prompt caching — how context is marked for cache reuse, and how cache invalidation works. Configuration — ~/.claude/ , .codex/ , environment variables, and CI hooks. Hooks and lifecycle — pre-tool, post-tool, and error hooks, each with their own contract. Switch from Claude Code to Codex and you're not just changing a model — you're rewriting your CI pipeline, your hooks, your prompt cache, your session recovery, and your team's muscle memory. That's the lock-in. The BYOK control plane inverts the dependency. Instead of your workflow depending on a specific agent, the agent depends on a generic provider contract. Your CI calls the control plane; the control plane decides which provider to hit, with whose keys, under what budget, and with what fallback. Swap providers and your workflow doesn't change. 2. What a BYOK Control Plane Actually Is A BYOK control plane is a self-hosted service (or embedded library) that sits between your developers/CI and the actual model providers. It exposes a single unified agent API and translates requests to provider-specific implementations. "BYOK" means the user supplies their own API keys, which the control plane stores securely and uses on their behalf — never exposing them to the developer's machine or to CI logs. Why build one? Four reasons: Reason What it buys you Portability Swap Claude for Codex or a local model without touching workflows Governance Centralized cost tracking, quotas, and audit trails Security Keys never live in developer configs, .env files, or CI artifacts Intelligence Capability-aware routing, prompt caching, and automatic fallback The control plane isn't an agent. It doesn't write code or run tools. It's a dispatcher and governor : it knows which providers exist, what each can do, what each costs, and how much budget each team has left. The actual agent logic (the loop, the tools, the file edits) stays in the client — the CLI, the IDE extension, or the CI job. 3. Claude Code stores sessions as a directory of JSON files with a specific prompt-cache layout. Codex uses a SQLite database. A local agent might use a simple transcript. Production Best Practices Building a control plane is straightforward; operating one is where the discipline lives. Here's the checklist I'd hand to any team taking this on: Start with one provider. Don't build the abstraction for five providers you don't have. Implement the interface for Claude, then add Codex once the contract is stable. Define the capability contract first. The ProviderCapabilities interface is the spec. Document what each field means and how the router interprets it before you write any provider code. Use config-as-code. Routing policies, budgets, and fallback chains should be declarative YAML or JSON, versioned in git, and reviewed like code. Audit every call. Log the provider, model, tokens, cost, and decision reason for every request. You'll need this for cost disputes and incident analysis. Cache aggressively. Prompt caching is the cheapest latency and cost win. Make the control plane responsible for marking cacheable messages, not the individual providers. Treat keys as secrets, not config. Never log a key, never put it in a URL, never store it in plaintext. The KeyVault should be the only component that touches decrypted keys. Test the fallback chain. Kill a provider in staging and verify the router degrades gracefully. This is a drill, not a one-time check. Version the API. The unified agent API will evolve. Version it from day one so you can add providers without breaking existing clients. 13. Conclusion The model layer is commoditized. The Reference Architecture: A Control Plane in Three Planes Before we dive into code, let's establish a common mental model. A BYOK control plane is not a single service; it's a composition of three logical planes, each with a distinct responsibility. You can implement them as separate microservices, as modules in a single binary, or even as a serverless function bundle—but the separation of concerns must remain. 1. The Policy Plane This is the brain. It decides what an agent is allowed to do, which model it may use, and when it may use it. It is the only component that holds the master keys—or rather, the references to the keys. The policy plane never exposes a secret to an agent directly; it injects it into the agent's runtime environment at the moment of invocation, and only after validating the request against a set of rules. The policy plane exposes a single gRPC or REST endpoint: Authorize(Request) -> Session . The Session is a short-lived token that carries the resolved permissions, the model endpoint, and a reference to the key material. The key material itself is not in the token; it's in a secure vault that the runtime plane fetches on the agent's behalf. 2. The Runtime Plane This is the executor. It takes an AuthorizedSession , fetches the key material from the vault, and launches the agent process (or container) with the key injected as an environment variable or a mounted secret file. The runtime plane is deliberately dumb: it does not know why a request is allowed, only that it is allowed. It enforces the session's time-to-live, network egress rules, and resource limits. In a serverless context, the runtime plane is often a sidecar or a wrapper script that runs inside the agent's execution environment. In a Kubernetes context, it might be a mutating admission webhook that injects the secret into a pod spec. 3. The Ledger Plane This is the accountant. It records every agent invocation: who asked, which model was used, how many tokens were consumed, how much time elapsed, and what the estimated cost was. The ledger plane is the source of truth for chargeback, budgeting, and anomaly detection. It writes to an append-only store (e.g., a Postgres table, a Kafka topic, or an S3 bucket of JSONL files). The ledger plane is also the audit plane. Every policy decision is logged, including the reason for a denial. This is what makes the control plane defensible in a security review: you can always answer the question "why did this agent see this key?" Deep Dive: Policy Enforcement and Secure Key Injection The previous tutorial showed a basic implementation. Now let's examine the security-critical aspects in more detail. Key Rotation and Versioning One of the biggest advantages of a control plane is that you can rotate keys without touching the developer's machine. When you rotate a key in Vault, you simply update the secret. The next time an agent runs, the runtime plane fetches the new version. There's no need to redistribute keys to hundreds of developers. But there's a subtlety: if an agent is already running, it holds the old key. The runtime plane should support graceful revocation . We can do this by having the runtime plane monitor a "key version" in Vault. If the version changes mid-run, the runtime plane can send a SIGTERM to the agent process, forcing it to restart with the new key. This is a simple but effective pattern. Session Tokens and Short-Lived Credentials Instead of passing the actual API key to the agent, you can pass a short-lived token that the agent exchanges for the real key at the provider's side. This is what AWS STS does for IAM roles. For Claude and Codex, this is harder because they expect a static API key. However, you can use a proxy pattern: The control plane issues a session token. The agent calls the control plane's /exchange endpoint with the session token. The control plane returns a one-time API key that is valid for 15 minutes. The agent uses that key for its API calls. This is more secure because the key is never stored on the developer's machine. It exists only in memory for the duration of the session. The trade-off is that you need to implement a proxy for the model API calls, or the agent must support a custom auth flow. Some agents (like Claude Code) support custom API endpoints, which makes this feasible. Policy as Code We used YAML for policy definitions. But in 2026, the best practice is to express policy as code—specifically, as a set of functions that are evaluated against the request. This allows for complex logic like "allow this model only if the user is in the platform group and the repository is critical-infra ." The Zero-Trust Agent Gateway In a zero-trust model, the control plane is the only component that can talk to the model providers. The agents themselves never have direct network access to the providers. Instead, the control plane acts as a gateway : The agent sends a request to the control plane's /proxy endpoint. The control plane validates the session, checks the policy, and forwards the request to the model provider with the API key. The provider's response is streamed back to the agent. This gives you complete visibility into every API call, the ability to rate-limit, and the ability to redact sensitive data in prompts. The downside is that you add latency and a single point of failure. In 2026, with the proliferation of local models, this is less of a concern because many requests can be served locally. Deep Dive: Cost Attribution and Metering The ledger plane is where the money is. In a BYOK world, the developer brings their own key, so you might think you don't need to track costs. But you do—because the whole point of a control plane is to provide a unified cost ledger across all providers, including local models. The Cost Model Every model provider has a different pricing structure. Some charge per token, some per request, some per second of compute. The ledger plane needs a normalized cost model. We'll define a simple schema: { "timestamp" : "2026-03-15T10:30:00Z" , "user_id" : "alice" , "agent_id" : "claude-code" , "model" : "anthropic/claude-3-5-sonnet" , "tokens_in" : 12000 , "tokens_out" : 4500 , "cost_usd" : 0.0495 , "session_id" : "sess_123" , "metadata" : { "repo" : "acme/backend" , "branch" : "feature/foo" , "duration_ms" : 8500 } } The cost_usd is calculated by the runtime plane after the agent finishes, using the actual token counts returned by the provider.
