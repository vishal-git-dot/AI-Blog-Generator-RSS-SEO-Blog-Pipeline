# OpenAI Prompt Caching: When Is the New 12-Hour Cache Cheaper?

## Overview

Your prompt caching dashboard shows a healthy read hit rate. The inference bill stays high anyway. Then OpenAI ships 12-hour prompt caching , and someone on the team asks whether you should switch. On GPT-5.6 and later, a 12-hour ( 12h ) cache write costs 2.5x the input price, while a write at the default 30-minute ( 30m ) lifetime costs 1.25x. So 12h only pays when the same unchanged prefix comes back after two or more gaps longer than 30 minutes inside a 12-hour window. Otherwise 30m is cheaper, even when 12h shows a higher hit rate. Hit rate counts reads. It says nothing about what you paid to write the prefix, and that write price now depends on the retention you pick. You can price each prefix from your own request logs with one rule and about 30 lines of Python. TL;DR On GPT-5.6 and later in the Responses API, you choose a 30-minute or 12-hour minimum lifetime, and the 12-hour write costs twice as much. Count the gaps longer than 30 minutes after which the same prefix is reused inside one 12-hour window. With zero or one, 30m is cheaper. From two, 12h is cheaper. A higher hit rate can come with a higher bill. In the modeled scenarios, 12h lifts the hit rate by five points and still costs more in one case, and ties on hit rate while costing 36% more in another. Decide from cost per prefix per window, calibrated with your own usage fields. What changed on October 20, 2026 OpenAI's changelog entry reads: "You can now choose 12-hour prompt caching in the API. 12-hour prompt caching keeps shared instructions, tools, and context cached longer to benefit from lower cached-input pricing, even when requests are hours apart. 12-hour cache writes cost 2.5x the input token price." The entry is tagged for the Responses API, and the two model generations now follow different rules. Models Setting Values Write charge What the lifetime means GPT-5.6 and later prompt_cache_options.ttl (Responses API) 30m (default) or 12h 1.25x input for 30m, 2.5x for 12h A minimum lifetime for read-price eligibility Earlier models prompt_cache_retention in_memory or 24h None A best-effort maximum The prompt caching guide says the older 24h setting "typically keeps entries available for around 30 minutes and can retain them for up to 24 hours." Twenty-four hours is the ceiling. The new 12 hours is a floor: for that long, a matching prefix is eligible for the cached-input price. Since May 29, 2026, 24h has been the default for organizations without zero data retention (ZDR), with no write charge. The guide adds: "The minimum lifetime governs eligibility for cache-read pricing. It does not guarantee that every request reuses stored KV tensors or has lower latency." How OpenAI prompt caching bills a prefix The cache stores key-value (KV) tensors for a reusable prefix , the unchanged tokens at the start of the prompt. It does not store the tokens themselves, and caching "does not change how the model generates output tokens." On GPT-5.6 and later, the minimum cacheable prompt is 1,024 tokens. Caching is on by default for supported models, and the guide documents no way to turn it off. You control where the prefix ends. With mode set to implicit , OpenAI places a breakpoint at the end of the latest eligible message. With explicit , you place your own breakpoints, and each request can create up to four cache writes. Tokens after the last breakpoint are billed at the uncached input rate with no write charge. Each prefix then meets three prices: The write: 1.25x the input rate for 30m, 2.5x for 12h. The read: 0.1x the input rate on most of these models, and 0.05x on gpt-6.1-sol . The rewrite: a full new write when a request arrives after coverage has ended. The guide works one example: "At the 0.1× read rate with 30-minute writes, writing a prefix once and fully reusing it once costs 1.35× its ordinary input cost, compared with 2× for processing it twice without caching." Reads also extend coverage. In the guide's words, "A 30-minute read refreshes coverage to at least 30 minutes after that read. If it uses an entry with valid 12-hour coverage, it preserves the later of the existing expiry and 30 minutes after the read. It does not restart a 12-hour clock or incur another write charge." Upgrading valid 30-minute coverage to 12 hours charges a new 12-hour write, with no credit for the earlier write. The prefix must also stay identical. Changes to tools , text.format , reasoning.effort , and text.verbosity affect the cached prefix, so keep stable instructions and shared reference material first and variable content at the end. The break-even rule The guide frames the choice in one line: "Compare the higher 12-hour write rate with the cost of rewriting the prefix after 30-minute coverage expires." With 30m, every long gap costs a fresh write at 1.25x. With 12h, you pay 2.5x once and every long gap costs only a read, so from the second long gap 12h costs less. Write the cost of one prefix over one 12-hour window as a multiple of its ordinary input cost: 30m: 1.25 × (1 + G) 12h: 2.5 + (r × G) The inputs: G (measured, from your trace): the number of gaps longer than 30 minutes after which the same unchanged prefix is reused inside one 12-hour window. r (from the guide and the price list): the read rate, 0.1 on most GPT-5.6 and later models or 0.05 on gpt-6.1-sol . 1.25 and 2.5 (from the guide): the write multipliers. Reads inside a burst cost the same under both options, so they drop out. At G = 0, it is 1.25 against 2.5. At G = 1, it is 2.5 against 2.55 (r = 0.05) or 2.6 (r = 0.1), so 30m still wins. At G = 2, it is 3.75 against 2.6 or 2.7, so 12h wins. A service that runs longer than 12 hours needs a new 12h write in each window, because reads do not restart the 12-hour clock. The openclaw maintainers merged 12h support the day after launch as an opt-in, with write-price accounting, in their pull request to opt into 12-hour prompt caching . Testing the counterargument: more hits can only help The case for switching: longer retention means more requests find the prefix warm, every extra hit is a read at a tenth of the input price or less, so turning 12h on can only help. On models before GPT-5.6, that holds. The longer 24h setting has no write charge, so extra retention costs nothing. On GPT-5.6 and later it holds only when a prefix returns after two or more long gaps, because the longer option doubles the write price.
