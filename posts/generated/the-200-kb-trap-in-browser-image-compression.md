# The 200 KB Trap in Browser Image Compression

## Overview

Three images. Three green “within limit” results. Zero files that met the upload rules I had written down. The compressor was doing what it promised. My acceptance check was asking a different question. For this experiment, I defined a hypothetical destination that accepts JPEG, exactly 600 × 800 pixels, at most 200,000 bytes . Then I ran three synthetic inputs through a browser compressor's “200 KB” preset and inspected the downloaded files with a separate image decoder. The “200 KB” preset explicitly meant 200 × 1,024 = 204,800 bytes . It allowed proportional resizing, preserved PNG by default, and left an already-small input untouched. A quality slider cannot decide the second one for you. Write the destination's rules before choosing an encoder A file-size ceiling is one field in a larger contract: const destination = { maxBytes : 200 _000 , mime : " image/jpeg " , width : 600 , height : 800 , animation : " reject " , transparency : " flatten-on-white-with-consent " , }; Some fields are machine-checkable. Others are product decisions. Flattening a transparent asset onto white changes its appearance; it is not a harmless technical default. A portrait that must remain 600 × 800 cannot quietly become 199 × 265 just because a smaller canvas produces fewer bytes. Ask these questions before processing: Does the receiver require an exact format or merely an allowed set? Are width and height exact, maximums, or unconstrained? Is the limit per file, per archive, or for the whole request? Must transparency, animation, metadata or a particular color profile survive? What is allowed to change when those requirements conflict? If the receiver says only “200 KB,” check its documentation or actual byte limit. 200,000 bytes and 204,800 bytes differ by 4,800 bytes. The second row in the table fits one and fails the other. Formatting a number as “199.3 KB” does not resolve that ambiguity. Use the encoded Blob.size , which is measured in bytes. Do not compare the length of a base64 data URL, a rounded display string, or the original file's size. Quality is an encoder input, not a byte budget This looks plausible: canvas . toBlob ( onResult , " image/jpeg " , 0.85 ); But 0.85 means neither “keep 85% of the original bytes” nor “produce an image of a predictable size.” It is also not a portable perceptual-quality score across codecs and browsers. I generated two 600 × 800 canvases: one with four flat rectangles, another with deterministic RGB noise. In the same browser, using the same JPEG quality parameter: Synthetic input Dimensions JPEG quality argument Encoded bytes Flat rectangles 600 × 800 0.85 7,221 RGB noise 600 × 800 0.85 344,122 The noise is deliberately difficult input, not a representative photo collection. This is evidence that the parameter does not enforce a budget; it is not a comparison of photo quality or a ranking of compressors. There are two more API details worth making explicit: toBlob() can return null through its callback. A completed callback is not necessarily a usable image. An unsupported requested output format falls back to PNG. Naming the download result.jpg does not make those bytes JPEG. My unsupported-type probe requested image/x-budget-lab-test ; the returned blob was image/png . An encoder wrapper should reject that mismatch when the output type is a requirement. PNG has another trap: the canvas quality argument is intended for formats with lossy compression. In this run, encoding the transparent PNG fixture at 0.1 and 0.9 produced 12,736 bytes each, with identical SHA-256 hashes . Moving that slider did nothing to this PNG. That exact hash equality is an observation from this browser, not a promise about every implementation. A small bounded encoder that is allowed to say no For a fixed-dimension JPEG destination, I prefer a small, explicit policy over silently shrinking the image until some file emerges. The following function: accepts an already-decoded canvas ; explicitly composites it onto white; preserves the canvas dimensions; tries six decreasing JPEG quality settings; returns a success only after checking the actual encoded bytes; returns a refusal when none of those candidates fits. The white background must be an accepted product choice. This function is not appropriate when alpha or animation must be preserved. Its pixel ceiling is a scope limit for the example, not a guarantee that every device can safely process that input. It preserves the dimensions you give it; it does not crop an arbitrary source into a 600 × 800 portrait. A server must independently enforce its byte limits, recognize and safely decode allowed formats, validate dimensions and apply its own resource limits. Every member being below 204,800 bytes does not make the archive below 204,800 bytes. A per-file budget and an attachment budget need separate checks. Four boundaries that deserve their own decisions Animation. Drawing a decoded image onto one canvas gives you a bitmap, not a frame-preserving animation pipeline. Decide whether to reject animation, retain the original or use a suitable animated codec pipeline. Do not silently discard the other frames and call that a successful compression. Orientation and metadata. Define dimensions in the orientation the receiver uses. createImageBitmap() defaults to using image orientation metadata when present. Re-encoding also should not be treated as a general guarantee that all metadata or color information was preserved—or removed. Test the fields your workflow actually depends on. Memory. A 6000 × 4000 RGBA bitmap contains 96,000,000 bytes of pixel data before additional buffers. Compressed file size is a poor proxy for that cost. Put limits on input bytes, dimensions, decoded work and retained outputs; process batches with bounded concurrency. This example starts after decoding, so it does not solve admission control for a malicious or enormous source file. Stale work. Someone can choose a new file while the previous encode is still running. The abort checks above prevent an aborted result from being returned, but do not cancel an in-progress toBlob() operation. The caller must abort the old run and ensure only the current run can update the UI. “I clicked Cancel” and “the encoder stopped consuming resources immediately” are different claims. If the page processes files locally, describe that claim narrowly. Local file processing does not imply that the website makes no network requests; loading assets and ordinary analytics are separate concerns. It also does not make a page appropriate for every confidential workflow. Reproduce the invariants—dimensions retained, returned type checked, successful blobs within the byte cap, explicit failure—not a claim that everyone should get the same JPEG hash. The local harness also exercised invalid budgets, invalid quality ladders, a pre-aborted run, a one-byte refusal and unsupported-format fallback. Those checks supplement the downloaded-file verification; a green test count by itself would not establish visual quality, cross-browser compatibility or safe handling of arbitrary inputs. The UI should report what it actually proved Instead of showing one ambiguous “Success” badge, report the constraints independently: Bytes: 179,501 / 200,000 PASS Format: PNG / JPEG required FAIL Dimensions: 199×265 / 600×800 FAIL Decision: Do not submit this file Then offer choices that match the failed rule: select a permitted format, obtain a suitable original, accept a resize only if allowed, or explain that the current policy has no fitting candidate. Do not keep lowering quality when the failing field is the format. The most useful compression result is not always the smallest file. It is a file whose properties match the destination—and a clear refusal when they do not.
