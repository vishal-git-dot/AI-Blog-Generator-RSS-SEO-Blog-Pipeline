# Avatar Uploads Without Versioning: A Rollback Policy for Object Storage

## Overview

Short answer: do not replace the only copy of an avatar unless losing the previous bytes is an accepted product decision. Upload the candidate under a new key, verify it, switch active_avatar_key in the database, and delete the old object only after that switch succeeds. With no object versioning, that sequence is your rollback boundary. The stable-key design is tempting: users/{id}/avatar keeps one database value and makes reads obvious. It also makes an accidental overwrite permanent. Storage cannot restore what it no longer retains, so the real design question is where you want recovery to live: in the provider, in your application, or nowhere. What should an avatar upload overwrite flow do when object storage has no versioning? Treat the change as a small state machine. First create a new, immutable candidate key such as users/42/avatars/2026-08-07T120000Z.png . Then check that the upload completed and that the object is the expected size and type. Only then update the user row to point at the candidate. The old key remains readable until the database commit is complete. This ordering matters because object storage and your database do not share a transaction. A failed upload must not alter the profile. A successful upload followed by a failed database update leaves an unreferenced candidate, which is untidy but recoverable. A database pointer changed before the bytes are ready leaves a profile that points at nothing useful. Concurrency needs an explicit home too. There is no If-Match conditional write in this storage surface, so two browser tabs can upload valid images and race to update the same row. Use a database compare-and-update rule or serialize avatar changes through a queue. If the update loses, remove the losing candidate and return the current profile state. I would also make the row update conditional on the version the client read, record the candidate key and request id in an audit table, and have the cleanup worker re-check both before deleting anything; that gives an operator enough evidence to distinguish a user retry from a genuinely stale browser request when the two arrive seconds apart. Short version: bytes first, pointer second. When is deleting the old object the wrong rollback policy? Deletion is cleanup, not part of the user-visible commit. Run it after the pointer switch, preferably in a job that checks whether the old key is still referenced. Keep a short retention window when support staff may need to undo a mistaken upload; keep immutable timestamped copies when an audit trail is a requirement. The catch is that this pattern does not create storage-level history. If your cleanup job deletes the prior object immediately, there is no later restore. For financial or legal records that require tamper resistance, choose a provider with versioning and WORM-style object lock, or maintain an external archive. An unversioned avatar bucket is not a compliance archive. Operational details are easy to miss. Lifecycle expiry has a one-day minimum, and multipart fragments have no automatic cleanup rule, so abandoned candidates need an application job. Listing filters by prefix rather than arbitrary metadata, which means your cleanup index should be a database table or a predictable key layout. Public-read ACLs are not available here; serve private objects through an authenticated or signed access path instead of promising a permanent public URL. How can a plain REST storage API fit this state transition? Any language that can send HTTPS requests can perform the three storage operations, while discovery documents the exact method and path. A rollout that keeps existing profiles intact Start by adding active_avatar_key while continuing to read the legacy stable key. For each new upload, write a distinct candidate, validate it, switch the pointer, and enqueue old-key deletion. A background reconciliation pass can identify rows still using the legacy path and migrate them one at a time. Keep the old read path until the metrics show that every active row has a valid new object. The final decision is simple but not universal: stable-key overwrite is fine for disposable images when rollback is explicitly out of scope. For user avatars with support expectations, new-key replacement plus delayed deletion is the safer default. For regulated history, use versioning or an external immutable archive; no application naming convention can manufacture retention that the storage layer does not provide.
