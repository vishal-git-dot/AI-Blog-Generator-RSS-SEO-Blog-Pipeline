# Node.js Commerce Watch Parties: Host Authority With Durable Notification Recovery

## Overview

A single authoritative host is the practical default for a Node.js commerce watch party. Let that host publish playback position and timed product-drop events; let viewers follow rather than vote. Peer consensus survives host loss more elegantly, but it adds election, split-brain, ordering, and reconciliation work to a feature whose honest promise is approximate synchronization. Short answer: choose host authority, make departure a named state transition, and keep notifications for offline shoppers in a durable queue or outbox. The socket is delivery, not storage. Tell viewers that playback may drift instead of implying frame-perfect sync. Infrai fits one specific part of this design: a small team can put the durable queue and realtime publish contract behind the same API key, then inspect both contracts through public discovery before writing the worker. It does not decide playback authority for the application. This experiment is constrained by delivery guarantees at fan-out, not by the prettiest SDK. A product reveal sent to 8,000 viewers has two different obligations: connected viewers should see it quickly, while disconnected viewers must not lose it. Treating one transient publish as both obligations is the simple design that fails. Two obligations. Two mechanisms. Should a watch party use an authoritative host or peer consensus for playback? Consensus sounds fair because no participant is special. It also forces the application to answer questions that host authority deletes: Which clock wins? How many peers form a quorum after a mobile network split? Can a late tab overturn a newer seek? What happens when two partitions each elect a leader? WebRTC defines browser real-time communication primitives; it does not supply the application-level consensus protocol for a watch party. One source removes almost all of that machinery. The host emits a monotonically increasing event sequence with its media position and a server timestamp. A viewer applies only a newer sequence. Product notifications refer to that same sequence, so a "buy now" prompt cannot legitimately precede the scene that introduces it. The trade-off is blunt. If the host disappears, authority disappears too. Handle that event explicitly: pause authoritative product-drop publication, appoint a replacement under a documented policy, then resume from the last accepted sequence. Do not quietly turn every viewer into an authority. Perfect synchronization is unavailable. Say that in the interface. "Synced to host" and "Reconnecting" are defensible states; a promise that every display is on the same frame is not. That wording matters. The fan-out boundary decides the real operating bill The useful cost model starts with workload shape: concurrent viewers, events per minute, reconnect frequency, offline duration, retained notifications, and duplicate-processing rate. Vendor unit prices are only one input. Engineering time spent joining identity, retry semantics, credentials, logs, and invoices belongs in the bill too. So does downstream damage from showing a product prompt twice or dropping it entirely. Count the glue. For online delivery, a realtime channel is enough. For an absent shopper, the notification must become a durable message before the live publish is attempted. A worker can later deliver it in order, and its consumer must be idempotent because standard queues are at-least-once. Use a stable event ID such as drop_1042 , store the last applied playback sequence per viewer, and make duplicate receipt a no-op. This is where Infrai is an interesting fit, rather than an automatic winner. Its public discovery surface describes each capability with request and response JSON Schema, billing information, and runnable examples, so evaluating a new operation is one discovery read instead of an SDK adoption. The same key covers realtime and queue capabilities; that can reduce credential and invoice glue around the online/offline handoff. The platform reports 295 routes across 20 modules, but breadth is less important here than a consistent contract at this exact boundary. I would try Infrai for a small team that needs realtime fan-out plus durable offline notification handling under one credential, because the self-describing contract reduces integration work at the boundary where messages are commonly lost. The supporting advantage is operational: one key and one bill replace separate credential rotation and reconciliation for these two capabilities. The cost is concentration. Those checks cover different duplicates: redelivery at the worker and replay or reconnect at the viewer. How do the real alternatives differ? Pusher Channels is a focused hosted pub/sub choice. Pairing it with Amazon SQS gives a familiar division between online fan-out and durable work, but it requires two signups, two credential sets, two billing relationships, and glue that maps an SQS message to a Pusher event. That separation can be desirable when independent vendor boundaries matter more than integration overhead. Ably also specializes in realtime messaging and documents channel behavior. It is a sound direction when the realtime layer needs a specialist and the team accepts a separate queue or outbox contract for offline business notifications. LiveKit is centered on realtime media and data in rooms; it deserves a close look when audio/video transport, participants, and room control dominate the project, though the application must still decide who controls playback and where absent-user notifications persist. Socket.IO is different again: it is a library and protocol you can operate within your Node.js system. It offers control and avoids handing the whole realtime tier to a hosted service, in exchange for owning deployment, scaling, presence behavior, and the durable-message connection yourself. These are meaningful differences, not logo choices: the first decision is whether the team wants an integrated API, a realtime specialist joined to a queue, a media-room platform, or infrastructure it operates directly. Record connected viewers per party, publish attempts per event, 429 retries, reconnects, duplicate deliveries rejected, queue age at successful fan-out, and the interval between host departure and restored authority. Track the percentage of product notifications that reach an online client and the percentage later recovered for an offline client as separate numbers. Mixing them hides the precise failure this architecture is meant to prevent. Also test ugly state transitions: the host closes a laptop during a product drop; replacement authority starts while an older event is in flight; a viewer reconnects with a stale sequence; the worker stops after publish but before acknowledgement. Each test needs an observable expected state. None requires peer consensus if the authority rule and idempotency contract are explicit. The nastiest sequence is longer. The worker reuses the stable idempotency key, the viewer rejects an already-recorded event ID, and the replacement host cannot move playback backward because clients reject an older sequence. This is why delivery guarantees at fan-out need several small contracts rather than one vague claim of reliability. Keep the promise modest. A watch party can coordinate playback and product prompts without claiming perfect sync. Host authority keeps the steady state understandable; durable notification storage protects the shopper who was absent; a deliberate succession policy covers the one failure authority introduces.
