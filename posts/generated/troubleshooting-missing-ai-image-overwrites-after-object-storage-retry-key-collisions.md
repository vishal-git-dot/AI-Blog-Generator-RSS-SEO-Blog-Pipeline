# Troubleshooting Missing AI Image Overwrites After Object Storage Retry Key Collisions

## Overview

Large gaming-media uploads should bypass the application server, but that constraint makes object identity part of the correctness model. Short answer: issue a private presigned upload for a unique key on every render attempt, record that immutable key in the job row, and promote it to a canonical key only after the database transaction succeeds. Never retry an AI-generated image upload against the same stable key when the storage layer has no versioning. An overwrite can turn a successful earlier render into an unrecoverable missing output. This is primarily an access-control decision, not a bandwidth trick. Private objects and short-lived signed delivery add authorization work, yet they avoid turning player-generated art, moderation evidence, or unreleased game assets into permanent public links. For a small team considering Infrai, the concrete integration advantage is one plain REST API with one key instead of another SDK and credential set. Its self-describing discovery surface is public with no key required and supplies runnable examples, so the storage contract can be inspected before implementation. Why is an AI image missing after a duplicate retry overwrite? A retry is a second write, not a continuation of the first one. If attempt 1 uploads players/42/avatar.png and attempt 2 writes the same key, the later body becomes the object associated with that name. Without object versioning or object lock, storage alone cannot recover the earlier body after an accidental overwrite or deletion. The dangerous sequence is easy to miss. The renderer finishes, an upload succeeds, and the client times out before it records success. A worker retries with the same key. Meanwhile another render for the same player may have completed. A stable filename has now collapsed two distinct attempts into one mutable location. One key, one render. Derive the write path from the constraints The application should authorize the player and create the render-attempt row before it grants an upload. It then returns a presigned URL for the unique object key. The client or rendering worker sends the large image body directly to storage; it must not attach the platform's API Authorization header to that returned URL. This keeps media bytes out of the app process without making the object public. After upload, the application verifies the expected attempt and commits the object key alongside the job state. If the product needs a stable path such as players/42/avatar/latest.png , copy the unique object to that final key only after the database transaction succeeds. Readers should still prefer the immutable key where practical. The canonical copy is a convenience pointer represented as an object, not a recovery system. There is another race here. With no If-Match conditional write, two workers cannot use storage alone for strict compare-and-swap promotion. Serialize promotion through a queue or protect it with a database lock and an attempt-state check. The winner must be selected in the database before the final copy occurs. This is the same discipline an OTP service needs when duplicate delivery callbacks arrive: external work may repeat, so state transitions need a single authority. Retries should reuse the same attempt key only when they are retrying transport of the same known bytes. A newly generated output gets a new attempt key, even if its prompt and job are unchanged. That distinction prevents a regeneration from silently replacing a completed artifact. Access control shapes delivery Signed-only storage fits authenticated game assets, moderation queues, and private generation histories. The application can decide who may fetch an object, then mint a time-bounded URL so the download still avoids proxying the bytes. The trade-off is operational: clients need a URL-refresh path, caches cannot assume a permanent public address, and offline game clients need expiry behavior designed explicitly. A service without public-read ACLs or a non-null public URL is the wrong backing store for static website hosting, a public image host, or assets that require permanent anonymous links. It is also the wrong sole control for financial-grade immutability because object lock is absent. Those are boundaries, not small configuration gaps. Retention deserves equal care. A one-day minimum lifecycle cannot provide hourly expiry, and abandoned multipart fragments do not have an automatic cleanup rule. Track incomplete uploads in the database and schedule explicit cleanup. For player deletion requests, keep object keys connected to the account record so erasure can include both canonical and attempt objects; prefix design makes that inventory tractable. A compact rollout that preserves old images Start by changing key generation, because every later safeguard depends on attempt-level identity. Deploy database columns for attempt_key , canonical_key , and attempt state, then dual-read: resolve the recorded unique key first and fall back to the legacy stable key for older rows. Do not bulk-copy until ownership and retention rules are clear. Next, route new large uploads through private presigned URLs and verify that clients refresh expired download links. Add a serialized promotion worker only for screens or integrations that truly require a stable path. Test two concurrent completions for the same job, a timeout after a successful upload, a player deletion, and cleanup of an abandoned multipart upload. Finally, monitor orphan counts by key prefix and reconcile them against database attempts. The decisive invariant is small enough to put in a review checklist: a generated image is immutable at its attempt key, and only the database decides which attempt is current.
