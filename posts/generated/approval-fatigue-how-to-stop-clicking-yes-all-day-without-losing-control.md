The fix for approval fatigue is not fewer approvals everywhere; it is approvals placed where a mistake would cost you, and nowhere else. What is approval fatigue with AI coding agents? Approval fatigue is what happens when an AI coding agent asks for permission so often that you stop reading what you approve. The first ten cards get a careful look. By the fortieth, your hand presses yes before your eyes reach the command. At that point you have the worst of both worlds. The agent is slow, because it waits on you all day. And you are not in control, because your yes no longer means "I checked this". A card that is always approved is not a safety step. It is a delay. The goal is simple to say: fewer cards, and every card that remains deserves a real look. Why does approving every step fail? Three reasons, and they compound. Most steps are boring. Listing a folder, reading a file, running git status or the test suite. These change nothing, or change nothing you cannot see in the next diff. Asking about them trains you to click. Risky steps look like boring ones. A command that deletes a folder or sends data to a server sits in the same card, in the same font, as ls. When you approve forty cards in a row, the one that matters gets the same half-second as the rest. Long tasks break. An agent that stops every few seconds cannot finish a real task while you are in a meeting. So people either stop using the agent for real work, or they switch every approval off. Neither is what you wanted. Which steps should run without asking, and which need your yes? Use three groups. Write them down for yourself or your team, then set your tool to match. Group Examples Suggested setting Let it run Reading files, searching, ls, git status, git diff, running tests No card Ask sometimes Editing files inside the task's folder, installing a dependency, starting a local server A card at first; loosen after a week of clean diffs Keep a person's yes git push, deploys, deleting files or data, anything that reaches the network or another machine, anything outside the project A card, every time, by your own policy The middle group is where most of the fatigue lives, and where most of the time is saved. The last group should stay small. If it holds twenty kinds of step, you are back to clicking all day. Treat the right-hand column as your own rule, not as a promise about any tool. Tools differ, and tools change. Section five shows how to check. How do approvals work in Mel? In Mel, you set this in Settings > Agent mode. The settings are: Apply code diffs: Agent decides, Always allow or Always ask. With Agent decides, the agent edits files in the conversation's folder without a card. Execute commands: Always allow or Always ask, plus a command allowlist and a denylist. The denylist is checked first, then the allowlist, then your choice. Run orchestrated agents: Never, Always allow or Always ask, for when a lead agent wants to start worker agents. A few details that matter for fatigue: Commands that only read, such as ls, cat, grep, git status and git diff, run without a card under Always ask. If you want a card for those too, turn on "Ask before read-only commands too". The allowlist and denylist take regular expressions matched against the whole command, for example npm test.* on the allowlist or git push.* on the denylist. A new install starts with a denylist that already includes commands such as rm, curl, ssh and the shells. Under Always allow, a command on the denylist still gets a card. The card for a file edit shows the change as a diff of the lines added and removed, so a yes on an edit can be a quick, real read. A change in Agent mode applies at once, in running conversations too. In a conversation, the A+ toggle overrides it and gives the agent full autonomy, so use that only when you mean it. How do you loosen approvals without losing control? Go one step at a time. Each step is a week, or a few real tasks, whichever is longer. Step 1: strict. Edits on Always ask, commands on Always ask. Read every card. Note which ones you approved without a second thought. Those are your candidates. Step 2: allow the boring commands. Add your test, lint and build commands to the allowlist. Reads already run without a card, so most of the noise is now gone. Step 3: let edits run inside the task. Move Apply code diffs to Agent decides. Read the diff at the end of the task instead of every edit along the way. This is where long tasks start to finish on their own. Step 4: commands on Always allow, with a denylist you wrote. Only if steps 1 to 3 went well. Before you switch, add your own risky commands to the denylist: git push.*, your deploy command, your database tool, anything that touches production. At every step, keep a short list of the cards you are glad you saw. If that list is empty after a week, you can loosen. If it is not, stay where you are. How do you check that your approvals really work? Do not trust a setting you have not tested. This applies to every tool, including ours. Make a throwaway repository with a few files and a fake remote. Ask the agent to do each step in your "keep a person's yes" group: push, deploy, delete a file, call an outside URL. Watch which ones raise a card and which ones run. Fix your settings for anything that ran when it should have asked, or keep that step out of the agent's hands. Repeat the check after you change a setting and after you update the tool. Ten minutes on a fake repository is cheaper than one surprise on a real one.
