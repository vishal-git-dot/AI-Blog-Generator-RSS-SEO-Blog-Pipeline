# Dice Contract Jobs Scraper: Filtering by Employment Type Without Babysitting a Browser

## Overview

Dice contract jobs — the Contract and Third Party postings specifically — are the reason IT staffing agencies use Dice.com over a general board in the first place, but most of the scrapers built against Dice hand you the entire firehose and leave the employment-type split for you to sort out by hand. That's a strange gap. Dice's own taxonomy already tags every posting as Full-time , Contract , or Third Party , plus a separate employer_type field ( Direct Hire vs. Recruiter ) that tells you whether you're looking at a company hiring directly or a staffing firm sourcing on someone else's behalf. If you run an IT staffing desk, that pair of fields is basically the whole job — and it's sitting right there in the data, unused as a filter by most of the tooling built to read it. We built Dice Tech Jobs Scraper to treat employment type as a first-class filter instead of an afterthought, and to hand back one typed row per posting — title, company, location, employment type, employer type, salary text as published, and optional skill tags — ready for CSV, JSON, or a straight API pull into your sourcing sheet or ATS. How the extraction actually works Dice relaunched on Next.js with React Server Components, which means the job-search page doesn't ship a tidy public REST API the way it used to — the older job-search-api.svc.dice.com host is gone. What replaced it is arguably more interesting: the full job list comes back embedded as escaped JSON inside <script>self.__next_f.push([1,"..."])</script> chunks in the server-rendered HTML. One HTTP GET to the search URL returns the page and the data in the same response — the trick is locating the right chunk (by scanning for the "jobList" key rather than trusting a fixed array index, since Next.js doesn't guarantee that index stays put across chunk-numbering changes) and pulling the structured payload out of it. That's a meaningfully different extraction problem than a typical DOM scrape: there's no CSS selector to write, no pagination link to click through, just a JSON blob to locate and parse — which is why this Actor doesn't reach for a browser at all. We still run every request through curl-cffi with rotating Chrome/Firefox/Safari TLS impersonation, retry on 408/429/5xx with exponential backoff up to 5 attempts, and rotate Apify Proxy sessions on any block — not because today's Dice throws up a wall, but because a Next.js frontend can change its chunk layout or add rate-limiting on any given week, and a scraper that only works against last month's markup is a liability the moment it silently stops working. If a page fails to parse, the run logs it and moves on instead of crashing the whole job or quietly returning nothing.
