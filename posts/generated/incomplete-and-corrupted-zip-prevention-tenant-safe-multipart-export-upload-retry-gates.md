# Incomplete and Corrupted ZIP Prevention: Tenant-Safe Multipart Export Upload Retry Gates

## Overview

A large B2B SaaS export should use multipart upload only when its size justifies the extra state. The decision rule is stricter than "all parts returned success": keep the export private, complete the multipart upload, verify the final object with HEAD, and only then expose a tenant-scoped download link. If archive generation fails, abort that upload before retrying. TL;DR: A ZIP that downloads but will not open often points to an upload that never reached a valid completed state, or to stale multipart state being reused. Treat completion as a commit. Record the upload ID and part results, abort failed jobs, and make HEAD verification the gate between uploading and ready . The byte path should bypass the application. A worker creates the private multipart session, the browser or worker sends parts to presigned destinations, and object storage assembles them. Your app carries control data, not a multi-gigabyte archive. Tenant isolation stays in that control plane: derive the bucket and key from authenticated tenant context, never accept either as free-form client authority, and issue short-lived signed access only after verification. How can an incomplete multipart export upload corrupt a ZIP download? Yes. Individual part success does not prove that the final object exists in completed form. Completion can be missing, a retry can refer to an earlier upload ID, or the application can publish a link while the job is between its last part and the complete call. A ZIP exposes the mistake because its central directory is near the end; a truncated object may download normally and fail only when opened. Use explicit states: generating , uploading , completing , verifying , ready , and failed . Only ready may trigger a customer notification. The database row should bind tenant_id , export ID, bucket, object key, and multipart upload ID. A retry gets a new attempt record or resumes the exact recorded attempt. It must never guess from a prefix. One boundary matters. If generation or any part upload fails, move the job to failed and explicitly abort its multipart session. No automatic cleanup rule for multipart fragments is assumed here, and the one-day lifecycle floor is not a substitute for immediate cleanup. Tenant isolation changes the design A presigned upload moves bytes away from the app, but it doesn't move authorization away from the app. The server must map the signed-in principal to one tenant, choose a private namespace such as tenant_id/exports/export_id.zip , and constrain create, complete, verify, and download actions to that record. Never let a browser nominate another tenant's bucket or prefix. Signed-only access fits the capability boundary here: there is no public or public-read ACL, and public_url remains null. This works for private customer exports, not static-site hosting, an image host, or permanent public links. There is no object versioning or object lock, so accidental overwrite recovery and WORM retention need an external design. Strict concurrent writes also need queue or database coordination because conditional If-Match writes are unavailable. The clean ownership rule is one active writer per export ID. Queue serialization or a transactional database lease keeps two workers from completing different sessions onto the same key. Keep keys immutable after a job becomes ready ; a regenerated export gets a new ID and key. Short-lived URLs help, but cache behavior matters. If a download response can pass through a shared cache, set a private cache policy at the serving layer and keep reusable signed URLs out of analytics events and logs. Percent-encode key path segments consistently. Spaces, percent signs, and slashes are mundane ways to create a link that works in one client and fails in another.
