# Your Order API Needs More Than an Idempotency Key

## Overview

An order API can accept an Idempotency-Key header on every request and still create a second order for the same intended purchase. Generate a fresh key after a timeout, and a server that deduplicates by key has no way to connect the retry to the first attempt. There is a separate server-side problem too. A lookup followed by an insert leaves a race if competing requests can both observe that the key is absent. The key needs an atomic relationship with the saved order. That is the argument worth testing. How much does your retry guarantee actually cover? This Python and SQLite lab commits an order, deliberately drops the response, and lets you retry it. You can inspect the database instead of guessing whether the request succeeded. It creates local order records only and never charges a wallet. The different status codes are deliberate in this teaching API. 201 means this request created the record; 200 means it recovered an existing one. Other APIs have different replay contracts. A competing writer has to wait or fail, rather than independently reading an absent key and proceeding with its own insert. The unique constraint is an additional guard; the server returns success only after commit. SQLite allows one writer at a time, so this approach trades write concurrency for a small, inspectable implementation. See SQLite transaction behavior . If SQLite cannot obtain the lock within the configured timeout, the HTTP handler returns 503 with database_busy_retry_same_key . A caller should retry with backoff and keep the same purchase key. This example does not establish a production throughput limit. There is a small but consequential choice in the replay branch. It returns the amount saved with the order. It does not calculate a new price from the catalog. A price change between attempts should not silently change the purchase already accepted under that key. The saved purchase key connects the retry to the order that already exists. Reproduce the uncertain result Now use a fresh key and the lab's fault-injection header. curl -i http://127.0.0.1:8765/orders \ -H 'Content-Type: application/json' \ -H 'Idempotency-Key: reader-attempt-0002' \ -H 'X-Demo-Drop-Response: yes' \ -d '{"sku":"field-kit"}' Curl should report an empty response, typically exit code 52. The handler committed the order and then shut down the connection before sending response bytes. This is a controlled failure in the lab, not evidence of a real network incident. Retry without the fault header, keeping the same key. curl -i http://127.0.0.1:8765/orders \ -H 'Content-Type: application/json' \ -H 'Idempotency-Key: reader-attempt-0002' \ -d '{"sku":"field-kit"}' The response should be 200 . Where this guarantee ends The test suite sends twelve HTTP requests from six client threads and checks that they produce one order ID. It also restarts the server against the same database. Those are useful checks of this local service, not a distributed exactly-once guarantee or a power-loss test. For a payment checkout, the next boundary is the call to a payment provider or blockchain. A committed SQLite row cannot by itself prevent a second external charge. Define a stable identity for that external operation and a recovery path for an uncertain result before adding real payments. This sample also lacks authentication and merchant isolation. In a multi-tenant API, derive the key's scope from the authenticated account and operation. Define which request fields must match and how long the key remains valid. Remove the demonstration disconnect header before adapting the pattern to a deployed service. A practical review question is whether the integration can recover the original order after its response is lost. “We send an idempotency header” leaves that question unanswered. For an API you maintain, would you return the original 201 on replay, or use 200 as this lab does?
