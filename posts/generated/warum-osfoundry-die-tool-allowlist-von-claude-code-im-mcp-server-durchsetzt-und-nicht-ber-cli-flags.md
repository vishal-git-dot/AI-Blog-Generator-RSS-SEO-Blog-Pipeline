# Warum osFoundry die Tool-Allowlist von Claude Code im MCP-Server durchsetzt und nicht über CLI-Flags

## Overview

Das hier ist die MCP-Konfiguration, die die Desktop-App von osFoundry an Claude Code übergibt, wenn sie es als Worker im Agent-Modus startet. Die Bridge ist hier mein Nachbau in Python, Port und Token stammen also aus diesem Lauf. Die Struktur ist die aus src-tauri/src/mcp_bridge.rs : { "mcpServers" : { "osfoundry" : { "type" : "http" , "url" : "http://127.0.0.1:51377/mcp" , "headers" : { "Authorization" : "Bearer 8dd5de…" }, "timeout" : 120000 }}} Vier Details tragen das ganze Sicherheitsmodell. Der Host ist 127.0.0.1 , niemals 0.0.0.0 . Den Port vergibt das Betriebssystem ( bind("127.0.0.1:0") ). Das Token besteht aus 64 Hex-Zeichen, erzeugt für genau diesen Lauf und sonst nirgends gültig. Und eine Tool-Liste steht überhaupt nicht drin. Die zugehörige Kommandozeile hat auch kein --allowedTools : claude -p "<conversation>" --output-format stream-json --verbose --include-partial-messages \ --permission-mode bypassPermissions --add-dir <folder> \ --mcp-config '<the JSON above>' --strict-mcp-config Die Allowlist gibt es. Sie liegt im Server. Unten steht, warum, plus ein lauffähiger Nachbau zum Ausprobieren. Warum liegt die Allowlist im Server? Der Agent-Modus startet Claude Code mit --permission-mode bypassPermissions , weil niemand am Terminal sitzt, der jeden Schritt freigibt. Der Kommentar in build_claude_command erklärt, warum keine Allowlist übergeben wird: Unter bypassPermissions ignoriert Claude Code --allowedTools . Das Flag wäre reine Deko. Der Header von mcp_bridge.rs sagt dasselbe kürzer: "Never trust the client; the server decides." Der allgemeine Grund gilt für jede Agent-CLI. Ein Flag ist eine Anweisung an den Client, und der Client ist genau die Partei, die modellgesteuerten Code ausführt. Das ist der falsche Ort für die eine Prüfung, die halten muss. Der Server sieht jeden tools/call und wird nicht vom Modell gesteuert, also bekommt er den Job. osFoundry macht das an zwei Stellen: tools/list liefert nur die Tools aus der Liste des Laufs ( agent_cli::tool_policy grenzt sie vorher ein). Dem Modell wird nie gesagt, dass es die anderen gibt. tools/call prüft den Namen gegen dieselbe Liste, bevor irgendetwas läuft. Ein Modell kann trotzdem einen Tool-Namen ausgeben, der ihm nie gezeigt wurde, aus den Trainingsdaten oder durch eine Prompt-Injection in einer gelesenen Datei. Dagegen hilft der erste Filter nicht. Der zweite schon. Was sieht die CLI beim ersten Aufruf? Drei POSTs, jeder auf einer frischen Verbindung, weil der Server mit Connection: close antwortet: → initialize ← 200 {"protocolVersion":"2024-11-05","capabilities":{"tools":{}},"serverInfo":{"name":"osfoundry",…}} → notifications/initialized ← 202, Content-Length: 0 → tools/list ← 200 {"tools":[{"name":"memory_search","description":…,"inputSchema":{…}}]} Das 202 mit leerem Body ist keine Pedanterie. Im Rust-Code ist festgehalten, dass der MCP-Client von Codex (rmcp) seinen Transport abbaut, wenn eine Notification {} mit 200 bekommt, und damit starb der ganze Lauf schon beim Handshake. Claude Code verträgt das. Codex nicht. Jede JSON-RPC-Nachricht ohne id oder mit einer notifications/ -Methode bekommt ein 202 ohne Body. Danach stellt Claude Code jedes Tool als mcp__<server>__<tool> bereit, aus memory_search wird also mcp__osfoundry__memory_search . Der Servername in der Konfiguration sorgt für das osfoundry in der Mitte. Der Nachbau Auf diesem Rechner ist kein claude -Binary installiert. Die Client-Seite ist deshalb ein Skript, das das tut, was ein Headless-Agent mit einem HTTP-MCP-Server tut: --mcp-config parsen, den Handshake durchlaufen, Tools aufrufen. Der Server ist die Logik der Rust-Bridge, nachgebaut mit der Python-Standardbibliothek. Vollständige Dateien: bridge.py , fake_cli.py und run_demo.py , zusammen etwa 230 Zeilen. Die Bridge fügt keinen eigenen Ausführungspfad hinzu. Sie entscheidet nur, ob ein Aufruf diese Funktion erreicht. Die Registry enthält drei Tools: memory_search , execute_command und delete_file . Der Lauf startet mit allowed=["memory_search"] . Ein Claude-Code-Prozess braucht allein zum Hochfahren deutlich länger, ein Server pro Lauf ist in der Praxis also gratis. Der abgelehnte Aufruf kostet genauso viel wie der erlaubte. Die Prüfung ist ein Listen-Lookup und geht im Rauschen eines TCP-Roundtrips unter. Die einzige Überraschung war der Shutdown. Pythons serve_forever prüft nur einmal pro poll_interval auf Shutdown, standardmäßig 0.5 s, also wartete jedes Laufende eine halbe Sekunde. Die Rust-Bridge hat dieses Problem nicht: Ihre Accept-Schleife ist ein tokio::select! über accept() und einen watch -Channel, der Shutdown weckt sie also sofort. In Python übergibst du ein kleineres poll_interval oder schließt den Socket im Exit-Pfad des Laufs. Warum HTTP und nicht stdio? Die meisten MCP-Server, die du an Claude Code hängst, sind stdio-Prozesse. Der von osFoundry nicht, und mcp_bridge.rs erklärt, warum. Der Tool-Executor braucht das AppHandle der App, und das lässt sich weder serialisieren noch in einen anderen Prozess verschieben. Ein stdio-Server wäre ein zweiter Prozess, der ohnehin jeden Aufruf zurück in die App weiterreichen müsste. Claude Code unterstützt "type": "http" -Server mit Bearer-Headern, also stellt die App MCP aus sich selbst heraus auf einem Loopback-Port bereit. Der Preis dafür sind Port und Token, und deshalb gelten beide nur pro Lauf. Wenn du das selbst verdrahtest Setz die Allowlist in den tools/call -Handler des Servers und filtere zusätzlich tools/list . Behandle CLI-Flags wie --allowedTools als Hinweise, besonders unter jedem "bypass"-Berechtigungsmodus. Binde Workspace, User und Channel beim Sessionstart. Übernimm sie nie aus Tool-Argumenten oder Headern, die der Client kontrolliert. Erzeuge das Bearer-Token pro Lauf und vergleiche es in konstanter Zeit ( hmac.compare_digest ). Verwende kein langlebiges Agent-Token für einen Endpoint, der Tools ausführt. Binde auf 127.0.0.1:0 und lass das Betriebssystem den Port wählen. Kopple die Lebensdauer des Listeners an den Kindprozess und prüfe, ob der Shutdown-Pfad wirklich sofort greift. Beantworte Notifications mit einem 202 ohne Body. Manche Clients brechen bei allem anderen die Verbindung ab. Übergib --strict-mcp-config oder das Pendant deiner CLI, damit die eigenen MCP-Server des Users nicht in einen Lauf rutschen, den du bewusst eingegrenzt hast.
