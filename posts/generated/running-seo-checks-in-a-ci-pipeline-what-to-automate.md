# Running SEO Checks in a CI Pipeline: What to Automate

## Overview

The deploy went green. Every test passed. Two days later, someone in marketing posted a Search Console screenshot in Slack: pages were dropping out of the index. A template change had shipped a noindex tag that was only ever meant for staging. Nothing in the pipeline caught it, because nothing in the pipeline was looking. Unit tests check that your code behaves. They don't check the HTML that Googlebot actually receives. This post is a practical plan for running SEO checks in a CI pipeline. It covers which checks to automate, where each one should run, and which ones to leave to humans. Every script below was tested before publishing, and you can drop them into a GitHub Actions setup today. If you've wanted to start automated SEO testing but weren't sure where the line was, this is it. Why SEO Breaks Quietly in Deploys SEO regressions are sneaky because nothing errors out. The page loads, the design looks right, and users can click around normally. Meanwhile: A staging noindex meta tag or X-Robots-Tag header goes to production. robots.txt ships with Disallow: / copied from a preview environment. Canonical tags point at the staging host. A layout refactor wipes page-specific titles and meta descriptions. Routes get renamed with no redirects, so old URLs return 404. A JSON-LD block breaks because someone added a trailing comma. The sitemap still lists URLs that no longer exist. Each of these takes seconds to detect with the right check and weeks to notice from traffic graphs. That gap is exactly what CI is good at closing. The Rule for What to Automate Not every SEO check belongs in a pipeline. Use one simple rule: Automate checks that are deterministic, fast and binary. A tag is present or it isn't. A URL returns 200 or it doesn't. These make good gates. Monitor checks that are noisy or depend on real users. Lab performance scores vary between runs, and Core Web Vitals field data comes from real visitors over weeks. Track these, but don't block merges on them. Keep judgment human. Content quality, search intent, keyword targeting and title copywriting need a person. The Four Layers at a Glance Pull request gate: lint the built HTML for missing or broken tags. Runs in seconds. Lighthouse sample: audit a handful of key templates for SEO and performance budgets. Post-deploy check: test the live server for robots rules, headers, redirects and sitemap health. Scheduled monitoring: catch slow drift such as broken external links and field performance. To decide which individual rules to codify, start from a reference list rather than a blank page. SEO Site Checker's 70 SEO checks explained groups on-page, performance, security and advanced checks with plain-language explanations, which makes it easy to pick the deterministic ones for your linter. Layer 1: Gate Pull Requests on the Built HTML The most important habit is to test the build output, not your source templates. Your framework, your CMS data and your layout components only come together in the final HTML, and that HTML is what search engines see. Point the checks at dist/ , out/ or whatever folder your static export produces. Checks That Belong Here Exactly one non-empty <title> , unique across the site, with a warning above 60 characters A meta description, with a warning above 160 characters A canonical tag that is absolute and points to the production host No noindex in meta robots, except on pages you deliberately allow One <h1> per page (warning only, since some layouts have good reasons) A lang attribute on <html> An alt attribute on every image (an empty alt="" is fine for decorative images) Basic Open Graph tags JSON-LD that parses and includes @context and @type , including inside @graph A Small Checker Script This script uses cheerio to parse every HTML file in the build folder. It separates errors, which fail the build, from warnings, which are only printed. That keeps it fast and immune to third-party sites being slow. External links get checked later, on a schedule. Keep this whole job under about a minute. If an SEO gate becomes the slowest step in CI, people start looking for ways around it. Layer 2: Lighthouse CI on Key Templates, Not Every Page Lighthouse is useful, but it's slow, and its performance scores change from run to run. Running it on every page of every PR is a recipe for flaky builds. Instead, audit three to five representative templates: the homepage, an article, a product or service page and a listing page. Lighthouse CI can serve your static build itself and assert on the results: { "ci" : { "collect" : { "staticDistDir" : "./dist" , "url" : [ "http://localhost/index.html" , "http://localhost/blog/sample-post/index.html" , "http://localhost/pricing/index.html" ], "numberOfRuns" : 3 }, "assert" : { "assertions" : { "categories:seo" : [ "error" , { "minScore" : 0.9 }], "categories:performance" : [ "warn" , { "minScore" : 0.8 }], "largest-contentful-paint" : [ "warn" , { "maxNumericValue" : 2500 }], "cumulative-layout-shift" : [ "warn" , { "maxNumericValue" : 0.1 }] } }, "upload" : { "target" : "filesystem" , "outputDir" : "./lhci-reports" } } } Save that as lighthouserc.json and add one step to the workflow: npx @lhci/cli autorun . Notice the split. The SEO category is an error, because its audits are mostly deterministic (crawlable links, valid hreflang, a document title and so on). Performance is a warning, because CI runners vary in speed. Three runs per URL lets Lighthouse CI use the median result, which smooths out the noise. Layer 3: Check Production Right After Deploy Some of the most damaging problems only exist on the live server. Response headers, robots.txt , redirects and host settings often come from CDN rules, server config or a hosting dashboard rather than your repository. A PR check can't see them, so test production immediately after every deploy. robots.txt and X-Robots-Tag Fail the run if robots.txt blocks everything for User-agent: * , or if key pages send noindex through an X-Robots-Tag header or a meta tag. The header is easy to miss because it never appears in the HTML. Google's robots meta tag and X-Robots-Tag docs explain how both are interpreted. Be precise about Disallow: / . Plenty of sites block specific bots, such as AI crawlers, on purpose, so the check should only fail when the rule applies to every crawler. A Redirect Map Test Keep a redirects.csv file in the repository with two columns, from and to . After each deploy, assert that every old URL returns a single 301 or 308 straight to the expected target, and that the target returns 200. This catches missing redirects, temporary 302s, wrong destinations and chains. Sitemap Sanity Request every URL in the sitemap and expect a 200. Then compare the URL count against a stored baseline, and fail if it drops sharply. A sitemap that suddenly loses a large share of its URLs usually means a routing change or a broken data source, not a deliberate cleanup. Handle them with a scheduled workflow that alerts people instead of failing builds: on : schedule : - cron : " 17 6 * * 1" # Mondays at 06:17 UTC workflow_dispatch : Good candidates for a weekly run: External link checks with lychee in online mode, since other sites change without telling you Core Web Vitals field data from the Chrome UX Report (CrUX) API, which reflects real users rather than a lab run Indexing coverage through the Search Console API, to spot a jump in excluded pages The post-deploy script again, to catch config changes made outside a deploy Post the results to Slack or open a GitHub issue. Nobody should be blocked from merging because a partner's website went down. Automation also doesn't replace a periodic human look at the whole site. Every month or so, run a full SEO audit on your key pages and compare it with the last one. What Not to Automate It's tempting to turn everything into a gate. Resist that for: Content quality and helpfulness. No linter can tell whether a page actually answers the searcher's question. Search intent and keyword choices. These are strategy decisions, not syntax errors. Title copywriting. You can check length automatically, but not whether the title is good. Internal linking strategy. You can check for broken links, but deciding what to link is editorial work. Lighthouse scores on every page as hard gates. They flake, people stop trusting the pipeline, and then they ignore real failures too. Automation keeps the floor up. Humans still have to raise the ceiling. For the judgment side, a manual technical SEO audit checklist covers what a script can't. Rolling It Out Without Annoying Your Team Start with warnings only. Run every check in warning mode for two weeks, fix the existing backlog, then promote the stable checks to errors. Keep an allowlist. Some pages, like internal search results or a 404 page, should be noindex . Put exceptions in one obvious place, like NOINDEX_ALLOWED in the script. Make failures readable. Each message should name the page, the rule and the fix. Consider posting a summary as a sticky PR comment. Give every check an owner. When a rule fires falsely, someone needs to fix the rule rather than add || true to the workflow. Frequently Asked Questions Can you automate SEO testing? Yes, for the technical layer. Anything with a clear pass or fail can be automated: tags, status codes, redirects, robots rules, structured data syntax and sitemap health. Content quality, search intent and strategy still need human review, so automation complements an SEO specialist rather than replacing one. Is Lighthouse enough for SEO checks in CI? No. Lighthouse's SEO category covers useful basics, but it audits one page at a time, doesn't compare titles across pages, can't see your redirects or robots.txt in production, and doesn't validate your structured data against your own rules. Use it as one layer alongside an HTML linter and post-deploy checks. Should SEO checks fail the build or just warn? Fail the build for deterministic, high-impact problems such as noindex on indexable pages, missing titles, broken canonicals and invalid JSON-LD. Warn for things that are noisy or subjective, like performance scores, title length or multiple H1 tags. Start everything as a warning, then promote checks once they've proven reliable. How do I test for noindex and robots.txt mistakes before they reach production? Lint the built HTML for noindex meta tags in every pull request, then run a post-deploy check against production for robots.txt rules and X-Robots-Tag headers. Headers and robots files often come from server or CDN config rather than your code, so the production check is essential. How do I check for broken links in GitHub Actions? Use a link checker such as lychee through its GitHub Action. Run it in offline mode on your build output during pull requests to check internal links quickly, then run it in online mode on a schedule to check external links without blocking merges when a third-party site is down. Do SEO checks slow down a CI pipeline? They don't have to. An HTML linter over a typical static build finishes in seconds. Lighthouse is the slow part, so limit it to a few key templates. Post-deploy and scheduled checks run outside the pull request flow entirely, so they never block developers. Wrapping Up A sensible SEO pipeline has four layers. It gates pull requests on the built HTML, samples key templates with Lighthouse, checks production right after deploy, and monitors slow drift on a schedule. Automate what's binary, monitor what's noisy, and keep judgment human.
