# Fixing PyInstaller --onefile tmpfs Issues by Switching to --onedir and Clarifying Size Myths

## Overview

Anatomy of the --onefile vs. --onedir Bundle and the Size Myth When you pass --onefile to PyInstaller, the build tool does not strip dead code, prune unused shared libraries, or shrink your Python interpreter. Instead, the bootloader appends a compressed archive (typically using zlib or LZMA) containing the exact same set of .pyc bytecode files, .so / .dll shared objects, and data assets that a --onedir build places into a directory tree. If your bundle contains a 600 MB scientific or machine learning stack, --onefile still carries all 600 MB of underlying payload inside that single executable. Any file-size reduction you observe on disk comes from archive compression ratios minus a small bootloader stub, whereas at runtime the uncompressed bytes must be written out anyway—meaning --onefile often inflates temporary storage pressure rather than saving space. The physical cause of tmpfs failures lies in how a --onefile binary boots. When launched, the C bootloader reads the embedded archive, decompresses each entry, and writes the unpacked files into a temporary directory—commonly under /tmp or TMPDIR —before loading the embedded Python runtime from those extracted files. Because tmpfs stores files in page cache backed by system RAM and swap rather than a persistent block device, every decompressed byte occupies volatile memory pages or hits a strict tmpfs size cap (such as a container's default 64 MB /dev/shm or tight /tmp mount). As decompressed bytes accumulate in tmpfs , free memory pages shrink or the mount hits its quota; once exhausted, the write syscall fails with ENOSPC (no space left on device) or the kernel's out-of-memory (OOM) killer terminates the process. Startup latency follows a parallel mechanical chain. Under --onefile , cold start requires sequential decompression and filesystem writes of potentially hundreds of megabytes into the temporary directory on every invocation, followed by dynamic linker symbol resolution and Python imports. Under --onedir , the files already sit unpacked on disk or in an existing directory, so launching skips the full-bundle decompression-and-extraction pass and goes straight to loading shared libraries and executing Python code. However, --onedir is not universally faster: if a network filesystem has high metadata latency across thousands of small files, or if a warm tmpfs page cache already holds the extracted payload while cold storage is slow, those local I/O dynamics can shift the balance. Decision Dominance: Choosing Between --onedir and --onefile Optimal default for tmpfs-constrained and production runtimes: --onedir . By eliminating runtime self-extraction into volatile temporary storage, --onedir avoids ENOSPC quota exhaustion and avoids duplicating payload bytes across both archive/page cache and extracted files in RAM-backed tmpfs . It is strictly more reliable than --onefile when temporary space is bounded or memory is tight. When --onedir stops working: When the deployment target only permits distributing a single standalone binary file with no directory bundle or archive wrapper allowed, or when the target filesystem has severe per-file open/stat overhead across thousands of tiny dependency files and cannot be pre-staged. Typical choice errors and their mechanism: Engineers frequently pick --onefile assuming single-file packaging shrinks the application, when in reality compression only trades CPU decompression time for a smaller transfer artifact while expanding back to full size in tmpfs at runtime. Another common mistake is pointing TMPDIR at a larger tmpfs mount without checking total system RAM: expanding tmpfs capacity without sufficient backing RAM/swap simply allows a giant extraction to push the host closer to OOM eviction. Selection rule: If /tmp or TMPDIR is backed by memory-capped tmpfs , or if cold-start speed and predictable memory headroom matter more than a single-file artifact -> use --onedir . Only use --onefile when a single-file executable is a hard distribution requirement and the target environment has ample temporary storage and RAM headroom to absorb full decompression on every launch. Why --onefile Breaks on tmpfs: Extraction, Memory, and Execution Constraints When a PyInstaller --onefile executable launches, a compiled C bootloader opens its own binary image, locates the trailing archive appended during build, decompresses entries (typically zlib or LZMA), and writes every extracted file into a temporary directory under TMPDIR or /tmp before starting the embedded Python runtime. When that target directory sits on a tmpfs mount, those writes do not hit a disk block layer; they allocate kernel page cache backed by physical RAM and swap. Switching to --onedir eliminates this runtime extraction phase because the bootloader loads pre-unpacked .pyc bytecode, shared libraries, and data files directly from disk rather than materializing a second copy in volatile memory. A common assumption is that --onefile shrinks an application because it produces a single file. It does not prune unused modules, strip dead bytecode, or shrink shared libraries; it packages the same dependency graph as --onedir inside a compressed container plus a bootloader stub. Any file-size reduction comes strictly from archive compression minus bootloader overhead, while runtime execution still inflates the uncompressed payload. Core Failure Mechanics on tmpfs Mount cap exhaustion (ENOSPC): Each extracted file written to a size-capped tmpfs mount consumes filesystem blocks out of the mount's configured capacity limit. Once uncompressed bytes plus filesystem metadata exceed that cap, the kernel rejects further write syscalls with ENOSPC , aborting bootloader extraction before Python starts. Page-cache and RAM pressure (OOM killer): Because tmpfs stores file contents in memory pages rather than persistent blocks, extracting a large scientific or AI bundle expands anonymous/page-cache memory usage while the Python process simultaneously allocates heap for interpreters and loaded .so libraries. When total memory and swap demand crosses the cgroup or system limit, the kernel out-of-memory (OOM) killer terminates the process. Noexec and permission enforcement: Bootloaders unpack shared libraries and helper binaries into the temp directory and invoke dynamic linking or execution against those extracted paths. If the tmpfs mount carries noexec or restricted permissions, loading shared objects or executing extracted binaries fails at the kernel/loader boundary even when free space and RAM remain available. Cold-start extraction latency: Every cold launch of a --onefile binary repeats archive scanning, decompression CPU work, and temp-directory file creation before symbol resolution and module imports even begin. A --onedir build bypasses decompression and write amplification on launch, moving straight to opening existing files.
