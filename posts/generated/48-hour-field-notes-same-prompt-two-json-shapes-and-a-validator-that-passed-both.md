# 48-Hour Field Notes: Same Prompt, Two JSON Shapes, and a Validator That Passed Both

## Overview

Six hundred markdown files landed in an inbox folder, and my only job was to turn them into a one-page morning report. The plan looked trivial: send each file to a model, get back four fields, append a line of JSONL, render a table. I gave myself forty-eight hours to make that loop boring, so like an idiot I built the happy path first. The happy path held for about six hours. The full run exited 0, the report rendered, and nobody on the receiving end noticed that one column had quietly stopped meaning anything. These are the field notes: what I tried, where it broke, and the small harness I would keep for next time. The constraints I actually had Before the timeline makes sense, here is the shape of the problem. Roughly 600 small text files per night, growing by maybe 5% a week. Four output fields per file: category , severity , needs_human , summary . A morning report that a human reads, so a wrong column is worse than a missing row. No budget, which meant a free tier and a free machine, and no assumption of either staying stable. That last one is the constraint people skip, and it produced every bug below. If your model access can change shape between Tuesday and Wednesday, then your real interface is not the API — it is the contract you wrote down and test. Hour 0–6: the validator that agreed with everything I wrote the extraction call, a parser, and a validator, and all three passed on the first twenty files. The validator was a dataclass with type annotations checked by isinstance , which felt rigorous and was mostly theater. # validate_v0.py -- the version that lied to me FIELDS = { " category " : str , " severity " : str , " needs_human " : bool , " summary " : str } def validate_v0 ( payload : dict ) -> list [ str ]: errors = [] for key , expected in FIELDS . items (): if key not in payload : errors . append ( f " missing { key } " ) elif not isinstance ( payload [ key ], expected ): errors . append ( f " { key } is { type ( payload [ key ]). __name__ } " ) return errors Do you see what is missing? Nothing checks the values . severity: str accepts "high" and "P1" and "HIGH " with a trailing space, and all three pass the same test. My validator was answering "is this a string" when the report needed "is this one of three levels". Hour 6–18: moving to the free server and 19 quiet repairs I moved the batch onto MonkeyCode's free server option, which is where the overnight run was supposed to live, and used its free model access for the extraction step. Disclosure: This article was prepared as part of MonkeyCode's product outreach. I treat both of those as conveniences rather than guarantees, which is why nothing below hardcodes a model name, a quota, or a machine size. The only thing I actually rely on is that a call returns text, and that text usually contains a JSON object. Nineteen of six hundred responses failed to parse, so I added a repair loop with a budget of one extra call. Nineteen became zero, the job exited 0, and I went to bed feeling clever. Two thirds of the rows said high , medium , or low , and the rest said P1 , Sev-2 , and one memorable critical! . No exception fired, no row was dropped, and the chart at the top just looked like a bad week. This is the failure mode I keep relearning: a schema that only checks structure will happily certify a semantic regression . The model had not broken. My contract had never specified the value domain, so the model was free to answer the question it thought I asked. What would you have checked at hour 18? I checked row counts, because row counts are the thing that goes wrong in demos. Row count was perfect. Hour 30–42: the artifact I should have written first I spent the next twelve hours building a shape checker, and it is the only part of this project I would keep. The idea is simple: fingerprint the structure of every response, pin the domain of every enumerated field, and make any deviation a non-zero exit code. 1. Hour 42–48: three live runs and the second drift On the second live run, needs_human came back as the string "false" on four rows. Under my old validator that would have been a truthy string that marked everything as needing a human. Under the new contract it was a retyped path, exit code 2, and a one-line message on the terminal. Three runs later I had a golden set of forty responses, a contract that fails loudly, and a repair budget I could tune without lying to myself about failure rates. Nothing about that is clever, and that is exactly the point. Decision table: repair, retry, or fail closed This is the table I wish I had written on hour one. Every time I let a validator "fix" a value, I created a bug that took longer to find than the original failure did. What I would repeat, and what I would throw away Repeat: writing the contract before the prompt, saving raw responses with hashes, replaying fixtures offline, and splitting exit codes by failure class. Throw away: the repair-on-any-error loop, the str -typed enums, and the row-count smoke test that told me nothing. I would also keep the free tier for what it is good at — a nightly batch at this size, on a machine I do not have to own. It is not a plan for ten times the volume, and I have not tested what happens then. Limitations and who should skip this Three honest limits. A fingerprint detects change, not correctness. If the model returns the wrong category with the right shape, this harness passes it. The domains are hand-written. {"billing", "bug", "account", "other"} came from reading fifty files, so it is a guess with a changelog. The fixtures are a snapshot. Forty saved responses are evidence about those forty responses, not a distribution. Skip this if you read every output yourself, or if your provider offers a strict schema mode you can enforce at generation time — that is a stronger guarantee than a post-hoc checker. Skip it too if the output reaches customers without a human seeing it first, because a contract test is not a review process. If you only take one thing: write down the shape and the allowed values before you write the prompt, then make drift fail the build. Your future self gets to sleep through the night, and that is worth twelve hours of anyone's weekend.
