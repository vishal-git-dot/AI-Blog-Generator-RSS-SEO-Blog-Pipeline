# Verify a company by name in 3 API calls (curl + Python)

Onboarding forms collect a company name, and company names are messy. "Infosys Ltd", "INFOSYS LIMITED" and "Infosys" might be the same company, or they might not. In this tutorial we'll take a typed name and go to a single verified record in three HTTP calls, using the Data Galactica API. Each call is shown with curl and with Python. Errors and not-found answers are free, and so are a few lookup endpoints, including the one in Call 1. export DG_API_KEY = "your_key_here" The base URL is https://api.datagalactica.com/api/v1 , and the key goes in an Authorization: Bearer header. Call 1 (free): see who shares the name Before you verify anything, see how many records share the name. /suggest is a free typeahead endpoint and doesn't need a key: curl "https://api.datagalactica.com/api/v1/suggest?q=infosys&type=company" The first three results when I ran it: DGC-8SFS42RSWAX9 gold Infosys Limited Bangalore, India DGC-QH4XM7Q9189S bronze Infosys Kolkata, India DGC-36DSG3SV65YH bronze Infosys Faridabad, India This is the whole reason to verify. All three are called "Infosys", and only one is the IT company. The grade (bronze, silver, gold, verified) describes the contact details the registry holds, not whether two records are the same entity. Data Galactica's own notes for developers say exactly this, and use these Infosys records as the example. To tell records apart, use the place, the identifiers and the sources. DGC- means an organisation and DGP- means a person. A Galactica ID doesn't change once it's issued. Call 2: verify what the customer typed /verify/company takes the typed name plus whatever else you have (country, city, website) and returns a verdict: curl -H "Authorization: Bearer $DG_API_KEY " \ "https://api.datagalactica.com/api/v1/verify/company?name=Infosys+Ltd&country=IN&website=infosys.com" A trimmed response, from the API documentation: { "ok" : true , "data" : { "verdict" : "match" , "confidence" : 1 , "operating" : true , "match" : { "id" : "DGC-8SFS42RSWAX9" , "name" : "Infosys Limited" , "status" : "operating" , "quality" : "gold" }, "checks" : { "name" : { "ok" : true , "score" : 1 }, "country" : { "ok" : true }, "website" : { "ok" : true } }, "candidates" : [ ... ] } } Three fields matter here. verdict gives the answer, checks shows which of your fields agreed, and operating tells you whether the company is still trading. If the verdict is possible_match , the developer guidance is to show the candidates to a person and stop, not to pick one automatically. Call 3: fetch the full record by Galactica ID Store the ID, not the name. Then fetch the record: curl -H "Authorization: Bearer $DG_API_KEY " \ "https://api.datagalactica.com/api/v1/company/DGC-8SFS42RSWAX9" { "ok" : true , "data" : { "id" : "DGC-8SFS42RSWAX9" , "name" : "Infosys Limited" , "status" : "operating" , "founded" : "1981-07-02" , "identifiers" : { "cin" : "L85110KA1981PLC013115" , "lei" : "335800TYLGG93MM7PR89" , "wikidata" : "Q26989" }, "quality" : { "overall" : "gold" } } } The same endpoint accepts other identifiers in place of the Galactica ID. /company/L85110KA1981PLC013115 (the Indian CIN) gets you the same record, and so do the LEI, a UK company number, a US SEC CIK or a Wikidata ID. So if your CRM stores CINs and your finance system stores LEIs, both resolve to one key.
