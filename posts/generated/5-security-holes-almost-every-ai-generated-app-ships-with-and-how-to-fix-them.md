# 5 Security Holes Almost Every AI Generated App Ships With (And How to Fix Them)

## Overview

AI app builders like Lovable, Bolt, and v0 are impressive. You describe what you want, wait a few minutes, and get a working app that looks ready for real users. It is not ready for real users. I'm Alon Trifonov, founder of Zyntari, a small engineering studio in Israel. A big part of my job is taking AI-generated prototypes and turning them into production software, mostly Python and Flask on the backend. After auditing a bunch of these apps, I keep finding the same five security holes. Not exotic, movie-hacker stuff. The boring classics: the kind that show up in the OWASP Top 10 year after year because developers keep making the same mistakes. Now AI generators are making those same mistakes at scale. Every one of them is fixable in under an hour. Here is what to look for, how to check if your app has the problem, and exactly how to fix it. 1. Debug mode left on Open the main file of your generated app. If you see this, you have a problem: if name == " main ": app.run(debug=True) Why it's dangerous: debug=True enables the Werkzeug debugger, an interactive Python console that runs in your browser. If it ever reaches a live server, anyone who triggers an error in your app gets a console that can run arbitrary code on your machine. The Werkzeug documentation says it in plain words: "the debugger must never be used on production machines." This is not a theoretical risk. In 2015, Patreon, a company with millions of users, left the Werkzeug debugger publicly accessible. Security researchers at Detectify warned them about it, and days later attackers walked in through exactly that hole and dumped 15 gigabytes of user data online, including 2.3 million email addresses. How to check: search your whole codebase for "debug". Every match should end up controlled by the environment, never hardcoded. The fix: import os if name == " main ": app.run(debug=os.environ.get("FLASK_DEBUG", "false").lower() == "true") And in production, don't use Flask's built-in server at all. Use Gunicorn: gunicorn -w 4 -b 0.0.0.0:8000 "app:create_app()" 2. Secrets sitting directly in the code Generated code loves this pattern: app.secret_key = "super-secret-key-123" STRIPE_API_KEY = "sk_live_..." Why it's dangerous: anything committed to a Git repository should be treated as public. Yes, even in a private repo, because repos get shared, cloned, screenshotted, and pushed by accident. GitGuardian scans every public commit on GitHub, and their State of Secrets Sprawl 2026 report found 28.65 million new hardcoded secrets pushed to public GitHub in 2025 alone, up 34% year over year. Worse for us specifically: AI-assisted commits leaked secrets at roughly double the baseline rate. How to check: grep -rInE "(secret|api[_-]?key|password|token)\s*=\s*[\"']" . --include="*.py" If that command prints anything that looks like a real value, that is your to-do list. The fix: secrets come from the environment, never from source code: import os app.secret_key = os.environ.get("SECRET_KEY") if not app.secret_key: raise RuntimeError("SECRET_KEY is not set. Refusing to start insecurely.") Generate a proper key: python -c "import secrets; print(secrets.token_hex(32))" Then set it wherever you deploy. Render, Railway, and Docker all have an environment variables section for exactly this. And if a secret already leaked: rotate it. Deleting the commit does nothing. The value already lives in the repo history and in every scanner's database. 3. SQL injection hiding in "dynamic" queries Generators usually do the right thing and use an ORM like SQLAlchemy. The trouble starts when the AI needs something "dynamic," like a search filter, and reaches for string formatting: email = request.args.get("email") query = f"SELECT * FROM users WHERE email = '{email}'" result = db.session.execute(query) Why it's dangerous: that f-string is a door directly into your database. A user who types ' OR '1'='1' -- as their email just bypassed your login. Injection has been in the top three of the OWASP Top 10 for over two decades, precisely because one formatted string is all it takes. How to check: search for f", %, or .format( on the same line as execute(. Any hit is a red flag. The fix: pass values as parameters and let the driver escape them: from sqlalchemy import text email = request.args.get("email", "") result = db.session.execute( text("SELECT * FROM users WHERE email = :email"), {"email": email}, ) Or stay fully in the ORM, which is even simpler: user = User.query.filter_by(email=email).first() Rule of thumb: if you ever see an f-string inside a database query in AI-generated code, review the entire file. Where there is one, there are usually more. 4. Login endpoints anyone can hammer forever A typical generated login route looks fine: @app.route("/api/login", methods=["POST"]) def login(): user = User.query.filter_by(email=request.json["email"]).first() if user and check_password(request.json["password"], user.password_hash): return jsonify(token=create_token(user)) return jsonify(error="invalid credentials"), 401 The problem is what it doesn't do: it lets anyone try passwords as fast as their machine can send requests. No limit, no slowdown, no lockout. Weak passwords fall in hours. How to check: look at your login endpoint and ask a simple question. What stops someone from sending ten thousand requests? If the answer is "nothing," that is the hole. The fix: rate limit the sensitive endpoints. Flask-Limiter makes it a two-line change: from flask_limiter import Limiter from flask_limiter.util import get_remote_address limiter = Limiter(get_remote_address, app=app, storage_uri="redis://localhost:6379") @app.route("/api/login", methods=["POST"]) @limiter.limit("5 per minute") def login(): ... Five attempts per minute per IP turns "try a million passwords tonight" into "try a few thousand over days." Most attackers just move on. Do the same for registration, password reset, and any endpoint that sends emails or SMS. Those are abuse magnets too. And make sure passwords are stored with bcrypt or argon2, via Werkzeug's generate_password_hash, never plain text or fast hashes like MD5. 5. No security headers at all Open your browser's developer tools, go to the Network tab, and click any response from your app. If you don't see headers like Content-Security-Policy or Strict-Transport-Security, your app is telling browsers "trust everything, embed me anywhere." Why it's dangerous: without a Content-Security-Policy, one reflected XSS, meaning a malicious script sneaked in through user input or a crafted link, runs with full access to your users' sessions. Without X-Frame-Options, an attacker can embed your app inside their own page and trick users into clicking things they can't see. That is clickjacking. Flask deliberately does not set these headers for you, and generators quietly skip the step. The fix: one extension, about ten lines: from flask_talisman import Talisman Talisman( app, content_security_policy={ "default-src": "'self'", "script-src": "'self'", "style-src": "'self'", }, force_https=False, # let your reverse proxy (Nginx/Cloudflare) handle HTTPS ) If your app legitimately needs external scripts like analytics or payment widgets, add those specific domains to the policy instead of disabling it. The bigger picture None of this is really the AI's fault. Generators optimize for "does it run and does it look right." Security is invisible until the day it fails, so it gets skipped by default. Every generated app needs one deliberate hardening pass before real users and real data touch it. One hour, one checklist: No debug=True anywhere near production No secrets in code. Environment variables only, and rotate anything that ever leaked No f-strings or string formatting inside database queries Rate limits on login, registration, and reset endpoints Security headers via Flask-Talisman Bonus: passwords hashed with bcrypt or argon2, and dependencies scanned regularly My rule of thumb, and the mindset behind everything we ship at Zyntari: treat AI-generated code like code from a fast, talented junior developer who has never been on call during a breach. A great starting point, never the finished product. Review the auth, review the queries, review the secrets. Then ship.
