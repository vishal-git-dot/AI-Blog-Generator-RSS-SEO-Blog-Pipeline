# FastAPI: clasifica fallos de email sin reintentar a ciegas

## Overview

En una API que envía emails, el reintento suele parecer la solución más fácil: si la entrega falla, esperamos un poco y repetimos. El problema aparece cuando tratamos igual un timeout, una dirección inválida y una bandeja temporal que todavía no ha recibido el mensaje. El sistema insiste, aumenta el ruido y al final nadie sabe qué ocurrió realmente. En proyectos con FastAPI me resulta más útil clasificar el fallo antes de decidir la siguiente acción. Así una automatización puede reintentar un problema transitorio, detenerse ante un error permanente y dejar el caso en revisión cuando falta información. Es un cambio pequeño, pero hace que las APIs sean más previsibles. El error no siempre merece otro intento Hay tres familias que conviene separar desde el principio: Transitorio: timeout, conexión reiniciada o respuesta 5xx del proveedor. Puede merecer un reintento con límite. Permanente: formato inválido, dominio inexistente o credenciales rechazadas. Repetirlo no lo arregla. Indeterminado: el proveedor aceptó la solicitud, pero la respuesta se perdió. Aquí hace falta una consulta de estado o una clave de idempotencia. El objetivo no es adivinar el futuro. Es evitar que el código convierta cualquier excepción en una orden de “hazlo otra vez”. Una función de dominio puede devolver una decisión clara: retry , stop o review . Primero se comprueba el límite de intentos y después el tipo de respuesta. Si no, un proveedor que devuelve 503 puede generar una cadena de reintentos infinita. El backoff es sencillo a propósito; luego se le puede añadir un poco de jitter para que varios workers no vuelvan al mismo tiempo. Un aviso de email con contexto real necesita decir qué evento falló, qué intento era y qué acción se tomó. La interfaz que consume la API no debería recibir solo “error 500”. Registra la decisión, no solo la excepción Para depurar una automatización, guardaría al menos estos campos: delivery_id, event_id, attempt, provider_status, classification, next_action, retry_after, created_at No conviene registrar el contenido completo del mensaje ni tokens de acceso. Un identificador de evento y una razón corta suelen bastar. Si el test usa un temp org mail o un dummy e mail , la fixture debe quedar aislada del correo real y tener una caducidad conocida. Para comprobar la bandeja, puedes aplicar polling de inbox con límites sanos . Q&A: dudas habituales ¿Debo reintentar todos los errores 5xx? No necesariamente. Un 5xx suele ser transitorio, pero el proveedor puede estar rechazando una operación por saturación o por una cuota. Usa un máximo de intentos, backoff y una ruta de revisión. Si existe un encabezado Retry-After , úsalo dentro de un límite razonable. ¿Qué hago si no recibo respuesta? Trátalo como indeterminado. Antes de enviar otra vez, consulta el estado con un identificador idempotente. Duplicar un email porque se perdió la respuesta es peor que tardar unos segundos en confirmar. Checklist de implementación Define las categorías transitorio, permanente e indeterminado. Pon un límite de intentos fuera del proveedor. Devuelve una acción explícita: reintentar, detener o revisar. Registra evento, intento y decisión sin guardar datos innecesarios. Añade backoff y, cuando aplique, Retry-After . Prueba una secuencia 5xx → éxito y otra con error permanente. Establece un timeout para cada polling y para el flujo completo. La automatización de email no necesita más reintentos, sino mejores decisiones. Cuando FastAPI expone un contrato pequeño y cada fallo deja evidencia suficiente, los workers pueden recuperarse sin ocultar los casos que necesitan atención humana.
