# Guarding CI Pipelines with Dependency Release Age Gates

## Overview

When an attacker compromises a package maintainer's credentials or publishes a typo-squatted package to PyPI or npm, the malicious release is immediately visible to automated tooling. Continuous integration pipelines, automated upgrade bots, and routine builds that pull the newest pinned dependencies will fetch and execute that code right away. In most cases, malicious releases are identified and yanked within a few days once security monitors and maintainers notice the compromise. However, if your automated builds pull new releases the moment they appear, your environment acts as the test bed during that dangerous early window. A dependency release age gate solves this by enforcing a cooldown period. By auditing dependency manifests and lockfiles to verify that every pinned package has existed in the public registry for a minimum number of days, you introduce a buffer period where bad releases can be caught before your build consumes them. The Problem Development workflows frequently update lockfiles through automated bots or manual upgrades. When dependencies update immediately to a release published only hours earlier, the build takes on unvetted supply chain exposure. Common threats during this early window include: Compromised developer accounts publishing malicious minor or patch updates. Fast package takeovers where existing package names are hijacked. Accidental breakages or incomplete releases that get replaced shortly after publishing. To mitigate this without completely halting updates, pipelines need an automated verification step: checking the upload timestamp of pinned dependencies against a cooldown policy. If an update is too young, the pipeline should flag it and recommend an older, verified version that meets the cooldown requirement. Install & Usage The tool is implemented as a self-contained Python script. It relies exclusively on the Python standard library, requiring no external packages from package managers. Installation Download the script file and place it in your project repository under the name depcooldown_dependency_release_age_gate.py . The script runs on standard Python. If you are running Python 3.11 or later, it uses the built-in tomllib module to read TOML files. If you run an earlier Python release, it uses an internal fallback parser to process package definitions from lockfiles. Limitations Before deploying the script into your automation, keep the following structural limitations in mind: Strict Pinning Requirement : The parser only evaluates exact equality pins ( == ). Flexible ranges such as >=1.2.0 , ~=2.1 , or caret dependencies in manifests are ignored unless resolved into a concrete lockfile like poetry.lock or package-lock.json . Simplified Version Parsing : Version comparison relies on parse_semver , which splits versions into major, minor, patch, and prerelease components. Complex PEP 440 specifications (such as post-releases, epoch numbers, or local versions) are parsed as zero-fallbacks or plain integers rather than strictly compliant PEP 440 objects. Minimal TOML Fallback : When running on Python versions older than 3.11 without tomllib , the script falls back to a basic line-by-line parser. While this fallback handles standard [[package]] entries in Poetry and uv lockfiles, complex or nested TOML structures may fail to parse. Registry Unavailability : If the registry metadata endpoint is unreachable, timed out, or blocked by a proxy, the tool returns an unverified status for that dependency rather than aborting. FAQ Can this tool be run in an environment without internet access? Yes. The RegistryClient supports an offline mode and local JSON cache files. If metadata was previously fetched and cached to disk, the script evaluates dependencies directly against the stored JSON cache without performing network calls. How does the script handle npm scoped packages? The script handles scoped npm packages (for example, @scope/package ) by preserving the @ character while percent-encoding the path separator when querying the npm registry endpoint. What happens if a brand-new package has no versions meeting the cooldown threshold? If a package is entirely new and none of its released versions were published before the cutoff threshold, the tool flags the pinned version as a cooldown violation and leaves the suggested version empty, indicating that no safe historical release exists in the registry.
