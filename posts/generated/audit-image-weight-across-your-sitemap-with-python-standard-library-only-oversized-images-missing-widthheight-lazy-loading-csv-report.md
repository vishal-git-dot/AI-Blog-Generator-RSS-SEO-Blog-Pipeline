# Audit Image Weight Across Your Sitemap with Python (Standard Library Only): Oversized Images, Missing Width/Height, Lazy Loading, CSV Report

## Overview

Image weight creeps up quietly. Someone uploads a 3000 pixel PNG straight from a design tool and the CMS shows it at 600 pixels wide. A theme update adds loading="lazy" to every image, including the hero at the top of the page. A gallery block drops the width and height attributes, so the text jumps down as each photo arrives. None of this breaks a page. It just makes it slower and jumpier, one upload at a time. This post builds an image weight auditor in Python using only the standard library ( urllib , urllib.robotparser , html.parser , xml.etree , struct , csv , concurrent.futures ). It reads your sitemap or sitemap index, fetches every page, collects each <img> , and checks every unique image once. It gets the file size from a HEAD request's Content-Length and falls back to downloading the file when the server refuses HEAD or sends no length. It reads the real pixel size from the first bytes of PNG, GIF, JPEG and WebP files, compares that with the declared width , flags images with no width / height , and checks how loading="lazy" is used. Output is a CSV with one row per image per page, a console summary with the heaviest pages, and an exit code you can use in CI. web.dev's Browser-level image lazy loading for the web and Optimize Cumulative Layout Shift (showing "Last updated: Feb 7, 2025"), Chrome for Developers' Properly size images Lighthouse page, and Google Search Central's image SEO best practices (showing "Last updated 2026-03-02 UTC") were opened on 17 Nov 2026, and every statement attributed to them below comes from those pages. What the guidance actually says (and what it does not) Size. Google's image SEO page says "images are often the largest contributor to overall page size, which can make pages slow and expensive to load," and asks you to "apply the latest image optimization and responsive image techniques." The web.dev lazy loading article cites the HTTP Archive: images "usually take up more bandwidth than any other resource," and "At the 90th percentile, sites send over 5 MB of images on desktop and mobile." Pixels versus display size. Lighthouse's Properly size images page explains how it decides an image is too big: it "compares the size of the rendered image against the size of the actual image," accounting for device pixel ratio, and fails the image "If the rendered size is at least 4KiB smaller than the actual size." The page now carries a warning that this audit "has moved into the Improve image delivery insight as of Lighthouse 13." The principle is unchanged: "your page should never serve images that are larger than the version that's rendered on the user's screen." Width and height. The Optimize CLS article lists "Images without dimensions" first among "The most common causes of a poor CLS," and says: "Always include width and height size attributes on your images and video elements. Alternatively, reserve the required space with CSS aspect-ratio or similar." Modern browsers use those attributes to set a default aspect ratio before the image loads, so width: 100%; height: auto in CSS still works with them. Lazy loading. The lazy loading article describes loading="lazy" as deferring an image "until it reaches a calculated distance from the viewport," and gives a clear caution: "Don't lazy-load images that are likely to be in-viewport when the page loads, especially LCP images." It also notes that without width and height an image defaults to 0x0 pixels, so in a gallery "the browser might decide that all of them fit inside the viewport at the start" and load everything. What none of these pages give is a kilobyte limit for a single image. The script's default of 200 KB is my own starting line, not a Google or Lighthouse number. Change it with --max-kb and keep it the same between runs. The pixel check uses 2x the declared width by default ( --max-scale ) so that images exported for high density screens are not flagged. And the script cannot know where the fold is. It does not render the page, so it treats the first two images in the HTML as "probably above the fold" ( --eager-first , default 2, because a header logo is usually image one and the hero is image two). How the audit works Sitemap URLs. It reads a urlset or a sitemap index (recursively, gzip supported) and keeps every <loc> . robots.txt is respected for page fetches. Images per page. It parses each page's HTML and collects every <img> in document order. Markup inside <script> , <style> , <template> and <noscript> is ignored, since lazy-load plugins often put a duplicate <img> in <noscript> . If src is empty or a data: placeholder and data-src is set (the classic JavaScript lazy-load pattern), the data-src URL is audited and the loading column says data-src . One probe per unique image. A logo used on 500 pages is fetched once. The probe sends HEAD and reads Content-Length . If HEAD returns 405 or 501, or the response has no length, it downloads the file in 64 KB chunks and counts the bytes. The size_from column tells you which happened. Pixel size from the header bytes. When the size came from HEAD , it sends a GET with Range: bytes=0-65535 and reads at most 64 KB, which is enough to find the dimensions in PNG, GIF, WebP and almost every JPEG. If the server ignores Range , the script still stops reading after 64 KB. --no-dimensions skips this step for a HEAD -only run. Checks per image tag. Size, pixels and attributes are compared per tag, because the same file can be fine on one page and oversized on another. What the script flags heavy : Meaning: File is larger than --max-kb (default 200 KB); What to check: Compress, switch format, or resize oversized_pixels : Meaning: Pixel width is more than --max-scale (default 2) times the declared width , and the tag has no srcset or <picture> ; What to check: Export at the size it is shown, or add srcset missing_dimensions : Meaning: No numeric width and height attributes, and no inline style with aspect-ratio or both width and height ; What to check: Add the attributes from the real pixel size lazy_above_fold : Meaning: One of the first --eager-first images has loading="lazy" ; What to check: Remove it from the hero; web.dev says not to lazy-load in-viewport images not_lazy : Meaning: An image after the first --eager-first has no loading="lazy" (and no data-src ); What to check: Add loading="lazy" if it starts below the fold image_http_404 (or other code) / image_fetch_failed : Meaning: The image did not load; What to check: Fix the path or remove the tag inline_or_empty_src : Meaning: src is empty or a data: URI with no data-src ; What to check: Check what the tag is for http_404 / blocked_by_robots / fetch_failed : Meaning: The page itself did not load or is disallowed; What to check: Fix the page or remove it from the sitemap Two limits to know up front. The script sees only the HTML your server returns, so images injected by JavaScript and CSS background images are not in the report. And a class-based CSS rule that sets aspect-ratio on images will not be seen, so missing_dimensions may list images that are actually fine. Google's image page also notes that Google "doesn't index CSS images," which is one more reason to use real <img> tags for content images. The script Save as image_weight.py . On a site with thousands of images, downloading every file to measure it is slow and costs the host bandwidth. Content-Length from HEAD is free. The download fallback is there because some CDNs and image proxies reject HEAD or stream responses with no length. Why only the first 64 KB for pixels. Every supported format puts its dimensions in the first few bytes, except JPEG, where the size sits in the frame header after any metadata segments. A camera JPEG with a large embedded thumbnail can push that past 64 KB; those rows show an empty pixels column rather than a wrong number. SVG has no pixel size to compare, so only its byte size is checked. A 100 KB SVG icon is usually an auto-traced bitmap and worth a look even under the limit. Responsive images ( srcset or inside <picture> ) are never flagged oversized_pixels , because the browser picks the candidate. The src fallback is still weighed, so a heavy fallback still shows up as heavy . Running it on your own sitemap python3 image_weight.py https://example.com/sitemap.xml --workers 2 --out image_weight.csv Options worth knowing: --max-kb 150 changes the size line. Pick one and keep it fixed so CSVs from different weeks compare. --max-scale 1.5 is stricter on pixels. Leave it at 2 if a lot of your traffic is on high density phones. --eager-first 1 if your pages have no image logo, or 3 if a header logo, a badge and a hero all come first. --no-dimensions skips the ranged GET and is the lightest run you can do. Sizes still fall back to a download where HEAD gives nothing, so on a CDN that rejects HEAD the run downloads those images in full. --workers 2 keeps the load polite. Images on a third-party CDN are fetched too, so a big site means a lot of requests. Sort the CSV by kb , then filter flags . Images shared across templates (a hero background, a footer badge) show up on every page, so fix those first: one export fixes hundreds of rows. Exporting at the displayed width (or 2x for high density screens) is usually the biggest single saving. Lighthouse's page names responsive images, image CDNs and SVG for icons as the main strategies, and Google's image page shows srcset and <picture> with a src fallback. Then heavy . Re-encode in a modern format and compress. Google Search supports BMP, GIF, JPEG, PNG, WebP, SVG and AVIF in img src , per its image page, so WebP and AVIF are safe choices. Fix lazy_above_fold before not_lazy . A lazy hero delays the image people see first. web.dev says to use the browser's default eager loading for images visible on load, "especially for LCP images," and to raise priority with fetchpriority="high" if needed. Add width and height everywhere. Take them from the pixels column (or the display size, keeping the aspect ratio). Keep height: auto in your CSS so the image still scales. Then add loading="lazy" to images further down. Keep each image's width and height , so lazy images in a gallery do not all count as in the viewport at 0x0. Rerun and diff. Keep each CSV. A page that jumps from 600 KB to 6 MB between deploys is usually one new upload. Extending it Weigh every srcset candidate. Parse srcset into URL and width pairs and probe each, so you can see the bytes a phone actually downloads. Check the rendered size. For an exact Lighthouse-style comparison you need layout, which means a headless browser. The script's declared-width check is a cheap proxy. Add response headers. Cache-Control and Content-Type are already on the HEAD response. Flag images with no caching or with a type that does not match the file extension (Google's image page recommends they match). Fail CI on regressions only. Compare kb per image URL with the previous run and fail when a page's total grows by more than a set percentage. FAQ What is a good maximum size for one image? None of the pages cited here give one. The script defaults to 200 KB as a starting line. Heroes and product photos often need more than icons and thumbnails, so some teams run the script twice with different limits, or filter the CSV by page section. Why use HEAD instead of downloading everything? Content-Length from HEAD gives the size without transferring the file, which matters when a sitemap references thousands of images. The script downloads only when HEAD is refused or has no length, and the size_from column shows which images that was. Does Content-Length match what the browser downloads? It is the size of the response the server sent to the script. With compression or an image CDN that serves WebP or AVIF based on the browser's Accept header, a browser can receive a different file. Send the same Accept header your users' browsers send if you want to measure what they get. Should every image have loading="lazy" ? No. web.dev says not to lazy-load images that are likely to be in the viewport on load, especially the LCP image. That is why the script flags lazy images among the first two and only suggests loading="lazy" for the rest. Do width and height stop images from being responsive? No. The Optimize CLS article explains that browsers use the attributes to compute an aspect ratio, and CSS like width: 100%; height: auto still sizes the image to its container. Can I run it in CI? Yes. It exits 1 when anything is flagged, 0 when clean and 2 when the sitemap cannot be read. Run it against staging with the limits you settled on. Wrap-up Image weight is one of the few performance problems you can audit from a sitemap without a browser. A HEAD request gives the bytes, the first few kilobytes of the file give the pixels, and the HTML gives the declared size and the loading attribute. Put those together per page and the CSV shows exactly which upload made which page heavy, which hero is waiting on lazy loading, and which gallery is still shifting text around.
