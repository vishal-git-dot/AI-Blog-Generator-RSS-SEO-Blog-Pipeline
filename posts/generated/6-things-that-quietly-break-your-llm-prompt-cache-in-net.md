# 6 Things That Quietly Break Your LLM Prompt Cache in .NET

## Overview

I had a support bot that sent the same 1,300-token system prompt on every request, and I assumed the provider's prompt cache was doing its job. OpenAI and Azure OpenAI cache long prompt prefixes automatically, and for the models I priced, cached input costs a tenth of normal input. Free money, as long as the cache actually hits. Mine didn't. When I finally measured it, only 7% of my input tokens were cached. The cause was one friendly line at the top of the system prompt: Today is 2026-11-13 09:14:07 UTC. You are helping Acme Robotics. That line fixed nothing and broke two things at once. It's also not the only way to lose the cache without noticing. Anything that changes a single byte early in the prompt makes everything after it a miss. So every breaker below is a variation of "something early in the prompt isn't the same as last time". 1. A timestamp (or GUID, or request id) in the system prompt The classic. "Today is ..." with seconds in it gives you a brand-new prefix every second. Request ids and GUIDs do the same thing per request. How it shows up: cached tokens near zero, even though "the prompt never changes". Fix: keep the date if the model needs it, just move it. Everything that changes goes into the last user message, inside a small context block. A regex check for ISO dates, clock times, GUIDs, long numbers and phrases like "today is" catches the well-meant "let's add the date" pull request before it ships. 2. Tenant or user text inside the shared prefix "You are helping Acme Robotics." looks harmless. But now Acme's prefix and Globex's prefix differ from the first sentence. At best you get one cache per tenant instead of one for everyone. At worst it's a smell that customer data is mixing into what should be shared instructions. How it shows up: the hit rate looks fine for your biggest tenant and terrible for everyone else. Fix: same as #1. The customer name and plan belong in the last message. In my linter, any tenant display name found inside the stable prefix is an error, not a warning. 3. A prefix that's too short to be cached at all This one is sneaky because the prompt is perfectly stable. It's just under the provider's minimum cacheable length, so caching never applies. Worse: a prompt sitting just above the minimum can drop under it after one small edit, and nobody notices. How it shows up: zero cached tokens on a prompt that never changes. Fix: know your prefix size in tokens (count it with the same tokenizer family the model uses), and warn when it's under the minimum or within one 128-token step of it. Sometimes the right fix is putting genuinely useful stable material in there, like a support handbook. Sometimes it's accepting that this prompt won't cache. Exactly the two problems in that one line. 4. Rewriting earlier turns of the conversation Multi-turn chat caches beautifully when history is append-only: the whole previous request is a prefix of the next one. It falls apart when the app "tidies up" earlier messages, re-summarises history every turn, or injects something new near the top. Same goes for putting anything in front of the stable system messages. How it shows up: good cache hits on turn one, then mysteriously worse as the conversation gets longer, which is exactly when caching should help the most. Fix: stable messages first, then history exactly as it was sent, then the new message. If you must compact history, accept that the next request is a cold start and do it rarely. 5. Switching models mid-conversation This is the one that surprised me. The prompt cache is per model. OpenAI's cache diagnostics even list model_changed as a miss reason. So if a cheap model answered turn three and the big model answered turn four, turn five on the cheap model starts cold. That matters the moment you add any kind of routing, like a small-model-first cascade. A "cheaper" model with a cold cache can cost more than staying on the model that already has the whole conversation warm. How it shows up: routing saves less than the price list says it should. Fix: make the router cache-aware. Predict cached tokens per candidate model before the call, compare expected costs, and stay on the warm model when that's cheaper. No cache key, or one key doing all the work prompt_cache_key helps the provider route requests with the same prefix to the same cache. Without it, hits can be patchier than they need to be. With a single key for all traffic, you can overload it: OpenAI suggests roughly 15 requests per minute per prefix and key combination.
