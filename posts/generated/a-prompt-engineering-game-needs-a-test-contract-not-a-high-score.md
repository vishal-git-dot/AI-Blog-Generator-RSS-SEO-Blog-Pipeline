# A Prompt Engineering Game Needs a Test Contract, Not a High Score

## Overview

The short answer An AI learning game should not award a “best prompt” score because one answer happened to look impressive. It should teach a repeatable decision: state the task, provide the context that matters, define what a useful answer must contain, and check the result against that rubric. Then it should let the player see why the answer passed or failed. A score without that explanation is entertainment, not evidence of learning. This matters especially for a prompt-engineering game. A player can win by writing a longer instruction, guessing the author’s preferred wording, or exploiting a scoring rule that has little to do with using an AI system at work. The game becomes more useful when each challenge names the model and version, gives an input and a deliberately difficult case, and checks observable output properties rather than the number of words in the prompt. The companion AI-DUE mini-games page already offers short exercises for neural networks, RAG ordering, AI concepts, and prompt engineering. The gap this article addresses is the missing “what makes a run good?” layer: a reusable test contract that a learner, teacher, or game builder can inspect, replay, and update when the model changes. The recommendation is to ship a small challenge set and a transparent scoring rubric before adding levels, badges, or a leaderboard. Treat model output as variable; treat the game’s acceptance rules as versioned product data. Do not claim that a game improves skill until you have actually measured a defined learning outcome with real participants. That gives a visitor a quick reason to click and a rough difficulty signal. It is a useful entry point, but it does not tell the player which dimension of prompting the challenge is testing, what counts as a valid answer, or how the game handles different models. That distinction is where an educational mini-game can add value. The unresolved buyer and learner question A public discussion in the Google AI Developers Forum describes a user’s system prompts behaving differently after an update and asks whether a silent change had occurred. That is an anecdote, not a measured rate of model regressions. It nevertheless surfaces a practical question for a learning game: if a challenge depends on a model response, what should the learner or teacher be told when model behavior changes? The forum thread is a useful example of the uncertainty people encounter; it cannot establish how common the problem is. The product implication is modest but important. A prompt game should not imply that the same wording yields identical output forever. It should show the tested model and date, separate stable rubric criteria from variable phrasing, and keep an example of a known failure. This turns a vague complaint—“it stopped working”—into a testable update question: which case changed, which criterion failed, and does the game need a new hint, an updated example, or a different model configuration? This is also a useful question for anyone who might reuse a prompt beyond the game. The game should train learners to ask for evidence: model/version, expected and invalid inputs, an example run, the acceptance check, and known limitations. A screenshot of a polished output is not a substitute for those controls. Start with a skill, not a prompt length Before writing a challenge, choose one behavior that can be observed. “Be better at prompting” is too broad to score. “Ask for a structured answer with exactly three fields and mark unknown information as unknown” is observable. “Avoid hallucinations” is not a complete acceptance test until you define which claim can be checked and what the system should do when evidence is absent. The skill statement should identify the player’s decision, the context they receive, the expected response shape, the evidence the response must use, and the failure the game is designed to reveal. A useful challenge makes the player choose an action, not merely recognize a vocabulary word. For example, ask a player to prepare a support reply using a small policy excerpt, then score whether the answer cites the relevant policy text, avoids inventing a refund commitment, and marks an unanswered detail for a human. Keep “prompt quality” separate from “output quality.” A clear prompt can still produce a weak output because of model variation, missing data, tool errors, or conflicting instructions. Conversely, a vague prompt may get a lucky answer. If the game awards points only for the final text, it can accidentally teach players to confuse luck with a reliable method. Score the reasoning steps and the outcome criteria separately, and explain the difference in the debrief. A scoring rule that can be inspected Use a small rubric whose criteria a player can understand before or after a run. One example is a four-part score: task clarity, relevant context, measurable output constraints, and a verification step. Each criterion can receive zero, one, or two points, but the number is a design choice—not an industry benchmark. A zero means the behavior is missing, one means it is present but incomplete, and two means it is explicit and usable in the case at hand. Do not reward verbosity directly. A 40-word prompt that names the task, input, and acceptance criteria can outperform a 400-word prompt containing irrelevant detail. If a game uses a model judge, make the judge’s decision explainable and give the player a non-model-based fallback rubric. A model-generated score must not be presented as ground truth merely because it is numeric. Show criterion-level feedback. “You scored 6/8” is less useful than “You stated the task and output format, but you did not say what to do when the source does not contain the answer.” If the player can revise once, preserve the first attempt, the second attempt, and the difference in criteria. Test the game loop, not just the final text A learning game has at least four things to test: the player’s prompt, the generated or selected response, the feedback loop, and the persistence of the score. A player should be able to understand the goal, make a choice, see the rule applied, and retry without the previous attempt disappearing. If an AI model generates hints, keep the scoring rule stable enough that the same rubric remains meaningful across model changes. For each challenge, record a baseline run before changing the prompt or model. Version the model, prompt, rubric, and challenge separately “The AI changed” is not a useful bug report unless the product records which component changed. Keep separate identifiers for challenge content, prompt template, rubric, model/provider, and game client. A teacher should be able to see that a challenge was authored against rubric 1.2, while a model alias may not expose a stable version. If the provider supplies no fixed identifier, record the alias and the test date; do not infer a hidden version from the response. When a provider updates a model, re-run the fixed suite and compare criterion-level results, not only exact output text. A phrasing change may be harmless if the answer still passes. A new unsupported claim or a failure to ask for missing context is more material. Keep examples that passed, examples that failed, and the decision about whether the game needs a new prompt, a clarified instruction, a rubric change, or a rollback. Do not call every difference a regression. Model outputs are stochastic or may vary due to settings, context, tool response, and provider changes. Define the observation rule in advance: for example, which rubric failures require blocking release, which trigger review, and which are accepted as natural variation. If you have not repeated a case, say so. A single output is a single observed run, not a reliable failure rate. When there is no study, say there is no study. Accessibility and fair scoring A game that measures speed, spelling, or comfort with a particular writing style may reward the wrong skill. A learner who types slowly, uses assistive technology, or writes in a second language can lose points even when they understand task framing and evidence boundaries. Decide whether the learning objective truly requires timed writing. If it does not, make the timer optional or remove it from the score. Expose keyboard controls, visible focus, readable contrast, clear error messages, and a non-color-only status cue. Let learners inspect the challenge and rubric without racing. Keep the score explanation in plain language. If the game accepts free text, provide examples of acceptable alternatives rather than requiring a single phrasing. Measure transfer, not just completion A player can finish a challenge without retaining the skill. Completion time, streak, and a high score tell you that a game interaction occurred; they do not automatically demonstrate that the learner can use the skill in a new task. If you want to make a learning claim, define an outcome beyond the game session, such as a short transfer task using a new domain and the same underlying reasoning rule. Keep the evaluation proportional. A small classroom pilot can be useful for finding confusing instructions, but it should not be described as proof of general effectiveness. Record how many people participated, what they did, what was excluded, how scoring was performed, and whether the evaluator knew which version they used. If you collect no learner data, describe the test as a design review or software acceptance test, not a learning study. Avoid turning all learner behavior into analytics by default. For school or workplace use, determine the applicable consent, privacy, and safeguarding requirements with the responsible organization before data collection. Failure modes to test before launch The word-count exploit. If the game awards points for adding constraints or detail, players may learn to write longer prompts even when the extra text conflicts. Test a concise complete prompt against a verbose but contradictory one. The rubric should reward relevant, usable information, not characters. The hidden answer-key exploit. If only one exact string passes, players can be marked wrong for a correct paraphrase. Include semantically equivalent responses and an explicit rubric for evidence, uncertainty, and format. If you cannot reliably evaluate paraphrases, keep a human review step rather than pretending the checker is smarter than it is. The confident guess. A model may fill a gap with plausible text. Include at least one case where the supplied source does not answer the question, and reward the player for saying what is missing. This is a behavior to test, not an assurance that any model will always abstain. The model-update surprise. A provider may change a model alias or response behavior. Keep a dated fixed suite, re-run it after relevant changes, and publish the observed difference without exaggerating it as a broad regression. The retry double-score. A network retry can create two submissions for one attempt. Use an idempotency key, test duplicate requests, and make retries return the first stored result. This follows the reliability distinction between safe repeated operations and work that must not run twice; it does not mean every game backend needs a distributed scheduler. The leaderboard turns into the lesson. Players may optimize for speed or points rather than thoughtful prompt design. Keep an unranked practice mode and inspect whether the scoreboard changes the behavior you intended to teach. The legal-sounding badge. A “copyright safe” or “privacy approved” label can imply a review that never happened. List actual review scope, date, and owner. Do not turn a checklist into a certification. The teacher cannot explain the score. If an educator cannot describe why an answer passed, the scoring is not ready for classroom use. Give teachers the rubric and a way to override or annotate a disputed result. Contradictions and where this recommendation fails There is a real tension between repeatability and openness. A fixed test set helps compare model versions, but publishing every answer can make the game easy to game. A hidden evaluation can reduce memorization but may make scoring opaque. The compromise is to publish the criteria and examples of the criterion, while rotating some scenario details and retaining reviewable release tests. There is also a tension between model freedom and predictable evaluation. A broad generative task can be engaging, yet it is harder to score consistently. A narrow fixed-output exercise is reproducible, yet may not teach transfer. Use an objective that genuinely requires generation; otherwise a fixed simulation or branching exercise may be safer and cheaper. A stable rubric will not make output deterministic. A model can pass one run and fail another; an updated provider model may improve some cases and worsen others. The right response may be to reduce the game’s reliance on open-ended generation, give the learner a choice of example, or make the evaluator human-reviewed. Do not promise that a version label prevents drift. Finally, legal statements in this article are limited to the cited U.S. Copyright Office and IRS materials, and Gumroad’s own current terms. They do not cover every jurisdiction, contract, platform, or type of game. A team distributing internationally should verify local consumer, tax, copyright, privacy, and child-protection rules before release. A 30-minute authoring and review protocol Minute 0–5: choose the skill. Write one sentence describing a behavior a learner can demonstrate. Name the input and the failure it should prevent. If the sentence contains “understand AI better,” make it more concrete. Minute 5–12: draft one challenge. Create a synthetic scenario, a good-enough answer, a plausible failure answer, and a rubric with no more than four criteria. Mark which facts are in the prompt and which are intentionally absent. Minute 12–18: write two adversarial variants. Add one conflicting constraint and one missing-information variant. Check whether the rubric still accepts reasonable paraphrases and rejects unsupported claims. Minute 18–24: test product state. Submit once, submit twice, refresh, and retry after a simulated network failure. Confirm the score is stored once and that the player can see which attempt was evaluated. Minute 24–30: review the claim. Ask a second person to inspect the objective, score rationale, accessibility path, and any statement about learning. If no learner study occurred, remove language implying that users learned, improved, or retained a skill. This protocol is not a validated time-and-motion study. The minutes are a facilitation format chosen to keep a design review bounded. A complex game, regulated school environment, or assessment used for employment or grading needs a more rigorous process and appropriate domain review. How to report original evidence honestly If you later publish results from this design, report what was actually tested. A useful methods note would state the date, challenge-set version, provider/model and settings, number of runs, evaluator rubric, who rated the outputs, how disagreements were resolved, what data was synthetic, and what was excluded. Include the raw challenge cases or a stable artifact hash so another reviewer can tell whether a later version changed. Do not turn “eight challenges” into a claimed sample of eight learners. It is a constructed test suite. If you run each case through a model five times, the experimental sample is forty model outputs, not forty people and not a representative estimate of performance in production. If one evaluator scores all forty, evaluator bias remains a limitation. If a product owner writes both the test and judges the answers, say so. When comparing versions, report criterion-level counts and the denominator. For example, “the newer model passed 7 of 8 authored cases in this run” describes one observed run if each case was executed once; it does not prove a 87.5% real-world success rate. Repeat enough runs for the decision, preserve failures, and state that a small test suite is a release screen, not a benchmark of every player or task.
