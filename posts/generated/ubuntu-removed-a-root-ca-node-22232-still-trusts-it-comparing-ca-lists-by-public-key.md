# Ubuntu removed a root CA. Node 22.23.2 still trusts it: comparing CA lists by public key

## Overview

On 30 October, apt on my Ubuntu 24.04 container installed ca-certificates 20260816ubuntu0.24.04.1 . Its changelog has one line that matters here: * Blacklist the following CA cert due to intermediate cert compromise (LP: #2171507) + "emSign ECC Root CA - G3" That is the root above the intermediates with tiny private keys that I wrote about in October . The system store dropped it. The question I wanted answered was narrower: what on this machine still trusts it? Answering it takes two steps. Ask each runtime which list it reads, then compare the lists by public key. Step 1: ask each runtime where it looks Python's ssl module reads whatever OpenSSL was built to read: import ssl print ( ssl . get_default_verify_paths ( ) ) ctx = ssl . create_default_context ( ) print ( ctx . cert_store_stats ( ) ) print ( any ( "emSign ECC Root CA - G3" in str ( c [ "subject" ] ) for c in ctx . get_ca_certs ( ) ) ) DefaultVerifyPaths(cafile='/usr/lib/ssl/cert.pem', capath='/usr/lib/ssl/certs', openssl_cafile_env='SSL_CERT_FILE', openssl_cafile='/usr/lib/ssl/cert.pem', openssl_capath_env='SSL_CERT_DIR', openssl_capath='/usr/lib/ssl/certs') {'x509': 120, 'crl': 0, 'x509_ca': 120} False /usr/lib/ssl/cert.pem is a symlink to /etc/ssl/certs/ca-certificates.crt , so plain ssl follows the distro: 120 roots, no G3. That stops being true the moment you pip install requests . The Requests docs say it "uses certificates from the package certifi", and certifi ships its own cacert.pem , frozen at whatever certifi version you have. Node is the interesting one. Since 22.15 it has tls.getCACertificates(type) , which returns the list for each source: bundled (the copy compiled into the binary), system , extra (from NODE_EXTRA_CA_CERTS ), and default , the list TLS clients actually use. Three things in that output matter. The default list is the bundled one. The Node docs describe it as "a snapshot of Mozilla CA store that is fixed at release time". 22.23.2 came out on 28 July (per Node's release index ), so its snapshot has G3, and no OS update can change that. NODE_USE_SYSTEM_CA=1 adds, it does not subtract. The docs for --use-system-ca say Node uses the system store "along with" the bundled one, and they are blunt about the consequence: "Node.js currently does not support distrust/revocation of certificates from another source based on system settings." So 145 bundled plus 360 system entries gives 505, which collapses to 149 distinct keys: the 145 bundled roots plus four roots that only the system store has. G3 is still in. Turning on the system store only helps with roots the bundle is missing, never with roots the distro removed. --use-openssl-ca reports an empty default list, and it still works. In that mode the default list leaves out the bundled roots, as the docs say it will, and the OpenSSL store that Node verifies against does not show up in it. So I checked that it really verifies against the system store rather than against nothing: node --use-openssl-ca -e "require('https').get('https://www.rfc-editor.org/', r => console.log(r.statusCode, r.socket.authorized))" SSL_CERT_FILE = /dev/null SSL_CERT_DIR = /nonexistent node --use-openssl-ca -e "require('https').get('https://www.rfc-editor.org/', r => console.log(r.statusCode)).on('error', e => console.log(e.code))" 200 true UNABLE_TO_GET_ISSUER_CERT_LOCALLY The 360 system entries for 120 roots are not a bug either. The docs warn that the array "may contain duplicates if the same certificate is repeatedly stored in multiple sources", and Node reads both the bundle file and the certificate directory.
