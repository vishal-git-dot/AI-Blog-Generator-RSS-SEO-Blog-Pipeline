# Google’s CDN Migration Guidance: How to Protect Crawling and Indexing

## Overview

Google has published new technical SEO guidance for websites moving to a content delivery network (CDN). The central warning is that a CDN launch can temporarily increase pressure on an origin server, including pressure from Googlebot, even when the migration is intended to improve speed and scalability. The reason is a combination of faster edge infrastructure and cold caches. When a domain begins resolving to CDN edge servers, lower latency can indicate that the host can handle more crawling. At the same time, edge caches may not yet contain requested pages. Initial requests can therefore pass through the CDN to the origin, where a higher crawl rate may create unexpected load. In its official post, Moving to a CDN without overwhelming your origin (or blocking Googlebot) , Google outlines measures intended to preserve crawlability and indexing while limiting operational risk during the transition. Why a CDN move can change Googlebot activity Google describes crawl capacity, sometimes called hostload, as the amount of crawling a site can support without harming users or server performance. Googlebot adjusts its activity using signals from the site, including response times and server behavior. A CDN can make a site appear faster to crawlers because requests are answered by nearby edge locations. That is normally beneficial. But the infrastructure change can also enable Googlebot to increase its crawl speed. If the edge cache is cold, many URLs requested for the first time will still need content from the origin. This creates a migration-specific problem: the CDN may be responding quickly, while the origin is doing more work than expected. The risk is particularly relevant for large sites with many crawlable URLs, publishers with deep archives, ecommerce stores with extensive product and category inventories, and sites that already operate close to origin capacity. The guidance is not a warning against CDNs. It is a reminder that CDN configuration, cache state, crawling, and web application firewall rules need to be planned together. Pre-warm the edge cache before routing all traffic Google’s first practical recommendation is to pre-warm CDN caches before directing all traffic through the new CDN setup. The goal is for the CDN to serve the majority of requests from edge cache rather than sending them back to the origin. Cache warming can reduce the chance that a surge of Googlebot requests becomes a surge of origin requests. It also helps protect the visitor experience if real-user traffic rises at the same time as crawler activity. The specific implementation depends on the CDN and site architecture, so Google does not prescribe a universal cache-warming process. Teams should instead determine which URLs are important to cache, how cache keys and expiration rules work, and whether dynamic pages can safely be served from edge cache. For SEO, priority pages commonly include: Key landing pages, categories, and product pages. Important editorial pages and evergreen content. URLs that are frequently crawled or receive meaningful organic traffic. Essential assets needed to render pages efficiently. The important principle is not to assume a newly enabled CDN will immediately protect the origin. A CDN can only serve an edge cache hit when the requested resource is already cached and eligible to be served that way. Monitor crawl rate and origin behavior during the rollout A CDN migration should be treated as a technical change that can affect crawling behavior, not solely as a performance deployment. Google recommends explicitly monitoring and managing crawl rate during the transition. Teams should watch origin-level indicators alongside CDN metrics. A high cache-hit rate may look reassuring, but it does not fully answer whether uncached HTML requests, redirects, API calls, or other workloads are reaching the origin at a problematic rate. Useful checks during a phased rollout include response times, server errors, origin request volume, cache-hit patterns, and Googlebot activity. Search Console and server logs can help teams distinguish verified Googlebot traffic from other automated requests. If crawling becomes disruptive while caches are warming, Google says sites can temporarily return HTTP 429, meaning Too Many Requests, or HTTP 503, meaning Service Unavailable. This is an emergency measure for a short period, from a few hours to one or two days, to reduce crawl rate. It should not become a routine migration configuration. Extended or widespread error responses can interfere with crawling and indexing. The underlying issue still needs to be addressed through capacity planning, caching, or targeted access controls. Do not block verified Googlebot with blanket bot rules CDN and web application firewall (WAF) configurations often include bot-management features. These can help control abusive automation, but broad blocks can also prevent legitimate search crawlers from accessing pages. Google advises allowing verified crawlers through CDN and WAF rules rather than applying blanket bot protections. Blocking Googlebot can prevent it from recrawling existing URLs, discovering new content, or processing changed pages during a period when a site’s infrastructure is already changing. This distinction matters because user-agent strings alone are not reliable proof of crawler identity. Security teams should use their provider’s verified-bot mechanisms where appropriate and follow Google’s documented approach to verifying Googlebot when building custom rules. For unwanted automation, Google points to more targeted options, including robots.txt and rules aimed at specific bot traffic. That approach allows a site to reduce undesirable requests without accidentally cutting off crawlers needed for organic visibility. A practical rollout framework Google’s guidance supports a staged approach rather than an all-at-once DNS change with no operational safeguards.
