# I checked the link previews of 35 new GitHub projects' homepages. 1 in 5 had no image

## Overview

When someone pastes your project's homepage into X, Slack or Discord, the crawler reads your raw HTML, without running JavaScript, and builds the preview from a few meta tags. If those tags are missing, you get a bare link. I wanted a number for how often that happens on brand-new projects, so I ran a small scan. Method GitHub search API: 60 repos created after 2026-11-01 with 100–2,000 stars, plus 40 repos created after 2026-10-15 with 200+ stars (sorted by stars). 100 repos total. For each repo I read the og:image GitHub serves for the repo page (custom social preview vs. GitHub's auto-generated card). For repos with a homepage set (and not pointing to GitHub), I fetched the homepage with a crawler user agent and parsed the meta tags. Two Discord invite links were dropped, leaving 35 sites . Run on 2026-11-28. Small sample, one day, not a study of the whole ecosystem. Results Check Count Repos using a custom GitHub social preview 19 / 100 Sites with no og:image / twitter:image in raw HTML 7 / 35 Sites with an image but no twitter:card 4 / 35 Sites with twitter:card = summary (small thumbnail, may be intentional) 1 / 35 Sites with image + summary_large_image 23 / 35 Preview image over 1 MB 1 (1.9 MB) The surprising part was where the misses were. 5 of the 7 sites with no preview image were GitHub Pages project demos ( user.github.io/repo/ ). They were demo pages or docs pages, usually a single index.html or a JS app shell, and nobody had added the tags. Two of them had fewer than 50 words of text in the raw HTML, which means everything, including any meta tags, is rendered client-side, where crawlers never see it. The default GitHub repo card is fine, so 81 of 100 repos not having a custom one isn't a problem. The repo link previews well either way. The project homepage is the link that gets shared at launch, and that's where previews broke. About twitter:card X's card markup docs list twitter:card as the tag that picks the layout, and it has no Open Graph equivalent. Third-party guides disagree on what happens without it: some say X shows a small summary card, others say a bare link. Either way, you don't get the large image. twitter:image , twitter:title and twitter:description do fall back to their og: versions, so the minimum is short: <meta property = "og:title" content = "Your project — one line" > <meta property = "og:description" content = "What it does, in one sentence." > <meta property = "og:image" content = "https://your.site/og.png" > <!-- absolute https URL, PNG/JPG, ~1200x630 --> <meta property = "og:url" content = "https://your.site/" > <meta name = "twitter:card" content = "summary_large_image" > If your site is a single-page app, these have to be in the served index.html (or rendered at build or server time), not injected by your router. One docs site's og:image was a Mintlify OG endpoint with query parameters. My first version didn't unescape &amp; in the attribute, so it requested a mangled URL and got a 404. After the fix, it returns 200. Before you tell someone their preview is broken, check that your parser isn't the cause. Three sites "failed" on the first pass because Python 3.9's urllib doesn't follow HTTP 308 redirects. All three had complete tags. My own page was in the 4/35 bucket. The small page I run had og:image but no twitter:card . It's fixed now. Limits Regex parsing, not a real HTML parser. It handles property / name before or after content , but not every edge case. No image dimension check (that needs Pillow or header parsing); it only checks size, type and status. Platforms cache previews. A fixed page can keep showing the old preview for a while.
