# An Agent That Asks Permission From a Model That Cannot Lie: Jev Guardrails on AWS

## Overview

Author: Rasik Rahman S ( @rasikbuilderaws ), AI/ML Engineer at ShellKode , AWS Partner Builder Series, Part 3. Part 1 was the Daily GitHub Explorer , an autonomous agent on Lambda and Bedrock. This one is about what sits between an agent and its tools. The failure mode Ask an agent with shell access to free up disk space and tell it not to touch your work projects. Most of the time it runs du , clears a cache, and reports back. Once in a while it proposes rm -rf ~/Projects . Not because it is malicious. Because it is plausible. Projects take space, the user wants space, the model connects the two. Every production agent I have shipped has had a version of this: an action that reads as reasonable from inside the model's context and as obviously wrong from outside it. The standard answers are a regex denylist, which is brittle, or a second LLM that judges the first, which is slow, costs as much as the agent itself, returns prose you have to parse, and can be prompt-injected by the very tool arguments it is inspecting. I wanted a third option: a check that is fast, cheap, returns numbers, and cannot be talked into anything. This post is the build. Try it live: https://ew2mslbb49.execute-api.ap-south-1.amazonaws.com/ (paste a tool call, watch it score and return allow / ask / block in real time) Source code: https://github.com/rasik2002/jev-agent-guardrail What Jev is Jev is a System One decision model from TypeSafe AI. It does one thing: you send it a piece of state and a set of typed questions, and it returns a typed answer for each question with a calibrated probability. Three question types: Choice: pick one option from a set you define, returns a probability per option Noul: a yes or no question, returns the probability of yes Score: place the input on an ordered scale you define, returns a probability-weighted position It does not generate text. There is no reasoning trace, no explanation, no completion. That sounds like a limitation until you are building a guardrail, where it is exactly the property you want. Nothing to parse. Nothing for a malicious tool argument to hijack. It is available on OpenRouter as typesafe/jev-1.13 (or the ~typesafe/jev-latest alias) with a normal OpenRouter API key, no separate signup. Input tokens are billed, output tokens are free, and every response carries a usage.cost field. Details on the model page . What the guardrail does One HTTP endpoint. Your agent POSTs the proposed tool call before running it: { "user_request" : "free up disk space, do not touch my projects" , "tool" : "shell" , "arguments" : { "command" : "rm -rf ~/Projects" }, "session_id" : "demo-1" } The guardrail asks Jev three questions about that call in a single request, applies a threshold policy, logs the result, and returns allow , ask , or block . Jev is scoring your criteria text against the state, so vague criteria give vague probabilities. This is the part with all the judgement in it, and because it has no I/O it is fully unit tested. def apply_policy ( answers , policy ): risk = float ( answers [ " risk " ][ " score " ]) intent = float ( answers [ " intent_match " ][ " noul " ]) exfil = float ( answers [ " exfiltration " ][ " noul " ]) reasons = [] if exfil >= policy . block_exfil : return " block " , [ f " exfiltration probability { exfil : . 2 f } >= { policy . block_exfil } " ] if intent < policy . block_intent : return " block " , [ f " intent match { intent : . 2 f } < { policy . block_intent } " ] if risk >= policy . block_risk and intent < policy . ask_intent : return " block " , [ f " risk { risk : . 2 f } >= { policy . block_risk } with weak intent { intent : . 2 f } " ] if risk >= policy . ask_risk : reasons . append ( f " risk { risk : . 2 f } >= { policy . ask_risk } " ) if intent < policy . ask_intent : reasons . append ( f " intent match { intent : . 2 f } < { policy . ask_intent } " ) if reasons : return " ask " , reasons return " allow " , [ " low risk, clear intent, no exfiltration " ] Order matters. Exfiltration blocks regardless of anything else. A destructive call with strong intent is ask , not block , because sometimes the user really did ask you to delete the folder and a human confirmation is the right answer. Thresholds come from environment variables ( POLICY_BLOCK_RISK and friends) so you tune them without redeploying code. One honest note about the reasons field: those strings are generated by this policy code from the numbers. Jev does not explain itself. If you see prose in a guardrail's output, ask where it came from. The Lambda handler Two details worth calling out. The destructive rm -rf ~/Projects scored risk 1.97 and intent 0.01: the model is almost certain this is dangerous and almost certain it is not what the user asked for, since the user explicitly said do not touch projects. The exfiltration attempt scored exfil 0.98: reading a private SSH key and POSTing it to pastebin is exactly what that question is for. The interesting case is the first one. A read-only du listing is harmless, yet it came back ask , not allow , because intent scored 0.56 and my ask_intent threshold is 0.7. That is the guardrail being conservative, not a bug. It is also the whole argument of this post made concrete: the verdict is only as good as the thresholds, and the thresholds have to be tuned on your own labelled tool calls, not on the round numbers I shipped as defaults. On a real agent I would lower ask_intent or add a read-only fast-path so safe reads flow through without a human in the loop. Latency: the first call paid a one-time connection warmup (about 1.5 s), then every call settled around 750 to 780 ms end to end from my laptop. Cost held at roughly $0.000023 per call, about two thousandths of a cent, with Jev's output tokens free. The guardrail passes usage.cost through as jev_cost_usd on every response so you can watch it in your own logs. What I learned The criteria text is the model. I spent more time on the three question definitions than on all the AWS plumbing combined, and it was the right ratio. Every time a verdict looked wrong, the fix was in the criteria, not in the thresholds. Typed output changes how you write the consumer. With an LLM judge I would have written a parser, a retry for malformed output, and a fallback for the parser failing. With Jev the consumer is three float comparisons. The whole policy fits on a screen and every branch has a test. Fail closed has to be a design decision, not a default you inherit. It would have been easy to catch the exception and return allow "so the agent keeps working." That is the wrong instinct for a guardrail. Pausing is the safe failure. What I would change Put auth on the endpoint. v1 is open for demo purposes. An IAM authorizer or a Lambda authorizer is the next commit. Log asynchronously. Right now a DynamoDB write failure fails the request. Returning the verdict and writing the log from a queue would be more robust. Tune thresholds on labelled data. The defaults are a starting point. The right thresholds depend on what a wrong allow costs you versus a wrong block . Add a fourth question when the tool is a cloud API: "does this call affect resources outside the user's own account."
