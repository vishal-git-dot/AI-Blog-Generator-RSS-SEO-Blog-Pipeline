# How to Generate MiniMax H3 RH Enhanced Videos via API: Text, Frames and Multi-Reference, With Polling or a Webhook

## Overview

A four-second 1080P clip from MiniMax H3 RH Enhanced took 218 seconds in our test. If your code holds an HTTP request open until the video exists, it will time out long before the video does. And because one model id covers three input modes, mixing the wrong fields gets you a 400 before anything renders. This tutorial shows the full loop for MiniMax H3 RH Enhanced: create a task, wait for it with polling or a webhook, download the MP4, verify it, and confirm what you were billed. MiniMax H3 RH Enhanced is an enhanced build of MiniMax's open-weight H3 video model that generates 4-to-15-second clips with an audio track at 480P, 768P or 1080P, from text, from a first and/or last frame, or from up to 9 reference images and 3 reference videos, optionally driven by your own audio. Disclosure: I work on apimodels.app, the API used in every example below, and the timings come from its test logs. Why one model id behaves like three The mode is picked from the fields you send, in this order: Any of reference_image_urls , reference_video_urls or reference_video_audio_urls → multi-reference . Otherwise, first_frame_url , last_frame_url or reference_audio_urls (voice references) → image-to-video . Otherwise → text-to-video , and prompt is required. Frames and references live in different pipelines, so a request with both is rejected at create time rather than having half its inputs silently ignored. Every mode also accepts audio_url (a driving track for lip sync) and audio_mode . Where apimodels.app fits apimodels.app is a multi-model API gateway: one API key and one OpenAI-compatible endpoint for more than 140 image, video, audio and language models. For most mainstream models it keeps more than one upstream route with automatic failover; failed requests are not charged; long jobs run asynchronously with the webhook shown above; and GET /v1/records/{id} returns the exact charge for any single request. This model does not have a failover route yet: a failed job is refunded, and resubmitting is up to you (check retryable ).
