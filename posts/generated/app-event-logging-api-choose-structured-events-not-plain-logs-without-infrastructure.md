# App Event Logging API: Choose Structured Events, Not Plain Logs, Without Infrastructure

## Overview

TL;DR: the simplest app event logging API is one small structured-event function that integrates without advanced infrastructure. Choose it over free-form text when an experiment must be compared across marketplace tenant cohorts or reconstructed after an incident. Keep the transport boring: emit locally, attach a stable event name and cohort keys, and let a collector or log destination handle delivery later. That decision keeps a notebook prototype close to production code. It also leaves room for an evaluation harness: the same event records can answer "what changed for this cohort?" without asking an operator to interpret prose written by several code paths. Keep it boring. One rule. The fields deserve more design attention than the file writer. In this marketplace case, tenant_id is the ownership boundary, experiment identifies the change under review, and cohort identifies the assigned path. Those values should come from the request's trusted assignment context, not from free text supplied by a client. event_name describes the state transition, while fields such as listing_count describe the observation. A request identifier is useful for joining nearby records, but it is not a substitute for a tenant or cohort key. Keeping these roles separate makes a later query legible: an operator can ask which tenants in treatment saw a failed checkout after an assignment, then inspect the request trail without mistaking an identifier for a business dimension. It also keeps the event contract small enough to test in a notebook before the application has a production collector. The API boundary I would choose For app event logging, the smallest useful API is a function that accepts an event name and a dictionary of fields. It should not know about a particular hosted service. It should produce one record per event, preserve the timestamp, and make failure behavior explicit. Here is a complete local example. It uses only Python's standard library and writes to a JSON Lines file, so each line remains an independent record that can be streamed or processed later. from __future__ import annotations import json import sys import time from pathlib import Path from typing import Any class EventLog : def __init__ ( self , path : str = " events.jsonl " ) -> None : self . path = Path ( path ) def emit ( self , name : str , * , tenant_id : str , experiment : str , cohort : str , ** fields : Any , ) -> None : record = { " event_name " : name , " event_version " : 1 , " timestamp_unix_ms " : int ( time . time () * 1000 ), " tenant_id " : tenant_id , " experiment " : experiment , " cohort " : cohort , ** fields , } try : with self . path . open ( " a " , encoding = " utf-8 " ) as stream : stream . write ( json . dumps ( record , separators = ( " , " , " : " )) + " \n " ) except OSError as exc : print ( f " event log write failed: { exc } " , file = sys . stderr ) log = EventLog () log . emit ( " checkout_attempted " , tenant_id = " tenant-42 " , experiment = " ranking-v3 " , cohort = " treatment " , listing_count = 18 , request_id = " req-7f3 " , ) The required fields make the decision axis visible. tenant_id supports tenant-level comparison. experiment and cohort prevent a treatment record from being mixed with a control record. request_id lets an operator connect an application event to other records without putting a full request payload into the log. The small event_version field gives a later schema change a name. The catch block is intentional. Logging should not turn a checkout request into a second failure when the local destination is unavailable. In a production process, the error policy needs an explicit choice: drop the event, buffer a bounded number of events, or fail the business operation for an audit-critical event. The right answer depends on the event's role, not on the convenience of the logging library. A local JSON Lines writer is a poor fit for a multi-process service that needs durable delivery, access controls, or centralized retention. In that case, put a collector or queue behind the same emit contract. The tradeoff is operational ownership: the tiny writer has almost no setup, while the pipeline adds configuration and another failure boundary. That boundary is the point. Why does the marketplace cohort matter during an incident? A marketplace experiment rarely fails for every tenant in the same way. A ranking change might affect high-volume sellers, a region, or tenants with a particular catalog shape. A single aggregate error rate can hide that pattern. Plain text such as checkout failed for seller is readable in a terminal, but it leaves the comparison to a human or to a fragile parser. Structured fields let the investigation ask for all checkout_attempted records in ranking-v3 , group them by cohort , and then inspect tenant-level outliers. That is the useful unit of evidence when the goal is incident reconstruction rather than a pretty dashboard. I initially treated the event name as enough. It was not. An event name says what happened; it does not say which experiment assignment produced it, which tenant saw it, or whether the record describes an attempt, a success, or a retry. Adding those dimensions makes each record a little larger, but it prevents a much more expensive inference later. Do not put every possible field into every event. A stable core plus event-specific fields is easier to validate than a giant universal schema. Keep names predictable, use numeric values for measurements, and avoid embedding unbounded user text in labels or index keys. Prometheus's naming guidance is written for metrics, but its underlying concern applies here too: names should describe the thing being measured, and dimensions should be chosen deliberately. A practical flow from notebook to production The data flow can stay plain: application code emits a record, a local stream or collector receives it, storage retains it, and an analysis job groups records by tenant and cohort. The application does not need to contain query syntax or vendor-specific transport code. In a notebook, I would first test the decision rule against a tiny fixture. The important test is not whether JSON can be serialized. It is whether a failed experiment can be reconstructed from the fields that were actually emitted. import json from collections import defaultdict from typing import Iterable def failure_rate ( records : Iterable [ str ]) -> dict [ str , float ]: totals : dict [ str , int ] = defaultdict ( int ) failures : dict [ str , int ] = defaultdict ( int ) for line in records : record = json . loads ( line ) cohort = record [ " cohort " ] totals [ cohort ] += 1 if record [ " event_name " ] == " checkout_failed " : failures [ cohort ] += 1 return { cohort : failures [ cohort ] / count for cohort , count in totals . items () if count } fixture = [ json . dumps ({ " event_name " : " checkout_attempted " , " cohort " : " control " }), json . dumps ({ " event_name " : " checkout_failed " , " cohort " : " control " }), json . dumps ({ " event_name " : " checkout_attempted " , " cohort " : " treatment " }), ] print ( failure_rate ( fixture )) This intentionally small function exposes a common trap: a cohort rate is only meaningful if the denominator is defined. If retries, sampled events, or missing records change the denominator, document that in the analysis and emit the event states needed to distinguish an attempt from a retry. A dashboard can render a number; it cannot repair an ambiguous event model. For an AI application, this same fixture can feed an evaluation harness. A ranking or agent change should be assessed with a known set of tenant scenarios, then checked against operational events. Token usage, latency, and failure state belong in separate numeric fields when they are relevant. Do not log prompts, customer content, or credentials merely because the application handled them. Redaction is part of the event design, not a cleanup task after an incident. What should plain logs still do? Plain logs remain useful at the edge of the system. A short human-readable message is often the fastest signal during local development, and a traceback carries information that should not be flattened into a handful of fields. The choice is not between readable output and structured data; one record can support both. The boundary matters. If the only interface is a formatted string, downstream code must infer fields from punctuation. If the interface accepts structured data first, a formatter can choose how to display it. Keep the structured record canonical, and render a compact text line only where a human needs it. Three operational constraints deserve attention: timestamps should use a consistent representation, identifiers should be stable enough to join records but not contain sensitive values, and event writes should have bounded impact on request latency. A synchronous file write is a useful demo, not a universal production transport. Before deployment, measure the write path under the expected request concurrency and choose buffering or a collector when that measurement requires it. A hosted log service, an OpenTelemetry-compatible pipeline, and a self-managed JSON Lines workflow can all sit behind this boundary. They differ in retention, querying, access control, and operational ownership. The application-facing API does not need to change just because the destination changes. That separation is the main simplicity win. How can I integrate app event logging without advanced infrastructure? Use plain text alone when the record is temporary diagnostic context, the audience is a developer at a terminal, and no later grouping or replay is expected. Use structured events when the record will be compared across tenant cohorts, joined to an incident timeline, or consumed by an evaluation or reporting job. The simplest option changes with the requirement: a terminal-only diagnostic does not justify a schema, while a tenant-level incident review usually does. The compromise I use most often is structured-first output with a human-readable message field. It keeps the API small while preserving queryable facts. If event volume grows, the next design question is not "which dashboard should we buy?" It is whether the event schema, delivery policy, and retention boundary are still clear. Before shipping, trace one synthetic marketplace experiment from assignment through success and failure. Verify that every record carries the intended tenant and cohort, that a retry is distinguishable from a fresh attempt, and that a failed log destination does not silently change the business result unless that behavior is required. Check the redaction path with realistic sensitive inputs. Then run the same fixture through the notebook analysis and the production query path. When those two interpretations disagree, fix the schema before adding more infrastructure. The schema version is 1 in the example. Treat that number as a contract: if a field changes meaning, make the change visible instead of teaching the incident reviewer to guess. The simplest API is therefore not the one with the fewest characters. It is the smallest stable contract that preserves the evidence your next incident review will need. For marketplace experiments, that means structured event records when replay and cohort comparison matter, with plain rendering available for humans at the edges.
