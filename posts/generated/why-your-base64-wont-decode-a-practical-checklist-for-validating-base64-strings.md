# Why Your Base64 Won't Decode: A Practical Checklist for Validating Base64 Strings

## Overview

This post covers what makes a Base64 string valid, the five problems I run into most, and a small normalizer in Python and JavaScript that fixes the common cases. What "valid Base64" actually means Standard Base64 (RFC 4648 §4) turns every 3 bytes of input into 4 characters from a 64-character alphabet: A-Z a-z 0-9 + / If the input length isn't a multiple of 3, the output is padded with = (one or two of them) so the total length is a multiple of 4. A valid standard string therefore has: Only alphabet characters, plus = at the very end At most two = , and only as trailing padding A length divisible by 4 Here's a quick check in Python: import base64 print ( base64 . b64encode ( b " Hello, World! " )) # b'SGVsbG8sIFdvcmxkIQ==' 13 bytes of input is 4 full groups of 3 plus 1 leftover byte, so you get 20 characters, the last two of which are == . There's also a URL-safe variant (RFC 4648 §5), often called Base64URL, which swaps + for - and / for _ and usually drops the padding. The same bytes encode differently: print ( base64 . b64encode ( b " \xfb\xff\xbf " )) # b'+/+/' print ( base64 . urlsafe_b64encode ( b " \xfb\xff\xbf " )) # b'-_-_' Keep that pair in mind. The five usual suspects 1. Missing padding. SGVsbG8 is Hello with its = stripped. JWTs, many APIs, and most Base64URL encoders drop padding on purpose. The fix is mechanical: append = until len % 4 == 0 . One catch: a remainder of 1 can never be fixed by padding. A single leftover character carries only 6 bits, which isn't enough for a byte, so the string was truncated. 2. Whitespace and line breaks. MIME (email) wraps Base64 at 76 characters, PEM files wrap at 64, and copy-paste from terminals adds \r\n . Python's default (non-strict) decoder silently drops these characters, while strict decoders reject them. Strip all whitespace before validating. 3. URL-safe characters in a standard decoder. If you see - or _ , it's Base64URL. Translate - → + and _ → / , then fix the padding. 4. A data URI prefix. Strings like data:text/plain;base64,SGVsbG8sIFdvcmxkIQ== include a header that isn't Base64. Drop everything up to and including the first comma. 5. URL encoding on top. If the string went through a query string, = may now be %3D and + may be %2B , or even a space. URL-decode first. A % sign is never valid Base64. And one that isn't a validation error at all: 6. Wrong character set when turning bytes into text. The browser's atob() returns one character per byte (effectively Latin-1), so UTF-8 text with multi-byte characters gets mangled: atob ( " aMOpbGxv " ); // "hÃ©llo" — the bytes are right, the interpretation is wrong The Base64 was fine. The bytes are 68 c3 a9 6c 6c 6f , which is héllo in UTF-8. Decode the bytes with TextDecoder instead. Also remember that valid Base64 doesn't have to be text: it can just as easily be a PNG, a ZIP, or ciphertext. That's a useful signal that you're looking at binary data, not a broken string. When to be strict and when to be forgiving Be strict at trust boundaries. If you're accepting Base64 from users or other services, validate with strict rules and reject bad input with a clear error. Forgiving decoders can hide real corruption. Be forgiving when debugging. When you're staring at a string from a log, normalize first, then decode. Don't treat "decodes successfully" as "is Base64". The string test is valid Base64 (it decodes to three bytes, b5 eb 2d ).
