Here's how. How YouTube Stream Extraction Actually Works (The "Bypass" Explained) This is the part nobody explains properly. When you open a YouTube video in your browser, the actual MP4/audio stream isn't directly accessible at a clean URL. YouTube obfuscates it in two ways: 1. Signature Cipher YouTube wraps the stream URL inside a JavaScript function that scrambles the signature parameter. The raw URL looks something like this: ( https://rr3---sn-xxx.googlevideo.com/videoplayback?...&sig=SCRAMBLED_SIG ) The actual playable URL only works when you un-scramble that signature. YouTube's own player does this in the browser using a JavaScript function it downloads fresh every session. The function changes regularly to break scrapers. yt-dlp's solution: It downloads YouTube's player JS, extracts the current cipher function, reverse-engineers the transformation steps (they're always a combination of reverse, swap, and splice operations), and applies them to reconstruct the real signature. This is why yt-dlp updates so frequently — YouTube rotates this function. 2. n-parameter Throttling Even with a valid signature, YouTube adds an n parameter to the URL that limits download speed to about 50 KB/s if not decrypted. yt-dlp decrypts it using the same JS extraction approach, unlocking full speed. In my bot , I run yt-dlp with 8 parallel fragment streams to max out the download speed: ydl_opts = { ' concurrent_fragment_downloads ' : 8 , ' cookiefile ' : ' cookies.txt ' , # handles age-restricted content ' quiet ' : True , } The cookies.txt handles age-restricted videos. You export your browser cookies with the Get cookies.txt extension and drop the file in the bot's folder. What Happens After Download: The FFmpeg Pipeline Once yt-dlp pulls the raw stream, FFmpeg takes over. For audio: # Extract audio and convert to MP3 at chosen bitrate ffmpeg - i input . webm - vn - ab 320 k - ar 44100 output . mp3 For video, I use Intel VAAPI hardware acceleration when available, which runs about 10x faster than CPU encoding: # Hardware-accelerated H.264 encode ffmpeg - vaapi_device / dev / dri / renderD128 \ - i input . webm \ - vf ' format=nv12,hwupload ' \ - c : v h264_vaapi \ - c : a aac output . mp4 On machines without VAAPI (Windows, Termux, most VPS), it falls back to software encoding automatically. The 50 MB Telegram Limit — How I Send Up to 2 GB Standard Telegram bots can only send files under 50 MB. Most bots just compress the video into a potato-quality file. Mine doesn't. The routing logic works like this: Under 48 MB → Send directly via standard Bot API. Instant. Over 48 MB, MTProto configured → Use native MTProto client (Telethon) which supports up to 2 GB natively with your API ID and hash from my.telegram.org Over 48 MB, no MTProto → Split the file into 44 MB chunks using lossless stream copy (zero re-encoding, zero quality loss, runs at disk speed) The lossless chunking command looks like this: ffmpeg - i input . mp4 - c copy - f segment \ - segment_size 46137344 chunk_ % 03 d . mp4 No quality loss. No waiting for re-encode. Just pure stream splitting. Database: Why SQLite Was the Right Choice I went with SQLite in WAL mode instead of PostgreSQL. For a single bot, this was the right call: WAL mode means readers and writers don't block each other — critical when multiple users are downloading simultaneously Zero ops overhead — no separate database server to manage Atomic crash recovery built in Every connection opens with: conn . execute ( " PRAGMA journal_mode=WAL " ) conn . execute ( " PRAGMA foreign_keys=ON " ) The schema tracks every user, every search, every download, and aggregated stats in real time.
