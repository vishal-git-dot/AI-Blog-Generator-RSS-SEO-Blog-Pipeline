# I tried to make my AI agents lazier with a 270M model. It backfired on the smartest one.

## Overview

This is a submission for the Hacktoberfest Open-Source AI Challenge Week 3: Slow and Steady What I Built My AI agent kept calling tools it didn't need. I gave gpt-oss-120b 161 tasks it can reliably answer on its own, no tools. It still reached for a tool on 69 of them. A small 4B model running locally did the same on 36 of 68. Every one of those is an extra round trip, more tokens and more waiting. This week's theme is making AI do less. So I tried to make my agents lazier, in the good way. Whetherman (as in weather*man*, it forecasts whether you need a tool) is a small proxy that sits between your agent and its model. Before every model call that offers tools, a fine-tuned FunctionGemma-270M makes one of four calls: Decision What the proxy does ACT Pass the request through untouched. This is the default. ANSWER Strip the tools and tell the model to answer from what it already has. ASK Strip the tools and ask the user one clarifying question. DECLINE Strip the tools and explain what it can't do. It only steps in when it's confident enough for that specific agent . If the router is slow, crashes or gets confused, the request goes through as ACT. Worst case, it does nothing. To be upfront: it didn't make any of my three agents better. It hurt the big one and was basically neutral on the other two. What I did learn is that whether a tool call is "necessary" depends on which agent is asking . A few results that stood out: Give the small agent the big agent's settings and it fails 32 more tasks out of 150 than with no gate at all. The router and the requests didn't change, only the profile did. Removing tools isn't free. gpt-oss wrote about 60% more output tokens when I took its tools away, and it tried to call the removed tools 20 times anyway. Where the agent is actually capable (math, code, primes), the gate cut calls from 18 to 6 with zero lost tasks. Everywhere else, a wrong skip cost way more than the cheap call it saved. One global "does this need a tool?" classifier can't serve both. So Whetherman has two parts: flowchart TD A[Agent request<br/>messages + tools] --> P{Proxy} P -->|no tools, streaming,<br/>forced tool_choice| U[Upstream model] P --> B[FunctionGemma-270M<br/>shared backbone + LoRA] B --> R[Per-agent profile<br/>logistic layer + τ] R -->|ACT or not confident| U R -->|ANSWER / ASK / DECLINE| S[Strip tools,<br/>add instruction] --> U The shared backbone is FunctionGemma-270M with LoRA and a 4-class head. It's trained on NVIDIA's When2Call, multi-step decision points I generated, and When2Tool tasks where all my agents agreed. It never sees which agent it's routing for. Training took about 50 minutes on my GTX 1660 Ti, in FP32, because that card has no BF16. The per-agent profile is fitted to one agent. whetherman calibrate runs a probe pack against your agent: every task 3 times with tools and 3 times without, 5 if the results are mixed. The agent's own results decide the label. If it always succeeds without tools, the label is ANSWER. If it fails without tools but succeeds with them, ACT. Anything in between is ambiguous and gets dropped. Then a small regularized logistic layer and a threshold τ are fitted on that, picking the smallest τ that keeps false skips at or under 5% on a separate split. The probe pack ships with real tools (a fixture repo to read and test, a calculator) and simulators for anything with side effects. If an agent says "email sent" without calling the tool, that's a fail. Rules I set before the held-out runs Held-out sets were frozen and run exactly once, after hashing the backbone, the profiles and the code (tag freeze-v3 ). False skips (withholding a tool that was actually needed) are always reported with the denominator and a 95% confidence interval. "0 false skips" means nothing if it's out of 8. When a gated episode failed, I replayed it with ACT restored at the skipped step. If that fixed it, that's evidence the skip caused it, though not proof, since replays aren't fully deterministic either. A rule picked in advance which probe pack to ship. It rejected my own "bigger probe pack" improvement. Two-choice "which city is warmer" tasks can be passed by guessing, so they're reported separately and left out of the headline. Why Does Open Innovation Matter? This project doesn't work at all without open models, on both sides of the proxy. The gate runs before every model call. If it costs money per call or adds a network hop, it can't save more than it spends. It has to be small, local and free, and FunctionGemma at 270M runs on a GPU from 2019. Calibration only works because I can measure the agent. The whole method is running the same model with and without tools until I know what it can do alone. With open models I pinned the exact weights, quantization and serving stack. With a closed API the model can change under you between your probe run and next Tuesday, and your profile silently goes stale. And I needed to get inside the router. I trained a LoRA, bolted on a classification head, read its hidden state for the per-agent layer and exported the whole thing to Hugging Face. None of that is possible through a chat endpoint. A closed frontier model would probably over-call less to begin with, which would leave a gate like this less to do. But you'd still have no way to calibrate anything against it, and you'd be paying per request to find out. What went wrong on the big agent It stopped one lookup too early. 11 of the 15 lost tasks have replay evidence of a false skip, and 7 of those are multi-hop retrieval: look something up, then look up the next thing. The gate answered after the first lookup. That makes sense in hindsight: every task in my probe pack is a first-step decision, so L's profile never once saw "one lookup done, another one needed". Fewer calls also didn't mean lower cost. With its tools removed, gpt-oss wrote longer answers: completion tokens went from 36k to 58k over the suite, and output costs 7× input. It also called tools that weren't there anymore 20 times. Each time, the proxy had to re-send the original request, so those steps saved nothing and cost an extra call. And the calls I was skipping were cheap to begin with. A calculator or a fixture file read costs almost nothing. One wrong skip can fail a whole task. This isn't specific to my router. Roughly: payoff ≈ (cost of a call × calls avoided) − (cost of a failed task × false skips) − (what removing tools does to the model) With cheap tools, that comes out negative. A gate like this only makes sense when the calls it skips are slow, expensive or risky: paid APIs, rate-limited search, anything with side effects. My benchmark had none of those. That's the next experiment. It did work on calculator, code, matrix and prime tasks on L: 18 calls down to 6, with no lost tasks. Laya vs FunctionGemma I also tested Laya , an encoder model built for typed decisions, as a second router. Same data, same splits, same calibration, offline only. FunctionGemma won on almost everything: E1-test macro-F1 0.642 vs 0.497, and on L, Laya couldn't find any safe threshold at all, so it never skipped. Laya was faster on short inputs on the GPU (36 ms vs 55 ms) but twice as slow on long ones (510 ms vs 249 ms), and it has to truncate anything over 512 tokens. L's never does. Prize Categories Gemma : FunctionGemma-270M is the router, so every decision Whetherman makes comes from it. I fine-tuned it on my 6 GB GTX 1660 Ti: LoRA rank 16 on every attention and MLP projection, plus a 4-class head on the last token's hidden state, trained in FP32 because Turing cards have no BF16. Training took about 50 minutes. The per-agent profiles sit on that same hidden state as a small logistic layer each, so one 270M model serves every agent and only the profile changes between them. On held-out When2Call it goes from macro-F1 0.519 untuned to 0.642, ahead of a prompted Qwen3.5-4B router (0.281) and Laya (0.497). It runs at 55 ms per decision in about 1.2 GB of VRAM on the same card. The adapter, the head and both profiles are on Hugging Face with a model card . DigitalOcean : DigitalOcean's serverless inference ran both hosted agents, so the agent side of every measurement happened there. Agent L is gpt-oss-120b and the unseen agent U is gpt-oss-20b, both called through the OpenAI-compatible endpoint with six parallel workers. That covered labeling L (every probe task 3 to 5 times with tools and 3 to 5 times without), calibrating U from scratch as a brand-new agent, and the dev and frozen held-out A/B runs: 20 logged jobs covering 952 tasks. The client retries rate limits and 5xx errors with jittered backoff, prices every response from its token usage at DigitalOcean's published rates and appends it to eval/results/spend.json , and a hard spend cap stops any job before it goes over. Every cost number in this post comes from that log. Limitations Three agents, measured on one serving stack each, on one day, at temperature 0. A different quantization or provider is a different agent. Recalibrate. Small denominators. About 120 usable probe labels per agent, and only tens of truly-needed calls in some held-out sets. The intervals are wide and they're in every table. The proxy handles non-streaming OpenAI-compatible chat requests with tool_choice auto. Everything else is passed through untouched. It's not a security guardrail. It decides whether a call is useful , not whether it's allowed , and it fails open on purpose. What I'd do next Multi-step probes, so the profile learns later-step decisions, especially "one lookup isn't enough". Test with tools that are actually expensive: paid APIs and slow web search. That's where the payoff math could flip. Factor the output-token shift into the skip decision, not just call counts. Detect per model when it ignores removed tools, and back off.
