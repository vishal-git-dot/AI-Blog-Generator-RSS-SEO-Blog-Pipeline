# Your Agent Boots. Phoenix Still Doesn’t Know It Exists.

## Overview

A MatrixOS agent can start, emit a beacon, and do useful work—while Phoenix’s swarm workspace still has no idea it exists. That is not a mysterious boot failure. It is usually a missing contract between two projects. The agent source defines what the process does. Phoenix’s per-agent metadata file tells the workspace how to find, configure, constrain, and present that agent. Leave out either half and you get the software equivalent of an operator arriving at the gate with a working radio and no badge. The radio is excellent. The gate remains unimpressed. This walkthrough follows the real layout: an agent package in MatrixOS, a JSON manifest in Phoenix, and optional configuration editors and custom panels. We’ll also look at how Phoenix treats signing and certificate requirements, so nobody puts a private key in a JSON file and calls it “automation.” Two projects, two jobs Keep the responsibilities separate: MatrixOS repository └── agents/python_core/shift_scribe/ ├── __init__.py └── shift_scribe.py # runtime behavior Phoenix repository ├── agents_meta/shift_scribe.json # workspace contract and defaults └── matrix_gui/ ├── swarm_workspace/cls_lib/agent/config_editors/ │ └── shift_scribe.py # optional configuration dialog └── core/panel/custom_panels/shift_scribe/ └── status_panel.py # optional custom controls The metadata file belongs to the agent type, not to each swarm instance. Phoenix reads the JSON files in agents_meta to populate the agent palette. When you add an agent to a workspace, its defaults become the starting configuration for that node; the workspace then saves the operator’s edits. 1. The filename stem and the name should match exactly; Phoenix uses that name to find the manifest and the runtime package. Here is a starter manifest: { "name" : "shift_scribe" , "universal_id" : "shift-scribe" , "constraints" : [ { "packet_signing" : { "in" : true , "out" : true } } ], "config" : { "ui" : { "agent_tree" : { "emoji" : "🧭" } }, "interval" : 30 , "report_to_role" : "hive.forensics.data_feed" , "alert_to_role" : "hive.rpc" } } The top-level fields have distinct jobs: name is the stable agent-type name used by Phoenix’s palette and module lookup. Keep it aligned with the MatrixOS folder and module. universal_id is useful metadata, but a workspace node gets its own runtime identity when it is added. Don’t hard-code one live swarm instance ID into a reusable agent type. constraints declares requirements the workspace must resolve. Phoenix checks that a constraint has a registered editor or auto-generation handler; an unknown name is not a wish Phoenix can grant. config holds defaults and Phoenix UI hints. The workspace copies these into a new node, and the agent reads the operational values from its directive. The little compass under config.ui.agent_tree.emoji is the return icon: it labels the agent in the palette/tree. Pick an emoji that survives your terminal font and looks different from the other thirty-seven shields. 3. Let constraints provision security material Phoenix’s constraints are more than badges. They tell the workspace and deployment path what resources an agent needs. For example, the real matrix_https metadata declares packet signing in both directions, a connection certificate, and HTTPS transport: "constraints" : [ { "packet_signing" : { "in" : true , "out" : true } }, { "connection_cert" : {} }, { "https" : {} } ] If the agent needs to phone home to Phoenix, give it a signing key pair. In this metadata, packet_signing in and out are both enabled: the agent needs its private signing key for outbound packets and the appropriate public key to verify inbound traffic. Phoenix’s registered packet_signing auto-generation handler creates the key material during deployment and injects only the fields required by the directive. The connection-certificate handler can likewise generate certificate bundles. For connection certificates, the transport matters: the current injection map uses them for HTTPS and WSS connections. That is the point of declaring the requirement in the type metadata: Phoenix can ask for or generate the matching resource and block deployment when a required item is unresolved. It does not mean you should paste a private key or certificate into the public meta-file. Keep secrets in Phoenix’s protected vault/provisioning path, and let the deployment flow inject only what the agent needs. Use a constraint name the Phoenix version actually registers. If you invent a new one, you must also implement and register the editor or auto-generation handler. Otherwise the workspace can reject the agent before deployment—with the digital equivalent of “your paperwork is in a language we do not speak.” 4. Defaults, configuration editors, and panels Put ordinary operational defaults under config: polling intervals, paths, role names, safe-mode flags, or feature toggles. The MatrixOS agent should still validate values and apply defensive fallbacks; a default is not input validation wearing a nicer jacket. Phoenix has a useful fallback for configuration. When an operator double-clicks an agent node, it looks for a module named after the agent under config_editors and a class named in CamelCase. For shift_scribe, that means: matrix_gui/swarm_workspace/cls_lib/agent/config_editors/shift_scribe.py class ShiftScribe(...) If no specialized editor exists, Phoenix uses its generic editor for simple fields. A custom editor is worthwhile when the config needs typed controls, validation, grouped sections, or role pickers. Its save action should update the node’s config and mark the workspace dirty. A custom operations panel is a separate, optional module. Add its path to config.ui.panel, for example: "ui" : { "agent_tree" : { "emoji" : "🧭" }, "panel" : [ "shift_scribe.status_panel" ] } Then create matrix_gui/core/panel/custom_panels/shift_scribe/status_panel.py. Phoenix resolves that dotted path beneath custom_panels, imports the module, and looks for a class named StatusPanel. Custom panels implement the Phoenix panel interface and can contribute buttons or views for agent-specific operations. If you declare a panel path, ship the matching module and class; otherwise Phoenix will politely log that the panel is missing and continue without it. 5. Service roles are the command contract A service-manager entry advertises service roles and handlers that can be routed to the agent. It is not the custom panel itself. A simplified entry might look like: "service-manager" : [ { "role" : [ "shift_scribe.status@cmd_status" ], "scope" : [ "parent" , "any" ] } ] The agent must implement the matching handler, and any custom panel button that calls it must send a compatible service request. Think of the role string as the radio frequency: listing it in Phoenix does not install a radio in the agent. Keep the declared role, handler name, payload shape, and panel request aligned. The existing matrix_https manifest shows this pattern with perimeter toggle and status roles. Its config.ui.panel points to matrix_https.matrix_https; that path leads to a real custom panel, while service-manager lists the services it can request. One is the cockpit; the other is the set of commands it can call. They work together, but they are not interchangeable. 6. If you declared a custom editor or panel, verify its module and CamelCase class load. Resolve the required constraints and deploy to a test environment. Verify the directive contains the intended config and provisioned fields, then confirm the worker logs, beacons, and service handlers behave as expected. If the agent is missing from the palette, begin with the JSON path and filename. If it appears but cannot be added, inspect the constraint registry. If the worker boots but behaves as though every setting is None, compare the editor’s saved config keys with the names read by the agent. If the panel button appears to salute and then do nothing, compare its service request with the role and handler that the agent actually registered.
