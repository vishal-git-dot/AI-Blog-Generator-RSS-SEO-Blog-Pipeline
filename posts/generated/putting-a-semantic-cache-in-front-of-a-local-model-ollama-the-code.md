# Putting a semantic cache in front of a local model (Ollama): the code

## Overview

A model you run yourself has no per-call bill. It still isn't free: every question takes your GPU a few seconds, and every repeated question takes it a few seconds again. We recorded the whole path of putting Sulci Cache in front of a model running in Ollama, two ways, in six minutes: This post has the code from the video, ready to copy, and one thing the video left out: which embedding model to use, measured. Everything here runs on your machine. No cloud, no account, no API key. Setup ollama pull llama3.2:3b pip install "sulci[sqlite]" openai The cache is a SQLite file on your disk. The embedding model that turns each question into numbers (MiniLM by default) downloads once, about 90 MB, and then runs offline. Path A: wrap your own call If you write the code that calls the model, wrap that call. Ollama speaks the OpenAI API, so the standard OpenAI client works against it: from openai import OpenAI from sulci import Cache ollama = OpenAI ( base_url = "http://localhost:11434/v1" , api_key = "ollama" ) # Ollama ignores the key cache = Cache ( backend = "sqlite" , db_path = "./my_cache" ) # threshold 0.85 by default def ask_ollama ( question ) : reply = ollama . chat . completions . create ( model = "llama3.2:3b" , messages = [ { "role" : "user" , "content" : question } ] , ) return reply . choices [ 0 ] . message . content def ask ( question ) : result = cache . cached_call ( question , ask_ollama ) print ( "HIT" if result [ "cache_hit" ] else "MISS" , f "{result['similarity']:.3f}" , f "{result['latency_ms']:.0f} ms" ) return result [ "response" ] ask ( "How do I reset my home Wi-Fi router?" ) # MISS: the model answers, the cache keeps it ask ( "What are the steps to reset my Wi-Fi router?" ) # HIT: same meaning, different words ask ( "How do I reset my Wi-Fi password?" ) # MISS: looks similar, different question cached_call returns a dict: response , cache_hit , similarity (the nearest stored question, even on a miss), latency_ms and source . The third question is the one to watch. It shares most of its words with the first, and it scored 0.780 against it, below the 0.85 threshold, so it went to the model. Catching repeats is the easy half. Knowing when not to answer is the important half. Path B: the proxy, no code change If you already have an app that talks to an OpenAI-compatible endpoint, don't touch its code. Start the proxy in front of Ollama: pip install "sulci[sqlite,proxy]" sulci-proxy --openai-upstream http://localhost:11434 It listens on http://127.0.0.1:8787 and keeps its cache in ./sulci_db . Point the app's OpenAI client at it with one environment variable: export OPENAI_BASE_URL = http://127.0.0.1:8787/v1 export OPENAI_API_KEY = ollama # the OpenAI client wants one; Ollama ignores it The app's code stays as it was: from openai import OpenAI client = OpenAI ( ) # reads OPENAI_BASE_URL raw = client . chat . completions . with_raw_response . create ( model = "llama3.2:3b" , messages = [ { "role" : "user" , "content" : "What are the steps to reset my Wi-Fi router?" } ] , ) print ( raw . headers . get ( "x-sulci-cache" ) , raw . headers . get ( "x-sulci-similarity" ) ) # hit 0.931… reply = raw . parse ( ) . choices [ 0 ] . message . content You only need with_raw_response to read the headers. A plain client.chat.completions.create(...) works the same through the proxy. Misses go on to Ollama; hits come back from the proxy with x-sulci-cache: hit . Safe in conversations A chat app sends the whole conversation every time, and its users ask vague follow-ups. "How do I speed it up?" means one thing after a PostgreSQL question and another after a Python question. A plain cache keyed on the words would file the first conversation's answer under "How do I speed it up?" and hand it to the second. Tell the proxy which conversation a request belongs to: raw = client . chat . completions . with_raw_response . create ( model = "llama3.2:3b" , messages = history , # the whole conversation so far extra_headers = { "x-sulci-session-id" : "postgres" } , # any stable id per conversation ) With a session id, the proxy reads a follow-up together with its own conversation. In the video, both "How do I speed it up?" turns came back as x-sulci-cache: miss-followup : the local model answered each one, and neither answer was stored. A follow-up never gets another conversation's answer. A reworded first question is still a repeat. In a new conversation, "How can I speed up slow PostgreSQL queries?" came back from the cache (similarity 0.941). If a turn inside a conversation really does stand on its own, send x-sulci-standalone: true with it and the proxy may store it. Which embedding model? Sulci Cache ships three local embedding models. You pick one by name: cache = Cache ( backend = "sqlite" , db_path = "./my_cache" , embedding_model = "mpnet" ) # "minilm" (default), "mpnet", "bge" We ran the demo's questions and a few harder ones through all three on the same laptop, with sulci's own embedder. Eleven pairs we wrote ourselves: a way to see how the models behave, not a benchmark. What this means in practice: MiniLM and mpnet served no wrong answers at 0.85. Both caught the three plain rewordings and turned away every look-alike: the Wi-Fi password question, MySQL after PostgreSQL, cancelling an order after cancelling a subscription. Both missed "Can I get my money back?" against "What is your refund policy?" (0.518 and 0.499). It means the same thing in completely different words, and it scores lower than some questions that mean something else. No single threshold gets every pair right for either model. When that happens, a cache should lean toward missing: a miss costs one model call, a wrong hit gives someone the wrong answer. mpnet didn't earn its cost on these questions. Its vectors are twice the size of MiniLM's and it took 6.2 ms per question against MiniLM's 2.9 ms, for the same calls at 0.85. MiniLM stays the default. bge scores everything higher , so 0.85 means something different for it. At 0.85 it served two wrong answers: the Wi-Fi password question would have got the router-reset answer (0.869), and the MySQL question would have got the PostgreSQL answer (0.869). On these same scores, a threshold of 0.90 would have served neither and still caught the three rewordings. That's read off eleven pairs, so check it on yours. Set the threshold for the model you use. Similarity scores from different models are not on the same scale, so a threshold tuned for one doesn't carry over to another. If you switch models, switch thresholds with it: rerun your own same-and-different pairs, and pick a threshold between the lowest "same question" score and the highest "different question" score. A cache that serves a wrong answer costs you more than one that misses. The script is short enough to adapt to your own questions.
