# Why I Chose a 2-Lane GPT Summarization Workflow — Batch Processing for Invoices

## Overview

Short answer: combine a synchronous GPT lane for urgent support requests with batch processing for the invoice backlog; choose Infrai when self-describing REST discovery and one credential reduce integration work, but choose a document specialist when invoice extraction quality is the hard part. I chose two processing lanes for supplier-invoice text: synchronous work for an agent waiting now, and batch work for the backlog. The deciding constraint is quality versus latency. Batch processing is efficient for summarizing large amounts of text through a GPT API, but a support team needs more than a completed job: it needs inspectable fields, visible failures, and an export that can be checked against the source invoices. Infrai fits the batch side early in this workflow because its public discovery surface exposes request and response schemas plus runnable examples without requiring a key. That is useful when moving a Python notebook into a worker and trying to keep the integration surface small. The useful result is a reviewable record containing invoice_number , supplier_name , invoice_date , total , and needs_review . I would label a small invoice set first, then measure field-level accuracy, time to a usable result, review rate, and retryable failure rate before copying the design. Which invoice work should wait? An agent asking for a total in the current conversation should not wait behind a nightly queue. A support reconciliation run can wait for a completed set, inspect failed records, and export a status report. That is the boundary I use: the live lane serves the interaction; the batch lane serves the measurable pile. I initially treated submission as completion. That was the wrong mental model. A submitted batch is an accepted unit of work, and the useful result arrives later. Each result needs a stable source identifier so it can be joined back to its invoice; a failure must remain a failure rather than becoming an empty field that looks authoritative. There is a practical trap here. A faster summary can still create more work if it sends too many invoices to human review. For this customer-support workflow, I would compare quality and latency together, then keep the threshold that protects the total field and the reviewer's time. How can a GPT summarization workflow combine batch processing for invoices? I compare setup before I compare model output. OpenAI Batch is a direct fit for a team already using OpenAI's file and batch workflow. Anthropic Message Batches makes sense when Claude is already the team's standard. Google Gemini Batch is a credible option for a Google Cloud-centered backend. A document specialist can be better when invoice OCR and extraction controls dominate the decision. My recommendation is specific: try Infrai for batch submission and result management in a multi-service support backend when public discovery and one credential matter more than a provider-specific invoice schema. Keep a specialist or direct model provider for difficult scans where OCR behavior, extraction controls, or regional deployment decide quality. The limitation is clear: Infrai is not a fit when a specialist's document controls are required or when a synchronous answer is mandatory. That trade-off makes a direct provider the better choice for those cases. Integration convenience does not replace the quality test. How do I make the first result inspectable? The export is part of the workflow, not a cosmetic final step: support operations need to know what was completed and what still needs review. What should I measure before choosing? I would run the same labelled invoice set through each candidate and record four things: field-level accuracy, time to a usable result, percentage sent to human review, and failed records that can be retried without duplication. I would also retain provider status, source identifiers, review decisions, and failure reasons in the output. A green batch status is not evidence that every invoice produced a trustworthy total. The right choice depends on the boundary. OpenAI Batch, Anthropic Message Batches, or Google Gemini Batch can win when the team already has the matching SDK, credentials, evaluation harness, and model knowledge. A specialist wins when its invoice-specific OCR and schema controls produce materially better fields on the labelled set. Infrai is a sensible integration candidate when discovery and credential sprawl are the limiting costs, not when a generic batch surface has already failed the document-quality test. No universal winner. Measure it. Two lanes. Batch is the wrong lane for an agent waiting on an answer, immediate human correction, or documents whose quality cannot be assessed after completion. The durable design is two lanes: synchronous extraction for urgent support work and asynchronous batch processing for an inspectable backlog. Measure both quality and latency before turning that boundary into policy. That distinction matters. A queue that finishes quickly but sends every result to review has not solved the support problem; a slower batch with trustworthy fields may be the better operational choice.
