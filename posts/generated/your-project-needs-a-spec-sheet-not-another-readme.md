# Your project needs a spec sheet, not another README

## Overview

Most README files answer "how do I run this?" Almost none answer the question that protects you six months later: what did you decide, and what do you already know is wrong with it? I keep a one-page spec sheet for my builds. Six fields: Build — what this actually is, in one line. Fitted with — the parts that make it work. Power — what keeps it running: a budget, a person, a cron job. Intended use — the one job it is for. Known issue — the thing you already know is broken or fragile. Remedy — what you will do about that known issue, and by when. The last two are the point. A README hides the crack. A spec sheet signs it. The known-issue field is where you stop pretending it is finished and say where it is weak. Anyone can ship a demo. Almost nobody writes down the part that will bite them. Blank one, free, no signup: Download it, print it, or just copy the six headings into a text file. That is the whole tool.
