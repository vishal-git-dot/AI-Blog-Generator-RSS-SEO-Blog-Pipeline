# Full feed coverage is not snapshot readiness: a tested JavaScript contract

## Overview

A dashboard can display every expected feed and still be unready for comparison. The distinction becomes visible when one source is developing, or when a cached observation belongs to the wrong completed interval. A 4/4 badge answers a coverage question. It cannot establish that four observations satisfy the snapshot policy. Declare the required slots first This example uses two fictional instruments and two timeframes. Each required slot has a symbol, a timeframe and an expected completed close time. A caller provides that plan. The evaluator does not infer exchange sessions or decide which candle should be complete. Daily and four-hour observations need not have equal close timestamps. They need to match their respective expected slots in the same declared plan. Comparing all timestamps for equality would reject legitimate multi-timeframe snapshots. const daily = Date . parse ( " 2026-10-11T00:00:00Z " ); const fourHour = Date . parse ( " 2026-10-11T20:00:00Z " ); const plan = [ " VENUE:A " , " VENUE:B " ]. flatMap ( symbol => [ { symbol , timeframe : " D " , expectedClose : daily }, { symbol , timeframe : " 4H " , expectedClose : fourHour } ]); These timestamps are synthetic fixtures, not an exchange calendar or live market observation. Keep coverage, confirmation and alignment separate The evaluator returns a reason along with the state. An unrelated row cannot replace a missing required slot, and a duplicate cannot increase coverage. Boundaries worth keeping explicit The upstream producer must establish correct session calendars and expected closes. The row identity uses exact supplied identifiers; it does not normalize symbol aliases or resolve continuous-futures adjustments. Unknown extra instruments are ignored, but a malformed row fails explicitly. The returned reason is the first blocker encountered in the check sequence; a production diagnostic view may need a complete issue list. This example has no price ranking, persistence threshold, liquidity model or order execution. A production system needs its own domain-specific gates, source provenance and failure handling.
