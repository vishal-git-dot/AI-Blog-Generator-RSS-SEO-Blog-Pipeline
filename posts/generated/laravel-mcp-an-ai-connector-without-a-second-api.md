# Laravel MCP: an AI connector without a second API

## Overview

Laravel 13, laravel/mcp 1.0, Passport 13, one public API. Our customers asked for something that sounds small. They wanted to ask their assistant about their site. Which pages lost their title since last week? Is the accessibility score moving? Launch the monthly audit and tell me what changed. Not a chatbot inside NessFlow: their own assistant, the one already open next to their inbox, connected to their NessFlow team. The Model Context Protocol is the standard way to do that. A server exposes tools, the assistant decides when to call them, and the user stays in the conversation. The protocol is the easy part. What decides whether the connector is still maintainable a year from now is what the tools stand on. The tempting path is one tool per question, each reaching into Eloquent. It works on the first afternoon, and it builds a second API: a second place where authorization is decided, a second validation of every filter, a second scoping to the tenant, a second shape for every resource. Those copies drift the way any two copies drift, quietly. In a multi-tenant product, the first drift that matters is a leak. We already had a public API, versioned, described by an OpenAPI document and tested against it. So the connector was built on one rule: the MCP server is a surface of that API, not a second product. 40 tools, 26 that read and 14 that act, over 51 published API operations. A typical read tool is a 25 line class with no logic in it. Its inputs, output schema, scopes, rate limit cost and annotations are derived from the API contract, and its execution is the API controller itself. 175 tests and 5,829 assertions hold the two surfaces together. What laravel/mcp takes off your hands The package owns the protocol: JSON-RPC, sessions, capability negotiation, the pagination of tools/list , the shape of a result. Everything else is left to the application, and that split is the right one. A server is a class, and it is mounted like a route. They reach the model once per session, before any tool, and they are where it learns the vocabulary: what a project is, where to start, what a quota of null means. They are also where the sequence between tools lives. A tool description in our catalogue never names another tool, because a description is read in isolation and a chain of cross references reads like an instruction injected into it. The rest of the package is just as Laravel shaped. shouldRegister() is called through the container, so a tool can ask for any service to decide whether it exists for the current caller. A result carries content for the model and structuredContent validated against a published outputSchema . Passport plugs in for OAuth with dynamic client registration, which is what consumer assistants expect when a user clicks "connect". Two defaults are worth knowing before production. tools/list is paginated at 15, and a client that does not follow nextCursor sees part of the catalogue without being told; ours lost its last tools that way, silently, hence the page of 50. The same model binding, under the team context, so a project of another team is a 404 for the connector exactly as it is for the API. The same validation of filters. The same cursor pagination. The same response shapes, already tested against the OpenAPI document. A bug fixed in the API controller is fixed in the assistant. Two details only show up when you do it. The network transmits strings, so an integer passed by a model ( limit: 2 ) failed the API's own rules until the invoker converted arguments the way the wire would. And a malformed identifier has to be refused before model binding: SQLite answers "nothing" for a garbage UUID, PostgreSQL raises 22P02 on a uuid column, and the connector would have reported an internal error in production on a test suite that passed. Annotations are derived, never written MCP tools carry four hints: read only, destructive, idempotent, open world. Clients use them to decide what to ask the user before calling. The specification's defaults are the trap. An absent destructiveHint means destructive, an absent openWorldHint means open world, so a tool that forgets them claims the worst about itself, and the major directories require all four to be explicit. So nobody writes them. A tool declares its nature, and the four hints follow. enum McpToolKind : string { case Read = 'read' ; case Write = 'write' ; case Billed = 'billed' ; case Destructive = 'destructive' ; } final public function annotations (): array { $kind = $this -> kind (); return [ 'readOnlyHint' => $kind -> readOnly (), 'destructiveHint' => $kind -> destructive (), 'idempotentHint' => $this -> idempotent (), 'openWorldHint' => $this -> openWorld (), ]; } Of the 40 tools, 26 are Read , 7 are Write , 5 are Billed and 2 are Destructive . Six are open world, the ones that make NessFlow reach a third party site or service, like launching a crawl. The method is final : a subclass cannot hand write a hint even by accident. One predicate for the catalogue and for the call The catalogue varies by caller. A connection that was granted read only does not list write tools. A plan without the backlinks module does not list the backlinks tool. That is a comfort for the model, which should not propose what the user cannot do. It is not the security. public function shouldRegister ( McpToolGate $gate ): bool { return $gate -> visible ( $this ); } final public function handle ( Request $request , McpToolGate $gate ): ResponseFactory { try { $gate -> authorize ( $this ); $gate -> consume ( $this ); $data = $this -> run ( $request ); $this -> ensureFits ( $data ); } catch ( Throwable $e ) { return $this -> refusal ( $e ); } // ... } visible() and authorize() call the same private method with the same inputs, which walks the refusals from the most general to the finest: the operational write switch, the verb the plan opens, the separate right to spend, the module, the scopes. A client can call a tool it never saw listed, so the call judges everything again. That pair is also a lesson about testing. The guard at the call is masked by the catalogue filter, because the package answers "unknown tool" before reaching it, so mutating either guard alone kills nothing. They are mutated as a pair, and the call guard is kept because a searchable catalogue will one day reach tools without listing them. Nothing that spends runs without a quote This is the agentic part, and it is a different problem from authorization. A model can be perfectly authorized and still wrong. It can misread a request, retry after a timeout, or follow an instruction it found in the text of a page it was asked to audit. So every tool that consumes the plan or destroys data answers its first call with a quote. $handle = $arguments [ 'confirmation' ] ?? null ; if ( ! is_string ( $handle ) || $handle === '' ) { return $this -> quote ( $arguments ); } The quote says what the gesture consumes, as used , limit and remaining for each quota of the plan, with null meaning unlimited and never zero. It returns a handle valid for ten minutes. Calling the tool again with that handle executes it, once. $quote = $this -> cache -> get ( $this -> key ( $handle )); if ( ! is_array ( $quote ) || $quote [ 'credential' ] !== self :: credential ( $identity ) || $quote [ 'tool' ] !== $tool ) { throw new ApiProblemException ( new ApiProblem ( 409 , 'confirmation.invalid' )); } if ( $quote [ 'arguments' ] !== self :: fingerprint ( $arguments )) { throw new ApiProblemException ( new ApiProblem ( 422 , 'confirmation.mismatch' )); } // One execution: whoever claims the handle first runs it. if ( ! $this -> cache -> add ( $this -> key ( $handle ) . A second call with a handle already redeemed replays the original response for 24 hours instead of spending twice, which is exactly what a model retrying after a timeout needs. It is the MCP version of the Idempotency-Key the API already required on billed writes. The rule that matters most is written at the top of the class: the handle is information, never authorization. When it is redeemed, every guard runs again at the point of spending, inside the action: plan, locks, spend brake. A quote obtained under one plan does not survive a downgrade. Three more limits sit around it. Spending is a separate right, unchecked by default on the consent screen, and without it the billed tools are not listed at all. Destructive tools are capped at three executions per connection, per tool and per day, counted and executed under one lock, because an independent security review found that parallel redemptions could all read the same count and cross the cap together. And the connector refuses inputs it will not honour instead of dropping them: a campaign created through the assistant cannot carry a crawl schedule, because a daily schedule is a recurring spend that no quote would ever cover. public function refusedInputs (): array { return [ 'schedule' ]; } Refused, with a stable code, never silently ignored. An ignored input lets the assistant announce a setting that was never applied. Confidentiality is mostly what never enters the conversation Everything a tool receives or returns passes through the assistant, and therefore through whoever runs the model. Most of the confidentiality design is deciding what never goes there. Secrets never enter a tool. Some campaigns crawl a site behind HTTP authentication, and the API accepts those credentials. The connector does not offer them as inputs at all. public function excludedInputs (): array { return [ 'http_user' , 'http_password' ]; } The activity journal records every write, successful or refused: the member, the credential, the client name, the tool, the target identifiers and the outcome code. No free text argument, no content, no IP address, and it is purged after 90 days. Team admins read it in NessFlow, on the same screen where a connection is revoked. Text from crawled sites is data. Titles, meta descriptions, page content and URLs come from a third party, and the connector is precisely a tool that reads pages written by strangers. Fourteen read tools return that kind of content, and their structured result opens with a notice saying so. We first carried that notice in the text summary, and the served test on 10 October 2026 showed why that was wrong: Claude Code forwards only structuredContent to the model, so the summary never reached it. The notice now travels inside the structured result, declared in its schema. A trap site with injection payloads in its title, metas, body, an alt , an HTML comment and an HTTP header is part of the test suite. A result that is too large is refused with an instruction, never truncated. Hosts cut results beyond roughly 150,000 characters, and a list cut in the middle reads like a complete list. Above 100,000 bytes the tool answers payload_too_large and asks for a smaller limit or narrower filters. Errors keep the API's stable codes, so the model can correct itself, and unexpected failures are reported and stay silent about their cause, because an exception message can carry SQL and its bindings. On the OAuth side, Passport needed tightening rather than extending. PKCE is required in S256 , where the library accepted plain by default. Redirect URIs are compared exactly against a list, after the review found that domain matching accepted any path on an allowed host. The consent screen asks for the password again when the last confirmation is older than 15 minutes. A refresh token that comes back after rotation revokes the whole connection. What production taught us in one day The served test on 10 October 2026, with a real assistant connected to mcp.nessflow.com , found defects that no feature test could have seen, because none of them involves our code alone. Five of them: Claude Code registers through a client metadata document that declares http://localhost/callback without a port, then redirects to a port chosen at runtime. The OAuth library frees the port for 127.0.0.1 and [::1] only, so localhost was compared byte for byte and refused. Fixed with a loopback aware authorization code grant, strict on the host. The consent screen loaded one shared Inertia prop lazily. The product's screens run on Inertia ( on purpose ), and here the framework did exactly what it promises, on the one page where that promise was wrong. Only structuredContent reaches the model in some hosts, as described above. A client keeps the schemas it read at connection time and validates every response against them. Our output schemas were closed, so the first deployment that added a field broke every open session until it reconnected. whoami did not say that a team set to read only cancels a connection's write rights, so the assistant described rights it did not have. The fourth one changed a rule. Schemas are now published open and tested closed. public static function openSchema ( array $schema ): array { if (( $schema [ 'additionalProperties' ] ?? null ) === false ) { unset ( $schema [ 'additionalProperties' ]); } foreach ( $schema as $key => $value ) { if ( is_array ( $value )) { $schema [ $key ] = self :: openSchema ( $value ); } } return $schema ; } Our tests validate every response against the strict schema, so an unexpected field still fails the suite. Clients see a schema open to additions. A removal, a rename or a type change remains a contract change: additive first, removal in a later deployment. What it costs The connector is welded to the API contract. That is the design, and it has a price. A change to an API response is a change to an MCP tool, and since clients cache schemas for the life of a session, a breaking change also breaks open conversations. Additive first, removal later, on both surfaces at once. We own a piece of framework plumbing. The in-process invoker swaps the container's request, substitutes bindings and restores the request afterwards. It is 205 lines nobody else maintains, and the restoration step survived a mutant the first time, because nothing in an MCP request reads request() after the tool. It now has a direct witness. A quote doubles the round trips. Every billed or destructive gesture is two calls, and the model has to carry a handle between them. That is latency and tokens on every spend, by design. Tool count is a budget. Every definition sits in the model's context for the whole session. We split reports into five tools rather than one parametrised tool because their rate limit costs differ, and a composite tool would have been charged the sum. At about forty tools, the next step is a searchable catalogue rather than a longer list. The suite grows with the catalogue. The connector's feature tests are 175 tests, 5,829 assertions and 14.7 seconds, and the mirror calls every read tool twice. That is cheap for what it proves, and it is wall clock added to every run. Feature tests cannot see the client. Five production defects on day one, all at the junction with a real assistant. Touching the consent screen or a schema now means a test with a real client, and a reconnection for sessions already open. What transfers Not our classes. They fit an application that already had an API described by OpenAPI and tested against it, and their shape follows from that. What transfers is the question we asked before writing the first tool: what already decides this in the application? Authorization, tenant scoping, validation, rate limits, response shapes. If the answer is "the API", the MCP server should be a projection of it, and laravel/mcp makes that projection cheap, because a server is a route, a tool is a class and registration goes through the container like everything else. The second thing that transfers is the quote. An assistant should be able to read freely and act deliberately. A tool that spends or destroys returns what it would do, and executes only when called back with that exact intent. It turns a model's mistake into a question the user can answer, which is the right place for an agentic product to put its trust.
