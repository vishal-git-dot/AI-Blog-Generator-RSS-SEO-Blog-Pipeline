# Two Files 100 Nanoseconds Apart Got the Same Timestamp in the Browser: JSON.parse and Integers Past MAX_SAFE_INTEGER

## Overview

A small Python server lists a folder of clips as JSON, with each file's modification time in nanoseconds. The browser page that reads that list decided two of the three files had the same timestamp, and when it sent one timestamp back to ask whether that file had changed since the listing, the server answered yes. Nothing had changed. The numbers were simply too large for JSON.parse to hold. Disclosure: I make an Android camera app. Nothing below uses its code or describes how it lists, names or stores files. Everything here ran on one Linux machine (kernel 6.8, Python 3.10.12, Node.js v22.23.2) against files the scripts create themselves. What the tests showed: Python wrote the timestamps exactly; Node's JSON.parse rounded two of them. Two files that were modified 100 nanoseconds apart came out with the same value. The rounded value round-tripped as a different number. The page sent back a timestamp the server had not written, so an only if unchanged check failed. A reviver can see the original digits. In Node 22 the third reviver argument, context.source , holds the exact text, so the value can be rebuilt as a BigInt. Sending a BigInt back needs one more step. JSON.stringify throws on a BigInt; JSON.rawJSON writes the digits out unchanged. The setup The script below makes three empty files and sets their modification times 100 nanoseconds apart with os.utime(ns=...) , so the result is the same on every run. The value for b.mp4 rounded down onto a.mp4 . The value for c.mp4 became 1792467605000000256, and Node prints that as 1792467605000000300, the shortest decimal that maps back to the same double. The check failed because the page could not hold the number it was asked to repeat. Turned around, the same rounding can make a check pass that should fail: a.mp4 and b.mp4 hold the same value on the page, so a page-side newer-than test cannot tell them apart. MDN's JSON.parse page puts the cause plainly: the reviver "is run after the value is parsed. So, for example, numbers in JSON text will have already been converted to JavaScript numbers, and may lose precision in the process." Plain JSON.stringify on an object holding a BigInt throws TypeError: Do not know how to serialize a BigInt . The page would fail at the moment it tried to send. A replacer that wraps each BigInt in JSON.rawJSON writes the digits as a bare JSON number. MDN describes the purpose of JSON.rawJSON in those terms: "The most typical use case is the floating point number loss of precision problem." With the fixed request in place, the server check passes: server has 1792467605000000200 page sent 1792467605000000200 unchanged? True Support is the cost of this route. MDN lists JSON.rawJSON as Baseline 2025 and says "Since March 2025, this feature works across the latest devices and browser versions. This feature might not work in older devices or browsers." The two older escapes Send the field as a string. MDN's own suggestion on the JSON.parse page is "to serialize them as strings, and revive them to BigInts, or other appropriate arbitrary precision formats." A string survives any JSON parser, old or new. The catch is ordering: // If the server sends the field as a string, the digits survive any parser. const clips = JSON . parse ( ' [{"name":"a.mp4","mtime_ns":"1792467605000000000"}, ' + ' {"name":"b.mp4","mtime_ns":"1792467605000000100"}] ' ); console . log ( " a === b: " , clips [ 0 ]. mtime_ns === clips [ 1 ]. mtime_ns ); // Ordering is the catch: strings compare character by character. console . log ( ' "999" < "1000": ' , " 999 " < " 1000 " ); console . log ( " as BigInt: " , BigInt ( " 999 " ) < BigInt ( " 1000 " )); a === b: false "999" < "1000": false as BigInt: true Equality on strings is exact. Ordering is not, once the strings differ in length. Nanosecond timestamps from the same era all have the same number of digits, so a plain string sort works on them for now, but an ID field that grows from 999 to 1000 will sort wrong. Convert to BigInt before comparing for order. Send whole milliseconds. Dividing by a million brings the value well under the safe limit, and every JSON parser handles it: # Dropping to whole milliseconds keeps the number safe, and loses the order. import json clips = json . load ( open ( " clips.json " )) for c in clips : ms = c [ " mtime_ns " ] // 1_000_000 print ( c [ " name " ], ms , ms <= 2 ** 53 - 1 ) a.mp4 1792467605000 True b.mp4 1792467605000 True c.mp4 1792467605000 True The number is safe and all three files now share it. For a gallery that sorts by date, that is usually fine. For an only if unchanged check, it means a file rewritten within the same millisecond looks unchanged, which is the failure the check exists to catch. If a server needs exact change detection, a millisecond timestamp alone is the wrong field. A content hash or a version counter sent as a string avoids the question. What I would do with this On the server, send any integer that can exceed the safe limit as a string. Nanosecond times, 64-bit IDs and byte offsets into very large files are the usual suspects. This works for every client. On the page, convert those strings to BigInt where order matters, and keep them as strings everywhere else. If the API already sends bare numbers and cannot change, revive the affected fields with BigInt(context.source) and send them back with JSON.rawJSON , after checking that every browser the page has to support has both. Add the Number.isSafeInteger audit from guard.js to a test that parses a real response. It fails loudly on the first unsafe integer. Things I did not test Browsers.
