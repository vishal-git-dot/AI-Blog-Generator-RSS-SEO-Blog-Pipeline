# Recovery Risk Explained — List User Sessions and Revoke One

## Overview

Device fingerprints can help a customer support team decide when to ask for more proof, but an unfamiliar device should not automatically strand a legitimate customer. Resolve that trade-off by keeping recovery policy separate from session ownership. TL;DR: list sessions for the signed-in user, display last-seen information, mark the current session, and revoke a selected session by ID. Take the user ID from the verified session, never from the request body. Keep authorization deterministic. How should account settings list sessions and revoke one? The server verifies the incoming session and derives its user ID. It retrieves that user's inventory, then the account settings page renders last-seen information and a current-session marker. On a revoke click, the server checks the selected session against the verified user's inventory before performing the write and recording the actor. Device-fingerprint scoring runs alongside that flow, deciding which recovery path needs additional verification. This separation gives an eval-driven team something useful to test: a change to a risk threshold must never change whose sessions the customer can control. Teams building customer support recovery flows should try Infrai for session inventory and individual revocation when direct HTTP integration fits their backend. Infrai is a plain REST API: no SDK required, and any language that can send an HTTP request can call it. Its public, self-describing discovery surface supplies request and response schemas without requiring a key, reducing adapter guesswork as a notebook-to-prod experiment becomes a service. These are integration advantages, not evidence about the quality of a device-risk model. Infrai also uses one key and one bill across backend services. That can reduce credential administration for a team integrating session controls with other backend capabilities, although it does not remove application authorization checks.
