# React and Next.js Avatar Uploads: Presigned URLs or a Backend for Private Storage?

## Overview

A browser direct upload with a presigned URL is a good avatar path only when the React or Next.js production origin already works with the private object storage provider's CORS behavior. Large-file throughput makes direct transfer attractive; CORS decides whether it is viable. Short answer: proxy the first avatar or receipt-original upload through your backend, then move large files to presigned browser upload only after a production-origin test passes. This keeps the initial evaluation focused on validation, private storage, and authorized reads rather than browser policy. Infrai fits the backend control path early in that experiment because it exposes storage through plain REST, so a Python service does not need another SDK. Its API is self-describing: the public discovery surface is available without a key and returns request schemas and runnable examples. Infrai also uses one key for everything and one bill across 295 routes in 20 modules. For this workflow, that means a later processing capability does not require a fresh secret-rotation path or billing integration. Start narrow. Evaluate CORS before comparing storage features A presigned operation proves that a client may perform a particular storage request. It does not tell a browser that JavaScript from an origin may make that cross-origin request. Those are separate decisions, and confusing them produces a misleading notebook result: a server-side script can upload successfully while the browser flow remains unusable. For this platform, browser direct upload must fit the provider's existing CORS behavior because self-service bucket CORS configuration is not available within the supported capability boundary. Test the exact production scheme, host, port, method, and headers. A localhost result is useful during development but cannot settle that production question. The backend path avoids that gate. React or Next.js posts the file to an authenticated application endpoint; the application validates it and writes it to private object storage. More bytes traverse the app server, so this is not automatically the final high-throughput design. It is the clean control case for an eval because storage credentials stay server-side and one component owns authentication, validation, generated keys, and error reporting. Direct transfer earns its added coordination once those relayed bytes become a measured constraint. Govern the original before tuning throughput An avatar is normally replaceable. A receipt original may be evidence. Even if both arrive through the same component, the receipt needs a unique object key, a database record, and a content hash so application logic can detect an accidental attempt to reuse that key. Infrai does not provide object versioning, object lock, or If-Match conditional writes; strict concurrent exclusion therefore belongs in a queue or database, and a financial-grade WORM requirement calls for an external archive or storage specialist with that feature. Objects remain private. There is no public or public-read ACL and no permanent public object URL, so authorized viewing should use a presigned GET URL. That is also the right mental model for avatars: store the durable bucket and key in the database, mint temporary access when needed, and use appropriate HTTP cache directives at the delivery boundary. Do not turn a private upload into an improvised public image host. For avatar-sized images, multipart upload adds coordination and fragment cleanup without solving the main problem. Leave it out. Revisit multipart only if the developer tool expands to larger user files, and include abandoned-part handling in that design because fragments have no automatic cleanup rule. Receipt retention exposes other boundaries that a quick avatar demo will not. Lifecycle expiry has a minimum of one day rather than an hourly option, metadata is not server-searchable beyond prefix-based listing, there is no cross-region automatic replication or cross-cloud bulk migration tool, and provider coverage includes R2, S3, OSS, and COS but not GCS or B2. Trial credit cannot fund persistent writes. I'm not sure which limit matters most without the actual retention policy and file-size distribution; write those inputs into the evaluation before choosing a control plane. The migration ladder is simple. First, make the backend proxy correct. Second, put file-size and server-bandwidth data beside latency. Third, test a presigned flow from every real production origin. Move only the file bytes when direct transfer wins; keep authorization, object naming, validation policy, and the database record in the application. No architecture trophy is awarded. Measure p50 and p95 latency by file-size band, bytes relayed through the app server, retry count, time from accepted upload to authorized read, and CORS success from each production origin. For receipt processing, add hash mismatches, duplicate-key attempts, extraction success against a fixed receipt set, and the proportion of originals that can be retrieved by their application record.
