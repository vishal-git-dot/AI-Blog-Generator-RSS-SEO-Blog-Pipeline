# How to Scrape Kalshi with Python: Markets, Order Books, Price History, and a Snapshot Tracker (2026)

## Overview

Kalshi has become one of the more interesting public datasets around. Every market is a running, money-backed estimate of how likely something is: an election, a Fed decision, tomorrow's high temperature in New York. If you do research, build dashboards, or want to compare Kalshi against polls or other prediction markets, you'll want that data in your own database. The good news is that you don't need to scrape HTML at all. The Kalshi API serves market data publicly, with no key and no login. The less good news is that it has a handful of quirks that will quietly give you wrong numbers if you don't know about them. In this post I'll build a small Python Kalshi scraper that: Pages through every open market in a series Reads the order book the right way (it only lists bids, more on that below) Exports hourly price candles to CSV Stores a snapshot on every run in SQLite, so you can see which markets moved Everything here was run against the live API in October 2026. Before you start: read Kalshi's API docs and Terms of Service, keep request rates low, and don't redistribute the data commercially without checking what you're allowed to do. This tutorial only reads public market data. It doesn't place orders and doesn't need an account. Your options, briefly Public market data endpoints (this post). GET requests under https://api.elections.kalshi.com/trade-api/v2 for markets, events, series, order books, trades, and candlesticks. No auth needed. Authenticated API. You need an account and an RSA-signed API key for anything that touches your portfolio: orders, fills, balance, and a few account endpoints. You don't need it for reading markets. WebSocket feed. Better if you want real-time ticks, but it needs an authenticated connection and you have to handle reconnects yourself. For a snapshot every few minutes, REST is simpler. Scraping kalshi.com HTML. Don't bother. The site is a JavaScript app that calls the same API anyway. How Kalshi data is shaped There are three levels, and the tickers tell you where you are: Series KXHIGHNY "Highest temperature in NYC" (recurring) Event KXHIGHNY-26OCT21 one occurrence: Oct 21, 2026 Market KXHIGHNY-26OCT21-T66 one yes/no contract: "above 66°?" A market is always a binary yes/no contract that pays $1. Prices are in dollars between 0 and 1, so a YES price of 0.23 means the market puts it at roughly 23%. To get a series ticker from a market page, look at the URL. On kalshi.com/markets/kxhighny/... , the first path segment uppercased ( KXHIGHNY ) is the series ticker. The status you filter by isn't the status you get back. You ask for status=open , but the records come back with "status": "active" . If you filter again on your side with == "open" , you'll get zero rows and spend ten minutes thinking pagination is broken. Unfiltered listings are full of combo markets. If you call /markets?status=open without a series or event, the first pages are auto-generated multi-leg "combo" markets with tickers like KXMVECROSSCATEGORY-... , mostly with zero volume. Add mve_filter=exclude to leave them out, or better, always scope by series_ticker or event_ticker . Step 3: Turn markets into clean rows Here's the part that bites people who copy older tutorials: Kalshi sends prices and sizes as strings , with suffixes on the field names. Older posts use integer-cent fields like yes_bid and volume . What you get now looks like this: "yes_bid_dollars" : "0.0100" , "yes_ask_dollars" : "0.0200" , "last_price_dollars" : "0.0200" , "volume_fp" : "2428.47" , "open_interest_fp" : "2252.09" _dollars is a price, _fp is a fixed-point count (contracts can be fractional now). Step 4: Read the order book the right way GET /markets/{ticker}/orderbook returns this: { "orderbook_fp" : { "no_dollars" : [[ "0.9600" , "441.00" ],[ "0.9700" , "592.00" ],[ "0.9800" , "398.00" ]], "yes_dollars" : [[ "0.0100" , "286.82" ]] }} Notice that there are no asks. Kalshi only lists bids for YES and bids for NO. Because a YES and a NO together always pay $1, a NO bid at 0.98 works the same as a YES ask at 0.02. So the best YES ask is 1 - best NO bid : def best_levels ( ticker ): ob = get ( f " /markets/ { ticker } /orderbook " , { " depth " : 5 })[ " orderbook_fp " ] yes_bids = ob . get ( " yes_dollars " ) or [] no_bids = ob . get ( " no_dollars " ) or [] best_yes_bid = max (( Decimal ( p ) for p , _ in yes_bids ), default = None ) best_no_bid = max (( Decimal ( p ) for p , _ in no_bids ), default = None ) # Only bids are listed. A NO bid at 0.97 is a YES ask at 0.03. implied_yes_ask = ( Decimal ( " 1 " ) - best_no_bid ) if best_no_bid is not None else None return best_yes_bid , implied_yes_ask Levels are sorted with the best price last, which is why I use max() instead of trusting the order. An empty side comes back as missing or empty, so handle None . In my run, one of the busiest markets had no YES bids at all, because it was all but settled at zero. Yesterday's markets are still in the open list, priced at 0.01 or 0.99, because trading has stopped but they haven't been settled yet. If you're looking for live opinion, filter on close_time in the future, or you'll be ranking markets that are already decided. The walls you'll hit Schema drift. The move from integer cents to _dollars and _fp strings broke many older scripts without any error message. Log a warning when an expected field is missing instead of quietly writing None . Rate limits without hints. A 429 doesn't tell you how long to wait. Use exponential backoff and a small sleep between pages. If you're polling hundreds of order books, you'll hit the limit faster than you expect. Volume and pagination. Some series, like sports and crypto, have thousands of markets. Scope by series or event and limit columns to what you need. Settled vs. closed vs. active. Status values in filters and records don't match one to one. Write down which states you care about and test them. What isn't in the public API. Trader profiles, the leaderboard, and comments are on the website but not in the public market data endpoints. Scraping those means dealing with the web app itself, which is much more fragile. Terms. Market data is public, but that doesn't make every use OK. Read Kalshi's terms before you publish or resell anything. When DIY stops being worth it For a few series checked every 15 minutes, the script above is all you need, and it's free. It gets tedious when you track a lot of series, want Polymarket and Kalshi in the same format, or need the profile and leaderboard data that the public market endpoints don't have. At that point I'd use a hosted API. I use ScrapeAtlas* for this. Its /v1/kalshi/markets endpoint takes series , event , tickers , status , closesAfter / closesBefore , cursor , and limit (1 to 200). There are also /v1/kalshi/price-history , /v1/kalshi/orderbook , /v1/kalshi/trades , /v1/kalshi/leaderboard , and /v1/kalshi/profile endpoints if you need history, depth, or trader data. Wrapping up Use the public API, not HTML. Kalshi market data is a GET request away, with no key. Parse _dollars and _fp strings as Decimal , and don't trust tutorials that use integer-cent fields. The order book only has bids. YES ask = 1 − best NO bid. Scope by series or event , exclude combos, and filter out markets that are closed but not yet settled. Snapshot on a schedule if you care about movement. Use candlesticks if you only need history.
