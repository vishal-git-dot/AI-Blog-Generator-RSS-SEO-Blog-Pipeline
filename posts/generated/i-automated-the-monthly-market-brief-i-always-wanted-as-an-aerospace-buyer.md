# I automated the monthly market brief I always wanted as an aerospace buyer.

## Overview

I spent four years buying aircraft parts, from propulsion components to avionics. Often, there was only one supplier to turn to, and I’d find out about a price increase when it landed in my inbox. Every month I had the same three questions before a negotiation: Is demand for these parts going up or down? Are supplier prices moving, and how fast? What is the exchange rate doing to my import cost? The answers exist, all of them public and free. They are just spread across three government sources that update on different days, in different formats, in two languages. So I built a pipeline that collects them, does the math and writes the one-page brief I wanted back then. It runs by itself on the 16th of every month. Repo: stephanyalves-eng/procurement-market-briefs What it produces Every edition has six one-page reports, each in English and Brazilian Portuguese, as HTML, PDF and PNG: Report Data Aerospace Supply Market Brief Public: Comex Stat, BLS PPI, Banco Central PTAX Brazil EV Supply Chain Brief Public: Comex Stat, import duty schedule Monthly Procurement Performance Report Synthetic buyer, indexed to public prices and FX Monthly Supplier Quality Report Synthetic EV plant Six Sigma Supplier Quality Report Synthetic EV plant Supplier Non-Conformance Report Synthetic EV plant The synthetic ones are labeled as synthetic on the page and in the README. More on how they are built below, because that part turned out to be the most interesting problem. Each page answers one sourcing question and ends with actions. The November edition opened with: aircraft parts imports up 11.1%, avionics producer prices up 17.2%, and a sharp BRL selloff raising import costs. A buyer can read that in ten seconds and walk into a meeting with it. How it works The flow has four steps: Fetch. pipeline/fetch_public.py downloads PTAX and IPCA from the Banco Central do Brasil, producer price indexes from the U.S. Bureau of Labor Statistics and import statistics by NCM code from Comex Stat. Extend the synthetic data. pipeline/synthetic.py appends the new month to a fictitious buyer's purchase orders, RFQs and quality notifications. Build. One Python module per report computes the metrics, draws the charts with matplotlib and writes the text. Playwright renders each page to an A4 PDF. Publish. A GitHub Actions workflow commits the new edition and attaches it as an artifact. Three decisions made the difference between a script that works once and a pipeline that runs every month without me. 1. The schedule follows the data, not the calendar The first instinct is to run on the 1st. That would publish stale numbers, because the sources release on different days. Comex Stat publishes the previous month early in the month, and the BLS releases the PPI around mid-month. So the workflow runs on the 16th, after both are out: on : schedule : # 16th of every month, 11:23 UTC (08:23 in Brasília) - cron : "23 11 16 * *" workflow_dispatch : The Comex Stat API only accepts a few requests per minute, so the client waits between calls and backs off on errors. That is why the job has a 90 minute timeout: the download alone takes 10 to 30 minutes. Every source also fails soft. If one API is down, the pipeline keeps the last file it has, finishes the edition and records the problem: for name in SOURCES : try : SOURCES [ name ] ( end ) except Exception as e : failed . append ( name ) log ( f "WARNING {name} failed, keeping the previous file: {e}" ) The page then states how far each source goes, so a reader never mistakes old data for new data. In procurement, a brief that silently shows last month's exchange rate is worse than no brief. 2. The headline is computed, not written This is the part I like most. A monthly report with a fixed sentence like "prices increased" is wrong the first month prices fall. So every headline, highlight and action is built from the numbers and changes wording when the data changes direction: up = k [ "g" ] >= 0 h1 = f "Aircraft parts demand {'up' if up else 'down'} {abs(g):.1f}% " \ f "and avionics prices {'up' if av >= 0 else 'down'} {abs(av):.1f}%" if fx_event and fx_event [ "chg" ] > 0 : h2 = ", while a sharp BRL selloff raises import costs" elif k [ "vs" ] < - 2 : h2 = f ", with the BRL still {abs(k['vs']):.0f}% stronger than a year ago" elif k [ "vs" ] > 2 : h2 = f ", and a BRL {k['vs']:.0f}% weaker than a year ago adds to import costs" else : h2 = ", with the BRL back near last year's level" (Simplified from briefs/aerospace.py , which also builds the Portuguese version in the same step.) The same idea handles layout. Long text would push a page past one A4 sheet, so render_fit renders the page, measures its height and tightens spacing step by step until it fits in 1123 px. The edition manifest records which level each page needed, which tells me when a text should be edited instead of squeezed. 3. Synthetic data that cannot see the future Real purchase order data is confidential, so the procurement and quality reports run on a fictitious company. The hard part was not generating fake rows. It was making a dataset that behaves like a real ERP export month after month. A real buyer looking at open orders on October 31 does not know which ones will arrive late in November. If the generator just created each month's data fresh, late deliveries would appear out of nowhere and the trend lines would jump. So the dataset has two layers: Truth tables hold every record with its real future dates: when an order will actually arrive, when a quality notification will actually close. The view is what a buyer would see on the cutoff date. Future receipts stay blank and open notifications stay open. def view ( cutoff ) : """Tables as a buyer would see them on the cutoff date.""" c = cutoff . isoformat ( ) P = P [ P . data_pedido <= c ] . copy ( ) P [ "data_recebimento" ] = np . where ( P . receb_real <= c , P . receb_real , "" ) . . . Two more rules keep it honest over time. Each new month is generated with a random seed derived from its own dates, so any edition can be rebuilt exactly. And extending the data only appends days after the last generated date; it never rewrites a past record. October's report does not change because November was generated. Prices in the synthetic orders are not random either. Each part category is indexed to the real BLS PPI series for its industry, and the currency conversion uses the real monthly PTAX. The company is fake, but its costs move with the real market. How I built it I developed this with AI pair programming (Claude). The split matters, so here it is plainly: the business questions, the choice of sources and metrics, the data logic (including the truth and view design for the synthetic data) and the review of every number are mine. The AI wrote much of the code with me and sped up the parts I am still learning. For someone coming from procurement into data, that is the honest way to work: I know which question a buyer needs answered and how to check that the answer is right, and the AI closes the gap between that and running code. What I would do differently Headline templates grow fast. Every new condition multiplies the branches I have to keep consistent in two languages. A small rules table would scale better than nested if statements. One run a month hides problems. A dry run a few days before the 16th, with --skip-fetch , would catch layout or data issues before the real edition. Monthly data is the ceiling. The PTAX is daily, but Comex Stat and the PPI are monthly, so the brief cannot react faster than its slowest source.
