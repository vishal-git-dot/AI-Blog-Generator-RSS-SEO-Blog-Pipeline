# Meta Said a Claude Tool Browsed at 4x Human Speed. Here's a 124-Line Python Fix for Impolite AI Agents

## Overview

On Saturday, 17 October, Instagram suspended the No Kings Coalition's account for about 90 minutes. On Sunday, Meta's communications VP Andy Stone said a tool linked to Anthropic's Claude had accessed the coalition's profiles, posts and hashtags at roughly four times normal human speed, in short intense bursts that resembled automated bot traffic. Meta called the suspension an error and apologised. It did not say which tool it was, who ran it, or what it was doing. So we don't know the full story, and I'm not going to pretend we do. But the mechanism Meta described is one I see constantly in agent projects: a model in a loop, a browser or HTTP tool, and nothing between them that understands "slow down". The platform's abuse systems don't care that the traffic came from a helpful assistant. They see bursts, and they act on the account or the IP behind them. This post is the guardrail layer I now drop into every agent that touches the web. It is 124 lines of standard-library Python. I ran it against a mock server that pushes back, and the real output is below. What "polite" means in code Seven things, each small: Per-host token bucket. A steady pace per site (default 12 requests a minute, burst of 2), so the agent can't fire 40 requests the moment the model decides to "check all profiles". Random jitter. A human doesn't click every 5.000 seconds. A fixed interval is itself a bot signature. Backoff on 429 and 503. If the server sends Retry-After , honour it exactly, in either of its two formats (seconds or an HTTP date). If not, back off exponentially with jitter. robots.txt. Checked with urllib.robotparser before any request, and Crawl-delay lowers the bucket rate if the site asks for it. An honest User-Agent. Name the bot and give a contact URL and email. Site operators can then reach you instead of blocking a whole range. A daily action cap. A hard ceiling that a runaway loop cannot get past. Retries count, because the server sees them too. An append-only action log. One JSON line per action, including the ones that were refused. When something goes wrong you can answer "what did the agent actually do?" in seconds. The honest caveats This is the part I care about most. Politeness is not permission. If a platform's terms forbid automated access, a slow and well-labelled bot still breaks them. This toolkit reduces collateral damage. It doesn't make prohibited automation acceptable. Prefer the official API. Meta, X, LinkedIn and most large platforms publish APIs with explicit quotas. Use them. Rate limits you are told about beat rate limits you guess. Logged-in scraping is a different risk. robots.txt governs crawlers on public pages. Once your agent uses a real person's session, the platform's account rules apply, and those usually prohibit automated access regardless of pace. The account you lose may belong to your client. Human pace is not a disguise. Jitter exists to avoid hammering servers, not to evade detection. The honest User-Agent is deliberate. If you're tempted to remove it, that's a sign the task shouldn't be automated. This covers HTTP, not browsers. If your agent drives a headless browser, every page load fires dozens of sub-requests. Put the bucket in front of navigations and clicks, and count each as an action. It's single-process. Run five workers and you get five budgets. For a fleet, move the bucket and counter into Redis or your database. Checklist before your agent touches someone else's site [ ] Is there an official API? Use it instead. [ ] Do the terms of service allow automated access for this use? [ ] Is every outbound request going through one rate-limited client? [ ] Does the User-Agent name the bot and give a working contact? [ ] Is robots.txt checked, including Crawl-delay? [ ] Does it honour Retry-After and back off on 429 and 503? [ ] Is there a hard daily cap that survives restarts? [ ] Can you reconstruct every action from the log? [ ] If it runs inside a user's logged-in session, has the user agreed and do the platform rules allow it? Rate limiting is only half of making an agent safe to deploy. The other half is controlling what the model is allowed to decide in the first place.
