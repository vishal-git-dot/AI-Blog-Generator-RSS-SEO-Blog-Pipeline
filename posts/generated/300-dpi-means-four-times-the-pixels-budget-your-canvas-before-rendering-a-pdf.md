# 300 DPI means four times the pixels: budget your canvas before rendering a PDF

## Overview

A JPEG size limit is checked after encoding. A canvas has to exist before that encoding can happen. That ordering matters in a browser PDF-to-image pipeline. Lowering JPEG quality can reduce the downloaded file while leaving the rendering dimensions unchanged. It is useful to give the raster its own budget before asking the browser to allocate it. AI disclosure: this article and its examples were prepared with AI assistance. The pixel calculations and budget invariants were checked with executable Node.js tests. The figures below are a storage model, not measurements of a browser's memory usage. Doubling DPI squares the pixel count Take a US Letter page represented as 612 × 792 PDF points. With 72 points per inch, the scale for a requested DPI is dpi / 72 . Doubling that scale doubles both dimensions. Here is the result for an uncapped page. The last column assumes an 8-bit RGBA buffer: four bytes per pixel, divided by 1,048,576 to express MiB. DPI Dimensions Pixels One RGBA8 buffer (MiB) 150 1275 × 1650 2,103,750 8.03 300 2550 × 3300 8,415,000 32.10 The raw pixel count is four times larger at 300 DPI. The eventual JPEG size does not appear in that calculation. MDN's ImageData reference describes RGBA ordering and the rgba-unorm8 pixel format. That gives a useful estimate for one RGBA8 buffer, not a guarantee about a canvas implementation. PDF decoding, fonts, image caches, temporary encoder buffers, retained downloads, and browser overhead are outside this table. A browser may use other pixel formats or storage strategies. Put limits on both area and edge length A pixel-area limit by itself leaves a gap: a very long, thin page may fit the area budget but exceed a browser's dimension limit. An edge limit by itself lets a square consume more pixels than intended. Use the smallest scale allowed by the requested DPI, either edge, and the total area. Then round the dimensions down and validate the final integer grid. This example rejects a grid that cannot satisfy the limits instead of silently returning an oversized result. They do not allocate a canvas, render a PDF, measure peak memory, or establish a safe device-specific limit. Those need separate browser tests with representative files. Budget the rest of the pipeline too The raster cap controls one page's dimensions. A multipage converter still needs a concurrency policy and a budget for retained output. An unbounded Promise.all over pages can start several renders before any encoder finishes. Processing pages sequentially, or with a small bounded pool, limits the number of active page jobs. With PDF.js, the same canvas also cannot render two pages simultaneously . Await the render and encoding work before reusing it. After a page is finished, clear references that are no longer needed and reset the temporary canvas dimensions in a finally block. Assigning canvas width resets its rendering context . Resetting dimensions is resource cleanup, not proof that the process's reported memory immediately drops. Meanwhile, the completed JPEG blobs may remain in memory for individual downloads or a ZIP. Count their blob.size values separately and stop retaining results when the application's output budget would be exceeded. That accounting does not include every byte an encoder or ZIP builder may temporarily allocate. A partial conversion should report its completed-page count and stop reason. An output limit reached after several pages is useful recoverable information; displaying the same success message as a complete conversion would hide the missing pages. The practical checks belong at different stages: calculate the raster dimensions before allocation, bound active jobs while rendering, and account for retained encoded files as they become ready. A small downloaded JPEG is evidence about the last stage only.
