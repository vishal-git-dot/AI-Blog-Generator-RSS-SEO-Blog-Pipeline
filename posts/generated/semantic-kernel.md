Semantic Kernel Fundamentals What Semantic Kernel is Semantic Kernel is a lightweight, open-source SDK (C#, Python, Java) that sits between your application and AI models. It provides: CONNECTORS A uniform way to talk to many AI providers (OpenAI, Azure OpenAI, Ollama, Hugging Face, and others) for chat, embeddings, image, and audio. PLUGINS A way to expose your own C# code (and APIs) to the model as callable tools. FUNCTION CALLING Automatic orchestration of the model <-> tool loop. PROMPT TEMPLATES Reusable, parameterized prompts with variables and function calls. MEMORY Chat history management and vector-store abstractions for retrieval. AGENTS Higher-level abstractions for autonomous, tool-using assistants and multi-agent systems. FILTERS Interception points for logging, approval, redaction, and safety. OBSERVABILITY Logging, metrics, and OpenTelemetry tracing built in. The Kernel: a service container plus an orchestrator The central object is the Kernel . BUILT-IN Core plugins (time, text helpers, etc.) — convenient, but review what you expose. Designing plugins well - THE DESCRIPTIONS ARE THE API. The model decides when and how to call a function from its name, its [Description], and its parameter descriptions. Write them like documentation for a new colleague: what it does, when to use it, what the arguments mean, and any limits. - SMALL, FOCUSED, WELL-NAMED functions beat a few giant ones. Use clear verbs (get_order_status). - LEAST PRIVILEGE. Expose only what the scenario needs. Every function you add is something a prompt-injected or confused model could call. - SEPARATE READ FROM WRITE. Reads are low risk; writes and irreversible actions (cancel, send, delete, pay) deserve confirmation (Section 5) and clear warnings in their descriptions. - RETURN SMALL, USEFUL TEXT. Whatever the function returns goes back into the model's context window and counts as tokens. Return the few fields needed, not an entire database record. - ENFORCE AUTHORIZATION IN CODE using the authenticated user (as above). Never let the model supply "which user am I acting as" as a parameter. - VALIDATE ARGUMENTS like any untrusted input — they come from a model steered by user text. Use parameterized queries; never concatenate them into SQL or shell commands. - RETURN HELPFUL ERRORS AS TEXT ("No order 123 found for this customer") so the model can recover or explain, instead of throwing opaque exceptions. 4. Function Calling Semantic Kernel runs the tool-calling loop for you In AI APIs with .NET , Section 6, you wrote the loop by hand: send tool definitions, receive tool calls, run them, send results back, repeat. Semantic Kernel does exactly that automatically when you enable function calling. 1. SK converts each registered kernel function (name, description, parameter schema from your C# types) into the tool definitions the model understands. 2. The model replies with a request to call a function (name + JSON arguments). 3. SK deserializes the arguments, invokes your C# method, and appends the result to the chat history. 4. SK calls the model again with the results — repeating until the model produces a final answer. var settings = new OpenAIPromptExecutionSettings { FunctionChoiceBehavior = FunctionChoiceBehavior . Auto () // offer all kernel functions; auto-invoke the chosen ones }; var history = new ChatHistory ( "You are a helpful customer-support assistant for ACME." ); history . GetChatMessageContentAsync ( history , settings , kernel ); // pass the kernel! Console . WriteLine ( reply . Content ); Passing the kernel is what gives the chat service access to your plugins. Function choice behaviors FunctionChoiceBehavior.Auto() The model decides whether and which functions to call; SK invokes them automatically (the default pattern). FunctionChoiceBehavior.Required() The model MUST call a function (useful to force structured extraction or a specific action). FunctionChoiceBehavior.None() Functions are described to the model but it cannot call them. Restrict WHICH functions are offered: FunctionChoiceBehavior.Auto(functions: [kernel.Plugins.GetFunction("Orders", "get_order_status")]) — offer only the functions relevant to this request; fewer tools means fewer mistakes, less risk, and fewer input tokens. Manual invocation: FunctionChoiceBehavior.Auto(autoInvoke: false) — the model's tool-call requests are returned to YOUR code, so you can inspect, approve, or run them yourself, then continue the conversation. Planning What "planning" means — and what happened to the planners Planning is deciding which steps to take, in what order to achieve a goal. Early versions of Semantic Kernel shipped dedicated planner classes (such as sequential, stepwise, and Handlebars planners): a planner asked the model to produce a multi-step plan from the available functions, then executed it. Those standalone planners have since been DEPRECATED and removed in favor of FUNCTION CALLING. Modern models are trained to plan implicitly through tool use — they call a function, read the result, decide what to do next, and continue — so SK's recommended "planner" is simply: FunctionChoiceBehavior.Auto() + well-described plugins + an iteration cap Older articles and samples that mention HandlebarsPlanner , FunctionCallingStepwisePlanner , or similar are describing an earlier era; modern SK code gets the same capability from automatic function calling, with less machinery, fewer extra model calls, and better results. Keeping planning bounded - CAP the number of tool-calling rounds (the MaxToolRoundsFilter in Section 5). - Set a TOKEN and TIME budget per request; cancel via CancellationToken. - Offer a SMALL, relevant set of functions per request — a model choosing among 5 tools plans better than among 50, and it costs fewer input tokens. - Write functions to be IDEMPOTENT and to return clear errors, so a retry or a wrong turn is recoverable. - LOG the full sequence of calls so you can see what the model decided and why. - Plans can be WRONG: validate each step's arguments and authorization at execution time, not at planning time. 10. Multi-Agent Systems Several specialized agents collaborating A multi-agent system divides a problem among agents with different roles, instructions, and tools — for example an analyst , a writer , and a reviewer — coordinated so their work combines into a result. Why split work among agents? - SPECIALIZATION: focused instructions and a small toolset per agent are easier to get right than one do-everything prompt. - SEPARATION OF CONCERNS: a reviewer agent can critique a writer agent's output with a different "mindset." - PARALLELISM: independent sub-tasks can run at the same time. - MODULARITY: agents can be developed, tested, and swapped independently. Why NOT? - Every agent boundary adds model calls, latency, and cost, and new failure modes (miscommunication, loops, error compounding). Start with ONE agent or a plain workflow; add agents only when a single one demonstrably struggles. GROUP CHAT Agents take turns in a shared conversation, with a manager deciding who speaks next and when to stop. HANDOFF One agent hands the conversation to another better suited to the request (triage -> billing -> tech). A simpler multi-agent pattern: agents as tools Instead of a full orchestration, wrap a SUB-AGENT as a kernel function on a main agent's kernel — a "research" function whose implementation invokes a research agent and returns its answer. The main agent then delegates by ordinary function calling. This keeps the control flow understandable (one agent in charge, others as specialist tools), and it reuses everything from Section 5, including filters for logging and approval. Controlling multi-agent systems - BOUND EVERYTHING: max turns, max total tokens, wall-clock timeouts. Agents can talk in circles. - LEAST PRIVILEGE PER AGENT: give each only its own tools — the reviewer needn't send email. - DEFINE TERMINATION: an explicit "done" condition, not "until they stop talking." - LOG THE TRANSCRIPT between agents; it's your only way to debug emergent behavior. - BEWARE COMPOUNDING ERRORS AND COST: an early mistake propagates, and N agents multiply token spend. - EVALUATE end to end on a test set (see RAG, Section 12) — multi-agent behavior is hard to judge by eye. - Consider whether a deterministic workflow with a verification step would do the job more reliably. Semantic Kernel vs. the Alternatives The layers of the .NET AI stack RAW PROVIDER SDK OpenAI / Azure.AI.OpenAI packages. Maximum control, no abstraction, you write the tool loop, history handling, and plumbing yourself. Microsoft.Extensions.AI Small, provider-neutral abstractions (IChatClient, IEmbeddingGenerator) plus middleware for logging, caching, telemetry, and automatic function invocation. A thin, stable foundation. SEMANTIC KERNEL Orchestration on top: plugins, prompt templates (Handlebars/YAML/files), filters, vector-store abstractions, agents, multi-agent orchestration, observability. MICROSOFT AGENT The newer framework from the SK and AutoGen teams focused on agents and workflows FRAMEWORK (including graph-based, multi-step workflows). Evaluate it for new agent-centric work. Choosing A few model calls, simple tools, you value minimal dependencies -> raw SDK or Microsoft.Extensions.AI. Don't adopt a framework for a single chat completion. A plugin-based assistant, reusable prompt assets, filters for governance, model routing, tidy DI integration -> Semantic Kernel. Autonomous agents, complex multi-agent workflows, long-running orchestrations -> evaluate the Microsoft Agent Framework alongside SK's agent framework; check current maturity and migration guidance. A fixed, well-understood RAG pipeline where you want full control over every stage -> plain C# services (as in the RAG guide), optionally using SK for templating, filters, and the generation step. Honest trade-offs of using a framework GAINS Less boilerplate; consistent patterns for tools, prompts, and filters; provider portability; built-in observability; a shared vocabulary for teams. COSTS A dependency that changes fast (renames, experimental APIs, deprecations — plan for upgrade effort); abstractions can obscure what is actually sent to the model, so inspect prompts and token usage; the common-denominator API may lag provider-specific features; more moving parts to debug. MITIGATE Keep your domain logic (plugins, retrieval, validation) in plain C# classes behind your own interfaces so the framework is a thin layer you could replace; pin versions and read release notes; log the real prompts (carefully); and keep an evaluation set so framework upgrades don't silently change behavior. 14. Semantic Kernel evolves quickly — planners were replaced by function calling, memory moved to vector-store abstractions, agent and orchestration APIs are still settling, and the Microsoft Agent Framework now sits alongside it for agent-centric work. Keep your domain logic in plain C# behind your own interfaces, pin versions, read release notes, inspect the prompts that are really sent, and keep an evaluation set so upgrades don't silently change behavior.
