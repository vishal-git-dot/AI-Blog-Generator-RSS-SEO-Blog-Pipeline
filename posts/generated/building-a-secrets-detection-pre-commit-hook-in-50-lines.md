# Building a Secrets Detection Pre-Commit Hook in 50 Lines

## Overview

Secrets leaking into git repositories cause a disproportionate share of real-world breaches. AWS keys committed to a public GitHub repo get scraped by bots within minutes — sometimes seconds. The fix is to catch them before they ever reach the commit, not after. Why a pre-commit hook? CI/CD scanners catch leaks after the fact. The commit is already in history at that point, and you need to rotate the secret, scrub the history with git filter-branch or BFG, and hope no bot grabbed it in the window between push and detection. A pre-commit hook runs locally before the commit lands — zero-latency interception. There are heavy tools like truffleHog , gitleaks , and detect-secrets . They're excellent for large organizations. But if you want something lightweight, auditable, and easy to customize for your team's specific patterns, 50 lines of Python gets you further than you'd think — and it's code your whole team can read and modify. What we're detecting The hook targets the most common categories of accidentally committed secrets: AWS access key IDs ( AKIA... followed by 16 alphanumeric characters) Generic API keys and tokens assigned to common variable names PEM-encoded private keys Passwords assigned in .env or config files Platform-specific tokens (Slack, GitHub) A regex-based approach covers these reliably without needing a trained model or external API call. It runs in milliseconds. Testing it Create a test file with a fake secret and try to commit it: echo 'AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY' > .env.local git add .env.local git commit -m "test" # => [BLOCKED] Possible secrets detected: # [AWS Secret Key] .env.local:1 # -> AWS_SECRET_ACCESS_KEY=wJalrXUtnFEM... The hook only scans added lines in staged changes, not the full file. This is intentional: it won't trigger on secrets already in history (that's a separate audit problem), and it won't fire on deletions. You're intercepting new leaks, not relitigating old ones. Handling false positives The Password in env and Generic API Key patterns are intentionally broad, which means they'll occasionally flag: Example credentials in README files ( password=changeme123 ) Test fixtures with realistic-looking but fake tokens SDK documentation embedded in source The cleanest solution for legitimate false positives is a # nosecret inline comment convention. Extend the scanner to skip lines containing that marker: elif current_file and line . startswith ( " + " ) and not line . startswith ( " +++ " ): line_number += 1 if " nosecret " not in line . lower (): hits . append (( current_file , line_number , line [ 1 :])) This gives developers a documented escape hatch that doesn't require bypassing the entire hook. Distributing the hook to your team The .git/hooks/ directory is not tracked by git. To distribute the hook: Store it in a committed directory like .githooks/pre-commit Add a setup step in your Makefile: setup-hooks : cp .githooks/pre-commit .git/hooks/pre-commit chmod +x .git/hooks/pre-commit Or configure git to use your hooks directory for the entire repo, which is cleaner: git config core.hooksPath .githooks This last approach requires no file copying and works automatically once developers run the one-time configuration command. Put it in your onboarding docs. Extending the patterns Some teams add patterns for their internal token formats. If your platform issues tokens like MYAPP_[a-z0-9]{32} , add it to PATTERNS . Keep the list small and precise — broad patterns generate false positives, and false positives teach developers to habitually --no-verify . That defeats the entire purpose. For a broader defense-in-depth posture, this hook pairs well with a CI-level scanner (truffleHog, gitleaks) as a backstop. The pre-commit hook catches accidental leaks locally; the CI scanner catches anything that slips through on branches, forks, or rebases. Both layers together give you meaningful coverage without relying entirely on developers' vigilance. But this hook stops the most common failure mode: accidentally staging a .env file or hardcoding a key during late-night debugging and forgetting to remove it before committing.
