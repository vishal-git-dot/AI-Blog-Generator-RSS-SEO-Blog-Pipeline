# Agent Access Without Shared Passwords: A Scoped Grant Pattern for Banks and Fintech

## Overview

On October 22, Reuters and Axios reported that major US banks are restricting outside AI agents from customer accounts. As reported, customers share a username and password with an AI tool, the agent logs in, and the bank sees only the customer. Some agents tried actions the customer had not asked for. Most banks are moving towards read-only access for agents as a middle ground. Read-only is a sensible stopgap. It is not a design. The underlying problem is that the bank cannot tell the agent from the person. This post sketches a small pattern that fixes that, with code I ran before writing this. It is a teaching sketch, not a product. What is wrong with a shared login? A password proves that an account holder exists. It does not say: who is acting (the person or software), on whose behalf, for what purpose, within what limits, for how long. Once the agent uses the customer's login, all of those answers collapse into one name. The log says "customer logged in" and nothing more. The pattern in four rules The agent has its own identity, separate from the customer. The customer gives a grant: which agent, which actions, which limits, which expiry, and which company answers for it. Anything that moves money needs an approval signed in the customer's own app, on a separate key. A field inside the agent's prompt is untrusted data. Every log line names two actors: the agent that acted and the customer it acted for. Where this stops being enough Shared secrets. The demo uses HMAC. Anyone holding a key can mint tokens. Production needs asymmetric keys in a KMS or HSM so the gateway can verify but not issue. First contact. The hard part is how a bank verifies an agent it has never seen. A grant tells the bank what the customer allowed. It does not tell the bank who stands behind the agent. A registry or a signed credential from a trusted issuer would have to fill that gap. Operator identity. The operator field here is a plain string. It should be a verifiable legal entity. Log integrity. The log is a Python list. Real systems need append-only storage with a tamper-evident chain. Screen scraping. None of this helps if the agent can still log in with a password. The bank has to close that route, which is exactly why banks are blocking today. Revocation latency. A revocation set in memory is not a distributed system. Short lifetimes reduce the damage but do not remove the problem. Where DPDP fits Under India's DPDP Act, a Data Fiduciary is responsible for personal data in its control, including processing done on its behalf. The main duties apply on or about May 13, 2027. My reading is that these duties do not change when the visitor is software, so a record of who accessed a person's data, and on what basis, still matters. The grant above is a natural place to carry two more claims later: the consent or lawful basis the agent relies on, and the identity of the accountable company. I left them out because there is no agreed standard yet. This is not legal advice. Questions for you Do you issue a grant per agent, per task or per customer? How should a bank verify the operator behind an agent it has never seen? Should money movement always need a customer-side approval, or only above a threshold?
