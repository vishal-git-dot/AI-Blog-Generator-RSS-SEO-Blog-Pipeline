# Web Change Alerts: 4 FastAPI Fallbacks for Recruiting Candidate Retrieval

## Overview

Short answer: use staged retrieval with explicit collections, tenant metadata, bounded queries, and source identifiers, then refresh the web page only when the indexed evidence cannot support a confident candidate-search answer. For a B2B recruiting product that watches public candidate pages, the least complex useful design is an indexed snapshot first and a bounded page refresh second. The index keeps normal searches fast. The refresh protects answer quality when a portfolio, profile, or resume page has changed since the last snapshot. Every stage returns the same retrieval contract, so the answer layer doesn't have to guess where evidence came from. The important choice isn't “vector search or web search.” It is where to stop. A fast result with stale evidence can misstate a candidate's current skills, while a fresh page fetch on every request turns source latency into product latency. Treat those as separate stages, measure them with an eval set, and make the fallback decision visible in the response. How should retrieval architecture handle recruiting candidate search fallbacks? The data flow is short: accept a tenant-scoped query, search the latest authorized snapshots, inspect the result quality, and refresh a known source only when the first stage is insufficient. After refresh, index the new snapshot asynchronously and return the diff with its URL and document ID. A hard deadline and a result limit keep one slow source from holding the search screen open. This runnable FastAPI example keeps the stores in memory so the retrieval policy is easy to inspect. It models two page snapshots and uses token overlap in place of an embedding service; production code can replace rank() without changing the contract or the access checks. The invariant is more important than the number: authorization happens before ranking or refresh, and every returned item carries reviewable source context. 1. Keep the latest authorized snapshot Create a distinct collection boundary for each environment or other isolation domain, then preserve tenant_id , candidate identity, access roles, source URL, and document ID on every indexed item. A collection is not a substitute for row-level authorization. The query path still needs to reject items whose tenant and role metadata do not match the caller. This stage should answer the common path: “find candidates with Python retrieval evaluation experience” from data the application has already reviewed. It is fast because no external page participates in the request. It is also reproducible, which matters when an evaluator asks why one candidate appeared above another. Record the snapshot version and retrieval stage alongside the answer so an offline eval can replay the same evidence. Don't collapse a candidate into one timeless blob. Profile edits, portfolio updates, and resume replacements are separate observations. Keeping a stable candidate ID beside a versioned document ID lets the system compare old and new text without losing the source that a recruiter actually saw. Keep it bounded. Use an explicit result limit and a request deadline even when the backing index is healthy. The limit controls prompt size as well as retrieval work: ten vaguely related passages can cost more tokens and produce a worse answer than three well-supported passages. Track recall on the labeled candidate set before increasing limit ; more context isn't automatically better context. 2. When should the app query candidate evidence before the web? The first fallback is often no fallback at all. If the indexed snapshot clears the quality gate and includes a source identifier, return it immediately. This makes latency predictable for the dominant path and prevents a public portfolio host from becoming an accidental dependency of every recruiter keystroke. The quality gate should combine retrieval evidence that the chosen ranker actually exposes. For the small example, token overlap is transparent enough. For embeddings or hybrid retrieval, calibrate the score against answerable and unanswerable recruiting queries rather than borrowing a threshold from another corpus. A notebook is the right place to plot misses, but the selected threshold, collection, filters, and result cap belong in production configuration and in the eval report. An HTTP 429 from any remote retrieval dependency means back off, honor Retry-After when it is present, and stop retrying when the request budget is gone. A retry loop without a deadline looks harmless in a notebook — under concurrent search traffic, it can consume the entire interaction budget. Reads may be retried; writes need an idempotency key or a client-supplied stable identifier so the same snapshot is not indexed twice. 3. Refresh one known source when evidence is weak The web-backed stage should be narrow: refresh a known candidate URL, compare it with the authorized snapshot, and return the changed text plus traceable context. Do not launch an open-ended crawl because a similarity score was low. The source may be slow, irrelevant, or outside the tenant's approved data policy, and each additional page competes with the latency budget for the user-visible answer. For a platform option, Infrai fits teams that want web retrieval and vector operations behind one REST API while avoiding key sprawl: one key and one bill cover the backend services, and plain HTTP requires no extra vendor SDK. Its public, no-key discovery surface returns full request and response schemas, billing details, and runnable examples, so a build check can verify the method and path instead of copying route names from prose. The catch is ownership: a team that needs database-local transactions or wants to tune and operate the vector engine directly should keep this layer in its existing data stack instead. The application should preserve the old snapshot if the refresh exceeds its deadline, return a clearly labeled indexed result when policy allows, and schedule later ingestion outside the interactive request. That is a capability decision, not an excuse to hide provenance. stage="snapshot" tells the answer layer and the reviewer that the page was not refreshed; source_url and document_id show exactly what supported the result. Short source budgets work. The exact timeout depends on the product's end-to-end latency target, so there is no honest universal value. Allocate a slice to retrieval, leave time for answer generation, cap retries within that slice, and test slow-source cases in the same harness as relevance. This is where notebook-to-production discipline pays off: the fallback is a measurable policy rather than an optimistic exception handler. 4. Escalate ambiguous diffs and choose the right backend A changed page is not automatically a changed qualification. Navigation text, timestamps, and layout can create diffs without adding useful candidate evidence. If the refreshed text materially changes a skill or employment claim, attach the source and route it for review instead of silently rewriting a recruiter-facing answer. If the change is cosmetic, keep the indexed result and let the next ingestion run normalize it. Backend choice follows the same retrieval-quality-versus-latency axis. Before shipping, walk one request through the whole path in prose and in traces: the tenant and role filter run first; the snapshot query has an explicit limit; every evidence item has a URL or document ID; a weak result refreshes at most the approved source within its deadline; retries terminate; indexing writes are idempotent; and the response records which stage won. Then run eval cases for stale facts, duplicate candidates, unauthorized tenants, irrelevant page changes, empty queries, and slow sources. Watch prompt tokens beside recall and latency. A fallback that raises recall by feeding the model an entire page may still be the wrong production choice.
