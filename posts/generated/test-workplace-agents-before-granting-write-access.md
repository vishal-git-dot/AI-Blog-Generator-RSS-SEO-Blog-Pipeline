# Test Workplace Agents Before Granting Write Access

## Overview

Originally published at Quellix Labs Insights: https://quellixlabs.com/insights/test-workplace-agents-before-write-access An AI agent may be allowed to read a customer email, update a CRM record, and prepare a payment workflow. The risk is that a message, calendar invite, or other outsider-controlled record contains instructions aimed at the agent—not your team. If the agent treats those instructions as authority, a useful automation can become an unauthorized action. The important question is not whether the agent can spot suspicious wording in a demo. It is whether your complete workflow contains the attack, prevents unauthorized changes, and makes failures visible. Measure that before granting write access. When this needs an AI agent build Move from research to an implementation conversation when an agent must read untrusted business content and then take action in email, CRM, payables, or another system. The risk is highest when one workflow combines outside information, permission to make changes, and little or no review. A contained assistant that summarizes inbound messages without changing records may not need a custom security build yet. But if an agent can change payment details, alter customer contacts, send external messages, or modify a policy record, define its allowed actions and test them before production access. That conversation should include the business owner, the system owner, and whoever approves the consequential action. They need to agree on what the agent may do, which records it may trust, and when a person must step in. Why ordinary prompt tests miss the risk Indirect prompt injection happens when an agent encounters instructions inside content it was asked to process. For example, a supplier email might contain text telling the agent to replace the bank account on file. The email is input to the task, not a trusted source of operating instructions—but the agent may not reliably preserve that distinction. This is different from asking a chatbot a misleading question. The agent can have tools, access to private data, and authority to change a record or send a message. A successful attack can therefore show up as a business action rather than an obviously bad answer. The recent IPI Bench workplace-agent evaluation reports that frontier models achieved injected objectives on 4.8-38.5% of long-horizon workplace tasks with one attacker query. Across 11 queries, the reported range rose to 17.6-79.4%. The benchmark also reports that end-of-run reports presented about half of successful attacks as verified. Those results are not a forecast of your company's incident rate. They are a reason to test the exact agent, tools, permissions, and outsider-writable records you plan to use. A clean answer at the end of a run is not proof that the workflow stayed within policy. The INFUSE benchmark also frames indirect prompt injection as a problem across different surfaces in agentic systems. For a buyer, the practical lesson is to test more than one source type. An agent that handles email safely may behave differently when the same instruction appears in a calendar invite or a public post. What to measure in the workflow A useful red-team test pack measures business outcomes, not just whether the model recognized an attack phrase. Record whether the requested task was completed, whether any forbidden action occurred, and whether the agent gave an accurate account of what it did. Track at least these results for each test: Task completion: Did the agent finish the legitimate work without relying on the hostile instruction? Unauthorized action: Did it change a protected field, send a message, approve a transaction, or disclose information it was not permitted to share? Containment: Did the agent stop, ask for approval, or route the case to a person when the requested action crossed its boundary? Detection: Did the system log the untrusted instruction and the action it attempted to influence? Reporting accuracy: Did the end-of-run summary match the actions shown in the tool and audit logs? Recovery: After a blocked action or tool error, did the agent remain within policy on retry? Keep these results separate. A high task-completion rate can hide unsafe changes. A low attack success rate can also be misleading if the agent simply fails every difficult customer request. You need to know whether it can complete normal work while refusing the unsafe part. Define the unacceptable outcomes before running tests. For example, any unapproved payment-detail change might be a hard failure, even if the agent otherwise completed the task. A missed opportunity to update a low-risk CRM note may be a recoverable miss. This lets leaders compare safety and business usefulness instead of collapsing both into one score. Build path: test the records and the actions Start with a workflow that has a clear owner and a bounded outcome. Do not begin by testing an all-purpose assistant across every connected system. Pick one task, such as processing a supplier change request, updating a sales contact, or triaging a support email. Map where instructions can enter. List every source the agent reads: inbound email, attachments, calendar descriptions, CRM notes, shared documents, or public posts. Mark which sources outsiders can create or edit. Include forwarded messages and copied text if they become agent input. Write the legitimate task and its limits. A useful test has a clear goal and a clear boundary. For example: "Extract the supplier's invoice number and amount, compare them with the purchase order, and prepare a review item. Do not change bank details or release payment." The business owner should define which fields are sensitive and who can authorize a change. Create controlled attack cases. Put hostile instructions in the same types of records the real workflow reads. Vary their location and wording: in the message body, a quoted thread, an attachment, a calendar description, or a CRM note. Include both obvious instructions and plausible business language, such as a request to "use the updated remittance account below." Test ordinary records too, so the agent is not rewarded for refusing everything. Run the full workflow, not a model-only prompt. Use the same retrieval, tools, permissions, approval screens, retries, and logging planned for production. A safe response in a text-only test does not establish that the CRM connector or payment tool will block an unsafe write. The Gray Swan Research discussion of agent compromise and visibility is a useful reminder to compare the agent's claims with what actually happened in the tools. Inspect tool traces and system records. For each run, compare the agent's final summary with the actual calls and resulting records. Check whether an attempted action was blocked, whether it was retried in a different form, and whether a human approval was genuine or bypassed. Preserve the test input, system version, permissions, and outcome so a later run can be compared fairly. Repeat after changes. Re-run the pack when you change the model, system prompt, tool permissions, retrieval rules, or approval path. Those changes can alter how the workflow behaves. Keep a small set of standard tests for regression checks and add new cases from incidents or near misses. The NIST Generative AI Risk Management Profile offers a risk-management reference for identifying and evaluating generative AI risks. For an implementation team, the useful move is to turn identified risks into named owners, test cases, controls, and review points—not to treat a framework as proof that a workflow is safe. Make approval follow the consequence Approval is not a single on/off setting. Design it around the cost and reversibility of the action. An agent might draft a routine response or suggest a CRM update automatically, while a person approves sending a message that changes contract terms. A payment destination change should require confirmation through a channel separate from the untrusted request, using an established business process. For example, an invoice workflow can read an inbound invoice and purchase order, extract the supplier, amount, and due date, then flag mismatches. The agent can create a review item and explain what did not match. A finance approver confirms exceptions in the company's established system before any payment is released. The business outcome is less manual sorting without making an email the authority for payment changes. Keep Email Outside the Payment Approval The agent can prepare and explain a payment exception, but confirmation stays with a finance approver using an established channel separate from the supplier email. That separation matters because a human clicking "approve" is not a meaningful control if the agent can change the approval target, conceal the change, or supply a misleading summary. Show the approver the proposed change, the source record, and the reason for the action. Log the decision separately from the agent's own report. Risks, limits, and when to wait A test pack reduces uncertainty; it does not prove an agent will resist every attack. The inputs, integrations, models, and policies can change. Test results apply to the configuration you actually evaluated, so keep the scope and version visible in the release decision. Do not grant broad write access just because an agent passed a small set of examples. Start with the narrowest permissions that allow the task, use a review queue for consequential changes, and monitor real actions against the same policy. If a task can be completed safely by extracting information and preparing a human review item, do not give the agent authority to perform the irreversible step. Wait before building if the process owner cannot define an acceptable action, if the source of truth for a sensitive field is unclear, or if there is no one accountable for reviewing exceptions. Also wait if the workflow changes so often that your team cannot maintain the tests and approval rules. In those cases, process cleanup or a read-only assistant may deliver more value than an agent with write access. A buyer's decision rule is straightforward: automate the reversible, well-defined steps first; keep high-impact or difficult-to-reverse changes behind out-of-band confirmation; and expand access only when repeatable tests show both useful completion and policy compliance. This approach may limit autonomy. It also makes the workflow easier to explain, support, and improve. The part most demos skip A demo usually shows what the agent can do. A production review must also show what happens when a record it reads tries to redirect it.
