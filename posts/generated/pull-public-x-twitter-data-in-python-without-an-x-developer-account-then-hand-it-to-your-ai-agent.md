# Pull Public X (Twitter) Data in Python Without an X Developer Account, Then Hand It to Your AI Agent

## Overview

I keep running into the same small job: "grab the last few hundred posts about a topic, plus the followers of a couple of accounts, and put them in a spreadsheet." It's not a big data project. It's an afternoon script. But X data has become awkward for exactly this size of task. Browser scrapers need logged-in accounts and proxies and break whenever the site changes, and the official API bills every post and profile it returns. This post walks through a small Python script that does both jobs with a pay-as-you-go REST API, TwexAPI , and then shows how to give the same access to an AI agent through MCP. Everything here uses public data and endpoints that are documented in its API reference. Disclosure and scope: TwexAPI is an independent third-party service. What did that cost? 200 posts plus 1,000 followers is 1,200 reads. At 5 Credits each that's 6,000 Credits, which fits comfortably inside the free 20,000. In dollar terms, 100,000 Credits is about $1, so the run is worth about six cents. Two billing details are useful to know when you're debugging: a request that comes back with no results still costs 5 Credits, and a request that fails with an error isn't billed. Step 5: Give the same access to an AI agent (MCP) Scripts are great for repeatable exports. For exploratory questions like "what are people in Japan posting about this launch?" it's often faster to let an agent figure out the calls. TwexAPI runs a hosted MCP server at https://api.twexapi.io/mcp (Streamable HTTP), authenticated with your API key in an x-api-key header. For Cursor, add this to .cursor/mcp.json in a project (or ~/.cursor/mcp.json globally): { "mcpServers" : { "twexapi" : { "url" : "https://api.twexapi.io/mcp" , "headers" : { "x-api-key" : "twexapi_YOUR_KEY_HERE" } } } } Claude Code uses the same shape in .mcp.json with "type": "http" added. Claude Desktop only speaks stdio, so the docs bridge it with the mcp-remote npm package. The MCP setup docs have configs for Codex CLI, VS Code, Windsurf and others. The server deliberately exposes just two tools: explore searches the endpoint catalog and returns names, methods, paths, parameter schemas, examples and a read_only flag. twexapi_request executes an authenticated call with a method , a relative path , and an optional query or body . So the agent first discovers the right endpoint, then calls it. I like this design because the tool list stays tiny (it doesn't flood the context window with dozens of tool definitions), and the read_only flag gives you something concrete to check before you let an agent run unattended. A prompt that works well for a first test: "Use twexapi to list the countries available for global trends, then show me the top trending posts for Japan." Behind the scenes that maps to GET /twitter/global-trending/countries and GET /twitter/global-trending/tweets?country=... . A few practical notes Keep the key server-side. Don't ship it in front-end code or commit it. The SDKs and CLI read it from the X_API_SCRAPER_KEY environment variable if you'd rather not hard-code anything. Back off on 429s. If you bump into rate limits, sleep and retry rather than hammering. The docs have an error-handling guide for this. Reads don't need an X account. Write actions (posting, liking, DMs) are a separate topic: they run with your own account's session, and I'd keep any agent on read-only endpoints unless a human reviews each action. Wrapping up For small and medium jobs, the pattern above covers most of what I need from X: a search, a follower export, and a CSV, in about 60 lines of Python. Then the same key can power an agent through MCP when the question is fuzzier. Start with a narrow query, check the Credits you used, and only then scale up.
