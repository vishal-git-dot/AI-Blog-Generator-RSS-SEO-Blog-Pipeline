# Signal #141: Agents Get Local Hands, Ruby and PHP Get Patched, and GitHub Closes a Trust Gap

## Overview

This week's cards cut across three layers of the stack: the local machine an agent can now reach, the runtimes and CI systems that are being hardened under our feet, and the data path that carries our prompts to inference providers. Two items demand action today, a Ruby heap overflow and a PHP session deserialization RCE, while the rest set up changes that are either already shipping or have fixed dates on the calendar. Raycast MCP lets agents control local Mac apps Enable Raycast MCP under Settings → MCP → Raycast MCP Server, add it to your agent app, and any MCP-capable client can reach Clipboard History, Snippets, Quicklinks, Focus, and browser tabs. Execution stays local, with no cloud relay in the middle, which is a meaningful difference from hosted tool servers that see your requests in transit. What matters is the permission surface. You opt in per extension, and the agent gets write access to clipboard, snippets, and app uninstall, which is more than a read-only convenience. That makes this a tool for replacing manual context-switching, not for exposing your whole desktop. Verdict: Evaluate. It's a shipped product and safe to try, but start with a narrow extension set and confirm what each one can mutate before you widen it. Ruby Case-Conversion Flaw Enables Heap Overflow Across Rails A one-byte heap overflow in legacy single-byte encodings is reachable through upcase , swapcase , downcase(:fold) , and casecmp? when the input is attacker-controlled. Default Rails and classic Sinatra apps hit the path through MethodOverride before authentication runs, so any app that parses a _method parameter is exposed. Bundled self-hosted products such as GitLab and Discourse inherit the risk until their Ruby runtime is rebuilt. The fixed releases are Ruby 3.3.14, 3.4.13, and 4.0.10. Ruby 3.2 and earlier are end of life and will not get this fix, so the upgrade path is the only real remediation for them. The Cloudflare WAF rules are a compensating control: they don't cover direct-to-origin traffic or non-HTTP entry points, so treat them as a bridge. Verdict: Ship now. Upgrade the runtime, then check distribution packages for backported fixes if you rely on system Ruby. PHP patches phpAfterShell RCE; Cloudflare WAF blocks attacks The fix for a CVSS 9.2 session-deserialization RCE is an upgrade to PHP 8.2.36, 8.3.37, 8.4.28, 8.5.13, or 8.6.0. Exposure is concentrated in deployments using the default file-based session handler on an affected version, and the advisory notes that real exploitability depends on conditions such as upload progress and serializer mismatches. Those conditions don't make the flaw safe to ignore; they just make it harder to scope. The hard part is inventory. PHP that arrives through CMS plugins or container images you don't rebuild directly is easy to miss. Linux distributions often backport fixes without bumping the version string, so compare the full package version against the distro advisory instead of trusting the number alone. The Cloudflare managed rules (Block by default on Free and paid plans, with the new PHP-FPM and SOAP rules set to Log) reduce exposure during rollout but cannot cover every path. Verdict: Ship now. Upgrade, restart every worker, and verify the package version against your distro's advisory rather than assuming the WAF has you covered. Dragos Canary Test Exposes Prompt Leakage Across Inference Providers The useful finding here is narrow: privacy flags like zdr: true govern the first hop only. Canary prompts seeded with fake credentials were mined for AWS keys within hours, and resellers on an open marketplace could read request data without any exploit. If your pipeline sends secrets to a model, the provider's retention setting is not the control you think it is. The mitigation is client-side. Put a scrubber in front of every LLM call, add per-request routing constraints such as data_collection: "deny" alongside zdr: true , and run pre-commit secret scanning so credentials don't enter prompts in the first place. Regex scrubbing is a seatbelt, not a guarantee, so layer it with seeded canaries that tell you when something leaks anyway. Verdict: Ship now as a layered control. Add redaction and per-request provider constraints to your agent and pipeline code, and audit existing accounts for ZDR coverage. GitHub blocks pull_request_target by default on December 2 Starting December 2, 2026, public repositories block pull_request_target by default, and organizations can enforce the block with a single policy. The risk is specific: a workflow that checks out fork pull request code under pull_request_target runs with read/write tokens and your secrets, so a stranger's PR can execute with your credentials. The Ultralytics and LiteLLM incidents are the cautionary cases. The migration is to move untrusted-ref workflows to the pull_request trigger, which runs fork code with a read-only token and no secrets. Before the cutoff, audit existing workflows, set the org-level event policy (Team/Enterprise) or the per-repo setting (Free), and check what the policy would block before you enforce it. The date is fixed, so the work has a deadline. Verdict: Ship now. Audit and migrate before December 2, and use the dry-run check to find breakage before enforcement does. Poppy 1.0 gives agents a standard business front door Poppy proposes a /.well-known/poppy.json file served over HTTPS so that agents acting for customers can identify themselves and learn what actions a business permits. Without a published file, a business is effectively invisible to Poppy-aware agents, and today's alternative is ad hoc scraping or undocumented API access. The protocol layers identity and permissions over existing MCP, OpenAPI, and UCP infrastructure rather than replacing them. The caveat is that this is draft 1.0, and the spec permits non-backward-compatible fixes. Serve the file, use OAuth for account-connected actions, validate against a test environment (the validator needs Node 22.18+), and pin your deployment to a specific revision. Re-validate after every spec change, because the file is cheap to publish and expensive to get wrong in production. Verdict: Evaluate. Worth publishing now for discoverability in a test environment, but treat the spec as unstable until it stops changing.
