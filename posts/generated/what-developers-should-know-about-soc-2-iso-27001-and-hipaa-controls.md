# What Developers Should Know About SOC 2, ISO 27001 and HIPAA Controls"

## Overview

Compliance usually gets discussed in meetings engineers are not invited to, and then it arrives in your backlog as a ticket that says something like "provide evidence of branch protection." If you have ever stared at that ticket wondering why it exists, this post is for you. You do not need to become an auditor. But knowing which parts of your daily work count as controls makes those requests far less mysterious, and it makes the work cheaper too. The same engineering habits satisfy three frameworks SOC 2, ISO 27001 and HIPAA are written in very different language, but when you translate them into engineering practice they ask for a short list of things. The good news is that most of them are things a well-run team already does. The only extra step is being able to show it. Here is the developer-facing version of that list. 1. Access control Auditors want to know who can touch production and how that access is granted and removed. In practice this means: Single sign-on for as many tools as possible, with MFA enforced. Role-based access in your cloud accounts, not shared admin credentials. A periodic review where someone confirms that each person still needs the access they have. A reliable offboarding process, so a departed engineer's accounts are closed quickly. If you use infrastructure as code for IAM, you get a bonus: the history in git is evidence of who changed what and when. 2. Change management This is the one developers touch most often. The expectation is that changes to production are reviewed, approved and traceable. Branch protection plus required reviews covers most of it. A CODEOWNERS file adds a nice touch by making sure the right people review sensitive paths: # .github/CODEOWNERS /infra/ @acme/platform-team /auth/ @acme/security-reviewers *.tf @acme/platform-team Pair that with a rule that pull requests need at least one approval and passing checks before merge, and you have a repeatable, provable process. Link each merge to a ticket and you have change-management evidence without anyone writing a report. 3. Vulnerability management Frameworks do not tell you which scanner to use. They ask that you find vulnerabilities, rank them, and fix them within a timeframe you have defined. A scheduled dependency check is a decent start: name : dependency-audit on : pull_request : schedule : - cron : " 0 6 * * 1" jobs : audit : runs-on : ubuntu-latest steps : - uses : actions/checkout@v4 - uses : actions/setup-node@v4 with : node-version : 20 - run : npm ci - run : npm audit --audit-level=high The workflow itself is not the control. The control is the policy behind it, for example "high-severity findings are fixed or formally accepted within a set number of days," plus the record showing you actually followed it. 4. Logging and monitoring You need to be able to answer "what happened?" after an incident. That means centralised logs for authentication, administrative actions and access to sensitive data, retained for a period you have defined, with someone responsible for looking at alerts. For HIPAA in particular, access to systems that store protected health information needs to be traceable to individuals. 5. Encryption and secrets Encryption at rest and in transit, managed keys, and secrets kept out of source code. Secret scanning on your repositories is a cheap way to show you take the last point seriously. Where the overlap pays off Notice that none of the five items above belongs to a single framework. A pull request review policy is relevant to SOC 2 change management, to ISO 27001's controls around secure development and change, and to HIPAA's expectations for protecting systems that handle patient data. That overlap is what makes a combined approach worthwhile. Instead of producing separate documents and proof for each standard, you define the control once and attach the evidence to every requirement it supports. The article on shared controls across SOC 2, ISO 27001 and HIPAA goes through how that mapping works and where a compliance platform like Drata fits in, which is useful context if your security team is considering one. What is different between them Do not assume everything transfers. A few places where the frameworks diverge: ISO 27001 wants a management system around the controls: documented scope, risk assessment, internal audits and management review. Engineers feel this as more paperwork and more scheduled reviews. HIPAA is specific to protected health information. If your system stores or transmits it, expect questions about business associate agreements with any vendor in the data path, and about breach notification. SOC 2 Type II looks at how controls operated across a period of time, so a one-off fix right before the audit is not enough. The control has to run consistently. Practical tips for engineers Make the secure path the easy path. If branch protection is configured in code and applied to every repo by default, nobody has to remember it. Keep evidence close to the work. Tickets, pull requests and pipeline logs already record what happened. Teach your team to link them instead of creating a separate record afterwards. Treat exceptions as first-class. Sometimes a hotfix skips a step. That is fine as long as the exception is recorded with a reason and an approver. Silent exceptions are what auditors dislike. Ask what the control is for. When a request looks strange, ask what risk it addresses. Usually there is a simple answer, and sometimes you discover your existing setup already covers it. Wrapping up Compliance work looks very different once you see it as a description of good engineering hygiene with receipts attached. Build the habits once, make them automatic where you can, and let the evidence accumulate as a side effect of normal work. Your future self, staring at the next audit ticket, will thank you.
