# Build a REST API with Fairyfly and SQLite

## Overview

I've been building Fairyfly , a lightweight, backend-focused JavaScript runtime built with Zig and powered by QuickJS. One of my goals with Fairyfly is to make backend development straightforward: write JavaScript, start an HTTP server, handle requests, and interact with a database without having to assemble a large stack of dependencies. In this tutorial, we'll build a small REST API using Fairyfly's native HTTP server and SQLite APIs. We'll create a task manager API that supports creating, retrieving, updating, and deleting tasks. By the end, we'll have a working backend with persistent database storage, input validation, and appropriate HTTP status codes. What we're building Our API will expose the following endpoints: Method Endpoint Description GET /api/health Check server health GET /api/tasks Retrieve all tasks POST /api/tasks Create a task GET /api/tasks/:id Retrieve a specific task PATCH /api/tasks/:id Update a task DELETE /api/tasks/:id Delete a task We'll use SQLite to store tasks locally. This means the data will remain available after the server restarts. No Express, no external database server, and no npm dependencies are required for this example. 1. Its handler receives three arguments: url , method , and body . Unlike frameworks that give you a request object, this handler receives the URL, HTTP method, and request body as separate values. The body is a string, so we need to parse JSON ourselves when accepting JSON requests. Second, the handler returns a Response . We can use Response.json() when we want to return JSON, including a specific HTTP status code. For the task manager, we'll expand this simple handler into a complete API. 4. Initialize SQLite We open a local database with: const db = Database . open ( " tasks.db " ); The CREATE TABLE IF NOT EXISTS statement creates our table on the first run. The table contains an automatically generated ID, a title, a completion flag, and a creation timestamp. Fairyfly exposes SQLite through its built-in Database API, so we don't need to install a separate JavaScript database package. The database file is relative to the current working directory. Running ff server.js from our project directory keeps tasks.db there. Parse and validate JSON The parseJson() function protects the API against malformed JSON. For example, a request containing an invalid JSON body should return 400 Bad Request , rather than causing an unhandled parsing error. We also validate the task title and reject empty titles or titles longer than 200 characters. Validation is important because clients cannot be trusted to send valid data. Use parameterized SQL Notice how database operations pass values separately: db . exec ( " INSERT INTO tasks (title) VALUES (?) " , [ title ] ); The ? placeholder binds the provided value to the SQL statement. We use the same approach for database lookups, updates, and deletions. This is preferable to concatenating user input into SQL strings and helps protect against SQL injection. Return consistent JSON responses Our helper function keeps JSON responses simple: function json ( data , status = 200 ) { return Response . json ( data , { status }); } We use 200 OK for successful reads and updates, 201 Created when creating a task, 400 Bad Request for invalid input, 404 Not Found when a task doesn't exist, and 405 Method Not Allowed when a task route receives an unsupported method. 5. What we've built We've now implemented a complete REST-style API with Fairyfly and SQLite. The application can create, list, retrieve, update, and delete tasks. It handles JSON input, validates user-supplied fields, uses parameterized SQL, and returns meaningful HTTP status codes. The architecture is deliberately simple: http.serve() handles incoming HTTP requests. Response and Response.json() produce responses. Database provides SQLite storage. A small routing function maps HTTP methods and paths to operations. There is no external web framework, package installation, or separately managed database server in this example.
