# PDF to clean Markdown for RAG: chunking-ready text from PDFs, Word and scanned files

## Overview

Most RAG quality problems I have debugged were not embedding or prompt problems. They were extraction problems: a table flattened into a soup of numbers, a heading glued to the paragraph above it, a scanned appendix that came back empty, so the retriever never had a chance. This post walks through turning PDFs, Word files and scans into Markdown that is ready to chunk, with a real test run and the actual output, warts included. Disclosure: I built the Apify actor used below ( Document to Markdown ). I also list the free DIY options, which are the right choice in plenty of cases. Why Markdown and not plain text? Three reasons that matter for retrieval: Structure becomes chunk boundaries. If section titles survive extraction, you can split on them. A chunk that is "6.1 Machine Translation" plus its paragraphs embeds far better than a fixed 1,000-character window that starts mid-sentence and ends in the next section. Tables stay rows and columns. An LLM can read | Transformer (big) | 28.4 | 41.8 | . It cannot reliably read Transformer (big) 28.4 41.8 2.3 1019 after the column headers were lost. Page markers enable citations. If every page starts with <!-- Page 8 --> , each chunk can carry a page number, and your answer can say "see page 8". The DIY options, honestly pdfplumber : Excellent low-level control, including table extraction with tunable settings. You write the logic for headings, reading order and Markdown output yourself, and there is no OCR. Best if you have one document layout and time to tune it. MarkItDown (Microsoft, MIT): One pip install and you get Markdown from PDF, DOCX, PPTX, XLSX, HTML and more. Office formats come out very well because they carry real structure. PDFs are mostly extracted as text, and scanned pages need extra setup. My actor uses MarkItDown internally for Office, HTML and EPUB files. marker : Uses layout and OCR models and produces the nicest PDF Markdown of the three, including real headings. The trade-off is heavy models, a GPU for reasonable speed on large batches, and licence terms you should read before commercial use. If you process a few hundred PDFs once and you are happy running Python locally, start with MarkItDown or marker. A hosted API makes sense when you do not want to maintain OCR models and dependencies, when the documents arrive as URLs inside an automation (n8n, Make, an AI agent), or when you need per-page control and billing. PDFs do not store "this is a heading", so PDF headings come out as plain lines, not ## . Word, PowerPoint and HTML files do keep real headings. So a heading-based chunker for PDFs has to recognise numbered section titles too, which leads to the next step. Step 3: Chunk by headings (and keep page numbers) The built-in outputChunks splits by paragraphs and size. Prepend the section title to each chunk before embedding ( f"{c['section']}\n\n{c['text']}" ) and store page as metadata for citations. In production, also merge tiny chunks (the 6 Results heading alone was a 9-character chunk) into the next one. Word files have no fixed pages, so every 3,000 characters of output count as one page. Summary Extract to Markdown, not plain text, and keep page markers. Expect PDF tables with complex headers to need cleanup. Simple tables and Office tables convert well. Chunk by section, not by a fixed window, and attach section and page as metadata. Use pdfplumber, MarkItDown or marker if you want everything local, and a hosted actor if you would rather not run OCR models yourself.
