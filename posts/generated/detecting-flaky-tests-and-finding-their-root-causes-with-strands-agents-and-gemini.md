# Detecting Flaky Tests and Finding Their Root Causes with Strands Agents and Gemini

## Overview

A few years ago (three years at most), one of the biggest challenges QA Engineers faced was: how do we convince the business and the team that we should invest in automated tests? Today, with AI, this issue has been mostly solved. We don't spend much time coding automated tests because we have AI to do it for us, but a new challenge appears: flaky tests . In this article, I will explain what a flaky test is, how I built a tool to help identify them, and how I used AI to run a first analysis. What Is a Flaky Test and Why It Matters Before going into more detail about the solution, let's understand what a flaky test is and why we should worry about it. In a few words, a flaky test is an automated test that produces both passing and failing results without any change to the code or to the test itself. If they pass, why should we monitor them? In the end, they pass. That may be your first thought, but once you understand what a flaky test is, you see that in big projects it can hurt the team's trust in their own product and tests, real failures start being ignored, and the CI time and cost per pipeline go up. Quick overview of the project Based on these concerns, I developed this project. The code is available on GitHub: flaky-test-detector . It starts by receiving a JUnit report in XML format (a standard output of most test frameworks, with one <testcase> per executed test), and parsers.py is responsible for parsing the information in this file into the proper format: class Outcome ( str , Enum ) : PASSED = "passed" FAILED = "failed" ERROR = "error" SKIPPED = "skipped" @dataclass ( frozen = True ) class TestResult : """A single test execution in a single CI run.""" __test__ = False # keep pytest from trying to collect this class name : str # "<classname>::<name>" outcome : Outcome commit_sha : str | None run_id : str | None time : float = 0.0 message : str | None = None source : str | None = None # file the result came from @property def passed ( self ) -> bool : return self . outcome is Outcome . PASSED If the file isn't a valid JUnit XML, an exception is raised; if it is valid, the parsing proceeds. When scoring.py is called, it uses the FlakinessScorer class, which is responsible for taking the TestResult objects and turning them into TestScore objects. Each result is grouped by test name and then by commit, and for each (test, commit) pair the scorer checks the outcome. It ignores: skipped tests, since they say nothing about flakiness; results from JUnit files without the commit_sha property (the commit id), since they can't be compared with each other. It then generates the data that the Ranker needs, in the following format: { "name" : "tests.checkout.test_cart::test_9" , "commits" : 10 , "flaky_commits" : 3 , "commits_where_flaky" : [ "gen0007d154385" , "gen05893e77ff9" , "gen059095256f8" ] , "error_messages" : [ "AssertionError: timeout waiting for gateway" , "ConnectionError: connection reset by peer" ] } When the FlakinessRanker class is called, it uses this data to rank the tests. It only considers tests with data from at least 5 commits ( min_commits ), so the score can be trusted, and it flags a test as flaky when its score is 0.1 or higher ( threshold ). Both values can be changed: def __init__ ( self , threshold : float = 0.1 , min_commits : int = 5 ) -> None : if not 0.0 <= threshold <= 1.0 : raise ValueError ( "threshold must be between 0 and 1" ) if min_commits < 1 : raise ValueError ( "min_commits must be >= 1" ) self . threshold = threshold self . min_commits = min_commits The score is the total of flaky_commits (the number of commits where the same test passed and failed) divided by the total of commits available for that test in the pipeline. One test ran on 10 commits, and on 3 of them it both passed and failed on the same commit. For this example, commits is 10 and flaky_commits is 3, so the score is 0.3. With this first implementation, we can already see the first results. I created some JUnit reports and, after running the command below, I got this output: python -m flaky_detector analyze ./results/*.xml --threshold 0.1 Each line shows the score, the test name and the number of flaky commits out of the commits with data for that test. What Can Be Done With This Ok, now it is possible to identify flaky tests and even analyze them. What can I do with this? First, you can start implementing it in your team. Monitoring your tests and flagging the flaky ones can help you improve the team's trust in what they are building, reduce CI costs, and avoid real bugs being ignored because the test passes on the second or third execution. When should you run this? It depends on how your team works: If your team has continuous deployment, and deploys every day or every week, it is interesting to run this once per week. It can also help if you have problems merging PRs in lower environments, to understand what is happening. If you don't have continuous deployment and deploy once per month, my recommendation is to run this on every deployment, always comparing the latest executions to see whether the number increased or not. The AI analysis is optional. You can run just the Score and Rank steps and, at the end of a cycle, a month or even a quarter, use the agent to give you feedback. Limitations and Integrations Today, the JUnit XML file must have the property <property name="commit_sha" value=""/> (the commit id) and the property <property name="run_id" value=""/> . Since the solution was built with GitHub Actions in mind, it may need changes for other frameworks and pipelines. When the results are fetched from GitHub Actions ( --repo ), both values are taken from the GitHub run itself. There is already a workflow to integrate with GitHub Actions ( .github/workflows/flaky-report.yml ). It runs every Monday, generates the reports and uploads them as an artifact. If you plan to add it to your own workflow, it may need adjustments, and the analyzed repository must publish its JUnit XML files as workflow artifacts. For the AI model, you can set up your favorite one. Remember to check Model Providers to adapt it to your context. Another suggestion is to integrate with a reporting tool, like Grafana, so you can see the behavior of your flaky tests at different points in time and whether they are decreasing or not. Conclusion Flaky tests are not just an annoyance: they erode the team's trust in the tests and hide real failures. Measuring them is the first step to dealing with them, and a simple score per test and commit is enough to get started. The AI analysis gives you a first look at the possible root causes, but it doesn't replace a human reviewing the results, since failures caused by the infrastructure can also look like flakiness. Give it a try and see how your own pipeline behaves!
