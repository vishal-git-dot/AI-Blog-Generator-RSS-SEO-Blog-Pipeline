# Import Incident Reconstruction: Compare Dashboard Events with a Custom Metrics API

## Overview

Short answer: choose the approach that preserves enough evidence to reconstruct why a scheduled customer-support import stopped producing results; use event analytics when operators need to explore individual runs, and use a custom metrics API when the business question and aggregation rules are stable. The dashboard is the last step, not the decision. A chart can show results_imported = 0 , yet that single number cannot distinguish an empty source, a skipped schedule, a rejected batch, or a run that never completed. For an AI support feature, those paths matter: an empty import may be valid, while a missing import can leave retrieval grounded in stale tickets. My evaluation constraint is simple: given only the retained telemetry, can an engineer explain one alert without reopening application logs or guessing? I first thought a success counter plus a failure counter would be enough. It isn't. The useful unit is an import attempt with identity, timing, outcome, and result count. Can a Business Metrics Dashboard Compare Event Analytics with a Custom API? Retain one record per scheduled attempt before deciding how to display it. At minimum, that record needs a stable run ID, schedule ID, expected time, actual start time, completion time, terminal state, result count, and a low-cardinality reason category. It should also carry the customer-support data source and deployment environment, because two simultaneous zero-result runs mean something different when they share a source than when they share only a deployment. There are two clocks. The scheduler clock answers, "Did a run begin when expected?" The production clock answers, "Did that run produce usable results before the freshness deadline?" Monitoring only completion events loses the first question. Monitoring only starts loses the second. Emit the expected schedule separately or derive it from versioned schedule configuration, then compare it with observed runs. Keep raw error text out of metric labels. Unbounded messages, ticket IDs, and run IDs create high-cardinality dimensions, which make aggregation expensive and dashboards noisy. Put those details in the per-run event or log record; expose a controlled reason such as auth , rate_limit , validation , or unknown to the aggregate layer. RFC 5424 is useful here because it separates severity from structured message content and defines ordered severity levels. A business outcome still needs its own field: a technically successful run that imports zero results isn't automatically an operational success. One alert should therefore evaluate absence and outcome together. For example: no completed run within the freshness window, or the latest completed run produced zero results when the source was expected to be nonempty. The expectation must come from business state, not a hard-coded assumption that every import always has data. That's the hinge. One Run, Four Conflicting Stories The simple approach stores one time-series point per run: timestamp, result count, and perhaps a Boolean success flag. It makes a clean line chart. It also collapses the sequence that explains an incident. If a run starts at 09:00, receives a rate-limit response, retries, and completes at 09:08 with 240 results, the final count looks healthy while the eight-minute freshness gap disappears. If only the retry error is counted, the same run looks failed. Neither projection is a faithful reconstruction. Instead, model the run as an ordered set of facts and derive dashboard metrics from it. If events arrive out of order, their occurrence timestamps restore the run sequence while ingestion timestamps still reveal pipeline delay. For monitoring, record attempts under the same logical run ID and count the final business outcome once. Otherwise, a three-attempt success becomes two failures plus one success, inflating both sides of a reliability chart. 429 can be a reason category for an attempt; it should not silently become the terminal state of the logical import if a later attempt completes. Where the Evidence Lives The named tools in this question sit in different operating models. Mixpanel and Amplitude are candidates for event-oriented exploration; Metabase and Redash are candidates for querying data already available to a database or warehouse; a custom metrics API is an application-owned projection. That taxonomy is more useful than a feature checklist because incident reconstruction depends on where the durable evidence lives and who owns its schema. Compare Metabase and Redash by testing the actual incident query against your store, including late-arriving events and access boundaries. I'm not sure a generic feature matrix can settle those questions; a replay of representative runs will. Your mileage may vary when the organization already has one of these data paths under reliable ownership. The catch is that event analytics is not suitable when the telemetry contains sensitive support content that cannot enter that system, or when operators need a tightly controlled operational endpoint rather than exploratory analysis. A custom API is not suitable when questions change weekly and the team cannot staff schema, storage, authorization, and on-call ownership. Stick with a query dashboard when the warehouse is already the timely source of truth and SQL gives responders enough detail; don't add another serving layer merely to draw the same aggregate. Make Silence Testable Treat the monitor like an eval harness. Build a compact corpus of run histories and assert the alert decision, reconstruction fields, and dashboard projection. Include an on-time nonempty completion, an on-time empty completion that is allowed by business state, a missed schedule, a started run with no terminal event, a late success, duplicate delivery, out-of-order delivery, and a retry that eventually succeeds. These are scenario classes, not invented production frequencies. Then test idempotency. Replaying the same run_id and event identity must not double the imported-result total. Test ordering by delivering completion before start. Test the boundary at exactly the freshness deadline. Finally, test configuration changes: the evaluator should retain which schedule version and threshold produced an alert, or a later responder may be unable to reproduce the decision. Prompt cost belongs in this loop if an AI component summarizes incidents. Keep alert detection deterministic; pass the reconstructed, bounded run summary to the model only after the threshold fires. Measure input tokens, output tokens, summary usefulness, and unsupported claims against the eval corpus. Don't ship raw ticket bodies merely to explain a scheduler state. A concise structured summary is easier to redact, cheaper to evaluate repeatedly, and less likely to distract the model with unrelated customer language. Sparse alerts deserve special care. A missing event cannot carry a severity level, so a separate evaluator has to notice the absence and emit an alert record. Map that record into the team's existing severity policy rather than inventing a second scale. RFC 5424 defines severity numerically from Emergency through Debug, but it does not decide whether one stale support import is critical for your business. That policy requires an explicit freshness objective and impact model. Short test suites lie. Before deployment, run the same corpus against the full path: event ingestion, storage, projection, alert evaluation, and the view responders open. A unit test of the reducer cannot reveal a delayed pipeline or a dashboard cache whose refresh interval exceeds the alert window. Roll out with shadow evaluation first, compare decisions with the current monitor, and preserve enough identifiers to explain disagreements without placing those high-cardinality IDs into aggregate labels. The Smallest Contract Worth Owning Measure reconstruction completeness before dashboard polish: the proportion of alerts for which the run, expected schedule, terminal outcome, result count, reason category, and policy version are all available. Also measure detection delay, late-event rate, duplicate-event rate, query latency during an incident, retained-event volume, and the engineering time spent changing the schema. For AI-generated summaries, add token use and evaluator-scored factual consistency. No single approach wins those dimensions. Choose event analytics when exploration and changing segmentation justify event governance. Choose a query dashboard when durable run facts already exist and the team can express the operational question safely in that data layer. Choose a custom metrics API when the contract is narrow, stable, and important enough to own. The dashboard can stay simple because the evidence underneath it isn't.
