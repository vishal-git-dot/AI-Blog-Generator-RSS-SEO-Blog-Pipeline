In-process, the harness, tools and session live in your program and end with it. With agents serve , the harness and your tools run on your servers and Mistral stores the session. With agents deploy , everything runs on Mistral and you "host nothing." One agent definition, three runtimes: your process, your servers, or Mistral's. Two deploy details are easy to miss. The deploy guide says agents deploy "builds the commit you pushed, not your working copy," and it refuses unpushed commits and branches without an upstream. And check your plan. Mistral's managed-deployment quotas , documented in the Workflows section, allow 0 concurrent deployments on Free and on Pro or Team without pay-as-you-go, 3 with pay-as-you-go, and 10 on Enterprise. Past the cap, creating or starting a deployment fails with a 403 . Managed deployments cover agents, workflows and apps, so expect the same caps on agents deploy . The default: your tools just run An agent with no permission_policy and the default permission_mode="auto" runs every tool call it decides to make. The other two modes are "ask" and "deny" ( approvals docs ). For anything that writes, add a policy. This one is Mistral's own example from the approvals page, rewrapped to fit, with the variable renamed to policy : policy = agents . PermissionPolicy ( default = " deny " , rules = [ agents . PermissionRule ( tools = [ " client.get_alert " ], decision = " allow " ), # opening a case asks agents . PermissionRule ( tools = [ " client.open_case " ], decision = " ask " ), ], ) Building the policy changes nothing until the agent gets it: agent = agents . Agent ( model = " mistral-large-4 " , permission_policy = policy , ) Three rules from the same page decide whether it does what you think. The first matching rule wins. A call that matches no rule gets the policy's default , so default="deny" is what turns this into an allowlist. And patterns match the tool ID, such as client.open_case , not the name the model sees. Check the IDs your agent actually reports before you trust a rule. A policy also needs permission_mode="auto" ; the Agent raises an error with any other mode. With no policy, every call goes through. A deny-by-default policy lets through only what you listed. Approval requests can be answered in code. An on_approval= callback returns AllowApproval() , DenyApproval() or KeepCallbackOpen() , and the last one leaves the call to a person. Mistral's own example auto-approves calls whose tool carries a read_only_hint annotation and hands everything else to a human ( approvals docs ). The defaults Mistral did get right Give the SDK its due. Several defaults fail closed. An agent has no environment unless you give it one. The default is NoSandbox , which the environment docs describe as "no code execution." When you add one, the page recommends MistralSandbox , a Mistral-managed container. The option with no isolation at all, DangerousLocalSandbox , won't start unless you set ALLOW_DANGEROUS_LOCAL_HOST=1 . If you only need file edits, access="files" gives the model read_file , write_file and edit and removes bash : agent = agents . Agent ( model = " mistral-large-4 " , environment = agents . MistralSandbox ( access = " files " ), ) A call nobody approves doesn't run either. It waits one hour, and then, per the approvals docs , "the call does not run, the model reads that nobody approved it, and the turn continues." A deployed session ends after 4 hours idle or 24 hours in total by default, per the session lifecycle page , and a session ended by a limit can't resume. On Mistral-managed deployments you can raise those to 24 hours idle and a week total; with agents serve , both go up to a year. If your agent waits on a human over a weekend, plan for a new session. Subagents need one more check. They "run in the root's sandbox and share its files," according to the subagents page , with at most 10 subagent turns at once and a tree two levels deep. The subagent approvals page has the catch for the policy above: "A default="deny" policy has no rule for agents.spawn , the tool that starts a subagent. Every start is denied." If you use subagents, add an allow or ask rule for agents.spawn . One on_approval handler answers approvals for the whole tree, so write it for every tool a subagent might call. The search index leaves chunking to you The managed search index is the other piece agents will lean on. The release notes describe it as "a hosted vector index from a name, an embedding model, and an optional schema." The Search Index overview says it supports vector, keyword and hybrid retrieval with filters, and is also in public preview. Mistral hosts the index. Per the same page, your pipeline still splits content into chunks, embeds them and sends them with their fields. The Search Toolkit supplies splitting and embedding components. Whether your agent finds the right clause depends on the chunk boundaries you pick. Tracing is on by default for managed agents. The release notes say agent, model and tool spans go to Studio with no extra package to install, and "Spans are redacted on the worker before they leave." Read what the redaction covers before you send customer data through a tool. I haven't run the SDK myself.
