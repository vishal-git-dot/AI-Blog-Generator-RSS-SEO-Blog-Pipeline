# How to Trim a Video With FFmpeg (and Prove the Cut Starts on the Right Frame)

## Overview

There are two ways to trim a video with FFmpeg, and they don't do the same thing: Fast, no re-encode: ffmpeg -ss 1 -i in.mp4 -t 2 -c copy out.mp4 . This is fast, but the video can only start on a keyframe . Exact, re-encode: ffmpeg -ss 1 -i in.mp4 -t 2 -c:v libx264 -crf 18 -c:a aac out.mp4 . This starts on the frame you asked for, but the video is encoded again. Most "my trim is off by a second" bugs come from using the first command and expecting the second. Below, I trim a real clip both ways, measure which source frame each output really starts on, and turn the results into pytest checks you can keep in a media pipeline. Everything was run with FFmpeg 9.0.1 on macOS. The test clip The fixtures are three short AI-generated clips published as examples on Voor's Vidu Q3 page : 1952×1062, 30 fps, H.264 + AAC. These clips have very few keyframes, which makes the difference between the two methods easy to see. Speed matters and the start can move: snap to a keyframe, then -c copy . Never use a bare -ss … -c copy and assume the start is where you asked. Check the keyframes first. If you need -to , know which side of -i your -ss is on, or use -t . Limits Results are for FFmpeg 9.0.1 with MP4/H.264 input. Older builds and other containers handle copy-trims differently (some write an edit list that hides the extra frames in some players but not others), which is exactly why the tests decode frames instead of trusting the command. Frame matching by small grayscale images works when nearby frames differ. On a static shot, several frames will score the same, so check frame_count and timestamps instead. Re-encoding changes bitrate and quality. Pin -crf and -preset in the function so batches stay consistent.
