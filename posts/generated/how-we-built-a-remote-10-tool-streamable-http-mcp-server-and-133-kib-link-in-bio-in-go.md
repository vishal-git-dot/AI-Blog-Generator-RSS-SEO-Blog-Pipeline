# How We Built a Remote 10-Tool Streamable HTTP MCP Server and 13.3 KiB Link-in-Bio in Go

## Overview

Public link-in-bio pages are structurally simple documents: an avatar, a name, a contact bar, and 5 to 20 links. Yet most commercial bio-link platforms render them as client-heavy Single-Page Applications that download hundreds of kilobytes of framework JavaScript inside Instagram, TikTok, or WhatsApp in-app WebViews before painting a button. When we built Linq.es and its Official Remote MCP Server ( https://linq.es/mcp ) , we took the opposite path on both the public frontend and the AI agent layer: Public profiles render server-side in Go ( html/template ) with inline critical CSS, 5.1 KiB of gzipped async CSS, 8.2 KiB of gzipped defer vanilla JS, and zero React, Next.js, or Vue runtime ( 13.3 KiB total gzipped first-party CSS + JS). AI agents connect directly to https://linq.es/mcp over Streamable HTTP ( JSON-RPC 2.0 , MCP spec 2025-03-26 ) using a Personal API Key ( lnq_live_... ), without installing a local npx or Python stdio wrapper. Below are the main architectural lessons we learned building both layers in Go. 1. Why Go HTML SSR beats heavy SPA bundles inside social WebViews Most link-in-bio clicks happen inside constrained mobile WebViews (Instagram, TikTok, LinkedIn, X, and WhatsApp) over variable cellular connections. Every extra script tag, font round-trip, and client hydration pass delays First Contentful Paint and increases bounce rates before a visitor taps a wa.me button or downloads a .vcf contact card. On Linq.es, public profiles render complete semantic HTML in the European Union behind a multi-tier cache (in-memory L1, persistent object storage L2, and Cloudflare Edge CDN): Async stylesheet: ~5.1 KiB gzipped (loaded non-blocking) Deferred vanilla JS: ~8.2 KiB gzipped (loaded with defer) Total external CSS+JS: 13.3 KiB gzipped (zero client SPA framework) No third-party ad pixels (Meta, TikTok, or GA4) are injected on public pages unless a Pro profile owner explicitly configures their own measurement IDs. 2. Streamable HTTP MCP ( 2025-03-26 ) vs local stdio wrappers Many early MCP integrations wrap an existing REST API inside a local Node.js stdio package that users run via npx -y @vendor/mcp-server . That introduces three recurring friction points: Node or Python version mismatches on developer machines Stale local npm packages when tool schemas or annotations evolve No support on cloud, browser, or mobile MCP hosts that cannot spawn local subprocesses With the 2025-03-26 Streamable HTTP specification, an MCP server runs as a standard HTTPS JSON-RPC 2.0 endpoint: GET https://linq.es/mcp serves human-readable discovery metadata ( name: "linqes-mcp" , protocolVersion: "2025-03-26" , transport: "streamable-http" ). POST https://linq.es/mcp handles initialize , notifications/initialized , ping , tools/list , and authenticated tools/call executions. Lesson #1: notifications/initialized must return 202 Accepted with an empty body During the MCP handshake, right after initialize succeeds, strict clients send a JSON-RPC notification ( {"jsonrpc": "2.0", "method": "notifications/initialized"} ) that omits the id field. If your HTTP router wraps every return path in a 200 OK JSON-RPC envelope with "id": null , strict clients treat the unexpected body as a protocol error.
