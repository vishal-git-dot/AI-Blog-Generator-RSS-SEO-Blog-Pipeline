# AWS WAF mobile SDK tokens for native app APIs

## Overview

Your app's API works in the phone but every request from your server comes back as an HTML page instead of JSON. That page is AWS WAF: the API expects an aws-waf-token cookie minted by the AWS WAF mobile SDK, and there is no challenge.js to solve because the app never loads one. AntiAwsWafMobileTask returns a fresh mobile token in about 1-3 seconds, with no URL, parameters or proxy. How the mobile SDK protects an API On the web, AWS WAF injects a JavaScript challenge into a page and the browser earns the token. Native apps skip all of that. The iOS and Android SDKs compute a proof-of-work over device signals inside the app, get an aws-waf-token back, and attach it to every API call: POST /api/v2/auth/login HTTP / 2 Host : api.example-app.com User-Agent : ExampleApp/5.4 CFNetwork/1494 Darwin/23.4.0 Cookie : aws-waf-token=8f3a1c2e-...:DAoA...:... Content-Type : application/json The WAF sits at the edge, in front of the app. It reads that cookie before your request reaches any application code. No cookie, an expired cookie or a forged one, and the edge answers for the app. This is why the web task types don't help here. AntiAwsWafTaskProxyLess and AntiAwsWafTask solve a page challenge and return a cookie scoped to that site. A mobile API checks for a token produced by the mobile SDK, so you need a mobile-minted token. Telling a WAF block from an app error Before you integrate anything, learn to read the responses, because a passing request often still returns an error status. We ran a controlled test against a mobile login endpoint: same IP, same request body, sent at the same moment, only the token changed. The body was an empty claims: {} object, so the app could never accept it as a real login. Token HTTP status Who answered fresh mobile token 400 the app, as JSON (a "phone number required" style error) garbage string 403 the AWS WAF edge, as HTML ("Connection unavailable") The status number is not the signal. The responder is. A JSON body in the app's own error format means the token passed the WAF and your request reached the application, even if it was a 400. An HTML body on a 403 means the edge stopped you. One caveat: a 403 HTML page can also come from IP reputation. If the egress IP is rate-flagged, the edge blocks it even with a valid token. Using the token from your own IP Mobile tokens are not tied to the IP that minted them. You present the token from your own server, which is why the task needs no proxy and why AntiAwsWafMobileTask has no ProxyLess twin. The gateway ignores a proxy field on this task type. That shifts the IP question to you. The token gets you past the token check, and your egress IP still has to pass whatever rate rules the WAF applies. Spread high-volume traffic across clean IPs the same way you would for any API client. Things that go wrong Reusing a token. Tokens are single-use and live for about 2 minutes. Request one per protected call and send it right away. Caching a token for the next request gets you the HTML 403. HTML 403 with a fresh token. Check the IP first (see the caveat above). If a clean IP still gets HTML, the app may use a different WAF integration than the one covered: send support the endpoint. Wrong user agent. Send solution.userAgent , not your HTTP library's default. A desktop browser UA next to a mobile token is an easy mismatch to flag. Mixing up task types. If the protected thing is a web page that loads challenge.js or jsapi.js , use the web tasks instead.
