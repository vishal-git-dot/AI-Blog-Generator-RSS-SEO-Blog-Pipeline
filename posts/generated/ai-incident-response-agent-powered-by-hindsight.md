# AI Incident Response Agent powered by Hindsight

## Overview

Overview The most dangerous thing an incident tool can do at 3 a.m. is hand an engineer a past fix and let them apply it without asking whether this incident is actually the same problem. I built RecallOps around the opposite habit: before the agent recommends anything, it has to argue, in writing, why this incident resembles a past one and where the resemblance breaks down. What Recall Ops does RecallOps is a small Python service with a Streamlit front end. An on-call engineer describes a production incident in plain text, picks the affected service and a severity, and hits one button. From there: 1. The incident description is sent to Hindsight as a recall query against a bank of past incidents. 2. The retrieved memories and the new incident both go into a comparison-and-reasoning prompt. 3. The model returns a structured analysis that walks through similarity, difference, and recommended checks before it ever proposes an action. 4. Once the engineer resolves the incident for real, the actual fix and outcome are written back to Hindsight with retain, so the comparison has more material to work with next time. The files that matter are small: agent.py # recall -> compare -> reason -> retain app.py # Streamlit UI hindsight_memory.py # minimal store/recall round trip seed_memory.py # loads the initial incident bank into Hindsight Hindsight is what supplies the raw material for comparison — it's the memory system behind every recall and retain call in this codebase, and its documentation is what I built the integration against. But the part of this project I actually spent my time on, and the part I want to write about, is what happens after recall returns something: how the agent decides whether a retrieved incident is actually relevant, and how it stops itself from treating a resemblance as a match. Why comparison, not lookup It would have been trivial to build RecallOps as a lookup tool: take the incident, find the nearest match in Hindsight, print the old resolution. That's a FAQ bot wearing an incident-response costume, and it's actively unsafe. Two incidents with the same symptoms can have different causes. Payment timeouts with connection errors could mean pool exhaustion, like a previous incident. They could also mean a slow query holding connections open, a stalled downstream dependency, or a bad deploy leaking connections. If the agent just surfaces "raise the pool limit" because that's what worked last time, an engineer under pressure at 3 a.m. is likely to apply it, and if the actual cause is different, they've just given the real problem more room to grow while doing nothing to fix it. So the core design decision in this project isn't the memory system, it's the reasoning contract I put on top of it: the model is never allowed to answer "what should I do," only "how similar is this, really, and what does that similarity actually support." The recall step is intentionally plain def investigate_incident(incident): # Search Hindsight for relevant past experience result = hindsight.recall( bank_id=BANK_ID, query=incident ) # Convert memories into readable text memories = "\n\n".join( memory.text for memory in result.results ) I pass the incident text to Hindsight exactly as the engineer typed it, with no pre-processing. That's a deliberate choice: engineers describe incidents in symptom language ("timeouts," "error rate up to 30%," "connection errors"), and the incidents stored in Hindsight are written the same way, so semantic recall works without an intermediate classification step. I keep this part of the pipeline boring on purpose, because the interesting work — deciding what the retrieved text actually means for this incident — belongs entirely to the comparison stage that comes next, not to retrieval. Forcing the model to compare before it concludes Here's the prompt structure, and it's the center of this whole project: IMPORTANT RULES: 1. Do NOT blindly copy a previous solution. 2. First identify what is similar between the new incident and the previous experience. 3. Clearly identify what is different. 4. A previous solution should only be recommended directly if the current evidence supports it. 5. If the previous incident only provides a similar pattern, describe it as a reference rather than a confirmed solution. 6. Do not claim certainty when there is insufficient evidence. 7. Prioritize checks that an engineer should perform before making a potentially risky production change. And the output format it's locked into: ### 1. Likely Root Cause ### 2. Hindsight Experience ### 3. Why It Is Relevant ### 4. What Is Different ### 5. Recommended Immediate Checks ### 6. Recommended Action ### 7. Previous Solution ### 8. Warnings Two sections do the actual comparison work: "Why It Is Relevant" and "What Is Different." They're required, and they come before "Recommended Action," which means the model has to lay out the case for and against the analogy before it's allowed to say what to do about it. "Recommended Immediate Checks" also comes before "Recommended Action," so the first concrete thing an engineer reads is what to verify, not what to change. "Previous Solution," where the retrieved fix is most directly discussed, is pushed to position seven, with an explicit instruction that it's a reference and not a guarantee.I built it this way because a free-text answer makes it easy for a model to skip the comparison and jump straight to a recommendation, and it's hard for a reader to notice that it happened. A fixed schema with a mandatory "what is different" section makes the skip visible: if that section is thin or generic, the analysis is weak, and anyone reading it can tell. I'm not claiming this format guarantees good reasoning — I haven't run anything that would let me claim that — but it does make bad reasoning easier to catch. What "relevant" actually means here The comparison only works if the retrieved memories give the model something real to compare against, so I paid attention to what goes into the Hindsight bank and how it's phrased. Every stored incident, seed data or engineer-submitted, follows the same shape: """ Production Incident: Notification service experienced a 35% failure rate with email request timeouts and intermittent 504 errors from the external email provider. Actual Resolution: The external email provider was experiencing an outage. Enabled retry with exponential backoff and queued failed notifications for later delivery. Outcome: Notification failures dropped below 2% after the provider recovered and queued notifications were delivered successfully. Lesson Learned: When an external notification provider returns intermittent 504 errors, verify provider health before increasing local resources. """ The Lesson Learned line is written as a condition, not a command: "when X and Y occur together, check Z first." That phrasing matters for the comparison step specifically. An imperative lesson ("increase the pool") gives the model nothing to test the new incident against — it's just an instruction waiting to be copied. A conditional lesson gives the model a premise it can check: does the new incident actually satisfy X and Y, or does it only look like it does on the surface? That's what "Why It Is Relevant" and "What Is Different" are actually evaluating against.I also made sure the seed bank isn't one-note. The first stored incident is a payment API with an exhausted database pool, fixed by raising the pool size. If every other memory pointed the same direction, the comparison step would have nothing to disagree with, and "What Is Different" would always come back empty. So other seeded incidents deliberately cut the other way — a queue backlog caused by stalled workers, not a database at all, and the notification case above, where the right call is to wait on an external provider rather than touch local infrastructure. A comparison is only as good as the contrast it's given, and that's a property of the bank, not something the prompt can manufacture on its own. Closing the loop without polluting the comparison The write path is narrower than the read path on purpose: def save_experience(incident, resolution, outcome): experience = f""" Production Incident: {incident} Actual Resolution: {resolution} Outcome: {outcome} Lesson Learned: This production experience should be considered when investigating similar future incidents. """ hindsight.retain( bank_id=BANK_ID, content=experience ) I never write the model's own analysis into Hindsight, only what the engineer confirms: the incident as described, the resolution actually applied, and the observed outcome. If the model's comparison were stored back into the bank, a wrong analysis today could become "prior experience" that biases tomorrow's comparison, and the whole point of forcing the model to argue about similarity and difference would erode over a few bad cycles. Keeping retain limited to human-confirmed outcomes is what keeps future comparisons grounded in what actually happened instead of what an LLM guessed happened. What the comparison looks like in practice An engineer types: Payment API is experiencing severe timeouts. Error rate has increased to 30%. Database connection errors are also appearing. Hindsight's recall surfaces the earlier payment incident, where the rate was 35% and the cause was pool exhaustion. The comparison sections of the response, in shape rather than verbatim, look like this: Why It Is Relevant: same service, same symptom pairing of timeouts with connection errors. What Is Different: the error rate is lower this time, and nothing in the new report confirms the pool is actually saturated — only that connection errors are occurring, which isn't the same thing. Recommended Immediate Checks: current pool utilization and whether connections are being held open by long-running queries, before anyone touches a config value. Previous Solution: raising the pool limit worked last time and could be adapted, offered as a reference, not a directive. Now change the input to a payment-provider outage with no database errors at all. Recall shifts to a different memory — the notification-provider incident, with its lesson about verifying provider health before adding local resources. The comparison sections change accordingly: "Why It Is Relevant" now points at the external-dependency pattern instead of the database one, and "What Is Different" notes that there's no connection-pool signal in this incident at all. Nothing in the agent's code special-cases "external dependency" or "database problem." The comparison follows whatever memory Hindsight hands it, and reasons about that memory on its own terms each time. The UI shows the raw Hindsight memories next to the analysis, in an expandable panel, specifically so the comparison is checkable. If the model claims two incidents are similar, the engineer can read the retrieved memory and judge the claim themselves. A "Why It Is Relevant" section that isn't backed by visible evidence isn't reasoning, it's assertion, and I wanted it to be obvious which one they were looking at. Lessons learned1. Retrieval isn't the hard part; deciding what a match means is. Building the recall call took an afternoon. Getting the agent to argue honestly about whether a retrieved incident actually applies took real iteration on the prompt's structure. 2. Force the "what's different" step, don't hope for it. A free-text prompt lets a model quietly skip straight to a recommendation. A required section for differences makes a skipped comparison visible instead of invisible. 3. Order the output so checks come before actions. Putting "Recommended Immediate Checks" ahead of "Recommended Action," and "Previous Solution" near the end, keeps the retrieved fix from reading as the headline. 4. Write conditional lessons, not imperative ones. "When X and Y occur, check Z" gives a comparison something to test. "Do Z" gives it nothing but an instruction to obey. 5. Keep the write path narrower than the read path. Only human-confirmed outcomes go back into Hindsight. Letting the model's own conclusions feed future comparisons would quietly undermine the whole exercise. There's more I'd want before calling this finished — comparisons scoped to the same service by default, and some way to weigh a very recent incident more heavily than an old one. But the bet behind this project has held up: an incident agent doesn't need to be clever, it needs to show its work when it says two problems are alike, and it needs to be at least as willing to say "this doesn't match" as it is to say "this matches."
